# Фаза 19 как проектный каталог: лаборатории и капстоуны

Дата: 2026-08-22

## Проблема

`source/phases/19-capstone-projects/` содержит 85 каталогов, и это два разных
формата под одной вывеской:

- каталоги `01`–`17` — капстоуны на 25–40 часов. Полиглотные (TypeScript/Bun,
  Go, CUDA, SQL, LaTeX), с секцией «Build It» из 6–8 этапов, рубрикой оценки на
  100 баллов и артефактом-скиллом в `outputs/skill-*.md`.
- каталоги `20`–`87` — 68 практикумов типа Build, все на Python, все примерно на
  90 минут, у каждого `code/main.py` (медиана 340 строк, максимум 908) и
  тестовый файл к нему.

Номера `18` и `19` в фазе отсутствуют.

Пропустить эти 85 юнитов через текущий конвейер (`buildLesson` → план на ~40
шагов → шаги) нельзя по трём причинам. Первая: 90-минутный практикум не
разворачивается в сорок теоретических экранов. Вторая: у капстоуна нет шагов —
у него этапы, критерии готовности и артефакт, и линейная лента «Дальше» его
структуру уничтожает. Третья: практикумы связаны в серии, собирающие одну вещь
(лаборатории 30–41 строят GPT от токенизатора до оценки), а плоский список
1→85 эту связь скрывает.

Отдельное препятствие: в `source/learning-exercises/` нет ни одного каталога
`p19-*`. Движок практики (`pytest` по `exercise.py`) нацеливать не на что.

## Что выяснено про исходники фазы 19

Эти факты определяют решение, поэтому вынесены отдельно.

1. **Лаборатории самодостаточны и локальны.** Ни одна не скачивает веса и не
   ходит в облако. За пределы stdlib выходят `torch` (24 юнита), `numpy` (~14),
   `safetensors` (1), `yaml` (1). Серия 76–81 использует `torch.multiprocessing`
   на CPU — идёт на Mac. В сеть ходит одна лаборатория: `42-large-corpus-downloader`
   через `urllib`.
2. **Тесты к лабораториям написаны автором.** 62 из 68 юнитов везут тестовый
   файл (`code/tests/test_*.py` или `code/test_main.py`), суммарно около 10 000
   строк. Без тестов ровно шесть: серия 76–81, которая запускается как
   `python main.py` и проверяется сходимостью процессов.
3. **Часть лабораторий многофайловая.** Пятнадцать импортируют соседние модули:
   `rules`, `benign`, `fixtures`, `mock_llm`, `classifiers`, `yaml_subset`,
   `safety_gate`. Многофайловость — вход в фазу, а не хотелка капстоунов.
4. **У каждого капстоуна есть Python-эталон «швов».** `code/main.py`, 164–292
   строки, только stdlib, модель застабана детерминированным скриптом. Шапка
   первого капстоуна: «The LLM is stubbed out with a deterministic script so the
   loop logic stays observable and testable without network calls». Это ровно
   то, что мы собираемся проверять в приложении, — уже написанное автором.
5. **У 14 капстоунов рядом лежит TypeScript-реализация с тестами**
   (`code/ts/src/*.ts`, `code/ts/tests/*.test.ts`). Мы её не запускаем, но
   отдаём человеку как ориентир для чтения.
6. **Python-тестов к капстоунам нет.** Их придётся генерировать — но проверяемо,
   потому что эталон существует.

## Решение

Фаза 19 представляется двумя форматами.

**Лаборатория** — обычный урок короткого формата. Новых сущностей не вводит:
живёт в `content/lessons/<slug>`, имеет план, шаги, чат, уточнения, квиз.
Отличий два: план на 8–12 шагов вместо ~40 и многофайловое упражнение.

**Капстоун** — единственная новая сущность. Шагов у него нет; есть бриф,
milestones, контракты, доказательства и рубрика.

### Принятые решения и их цена

| Решение | Почему | Цена |
|---|---|---|
| Содержание капстоунов не меняем: остаются облачными | Срезать 30 часов до 8 значит выкинуть то, ради чего капстоун существует | Реальный прогон происходит вне приложения; приложение проверяет только швы |
| Швы всегда на Python | Швы проверяют форму контракта (состояния, порядок хуков, схемы, потолки, обрезку вывода) — это языконезависимо. Движок практики умеет только `pytest` | Шов и реальный код человека живут на разных языках; переносится понимание, а не файлы |
| Упражнения и контракты выводятся из кода курса, не выдумываются | `code/main.py` есть у всех 85 юнитов, тесты — у 62 лабораторий | Планировщик решает только, что вырезать; свободы «придумать задачу» нет |
| Редактор — табы на фиксированный набор файлов | В упражнении 3–5 файлов; дерево, переименование, удаление, поиск не нужны | Человек не может создать новый модуль; шаблон везёт все файлы, включая пустые |
| Прогресс фазы 19 считается отдельно | 85 юнитов, влитые в общий счёт, обнулят смысл полоски прогресса курса | На главном экране две шкалы вместо одной |
| Никаких сторонних сервисов | Требование: всё внутри сайта | Colab, внешние раннеры и прикрепление чужого репозитория для прогона команд отвергнуты |

### Раскладка на диске

```
source/learning-exercises/p19-l20-agent-harness-loop-contract/
  exercise.template/           # каталог, а не один файл
    main.py  hooks.py  events.py
  solution/                    # code/main.py курса как есть
    main.py  hooks.py  events.py
  test_exercise.py             # штатные тесты курса, перенесены без изменений
  exercise/                    # файлы человека, разворачиваются из шаблона

source/learning-projects/p19-c01-terminal-native-coding-agent/
  project.json                 # milestones, рубрика, требуемые фазы
  m01-tui-command-loop/
    contract.template/         # швы, которые пишет человек
    fakes/                     # стабы из code/main.py курса — даёт курс
    solution/                  # эталон из code/main.py
    test_contract.py           # сгенерирован, принят двусторонней проверкой
  m02-plan-state/ …

content/lessons/19-capstone-projects__20-agent-harness-loop-contract/
  lesson.json  steps/*.md  clarifications/*.md  visuals/*.html

content/projects/19-capstone-projects__01-terminal-native-coding-agent/
  project.json                 # бриф, тексты milestones, критерии готовности
  milestones/m01-tui-command-loop.md
  clarifications/<milestone-id>.md

content/phase-19/tracks.json   # 9 треков + привязка капстоунов, пишется руками
```

Slug лаборатории — обычный `<phaseDir>__<lessonDir>`, то есть
`19-capstone-projects__20-agent-harness-loop-contract`. Каталог упражнения
следует существующей схеме `p19-l20-*` (`exercisePrefix` из
`src/lib/source/naming.ts` строит её без правок). Капстоуны лежат в отдельном
корне `source/learning-projects/`, поэтому `parseExerciseSlug` и регулярное
выражение `EXERCISE_SLUG` их не касаются вовсе и не меняются.

Материал для вывода упражнений уже на диске: `collectLessonFiles` копирует
каталог урока целиком (`phases/<phase>/<lesson>`), то есть `docs/`, `quiz.json`
и `code/` вместе с ним. Значит `source/phases/19-capstone-projects/<unit>/code/`
— это и есть источник, из которого рождаются `solution/`,
`exercise.template/` и `test_exercise.py`. Отдельного шага импорта не нужно;
существующий отсев `LEARNER_OWNED` (не копировать чужой `exercise.py`) остаётся
в силе.

## Лаборатории

### Как рождается упражнение

Из `code/main.py` и штатных тестов, а не из головы модели:

- `solution/` — `code/main.py` (и соседние модули) как есть. Настоящая
  реализация автора курса.
- `exercise.template/` — те же файлы, но у выбранных функций тела заменены на
  docstring с условием и `raise NotImplementedError`.
- `test_exercise.py` — тестовый файл курса, перенесённый без изменений.

Планировщик выбирает из `main.py` от 4 до 8 функций или методов под практику.
Остальной код приезжает готовым каркасом: человек его читает и опирается на
него. Это единственный способ уложить 340 строк в 90 минут.

### План лаборатории

8–12 шагов: один шаг постановки задачи, два-три шага теории или схемы (в
исходниках builds уже есть mermaid-диаграммы и блоки `figure` — берутся
напрямую), 4–8 code-шагов по выбранным функциям, финальный шаг с итогом и
квизом. Один `check` перед первым code-шагом («понял ли контракт, прежде чем
его реализовывать»), а не после каждого экрана.

`recall`-шаги внутри трека осмысленны и работают существующим механизмом:
`findPreviousImplementation` найдёт реализацию токенизатора в упражнении
предыдущей лаборатории серии. Валидатор плана уже требует, чтобы функция
`recall` была написана человеком раньше, — правило остаётся в силе.

### Многофайловость

`ExerciseInfo` перестаёт быть «один шаблон, плоский список функций».
`exercise_fn` в `stepMetaSchema` становится парой файл + функция. Проверки
`validatePlan` (существование функции, покрытие каждой ровно одним шагом)
начинают работать с парами.

Опасный угол: `pytest -k` фильтрует по именам тестов, а не по путям, и в
многофайловом упражнении имена функций могут совпасть (`encode` в двух
модулях) — тогда фильтр шага отберёт чужие тесты. Лечится на импорте: если имя
функции внутри упражнения не уникально, импорт печатает предупреждение, а тесты
такого шага гоняются целым файлом с честной пометкой — так уже сделано для
случая, когда фильтр не выбрал ничего. Молча угадывать нельзя.

### Серия 76–81: прогон скрипта

Распределённая серия тестов не везёт: она запускается как `python main.py`,
поднимает процессы через `torch.multiprocessing` и сходится или нет. Для неё
добавляется третий вид зачёта шага помимо «зелёные тесты» и «верные ответы»:
**успешный прогон скрипта с кодом выхода 0**. Это отдельная функция рядом с
`runTests`, а не флаг внутри неё: результат разбирается иначе — код выхода и
вывод, а не JUnit-XML с числом зелёных.

Результат такого прогона пишется в существующую `test_runs`: `passed` = 1 и
`failed` = 0 при коде выхода 0, обратное иначе, а в `exercise_fn` ложится имя
запущенного файла. Колонка названа под функцию, поэтому имя файла там надо
пояснить комментарием к схеме — как и slug проекта в `lesson_slug` ниже.

### Зависимости

У лаборатории в метаданных появляется список требуемых пакетов (`torch`,
`numpy`, `safetensors`, `yaml`). `health.ts` проверяет их при открытии страницы
практики. Без этой проверки красный тест из-за отсутствующего `torch` человек
прочитает как ошибку в своём коде — худший вид обратной связи.

`42-large-corpus-downloader` помечается как требующая интернета. Офлайновая
фикстура убила бы смысл урока (докачка, проверка хеша большого корпуса).

## Капстоуны

### Три слоя

1. **Бриф** — зачем проект, что получится, какие фазы задействует, сколько
   времени. Собирается из секций Problem, Concept, Architecture, Stack
   существующего `docs/en.md`.
2. **Milestones** — формализованная секция «Build It». У каждого четыре поля:
   *что делаешь*, *готово когда* (критерии для самопроверки), *контракт* (что
   пишется и проверяется в приложении), *доказательство* (что принести из
   реального прогона: ссылка на PR, лог, вывод команды, скриншот).
3. **Рубрика** — таблица критериев с весами на 100 из `docs/en.md`. Заполняется
   в конце, по проекту целиком. Может заполняться с помощью CLI-агента
   (механика `review-code` уже есть), но это не автоматический зачёт.

### Что такое контракт на практике

Пример распределения для капстоуна 01 (`terminal-native-coding-agent`):

| Этап | Что в облаке | Что проверяется в приложении |
|---|---|---|
| m01 TUI и командный цикл | Ink, живой терминал | Разбор `agent run <repo> "<task>"`; `SessionEnd` срабатывает до выхода при отмене |
| m02 Состояние плана | — | Схема TodoWrite, запрет инкрементальной мутации, запись и восстановление `.agent/state.json` — целиком |
| m03 Набор инструментов | MCP StreamableHTTP | Шесть инструментов, обрезка вывода на 4k токенов, диспетчеризация по схеме — на фейковой ФС |
| m04 Обёртка сандбокса | E2B, Daytona | Ни один вызов не идёт мимо границы: клиент сандбокса подменён локальным фейком, хост недостижим |
| m05 Хуки | — | Восемь типов, порядок регистрации, блокировка `rm -rf` вне worktree — целиком |
| m06 Цикл eval | SWE-bench Pro | Тот же раннер на фикстурных задачах |
| m07 Контроль расходов | реальные токены | Три потолка, срабатывание `PreCompact` на пороге — на фейковой модели с предсказуемым расходом |
| m08 Постинг PR | GitHub App | Фейковый GitHub-клиент: тело PR, push в ветку задачи |

Из восьми этапов три проверяются полностью, четыре — на подменённом бекенде,
один требует внешнего бенчмарка. Фейки (`fakes/`) пишет курс, взяв их из
`code/main.py`. **Если фейк пишет учащийся, он подгонит его под свой код, и тест
перестанет что-либо значить** — это правило, не рекомендация.

### Готовность milestone: два независимых признака

- `contract_state` — швы зелёные. Ставится тестами, вручную не отбирается.
- `verified_at` + `evidence` — человек отметил, что реальный прогон сделан, и
  приложил доказательство.

На странице они показываются раздельно: «швы 8 из 8, реальный прогон 5 из 8».
Слить их в один статус нельзя: зелёный на моках начнёт читаться как готовый
проект, а это самообман.

Капстоун завершён, когда все milestones зелёные по швам, все отмечены
проверенными и заполнена рубрика.

## Редактор, раннер, проверки среды

**API упражнения.** `GET /api/lesson/<slug>/exercise` отдаёт массив файлов, у
каждого свой `mtimeMs` и список функций; `PUT` принимает `{file, code, mtimeMs}`.
`exerciseFilePath` сохраняет проверку «внутри `source/learning-exercises`» и
получает два условия: расширение `.py` и вхождение в список файлов шаблона.
Защита от затирания чужой правки (409 с актуальным содержимым) работает
по-файлово.

**Новые файлы человек не создаёт.** Шаблон везёт все файлы сразу, включая
пустые с докстрокой. Это оставляет проверку пути закрытым списком вместо
открытой записи в каталог.

**Совместимость с 382 существующими упражнениями.** Одно-файловое упражнение
остаётся ровно таким, как сейчас: `exercise.template.py`, `solution.py`,
`exercise.py` в корне каталога. Многофайловое использует форму с каталогами
(`exercise.template/`, `solution/`, `exercise/`). `readExerciseFile` отвечает
списком файлов в обоих случаях — для старой формы список из одного элемента,
и панель практики про разницу не знает. Переносить старые упражнения на новую
форму не нужно.

**Табы, не дерево.** Файлов 3–5 — это горизонтальные табы над Monaco.
Межфайловые импорты разрешаются сами: модель на файл уже ключуется по
`monaco.Uri.file`, а pyright запускается с `rootUri` на каталоге упражнения.
`setHiddenAreas` продолжает показывать одну функцию, но переключается на файл
текущего шага.

**Соседи.** `reset` умеет сбрасывать один файл или все. `recall` ищет прошлую
реализацию по тройке slug + файл + функция. `bench.py` получает имя файла
параметром, сравнивать продолжает по функциям.

**Чего не делаем.** Дерева каталогов, переименования, удаления файлов, поиска по
проекту, терминала. Капстоун человек пишет снаружи; лаборатории на 90 минут
файловый менеджер не нужен.

## Навигация и прогресс

**Главный экран.** Фаза 19 рисуется отдельным блоком: сначала 17 капстоунов как
проекты портфолио, затем 9 треков лабораторий, каждый свёрнут в строку с
названием, числом лабораторий и прогрессом. Раскрытый трек показывает свои
лаборатории по порядку.

**`content/phase-19/tracks.json`.** Для каждого трека: название, зачем он,
список лабораторий по порядку, какие капстоуны он готовит. Порядок внутри трека
жёсткий — лаборатории собирают одну вещь по частям. Необязателен трек целиком, а
не отдельная лаборатория внутри него. Капстоун ссылается на треки, которые
стоит пройти раньше: это и есть рекомендуемые траектории вместо порядка 1→85.
Файл пишется руками один раз.

Девять треков по нумерации исходников: 20–29 (харнесс агента), 30–41 (LLM с
нуля), 42–49 (инфраструктура тренировки), 50–57 (research-агент), 58–63
(мультимодальность), 64–69 (RAG), 70–75 (eval), 76–81 (распределённое
обучение), 82–87 (безопасность). Каждый трек кончается лабораторией
`end-to-end-*`.

**Страница капстоуна** — новый маршрут `/project/<slug>`, а не подвид
`/lesson/<slug>`: у капстоуна нет шагов и нет ленты «Дальше», а позиция в нём —
открытый milestone. Сверху бриф, слева список milestones с состояниями, справа
тело открытого milestone: задача, критерии, панель контракта (существующая
`ExercisePanel` целиком), блок доказательства. Внизу рубрика.

**Чат и уточнения — без миграции.** `chat_sessions` и `chat_messages` ключуются
парой `lesson_slug` + `step_id`; для капстоуна это slug проекта и id milestone.
Уточнения ложатся в `content/projects/<slug>/clarifications/<milestone-id>.md`.

**Новые таблицы.**

```sql
CREATE TABLE milestone_state (
  project_slug   TEXT NOT NULL,
  milestone_id   TEXT NOT NULL,
  contract_state TEXT NOT NULL CHECK (contract_state IN ('unopened','failed','passed')),
  verified_at    TEXT,          -- отметка человека «реальный прогон сделан»
  evidence       TEXT,          -- ссылка на PR, лог, вывод команды
  opened_at      TEXT,
  PRIMARY KEY (project_slug, milestone_id)
);

CREATE TABLE project_rubric (
  project_slug TEXT NOT NULL,
  criterion    TEXT NOT NULL,
  score        INTEGER,         -- из веса критерия
  note         TEXT,
  PRIMARY KEY (project_slug, criterion)
);
```

`step_state` для milestones не переиспользуется: там одно состояние из четырёх и
правило «не откатывать назад», а у milestone два независимых признака, и слить
их в одну колонку значит потерять различие ровно там, где оно важнее всего.

Прогоны тестов ложатся в существующую `test_runs`: `lesson_slug` получает slug
проекта, `step_id` — id milestone. Это надо написать словами в комментарии к
схеме, иначе через полгода такая строка будет выглядеть багом.

Лаборатории новых таблиц не требуют: это уроки, у них шаги.

**Полоска прогресса.** Фаза 19 считается отдельно от курса: «треков пройдено 2
из 9, капстоунов сдано 1 из 17». В общий счёт шагов курса не вливается — иначе
человек, прошедший восемнадцать фаз, увидит, что он «прошёл половину».

## Генерация

Конвейер симметричен для лабораторий и капстоунов; отличается источник
разбиения.

**Лаборатория.** Новый промпт `prompts/plan-lab.md` получает `docs/en.md` и
`code/main.py`, выдаёт 8–12 шагов и список функций под вырезание. Шаги пишутся
существующим `write-step.md`, но в промпт шага добавляется код той функции, о
которой шаг: сейчас промпт видит только текст урока, а на лаборатории теория
неотделима от кода.

**Капстоун.** Новый промпт `prompts/plan-project.md` сводит секцию «Build It» из
`docs/en.md` с секциями `code/main.py` (файл поделён комментариями-разделителями
на `plan state`, `budget`, `tool dispatcher`, `hooks` — те же куски). Результат —
`project.json`: бриф, milestones с критериями и набором функций под контракт,
вид доказательства, вес из рубрики. Новый промпт `prompts/write-milestone.md`
пишет текст этапа — крупнее шага урока, ближе к брифу задачи. Тесты контрактов
генерируются (Python-тестов к капстоунам курс не везёт).

**Правило приёмки сгенерированных тестов.** Набор принимается только при
двусторонней проверке:

1. на эталоне (`solution/`) все тесты зелёные;
2. на шаблоне с вырезанными телами они **красные**.

Второе условие не менее важно первого: без него бывает, что функцию вырезали, а
тесты её не задевают — и шаг зачитывается зелёным, стоит открыть страницу.
Механика есть: `generateExercise` уже прогоняет тесты и возвращает модели ошибку
на переделку; добавляется второй прогон с обратным ожиданием. То же правило
применяется к лабораториям, где тесты готовые: проверить, что выбранная под
вырезание функция действительно покрыта тестами.

**Точки входа.** В `buildLesson` первый шаг для лаборатории меняется: вместо
«придумываю упражнение» — «вывожу упражнение из кода курса». Для капстоуна нужен
`buildProject` рядом: milestones → контракты → тексты. `scripts/write-lesson.mts`
получает флаг для фазы 19, чтобы ночной прогон работал как для обычных фаз.

## Порядок работ

Порядок выбран так, чтобы каждый кусок проверялся на живом материале сразу.

1. Многофайловое упражнение: `ExerciseInfo`, `exercise_fn` как пара, API, табы в
   редакторе, `reset`, `recall`, `bench`. Проверяется на существующем уроке,
   разложенном на два файла.
2. Вывод упражнения из кода курса плюс правило двусторонней приёмки. Проверяется
   на лаборатории 20 (одна файловая, тесты есть).
3. `plan-lab.md` и генерация лаборатории целиком. Первый трек 20–29.
4. Прогон скрипта как вид зачёта. Серия 76–81.
5. Проверка зависимостей лаборатории в `health.ts`. Любая torch-лаборатория.
6. `tracks.json`, блок фазы 19 на главном экране, отдельная шкала прогресса.
7. Капстоун: `project.json`, таблицы, маршрут `/project/<slug>`, страница с
   milestones и панелью контракта.
8. `plan-project.md`, `write-milestone.md`, генерация контрактов. Капстоун 01.

## Что в этот срез не входит

- Изменение содержания капстоунов под локальный запуск. Остаются облачными.
- Запуск чужих команд из подключённого репозитория, `bun test`, `go test`.
- Google Colab и любые сторонние сервисы.
- Дерево файлов, переименование, удаление, поиск по проекту, терминал в
  редакторе.
- Автоматическая оценка по рубрике как зачёт. Рубрика — ручная, при желании с
  помощью агента.
- Экспорт артефакта капстоуна (`outputs/skill-*.md`) во что-либо.
- Запуск TypeScript-эталонов капстоунов. Они только для чтения.

## Риски

- **Вырезали не то.** Планировщик выбирает 4–8 функций из 340 строк, и может
  выбрать периферию вместо сути. Ловится двусторонней приёмкой лишь частично:
  тесты покажут, что функция покрыта, но не что она главная. Смягчение — в
  промпте требовать, чтобы выбранные функции были теми, о которых говорит текст
  урока, и печатать выбор при генерации, чтобы он был видно на глаз.
- **Совпадение имён в многофайловом упражнении.** Описано выше; лечится
  предупреждением на импорте и прогоном всего файла.
- **Сгенерированные тесты контрактов слабее авторских.** Двусторонняя приёмка
  отсекает пустышки, но не гарантирует глубины. Для капстоунов это принимаемый
  риск: альтернатива — писать 17 наборов руками.
- **Зависимость лабораторий от порядка внутри трека.** Человек может открыть
  35-ю лабораторию, не пройдя 30-ю, и получить незнакомый каркас. Смягчение —
  явная ссылка на предыдущую лабораторию трека на странице.
- **`torch` на машине без него.** Проверка в `health.ts` обязательна, иначе
  красные тесты будут читаться как ошибки кода.

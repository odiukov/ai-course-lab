# Генерируемые визуализации вместо ASCII-схем

Дата: 2026-08-10

## Проблема

Шаг `004-dlina` урока `01-math-foundations__02-vectors-matrices-operations`
содержал ASCII-схему треугольника 3-4-5, в которой гипотенуза начиналась не в
точке (0, 0), а примерно в (0, 1.9): символы `╱` обрывались на `y=2`, четыре
нижние строки диагонали отсутствовали. Основание вертикального катета (`┴`)
стояло на колонке 12, тогда как тик `3` оси X — на колонке 13.

Причина не в конкретной опечатке. ASCII-арт требует расставить символы по
колонкам вручную, и корректность картинки не следует ни из чего — она держится
на том, что модель посчитала отступы правильно. Схема с числами, которые
подписаны рядом (`3`, `4`, `(3,4)`), выглядит проверяемой, но проверить её
может только человек, который пересчитает колонки.

Аудит: ASCII-схема нашлась в 1 шаге из 33. Единичный случай, но класс ошибки
воспроизводимый — в `prompts/write-step.md` про ASCII нет ни слова ни в
разрешающем, ни в запрещающем смысле, и никакой валидации выхлопа нет.

## Что уже есть

- `source/learning-visuals/*.html` — 7 интерактивных визуализаций, пришедших с
  исходным курсом. Все самодостаточны: ноль внешних `src`/`href`. 4 из 7 на
  SVG, 3 (`matmul`, `shapes`, `transpose-trace`) — на DOM/CSS.
- `prompts/plan-lesson.md`, правило 5: планировщик заполняет `visual` **только**
  дословным путём из списка `{{visuals}}`. Агент визуализации не создаёт.
- `validatePlan` (`src/lib/content/lesson-plan.ts:77-82`) отвергает `step.visual`,
  которого нет в `source.visuals`.
- `/api/visual?path=` + `resolveVisualPath` — раздача из `<sourceDir>/learning-visuals`
  с проверками на traversal и symlink.
- Reader рендерит `step.visual` в `<VisualFrame>` — iframe с `sandbox="allow-scripts"`.

## Решение

Шаг, которому нужна схема, а готовой в курсе нет, получает **сгенерированный
самодостаточный HTML** — тот же механизм показа, что у семи существующих.
ASCII-арт запрещается.

Ключевой пункт — не «HTML вместо ASCII» сам по себе. HTML умеет врать так же, а
сломанный скрипт даёт пустой iframe, что хуже заметно кривой картинки. Класс
ошибки убирается требованием считать геометрию из данных (раздел «Промпт
рисовальщика»).

### 1. Контракт плана

`stepMetaSchema` (`src/lib/content/step-file.ts:19`) получает поле
`visual_brief?: string`.

Инварианты:

- `visual` — по-прежнему только дословный путь из `source.visuals`.
- `visual_brief` без `visual` — «готовой схемы нет, нарисовать». Непустая
  строка (`z.string().min(1)`): пустой бриф хуже отсутствующего, потому что
  запускает рисовальщика без задания.
- `visual` и `visual_brief` вместе — ошибка валидации. Одна схема на шаг.
- `type: visual` обязан иметь либо `visual`, либо `visual_brief`. Сегодня
  visual-шаг без пути молча даёт шаг без картинки; закрывается заодно.
- `visual_brief` на шаге любого другого типа — ошибка валидации. Схема, которую
  никто не покажет, стоит вызова агента и тихо пропадает.

`prompts/plan-lesson.md`, правило 5 переписывается под два варианта.
`visual_brief` — одна фраза о том, что схема должна показать, с конкретными
числами, если они есть в уроке. Без брифа рисовальщик получает только заголовок
шага, а «Как работает свёртка» можно нарисовать десятью способами.

### 2. Точка вызова

Новый модуль `src/lib/generate/draw-visual.ts`, промпт `prompts/draw-visual.md`.

Вызывается из `ensureSteps` (`src/lib/generate/write-step.ts:116-137`) сразу
после `writeStep`, если `meta.visual_brief && !meta.visual`. Рисовальщик
получает уже написанное тело шага.

В промпт идут: `step_title`, `visual_brief`, готовый `body` шага, кусок
исходника (тот же `excerpt`, что у писателя).

Идемпотентность: файл на диске есть — пропуск. Зеркалит `readStep`-skip на
`write-step.ts:117`.

**Известное ограничение.** Два независимых skip'а не связаны между собой, и
шаг, чей текст записался, а схема нет, не будет дорисован никогда: `readStep`
обрывает итерацию до `drawVisual`. Перерисовка руками требует удаления **обоих**
файлов — `steps/<id>.md` и `visuals/<id>.html`. Удалить только файл шага —
ловушка: `ensureSteps` напишет новое тело, `drawVisual` упрётся в
`fs.existsSync` и промолчит, и шаг получит текст и схему из разных прогонов, без
ошибки и без кадра в SSE.

### 3. Промпт рисовальщика

Здесь живёт устранение класса ошибки:

- Один самодостаточный HTML-файл. Ноль внешних запросов: браузеру их запрещает
  CSP-заголовок `/api/visual` (раздел 4), а проверка на генерации нужна, чтобы
  упасть раньше, чем ученик увидит битую картинку.
- **Ровно одна пара функций перевода данные→пиксели, выведенная один раз из
  одного `origin` и одного `scale`. Каждая координата каждого элемента —
  вызов этой функции: концы отрезков, оси, засечки, точки привязки подписей,
  наконечники стрелок.** Литералами разрешено быть только массиву данных,
  размерам холста, пиксельным отступам подписей, толщинам линий и размеру
  шрифта. Следствие, на котором сломался ASCII-вариант: данные `(0, 0)`
  отображаются вызовом той же функции, а не подставляются числом.
  Требование «числа из данных» без единой функции перевода не связывает —
  каждый элемент можно посчитать своей формулой от своего смещения, и
  гипотенуза снова не сойдётся с началом координат.
- Соотношение сторон не меняется. `preserveAspectRatio="none"` — наивный
  способ «тянись по ширине», и он молча превращает прямой угол в непрямой.
- Деградация вместо пустоты. Геометрия считается в рантайме, так что ошибка
  в скрипте даёт пустой блок на 520 пикселей — заметно хуже кривой картинки, и
  `validateVisualHtml` этого не поймает (`<svg></svg>` проходит). Заголовок
  схемы живёт в статической разметке, построение обёрнуто в `try/catch`,
  который при сбое выводит бриф текстом.
- Тема через `prefers-color-scheme`. Иначе iframe станет белым пятном на тёмной
  странице.
- Объём как у существующих семи: 7-10 KB.

### 4. Хранение и адресация

Файл: `content/lessons/<slug>/visuals/<step-id>.html`.

Путь **выводится из id шага и в frontmatter не пишется**. Два следствия: модель
не может подсунуть произвольный путь, и `validatePlan` не конфликтует с
проверкой «visual есть в source.visuals».

`resolveVisualPath` получает второй разрешённый корень с той же схемой проверок:
lexical containment, `realpathSync` для обоих концов, `.html`, `isFile`.

API: `/api/visual?lesson=<slug>&step=<id>` для сгенерированных, существующий
`?path=` — для пришедших с курсом. Раздельные пространства имён вместо одного
смешанного.

Форма id — не пожелание промпту, а правило `validatePlan`: `SAFE_SEGMENT`
(`src/lib/content/paths.ts`) сторожит обе стороны, потому что из id собирается
и путь записи (`drawVisual` делает `mkdirSync` + `writeFileSync`), и путь
раздачи. Без этого id `004-длина` доезжал до ридера файлом на диске и умирал
там 400-м — ровно тем пустым iframe, ради которого в разделе 6 вводится флаг.

Раздача ставит заголовок
`Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; script-src 'unsafe-inline'`
на **оба** пространства имён. `sandbox="allow-scripts"` сеть не режет, а
`/api/visual` — обычный same-origin адрес: открытая прямой ссылкой схема
работала бы с полными правами приложения. Заголовок закрывает `fetch`,
динамический `import()`, `@import`, `url(https://…)` и `srcset` — всё, мимо
чего проходит регулярка `EXTERNAL_REF` из раздела 5. Семь пришедших с курсом
схем под ним работают: у каждой ровно один инлайновый `<style>` и один
инлайновый `<script>`, ни одного `src`/`href`, ни одного `data:`-URI и ни
одного `@font-face`.

### 5. Валидация сгенерированного файла

После генерации, до записи на диск:

- файл непустой;
- содержит `<svg`;
- не содержит `https?://` в атрибутах `src` / `href`.

Три проверки, больше ничего. Ни парсинга HTML, ни исполнения скрипта.

Третья проверка — не барьер безопасности, а способ упасть раньше. Барьер —
CSP-заголовок раздела 4; регулярка ловит только очевидный случай, чтобы файл
с внешней ссылкой не лёг на диск и не показался ученику битым.

SVG обязателен для сгенерированных, хотя 3 из 7 эталонов на DOM/CSS. Стандарт
строже исходного сознательно: в SVG геометрия живёт в координатах, что прямо
обслуживает требование из раздела 3.

Провал валидации: файл не пишется, `error` уходит в SSE, шаг остаётся текстом.
Генерация схемы не блокирует шаг.

### 6. Рендер

`step.visual` → `<VisualFrame>` как сейчас.

Для сгенерированных lesson API добавляет в `StepData` булево
`generatedVisual` — «шаг попросил схему в текущем плане, и файл лежит на
диске». Одного `existsSync` недостаточно: `content/lessons` в гите, файлы
переживают перегенерацию плана, и переиспользованный id получил бы чужую
схему. Reader рисует iframe только когда
оно `true`; иначе шаг остаётся текстом. Без этого флага reader не отличает
«схема ещё не нарисована» от «нарисована» и вставлял бы пустой iframe на 404.
Само `visual_brief` в клиент отдавать не нужно.

### 7. Запрет ASCII

`prompts/write-step.md` получает запрет ASCII-арта: нужна схема — это работа
планировщика через `type: visual`.

Уже написанные шаги не чистим: единственный найденный (`004-dlina`) исправлен
руками, остальные перегенерятся естественным порядком.

## Тесты

- `validatePlan` — четыре комбинации `visual` / `visual_brief`: только путь;
  только бриф; оба; ни одного при `type: visual`. Плюс форма `id`: кириллица,
  точка, слэш, пробел, пустая строка отвергаются, `004-dlina` и `005_zachem-2`
  проходят.
- `readGeneratedVisualIds` — id, вернувшийся в плане без `visual_brief`, схему
  не получает, хотя файл на диске есть.
- `/api/visual` — успешный ответ несёт CSP-заголовок.
- `resolveVisualPath` — второй корень: нормальный путь, traversal, symlink
  наружу, не-`.html`, директория.
- `draw-visual` — валидация отвергает пустой файл, файл без `<svg`, файл с
  внешним `src`; повторный вызов при существующем файле не зовёт агента.
- `ensureSteps` — рисовальщик зовётся только для шагов с `visual_brief` без
  `visual`; провал рисовальщика не мешает шагу записаться на диск.

## Явно вне объёма

- **Визуальная валидация смысла.** Headless-загрузка, скриншот и второй агент,
  сверяющий «схема отвечает тексту» — ловило бы и смысловые ошибки, но требует
  playwright в зависимостях и ещё одного вызова агента на шаг. Отдельный срез.
- **Зачистка существующего ASCII** — нечего чистить.
- **Перерисовка семи пришедших с курсом визуализаций.**
- **Уборка осиротевших файлов** после перегенерации плана со сменой id шагов.
  Мёртвые HTML в `content/lessons/<slug>/visuals/` не показываются: флаг
  `generatedVisual` считается по шагам текущего плана, у которых есть
  `visual_brief`, а не по одному `existsSync`. Исчезнувший id схемы не получит,
  и переиспользованный (последовательные `NNN-slug` переиспользуются легко)
  тоже — если в новом плане он не просит схему. Что остаётся: id, который
  просит схему **с другим брифом**, унаследует старый файл, потому что бриф
  нигде не запоминается, а `drawVisual` пропускает существующий файл. Лечится
  удалением файла схемы.

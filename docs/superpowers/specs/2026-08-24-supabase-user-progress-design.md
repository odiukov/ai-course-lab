# Юзеры и облачный прогресс статического сайта

Дата: 2026-08-24

## Проблема

Прогресс на опубликованном сайте живёт в `localStorage` браузера. Это записано
прямо в комментарии `src/lib/site/client.ts`: «сервера у статики нет, и хранить
его негде больше. Отсюда же следует, что на другой машине прогресс свой — это
цена бесплатного хостинга». Цена оказалась выше, чем казалась: человек, который
читал курс с ноутбука, на телефоне открывает чистый курс. Чистка данных сайта,
приватное окно, другой браузер — прогресс исчезает без следа и без возможности
его вернуть.

Нужны аккаунты и облачный прогресс: вход, единая история чтения и написанного
кода на всех устройствах, и — отдельным требованием — то, что уже накоплено в
браузере локально, должно переехать в аккаунт при первом входе, а не пропасть в
пользу пустого облака.

Локальное приложение Next.js эта работа не трогает вовсе. Оно остаётся
однопользовательским, с прогрессом в `data/progress.db`, и с облаком не
синхронизируется. Всё описанное ниже касается только статики, которая уезжает на
GitHub Pages.

## Что уже есть

- `src/lib/site/client.ts` — весь клиентский JS сайта, собранный строками:
  `PROGRESS_SCRIPT` (счётчик и полоска на шаге), `LESSON_INDEX_SCRIPT`,
  `EXERCISE_SCRIPT` (редактор и прогон тестов в pyodide), `CATALOG_SCRIPT`,
  `QUIZ_SCRIPT`, `FRAME_SCRIPT`. Общий кусок `STORE` даёт `readProgress(slug)`
  и `markRead(slug, stepId)`; всякое обращение к `localStorage` обёрнуто в
  `try`, потому что в приватном окне Safari запись бросает.
- Ключи в `localStorage` сегодня такие:
  - `course-progress:<lesson-slug>` — массив id прочитанных шагов
    (`PROGRESS_KEY_PREFIX` экспортируется из `client.ts`);
  - `course-exercise:<slug>` для одного файла и `course-exercise:<slug>:<file>`
    для многофайлового упражнения — полный текст файла;
  - `<ключ упражнения>:recovery` — копия на случай, когда границы функции в
    файле разъехались.
- Результаты прогона тестов и ответы на вопросы квиза нигде не сохраняются.
  Прогон считает зелёные и красные прямо в DOM (`client.ts`, около строки 645),
  `QUIZ_SCRIPT` подсвечивает верный ответ и на этом заканчивает. После
  перезагрузки страницы от них не остаётся ничего.
- `src/lib/site/render.tsx` — `htmlDocument({ title, basePath, body, scripts,
  modules })` собирает страницу; `modules` — уже существующий механизм для
  внешних файлов скриптов, они грузятся до инлайновых.
- `scripts/build-site.mts` — сборщик: `write(relPath, content)`, `basePath` из
  переменной `BASE_PATH` со значением `/ai-course-lab` по умолчанию,
  `buildEditor()` собирает CodeMirror через esbuild в `out/assets/editor.js`,
  `copyPyodide()` и `copyKatexAssets()` кладут зависимости рядом с сайтом, а не
  ссылаются на чужой CDN.
- Константа `CSP` в `build-site.mts` — политика для iframe со схемами, её
  подшивают внутрь файла схемы. К страницам сайта она не относится; своей CSP у
  страниц нет, и GitHub Pages произвольных заголовков не отдаёт.
- `scripts/publish-site.mts` — публикация `out/` в ветку `gh-pages` из
  временного каталога.

## Решение

Supabase на бесплатном тарифе: аутентификация через GitHub OAuth, Postgres с
построчной защитой (RLS) и запросы прямо из браузера, без своего сервера.
Клиентская часть — отдельный бандл `assets/auth.js`, который собирается тем же
esbuild-шагом, что и редактор, и подключается к страницам через уже
существующий `modules`.

Ключевое решение — **local-first**. `localStorage` остаётся рабочим хранилищем,
как сегодня, а облако служит зеркалом. Из этого следует три свойства, ради
которых подход и выбран:

1. Аноним видит ровно нынешнее поведение — ни одного сетевого запроса, ни одной
   новой причины для поломки.
2. Отметка «прочитан» перед переходом остаётся синхронной записью в
   `localStorage`. Она успевает до навигации именно потому, что синхронна;
   сетевой запрос такой гарантии не даёт, и порядок «сначала диск, потом сеть»
   для неё обязателен.
3. Офлайн, приватное окно и уснувший проект Supabase деградируют мягко: сайт
   работает, синхронизация ждёт.

Отвергнутая альтернатива — писать напрямую в Postgres и держать `localStorage`
кешем. Она проще в описании, но ломает пункты 2 и 3 сразу.

Вторая отвергнутая альтернатива — один документ JSONB на пользователя. Одна
строка и один `upsert` выглядят соблазнительно, но конфликт двух устройств
затирает весь прогресс целиком, а текст упражнений заставляет переписывать
документ на каждое сохранение кода.

### Границы: что синхронизируется

Синхронизируются три вещи: прочитанные шаги, состояние шага после прогона
тестов или вопросов (`passed`/`failed`), текст файлов упражнений.

Из этого следует работа, которой не было в изначальном списке: **сегодня
состояние `passed`/`failed` на статике не хранится нигде**, его нужно сначала
начать записывать локально, и только потом зеркалить. Формат существующего
ключа `course-progress:<slug>` при этом не меняется — иначе прогресс всех, кто
уже читает сайт, окажется в неизвестном формате. Состояния едут в новый ключ:

- `course-step-state:<lesson-slug>` — объект `{ "<step-id>": "read" | "failed" |
  "passed" }`.

Старый массив прочитанных остаётся источником правды для галочек и полоски, а
новый ключ дополняет его состоянием практики. Пустой новый ключ означает ровно
то, что означает сейчас: про практику ничего не известно.

Ещё один новый локальный ключ появляется у упражнений:

- `<ключ упражнения>:updatedAt` — время последней правки в ISO. Сегодня время
  правки не хранится, и это единственная причина, по которой слияние кода не
  может быть честным (см. ниже).

### Модель данных и RLS

Схема лежит в репозитории файлом `supabase/schema.sql` и накатывается руками
через SQL Editor в консоли Supabase. Механизма миграций не заводим: таблиц три,
проект один, а инструмент миграций Supabase потребовал бы CLI и связанного
локального Postgres ради трёх `create table`.

```sql
create table step_progress (
  user_id     uuid not null default auth.uid() references auth.users on delete cascade,
  lesson_slug text not null,
  step_id     text not null,
  state       text not null check (state in ('read', 'failed', 'passed')),
  updated_at  timestamptz not null default now(),
  primary key (user_id, lesson_slug, step_id)
);

create table exercise_files (
  user_id    uuid not null default auth.uid() references auth.users on delete cascade,
  slug       text not null,
  file_name  text not null,
  content    text not null check (length(content) < 200000),
  updated_at timestamptz not null default now(),
  primary key (user_id, slug, file_name)
);

create table run_results (
  user_id     uuid not null default auth.uid() references auth.users on delete cascade,
  lesson_slug text not null,
  step_id     text not null,
  passed      integer not null,
  failed      integer not null,
  created_at  timestamptz not null default now(),
  primary key (user_id, lesson_slug, step_id)
);
```

`run_results` хранит только последний прогон каждого шага, а не историю: в
интерфейсе сайта истории прогонов нет и не планируется, а бесплатные 500 МБ
при открытой регистрации не то место, где стоит копить журнал.

`check (length(content) < 200000)` на тексте упражнения — не косметика.
Регистрация открытая, ключ публичный, и без потолка одна вкладка забивает базу
проекта целиком. 200 000 символов — это примерно два порядка сверх самого
большого файла упражнения в курсе, то есть потолок, который не задевает
реальную работу и при этом делает заливку мусора бессмысленной.

Защита строк включается на всех трёх таблицах одинаково:

```sql
alter table step_progress  enable row level security;
alter table exercise_files enable row level security;
alter table run_results    enable row level security;

create policy "own rows" on step_progress
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
-- то же самое для exercise_files и run_results
```

Это единственное место во всей работе, где ошибка стоит дорого: анонимный ключ
лежит открытым текстом в HTML — так устроен Supabase, ключ публичен по замыслу,
и защищает не он, а RLS. Без политик тот же ключ отдаёт содержимое таблиц
любому желающему. Поэтому в порядке работ отдельным пунктом стоит проверка:
из анонимной сессии `select` по каждой из трёх таблиц возвращает ноль строк, а
`insert` отказывает.

### Модули

Разделение сделано так, чтобы вся спорная логика оказалась в чистых функциях,
которые проверяются обычными тестами, а сетевой слой остался тонким и глупым.

- `src/lib/sync/merge.ts` — правила слияния. Чистые функции без импорта
  Supabase и без обращений к `localStorage`.
- `src/lib/sync/migrate.ts` — сбор локальных ключей в пакет для заливки и
  решение, что с чем сливать. На вход принимает снимок хранилища как обычный
  объект, на выход отдаёт список операций. Тоже чистый.
- `src/site-auth/auth.ts` — точка входа для esbuild, собирается в
  `out/assets/auth.js` рядом с `editor.js`. Здесь клиент Supabase, сессия,
  кнопка входа, дебаунс отправки, вызовы функций из двух модулей выше.

Такое деление держит `auth.ts` в размере, который можно прочитать целиком:
всё, что требует размышления, вынесено и покрыто тестами, а в бандле остаётся
последовательность вызовов.

### Слияние

Правила слияния — ядро работы, и каждое из них выбрано по принципу «никогда не
терять уже достигнутое».

**Прочитанные шаги** сливаются объединением множеств. Отметка «прочитан» не
снимается обратно ни при каких обстоятельствах.

**Состояние шага** сравнивается по рангу: `read` и `failed` — ранг 1, `passed` —
ранг 2. Побеждает больший ранг; при равных рангах — более позднее
`updated_at`. Отсюда следует главное: красный прогон на втором устройстве
никогда не сбрасывает шаг, уже сданный на первом.

**Текст упражнения** — единственное место, где честного правила нет, и это
надо назвать прямо. Локально сегодня хранится только текст, без времени
правки, поэтому при первой встрече двух разных текстов вычислить, какой из них
новее, нечем. Правило на этот случай:

- в облаке строки нет — заливается локальный текст;
- строки совпадают — ничего не происходит;
- тексты разошлись — **побеждает облако**, а локальный текст откладывается в
  ключ `<ключ упражнения>:local-backup`, и на странице упражнения появляется
  одна плашка: на этом устройстве был другой код, копия сохранена.

Молча терять чужой код нельзя, а угадывать без отметки времени — тем более.
Начиная с миграции пишется `<ключ упражнения>:updatedAt`, и для всех
последующих правок сравнение идёт по времени, обычным «новее выигрывает».
Правило выше — разовая цена за то, что отметки времени не было раньше.

**Цифры прогона** (`run_results`) не сливаются вовсе. Локального зеркала у них
нет: в `localStorage` едет только состояние шага, а количество зелёных и
красных уходит прямо в облако в момент прогона, если человек вошёл. При
открытии страницы они не читаются обратно — таблица нужна как след для
будущего разбора, а не как состояние интерфейса. Конфликта двух устройств тут
не бывает: строка перезаписывается последним прогоном.

### Миграция локального прогресса

Миграция выполняется один раз на пару «браузер + пользователь» и является тем
самым требованием, ради которого всё затевалось.

1. Человек входит через GitHub и возвращается на страницу `/auth/`.
2. Проверяется флаг `course-synced:<user-id>` в `localStorage`. Если он стоит —
   миграция уже была, ничего не делаем.
3. Собираются все ключи `course-progress:*`, `course-step-state:*` и
   `course-exercise:*` (кроме служебных суффиксов `:recovery` и
   `:local-backup`).
4. Тянутся все строки пользователя из трёх таблиц.
5. `migrate.ts` считает список операций по правилам слияния выше.
6. Операции уезжают пакетными `upsert`, результат слияния пишется обратно в
   `localStorage`.
7. Ставится флаг `course-synced:<user-id>`.
8. На странице показывается одна строка с итогом: сколько шагов и файлов
   уехало, и была ли отложена копия кода.

Локальные ключи при этом не удаляются никогда. Выход из аккаунта не должен
оставлять человека с пустым курсом — после выхода сайт просто возвращается к
нынешнему анонимному поведению поверх тех же данных.

### Вход и адреса

В шапке каждой страницы появляется одна кнопка: «Войти через GitHub» для
анонима, имя с «Выйти» для вошедшего. Шапки у страниц разные
(`step-header`, `lesson-header`, `index-header`), поэтому кнопка вставляется
не в разметку каждой из них, а создаётся скриптом `auth.js` и подставляется
первым элементом `header`. Так три места рендера остаются нетронутыми.

Новая страница `out/auth/index.html` — адрес возврата OAuth и единственное
место, где виден ход миграции. Она разбирает токен из адреса, гоняет
миграцию, показывает итог одной строкой и уводит обратно, откуда пришли, по
параметру `?next=`. Значение `next` перед переходом проверяется на то, что это
путь внутри `basePath`: адрес приходит из строки запроса, и без проверки
страница входа превращается в открытый редирект на чужой сайт.

В настройках Supabase в список Redirect URLs добавляются адрес опубликованного
сайта и `http://localhost` для проверки сборки на месте.

### Конфигурация сборки

`SUPABASE_URL` и `SUPABASE_ANON_KEY` читаются в `build-site.mts` из окружения и
вшиваются в бандл через `define` esbuild. Обе переменные попадают в
`.env.example` с комментарием, что анонимный ключ публичен по устройству
Supabase и его нахождение в HTML — не утечка.

Отсутствие переменных не ломает сборку: без них `assets/auth.js` не собирается
и не подключается, кнопки входа нет, сайт получается ровно такой, какой
собирается сегодня. Это важно и для чужих сборок репозитория, и для быстрой
проверки, что новая часть ничего не сломала в старой.

### Обработка ошибок

- Сеть недоступна или проект Supabase спит: запись в `localStorage` уже
  прошла, отправка помечается неудачной и повторяется при следующем действии
  или при следующем открытии страницы. Отдельной очереди повторов не заводим —
  следующее действие и есть повтор.
- Токен протух: клиент Supabase обновляет его сам; если обновление не удалось,
  сессия сбрасывается, кнопка возвращается в состояние «Войти», данные на
  месте.
- OAuth вернул ошибку: страница `/auth/` показывает текст ошибки и ссылку
  обратно на курс.
- `localStorage` бросает (приватное окно Safari): поведение как сегодня —
  обёртка `try` глотает исключение, страница работает, прогресс не переживает
  перезагрузку. При этом облачная запись всё равно уходит, если человек вошёл.
- Запрос отбит политикой RLS: ошибка пишется в консоль, интерфейс не
  показывает ничего — это состояние означает ошибку в схеме, а не в действиях
  человека.

### Тесты

Чистые модули покрываются обычным vitest, как остальной `src/lib`:

- `src/lib/sync/merge.test.ts` — ранги состояний в обе стороны (`passed` не
  сбрасывается в `failed`, `failed` уступает `passed`), равенство рангов
  решается временем, объединение прочитанных, три случая для текста
  упражнения.
- `src/lib/sync/migrate.test.ts` — сбор ключей из снимка хранилища, пропуск
  служебных суффиксов, идемпотентность (повторный прогон не даёт операций),
  пустое локальное хранилище, пустое облако.
- `src/lib/site/client.test.ts` — дополняется проверкой, что состояние
  `passed`/`failed` после прогона и после вопросов действительно записывается
  в `course-step-state:<slug>`.

Сетевой слой в тестах не поднимается. Вместо этого в порядке работ есть ручной
чеклист: анонимная сессия не читает чужих строк, вход и выход, миграция с
непустым локальным прогрессом, второй браузер видит прогресс первого,
разошедшийся код кладёт копию и показывает плашку.

## Ограничения бесплатного тарифа

Три вещи, которые нужно знать до, а не после:

1. Встроенная почта Supabase шлёт порядка двух-трёх писем в час. Для открытой
   регистрации это неработоспособно, и именно поэтому вход только через GitHub
   OAuth: писем он не отправляет вовсе. Email с паролем потребовал бы своего
   SMTP.
2. Проект на бесплатном плане засыпает после семи дней без запросов. Первый
   заход после паузы упирается в ручное пробуждение из консоли. Для активно
   читаемого курса это не проявится, но знать об этом надо.
3. Лимиты — 50 000 активных пользователей в месяц и 500 МБ базы. С потолком на
   размер файла упражнения обе цифры недостижимы в обозримом будущем.

## Что остаётся за рамками

- Синхронизация с локальным приложением Next.js и его `data/progress.db`.
  Локальное приложение остаётся однопользовательским.
- Своя таблица профилей с именем и аватаром: `auth.users` достаточно.
- Лидерборды, публикация прогресса, сравнение с другими.
- Realtime-подписки: две вкладки одного человека синхронизируются при
  перезагрузке, и этого хватает.
- История прогонов тестов: хранится только последний по каждому шагу.
- Экспорт и удаление данных аккаунта по запросу.

1. Завести проект Supabase, накатить `supabase/schema.sql`, включить RLS,
   настроить GitHub OAuth и Redirect URLs. Проверить из анонимной сессии, что
   `select` по всем трём таблицам пуст, а `insert` отказывает.
2. `src/lib/sync/merge.ts` с тестами.
3. `src/lib/sync/migrate.ts` с тестами.
4. Локальная запись `passed`/`failed` в `course-step-state:<slug>` и
   `updatedAt` у упражнений, с тестами в `client.test.ts`. Пока без сети — это
   самостоятельное улучшение статики.
5. `src/site-auth/auth.ts`, сборка в `build-site.mts`, подключение через
   `modules`, кнопка в шапке, страница `out/auth/index.html`.
6. Подключение отправки к существующим скриптам: отметка шага, результат
   прогона, сохранение кода с дебаунсом в две секунды.
7. Подтягивание облака при открытии страницы урока и слияние с локальным.
8. Ручной чеклист из раздела «Тесты», затем публикация.

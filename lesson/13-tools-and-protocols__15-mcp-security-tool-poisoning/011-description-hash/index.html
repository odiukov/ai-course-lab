Пишем description_hash

У тебя на руках объект инструмента: имя, описание, схема параметров. Надо получить из него одну короткую строку, которую можно положить в файл и через месяц сравнить. Выглядит как работа на одну строчку: позвал hashlib.sha256, взял hexdigest(), готово.

Только сначала — что именно ты туда кладёшь?

Хеш считается от байтов, а не от словаря. Между инструментом и хешем есть шаг, который пишешь ты сам: собрать нужные поля (какие — уже разобрали в шаге 10) в один текст. И этот шаг обязан давать один и тот же текст всегда. Словарь, отданный в JSON без сортировки ключей, сегодня выдаст один порядок, завтра другой — и хеш разойдётся, хотя описание не тронули. Значит: сортировка ключей включена, кодировка зафиксирована (utf-8), настройки сериализации одни и те же навсегда.

Отдельно реши, что делать с мусором: сервер может прислать описание с хвостовым пробелом или с \r\n вместо \n. Или подчищай это по явному правилу, или не подчищай вовсе — но одинаково в обоих местах, где считаешь хеш.

Как проверить, что функция рабочая: посчитай хеш дважды подряд на одном объекте — строки совпадают до символа. Поменяй в описании одну букву — результат не похож на прежний ни началом, ни концом. Переставь ключи в схеме параметров местами — хеш не шелохнулся.

Прибитый хеш ловит подмену только тогда, когда сам он не зависит ни от чего, кроме содержимого.

🎒 На пальцах. Монетоприёмник взвешивает монету с точностью до сотых грамма. Настоящая десятка с прилипшей крупинкой сахара — уже не десятка, автомат её выплёвывает. Виновата не монета: ты не протёр её перед тем, как сунуть. Нормализация — это и есть «протереть»: убрать хвостовой пробел, привести перевод строки к одному виду. По одному и тому же правилу каждый раз, иначе детектор будет орать на честный сервер.

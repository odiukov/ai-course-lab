Пишем new_runtime

Ты запускаешь демо второй раз — а в очереди внезапно остаётся сообщение из прошлого запуска. Ещё хуже: актор, созданный раньше, обнаруживается в новом рантайме. Значит, два экземпляра незаметно делят изменяемое состояние.

В new_runtime тебе нужно собрать свежий рантайм из трёх пустых частей, описанных в шаге 9: очереди сообщений, реестра акторов и подписок на топики. Функция пока ничего не доставляет и никого не регистрирует — она лишь подготавливает чистую площадку для дальнейшей работы.

Обрати внимание на два условия:

  • очередь должна поддерживать добавление сообщений в конец и извлечение из начала;
  • каждый вызов new_runtime должен создавать новые контейнеры, а не переиспользовать прежние.

Второе условие легко недооценить. Проверь мысленно: если создать first = new_runtime() и second = new_runtime(), а затем положить сообщение в очередь first, изменится ли second? Правильный ответ — нет. То же относится к реестру и подпискам.

После реализации посмотри не только на то, что все три коллекции пусты. Убедись, что это независимые объекты. Сейчас ты не учишь рантайм работать — ты гарантируешь, что каждый запуск начинает собственную историю.

🎒 На пальцах. Представь новую партию в настольную игру. Ты ставишь на стол пустую коробку заданий, чистый список игроков и незаполненную таблицу команд. Если взять эти предметы из прошлой партии, старые ходы вмешаются в новую. new_runtime раскладывает новый комплект, поэтому две партии можно вести рядом, и состояние одной не просочится в другую.

Практика: new_runtime

Редактируется только функция этого шага — остальной файл упражнения подставится при запуске. Для метода ниже также показан контекст класса: его поля и готовые методы. Код выполняется прямо в твоём браузере: первый запуск качает Python, примерно двенадцать мегабайт, дальше из кэша.

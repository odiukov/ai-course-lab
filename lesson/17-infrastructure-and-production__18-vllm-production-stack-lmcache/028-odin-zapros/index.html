Обслуживаем запрос: восстановить KV или выполнить prefill и сохранить результат

Запрос с тем же длинным промптом приходит во второй раз. Кажется, его можно сразу считать попаданием, но совпадения ключа недостаточно: нужная запись могла быть вытеснена ограниченным кэшем. Поэтому сначала ты вызываешь cache_lookup из шага 25 и только после этого выбираешь один из двух путей.

Если запись найдена, повторный prefill не нужен. Система восстанавливает сохранённый KV, а время этой операции оценивает через restore_ms из шага 16. Само попадание также обновляет горячесть записи: часто используемый KV дольше остаётся в кэше.

Если записи нет, восстанавливать нечего. Тогда система выполняет prefill заново, учитывает его стоимость через recompute_ms из шага 14, а полученный KV передаёт в cache_put из шага 27. Сохранение важно: текущий запрос оно уже не ускорит, зато подготовит быстрый путь для следующего совпадения. Если места не хватает, cache_put заодно вытеснит наименее недавно использованную запись.

Есть тонкость: промах — не ошибка обслуживания. Запрос всё равно будет выполнен, просто более дорогим способом. А попадание — ещё не готовый ответ модели: восстановленный KV лишь позволяет продолжить работу без повторной обработки уже знакомого промпта.

Получается, каждый запрос проходит через одну развилку: либо платит за перенос готового состояния, либо за пересчёт и создание нового состояния.

🎒 На пальцах. Представь мастерскую, где для каждого клиента хранят настроенную форму для отливки ключа. Если форма нашлась на полке, мастер ставит её в станок и продолжает работу. Если формы нет, он заново снимает размеры и изготавливает её, а затем оставляет на полке. Текущий ключ готов в обоих случаях, но цена подготовки различается.

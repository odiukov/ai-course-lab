Ставим Adam между коллективами

Ты смотришь на четыре процесса и замечаешь странный выбор: у каждого есть свой кусок параметров, но привычный Adam привык обновлять модель целиком. Если запустить его на каждом процессе для всей модели, появятся четыре копии его служебной памяти — и экономия ZeRO-1 исчезнет. Если обновлять до синхронизации градиентов, процессы ещё и примут решения по разным данным.

Выход подсказывает порядок из шага 3: Adam ставят ровно между двумя коллективными операциями. Первая собирает вклад всех процессов и оставляет каждому синхронизированный градиент только для его части параметров. Теперь у процесса есть всё необходимое, чтобы обновить принадлежащий ему шард — и ничего лишнего.

Сам Adam можно представить как настройщика, который для каждого параметра ведёт две записи: куда градиент обычно направляет изменение и насколько сильно он колеблется. Эти записи называют состоянием оптимизатора. В ZeRO-1 они лежат рядом только с тем шардом, за который отвечает процесс. Поэтому каждый процесс обновляет свою мастер-копию параметров локально, а затем вторая коллективная операция раздаёт обновлённые части всем участникам. К следующему forward у каждого снова собрана одинаковая модель.

Для тренировочного цикла вся эта механика остаётся одним действием на месте обычного optimiser.step: синхронизировать градиенты, выполнить локальный Adam, собрать параметры. Цикл задаёт момент шага, но не узнаёт, кто владеет каким куском.

🎒 На пальцах. Представь мастерскую, где четыре реставратора совместно восстанавливают одну мозаику. Сначала они сводят все замечания и каждому выдают согласованные поправки только для его фрагмента. Реставратор хранит историю решений лишь по своим камням, вносит изменения, а затем показывает обновлённый фрагмент остальным. В итоге у всех снова есть фотография одной и той же мозаики, хотя рабочие журналы не дублируются.

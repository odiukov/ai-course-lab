Пишем page_in

Ты спросил у агента: «какой дедлайн по договору с типографией?» Агент честно позвал archival_search из шага 23, получил три записи с самым высоким пересечением слов — и замолчал. В ответе ни слова про дедлайн.

Почему? Потому что список из трёх словарей вернулся в питон, а не в промпт. Модель видит только то, что собрал render_main_context из шага 19. Поиск сработал, а найденное осталось за стеклом.

Вот эту щель и закрывает page_in — та самая подкачка внутрь, про которую шла речь в шаге 26 и шаге 27. Функция принимает запрос, зовёт нужный поиск (архивный или по прошлым ходам — из шага 25), берёт top_k лучших записей, склеивает их в один читаемый текстовый блок и кладёт его в буфер сообщений через append_message из шага 17 — с ролью наблюдения, не «assistant». Иначе модель решит, что сама это сказала.

На что смотреть, пока пишешь:

  • В блок тащи id и tags из шага 20, а не только текст. Тогда агент может сослаться на источник, а ты — проверить, откуда факт.
  • Пустой результат — тоже результат. Допиши явное «по запросу X ничего не найдено», иначе агент будет искать то же самое по кругу.
  • Уже подкачанное не подкачивай снова: проверь, нет ли этого id в буфере. Три повтора одной записи съедают окно.
  • page_in копирует, а не переносит: в архиве запись остаётся. И помни, что три записи по 400 слов вытеснят из буфера старые сообщения по политике из шага 16.

Пока page_in не написан, весь архив — мёртвый груз: найти можно, прочитать нельзя.

🎒 На пальцах. Как заказ в архиве документов: ты не уносишь домой сам том — тебе выносят фотокопию нужной страницы, а на копии стоит штамп с шифром дела. Оригинал остаётся на полке, копия ложится к тебе на стол и занимает место среди других бумаг. Штамп нужен, чтобы потом сказать, откуда цифра. Ровно это page_in и делает: копия, штамп, место на столе.

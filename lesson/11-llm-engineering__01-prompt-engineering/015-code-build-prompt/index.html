Пишем build_prompt

Ты второй раз за день собираешь вызов вручную: достал шаблон из каталога шага 14, прогнал его через render_template из шага 13, скопировал system-текст, приклеил prefill. Ответ пришёл — но какой-то расплывчатый. Через минуту находишь причину: температуру рядом с шаблоном ты видел, а в вызов её перенести забыл.

И так будет каждый раз, пока сборка живёт у тебя в голове, а не в коде.

Поэтому следующая функция — build_prompt. Она принимает имя паттерна и словарь значений, а отдаёт готовый вызов целиком: отрендеренный system-текст, список сообщений и температуру из карточки паттерна. Одна дверь, через которую проходит любой промпт.

Внутри всё уже знакомо: найти карточку по имени, прогнать через render_template и system-шаблон, и user-шаблон (значения-то одни и те же), собрать сообщения в порядке из шага 5 — user, а следом assistant-prefill.

Смотри на три места. Первое: имя паттерна, которого в каталоге нет, — не молчи, скажи прямо, какие есть. Второе: prefill необязателен, и когда его не передали, лишнего пустого assistant-сообщения быть не должно — не пустая строка, а вообще нет элемента в списке. Третье: пропущенные переменные ты уже ловишь в render_template, и здесь эту проверку не дублируй — пусть ошибка всплывает оттуда.

Проверь себя так: вызови build_prompt дважды с разными значениями — структура на выходе обязана совпасть до последнего ключа, отличаться должен только текст внутри.

🎒 На пальцах. Повар на кухне не вспоминает состав бургера — он читает чек и кладёт слои всегда в одном порядке: булка, котлета, соус, крышка. Соуса в заказе нет? Слой просто не кладут — не мажут воздухом «на всякий случай». Твой build_prompt — тот же чек: неважно, какой паттерн заказали, на выдачу уезжает одинаково собранная стопка, и ничего не теряется по дороге.

Практика: build_prompt

Здесь только функция этого шага — остальной файл упражнения подставится при запуске. Код выполняется прямо в твоём браузере: первый запуск качает Python, примерно двенадцать мегабайт, дальше из кэша.

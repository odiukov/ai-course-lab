Пишем is_terminal

Ты пишешь клиент, который каждые две секунды дёргает tasks/status. Когда останавливаться? Пишешь if state == "completed": break. Потом вспоминаешь про failed — дописываешь. Потом про cancelled. Потом такая же тройная проверка нужна там, где решается, можно ли ещё отменить задачу. И там, где чистится хранилище. Три места, в каждом по три сравнения — и однажды в одном из них cancelled не окажется, а клиент будет вечно спрашивать про задачу, которую пользователь сам же отменил.

Поэтому знание «это конец пути» из шага 14 стоит вынести в одну функцию: is_terminal(state). На вход — строка состояния, на выход — True или False. Больше ничего: ни задачи целиком, ни времени, ни обращения к хранилищу.

Из пяти состояний шага 12 три дадут True и два — False. input_required соблазнительно записать в терминальные: работа-то стоит, сервер ничего не считает. Но это петля, задача жива и вернётся в working — опрос прекращать нельзя. Это и есть главная ловушка шага.

Смотри на две вещи. Первое: реагирует ли функция на регистр — если сервер пришлёт "Completed", что вернётся? Второе: не путай её с is_expired из шага 8. Та смотрит на часы, эта — только на строку. Задача может быть завершённой и ещё живой; может быть в working и уже протухшей.

Проверь на всех пяти состояниях сразу — три True, два False, и ни одного «наверное».

🎒 На пальцах. Залитый бетон: пока не схватился, его можно разровнять, добавить, переделать опалубку. Схватился — форма окончательна, дальше только принимать как есть. is_terminal — это ровно один вопрос к плите: «застыла?» Не «сколько ей дней», не «выдержит ли нагрузку» — это другие вопросы и другие функции. Один вопрос, один ответ, одно место в коде, где записано, что считать застывшим.

Практика: is_terminal

Здесь только функция этого шага — остальной файл упражнения подставится при запуске. Код выполняется прямо в твоём браузере: первый запуск качает Python, примерно двенадцать мегабайт, дальше из кэша.

Пишем validate_args

Модель прислала для search_issues такой словарь: {"limit": "5", "status": "in_progress"}. Три проблемы сразу: "5" — строка вместо числа, "in_progress" нет среди разрешённых, а обязательное query вообще забыто. Починку строки ты уже умеешь делать через coerce_value из шага 21, три случая на отказ разобрал в шаге 22.

Но кто вызывает эти проверки, в каком порядке — и что возвращает наружу?

Это и есть validate_args. Она берёт контракт инструмента (тот, что собирает make_tool из шага 14) и словарь от модели, и проходит по схеме поле за полем. Обязательное отсутствует — запиши ошибку. Поле есть — сначала приведи тип, и только потом сравнивай с enum: если проверять "5" против списка чисел до приведения, отказ будет ложным. Дальше формат — датам и email нужен настоящий парсер.

Два момента, на которых люди спотыкаются.

Первый: не останавливайся на первой ошибке. Собери все три и верни списком — иначе модель будет чинить по одному полю за ход, и на один вызов уйдёт три круга.

Второй: возвращай не исходный словарь, а новый, с приведёнными значениями. Иначе limit уйдёт в инструмент строкой "5", и ты получишь падение уже внутри — там, где схему никто не смотрит.

И не бросай исключение: пусть функция вернёт результат — успех с чистыми аргументами либо перечень претензий. Почему именно так, а не через raise, — следующий экран.

🎒 На пальцах. Собираешь шкаф. Перед началом высыпаешь пакет фурнитуры и сверяешь со списком: винтов 8 — есть, но один короче остальных; шкантов 3 из 4. Ты не бежишь в магазин за шкантом, чтобы потом обнаружить винт, — ты выписываешь обе строчки и идёшь один раз. И на стол кладёшь пересчитанную, отобранную кучку, а не тот же пакет как был.

Практика: validate_args

Здесь только функция этого шага — остальной файл упражнения подставится при запуске. Код выполняется прямо в твоём браузере: первый запуск качает Python, примерно двенадцать мегабайт, дальше из кэша.

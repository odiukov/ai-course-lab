Полное слияние контрактов применяет отдельное строгое правило к каждому измерению объёма

Представь два контракта для одной работы. Проектный разрешает 45 минут, требует согласования миграций и не ограничивает сеть. Задачный даёт 20 минут, требует согласования публикации и разрешает сеть только к api.example.com. Какой контракт «строже» целиком?

Выбрать один нельзя. Проектный строже по миграциям, задачный — по времени и сети. Если просто оставить «более строгий контракт», часть ограничений исчезнет. Если механически объединить все поля одинаково, результат тоже сломается: для разрешений объединение расширило бы доступ, хотя слияние должно сохранять наименьшие привилегии.

Поэтому полный merge рассматривает каждое измерение объёма отдельно. Для файлов действуют пересечение разрешений и объединение запретов из шага 31. Для времени — минимум, а для одобрений — накопление, как в шаге 32. У network_egress своя трёхсоставная логика из шага 33: отсутствие ограничения уступает списку, два списка пересекаются, полный запрет поглощает всё.

В нашем примере итог даст 20 минут, оба обязательных согласования и доступ только к api.example.com. Ни один исходный контракт не победил целиком — зато каждое его ограничение сохранило силу в своём измерении.

Строгость здесь — не одно общее число, а набор независимых правил.

🎒 На пальцах. Ты собираешься в поход по требованиям двух инструкторов. Один ограничил вес рюкзака и потребовал аптечку, другой сократил маршрут и запретил разводить огонь. Нельзя выбрать «более строгого» инструктора целиком: их требования относятся к разным вещам. Ты отдельно берёшь меньший вес, короткий маршрут, аптечку и запрет на огонь — только так ни одна граница не потеряется.

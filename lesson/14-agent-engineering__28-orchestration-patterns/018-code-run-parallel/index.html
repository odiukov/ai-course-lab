Пишем run_parallel

Ты запускаешь трёх предлагающих агентов и замечаешь странность: второй начинает работу только после ответа первого, а третий — после второго. Предложения независимы, но время складывается. Значит, обычный цикл с ожиданием внутри превратил параллельную топологию из шага 17 в последовательную очередь.

В run_parallel сначала создай отдельную задачу для каждого агента, не дожидаясь её результата. Всем передай один и тот же исходный запрос: предлагающие агенты не должны видеть ответы соседей или дописывать общий черновик. Лишь когда запущена вся группа, дождись её завершения и собери предложения.

Обрати внимание на соответствие ответа агенту. Быстрый агент может закончить первым, хотя стоял последним в исходном списке. Поэтому результат функции должен позволять понять, кто что предложил: например, сохранять исходный порядок или возвращать пары «агент — ответ». Выбери один контракт и соблюдай его последовательно.

Проверь функцию на искусственных задержках. Если три агента отвечают за 1, 2 и 3 секунды, общее ожидание должно быть близко к 3 секундам, а не к 6. Ещё проверь, что каждый получил неизменённый запрос, а число результатов совпало с числом агентов.

run_parallel пока только запускает независимые предложения и собирает их. Критика и выбор победителя появятся позже: здесь важно получить несколько самостоятельных голосов одновременно, не смешав их раньше времени.

🎒 На пальцах. Представь трёх переводчиков в отдельных кабинах. Ты одновременно раздаёшь им один текст, а затем собираешь три подписанных перевода. Если отдавать текст следующему лишь после возвращения предыдущего, кабины простаивают. Если разрешить переводчикам заглядывать в чужие листы, исчезает независимость. Параллельный запуск сохраняет и время, и самостоятельность ответов.

Практика: run_parallel

Здесь только функция этого шага — остальной файл упражнения подставится при запуске. Код выполняется прямо в твоём браузере: первый запуск качает Python, примерно двенадцать мегабайт, дальше из кэша.

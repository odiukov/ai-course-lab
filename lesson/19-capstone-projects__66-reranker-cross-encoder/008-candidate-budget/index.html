Оцениваем только пул кандидатов и сохраняем батчинг

В каталоге миллион документов, а первая стадия вернула тебе 50 кандидатов. Можно по привычке запустить cross-encoder для каждого документа каталога — но тогда быстрый отбор из шага 1 теряет смысл. Можно обработать только эти 50, но вызывать модель 50 раз подряд — и получить правильные баллы с ненужной задержкой.

Здесь важно сохранить обе границы: cross-encoder видит только пул кандидатов первой стадии, а весь пул проходит через него одним батчем. Для 50 кандидатов ты собираешь 50 пар: в каждой строке один и тот же запрос и свой документ. Порядок внутри пары остаётся тем, который закреплён в шаге 3: сначала запрос, затем документ. После упаковки получаются батчевые тензоры, и модель выполняет один прямой проход.

Батч не смешивает документы между собой и не вычисляет для них общий балл. Это просто пачка независимых примеров, обработанных одновременно. На выходе всё равно должно быть 50 отдельных чисел — по одному для каждой входной пары, как следует из контракта шага 5. Соответствие позиций тоже сохраняется: первая пара даёт первый балл, вторая — второй и так далее.

Так быстрый retriever ограничивает объём дорогой работы, а батчинг не даёт накладным расходам повториться 50 раз.

🎒 На пальцах. Представь досмотр ручной клади в аэропорту. Сотрудник уже отобрал 50 сумок для дополнительного сканирования — тащить к аппарату весь багаж аэропорта незачем. Но и включать ленту отдельно ради каждой сумки расточительно. Все 50 кладут на одну ленту: аппарат делает один проход, однако снимок и результат проверки остаются отдельными для каждой сумки.

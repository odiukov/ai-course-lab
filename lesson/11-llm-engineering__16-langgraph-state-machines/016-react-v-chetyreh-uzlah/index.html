Граф ReAct: два узла и два ребра

Открой любой продакшен-агент на LangGraph и посчитай узлы. Сколько их там? Кажется, должно быть много: один думает, второй планирует, третий проверяет, четвёртый пишет ответ. А в рабочем ReAct-агенте узлов ровно два.

Первый — agent. Он берёт всю историю сообщений из состояния, отдаёт её модели и возвращает одно сообщение ассистента. Внутри этого сообщения либо готовый ответ человеку, либо tool_calls — просьба «посмотри мне погоду в Киеве».

Второй — tools. Он смотрит на последнее сообщение ассистента, выполняет все tool_calls, которые там лежат, и отдаёт результаты как сообщения инструментов. Именно отдаёт: приклеивать их к истории будет редьюсер add_messages из шага 12, а не сам узел.

Теперь стрелки. Из tools ребро одно и статическое — всегда обратно в agent: сходил за данными, вернись думать. Из agent ребро условное (оба типа мы разбирали в шаге 8): есть tool_calls — иди в tools, нет — в END.

Всё. Посмотри, что получилось: выйти из этой пары можно ровно в одном месте — на условном ребре из agent. У tools выхода нет вообще, у него единственный путь — назад. Это тот самый while True с break из шага 1, только развёрнутый в две стрелки: agent — «подумал», tools — «сделал», условное ребро — «а надо ли ещё?». Полный цикл Thought, Action, Observation, снова Thought — и всё это с чекпоинтами, прерываниями и стримингом из шага 3, примерно в сорока строках.

Цикл здесь не написан кодом. Он нарисован рёбрами.

🎒 На пальцах. Аэропортовый шаттл ходит между терминалом и дальней стоянкой. Со стоянки маршрут один — всегда назад к терминалу, других вариантов у водителя просто нет. А у терминала диспетчер смотрит в список: остались пассажиры на стоянку — езжай ещё круг; список пуст — рейс закрыт. Двери на улицу есть только у терминала. Круги гоняет не расписание, а отсутствие второго выхода.

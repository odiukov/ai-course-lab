Пишем schedule_continuous

Запусти мысленно три запроса при двух слотах: короткому A нужна одна итерация, длинному B — четыре, а C ждёт в очереди. После первого шага A завершён. Если его место остаётся пустым до окончания B, у тебя снова получился статический батч, только под другим именем.

В schedule_continuous время движется по одной итерации decode. На каждой итерации повтори порядок из шага 21: убери завершённые запросы из RUNNING, заполни освободившиеся слоты доступными запросами из очереди, затем уменьши оставшуюся работу каждого запущенного запроса на один токен. Состав RUNNING должен меняться так, как ты проследил в шаге 22.

Следи за двумя границами. Запрос нельзя принять раньше его времени поступления, даже если слот свободен. Но если запрос уже поступил, он должен попасть в первый освободившийся слот без ожидания окончания остальных. Именно это поведение симулятора было подготовлено в шаге 23.

Сохрани порядок очереди и формат результата таким же, как у schedule_static из шага 4, чтобы сравнение стратегий измеряло планирование, а не различия интерфейса. Для самопроверки возьми A, B и C из первого примера: C должен начать работу сразу после A, пока B продолжает выполняться. Если C ждёт B, проверь момент удаления завершённых запросов и повторного заполнения слотов.

🎒 На пальцах. Представь две стиральные машины в прачечной. Одна закончила короткую стирку, а вторая ещё долго крутит бельё. Ты не ждёшь, пока остановятся обе: сразу загружаешь следующую корзину в свободную машину. schedule_continuous делает то же самое — проверяет свободные места после каждого цикла и тут же использует их.

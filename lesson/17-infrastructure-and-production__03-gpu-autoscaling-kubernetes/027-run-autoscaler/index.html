Пишем run_autoscaler

В симуляции приходит новая минута нагрузки: очередь выросла, текущих реплик не хватает, но дополнительные GPU ещё не готовы. Тебе нужно провести автоскейлер через эту минуту так, чтобы не перепутать решение о масштабе с фактическим состоянием кластера.

В run_autoscaler собери цикл из шага 26. На каждом такте функция должна получить метрики нагрузки, вычислить желаемое число реплик через desired_replicas из шага 23, а затем пропустить результат через stabilize из шага 25. Обрати внимание на порядок: стабилизировать нужно новое решение, а не исходную метрику.

После этого примени изменение к симулируемому кластеру. Здесь особенно важна выбранная стратегия. Наивный HPA смотрит на duty cycle, вариант с очередью использует её глубину, а режим KAI дополнительно соблюдает gang scheduling: группа либо получает нужные GPU целиком, либо пока не запускается. Частично доступные ресурсы нельзя незаметно превратить в работающую реплику — это снова создало бы ловушку, разобранную в шаге 11.

На каждом такте обновляй состояние очереди и занятых реплик. Проверяй граничные случаи: нулевая нагрузка, отсутствие реплик, запрос на масштабирование выше доступной ёмкости и неполная gang-группа. Результат функции должен сохранять ход симуляции, чтобы позже из него можно было получить показатели отчёта. Пока не смешивай их подсчёт с самим циклом: этот шаг отвечает за честное изменение состояния во времени.

🎒 На пальцах. Представь диспетчера железной дороги с журналом по минутам. Он видит пассажиров, решает, сколько составов запросить, учитывает запрет на резкие перестановки и отмечает, какие составы действительно вышли на линию. Если для длинного поезда не хватает вагонов, половину состава отправлять нельзя. run_autoscaler — именно такой журнал решений и последствий.

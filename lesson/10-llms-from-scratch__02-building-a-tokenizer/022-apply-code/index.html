Пишем apply_merges

Перед тобой байтовая последовательность [97, 98, 99] и два обученных правила:

  • (97, 98) → 256
  • (256, 99) → 257

После первого правила последовательность станет [256, 99], поэтому второе сможет превратить её в [257]. Если применить правила в обратном порядке, пары (256, 99) сначала ещё не существует — получится другой результат. Значит, apply_merges не выбирает «самую подходящую» пару: она строго воспроизводит порядок обучения, зафиксированный в таблице merges, как мы договорились в шаге 21.

Напиши функцию, которая принимает байтовую последовательность и список правил. Заведи текущую последовательность, затем проходи по merges от первого правила к последнему. Для каждого правила передавай текущий результат, пару и её новый ID в уже имеющуюся apply_merge. Возвращённая последовательность становится входом для следующего правила. В конце верни то, что осталось после всего списка.

Обрати внимание на два случая: пустой список merges должен оставить вход без изменений, а правило, пары для которого сейчас нет, не должно ничего ломать. Самостоятельно разбирать соседние элементы внутри apply_merges не нужно: поиск всех непересекающихся вхождений уже выполняет apply_merge. Здесь твоя задача — правильно организовать последовательность вызовов.

Проверь функцию на примере выше: промежуточный ID 256 должен появиться раньше, чем правило с ним будет применено.

🎒 На пальцах. Представь редактора с упорядоченным списком замен. Сначала он во всём тексте заменяет ab на новый знак X, а следующая строка предписывает заменить Xc на Y. Нельзя начать со второй строки: нужного X в тексте ещё нет. apply_merges просто ведёт редактора сверху вниз по этому списку.

Проверяем merges по сырым байтам и сверяем chat template с эталонным токенизатором

Ты выводишь выученный токен и видишь the. Всё выглядит разумно — но был ли там начальный пробел? А может, часть UTF-8-последовательности превратилась при печати в невидимый или заменяющий символ? Обычная строка здесь способна скрыть именно ту ошибку, которую ты ищешь.

Добавь get_token_bytes(id), возвращающий байты из vocabulary без декодирования. Для нескольких десятков частых merges печатай их через представление наподобие repr: тогда b' the', b'def ' и байты эмодзи останутся различимыми. Заодно проверь механическое условие из шага 24: байты результата каждого merge должны в точности равняться байтам левой части плюс байтам правой. Так ты исследуешь не красивое отображение, а фактический материал токена.

Затем подними проверку на уровень целого чата. Возьми короткий список сообщений, пропусти его через свою функцию из шага 43 и через эталонный токенизатор HuggingFace для той же версии Llama 3. Настройки тоже должны совпадать, особенно добавление приглашения для ответа ассистента. Сравнивай прежде всего полный список token IDs, а при первом расхождении посмотри на сырые байты соседних токенов. Часто виноват один лишний перевод строки, пробел или неверный служебный маркер из формата шага 41.

Совпавший декодированный текст ещё может маскировать ошибку; совпавшие IDs уже фиксируют точное поведение конвейера.

🎒 На пальцах. Представь часовщика. Сначала ты рассматриваешь зубцы каждой новой шестерёнки под лупой: подпись «маленькая шестерня» недостаточна, важна точная форма. Затем собираешь часы и сверяешь каждый тик с эталонным механизмом. Сырые байты проверяют шестерёнки, а одинаковая последовательность IDs подтверждает, что весь механизм чата собран без лишнего зубца.

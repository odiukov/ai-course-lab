Пишем cheapest_path

Ты запускаешь сравнение и видишь заманчивый вариант за €120. Рядом — вариант за €180. Хочется сразу выбрать первый, но у него не хватает зарезервированной мощности для пиковой нагрузки. Значит, «самый дешёвый» ещё не означает «подходящий».

В cheapest_path тебе предстоит разделить выбор на два действия. Сначала отбрось пути, которые не удовлетворяют нагрузке. Для PTU используй необходимое число блоков из функции, написанной в шаге 12, и стоимость резерва из шага 14. Стоимость on-demand уже умеет считать функция из шага 10. Затем сравни итоговые суммы только у оставшихся вариантов и верни путь с минимальной стоимостью.

Следи за тем, чтобы сравнивались расходы за один и тот же период и для одного объёма нагрузки. Ещё одна частая ловушка — выбрать PTU по цене одного блока, хотя пик требует нескольких: округление вверх уже учтено в ptu_units_needed, терять его здесь нельзя.

Проверь функцию на трёх случаях: on-demand дешевле, PTU дешевле и самый дешёвый по цене вариант не выдерживает нагрузку. Если ни один путь не подходит, функция должна сообщить об этом явно, а не возвращать случайного победителя.

Сначала допустимость, потом цена — именно этот порядок делает выбор честным.

🎒 На пальцах. Ты выбираешь дорогу для грузовика к складу. Один мост берёт пошлину €4, другой — €7, но дешёвый мост выдерживает только две тонны, а грузовик весит пять. Сначала ты вычёркиваешь дороги, по которым груз не проедет, и лишь затем сравниваешь пошлины. cheapest_path делает то же самое с нагрузкой и стоимостью.

Практика: cheapest_path

Здесь только функция этого шага — остальной файл упражнения подставится при запуске. Код выполняется прямо в твоём браузере: первый запуск качает Python, примерно двенадцать мегабайт, дальше из кэша.

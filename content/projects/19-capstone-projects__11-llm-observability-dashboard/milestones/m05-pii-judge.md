Добавь отдельный LLM-judge для обнаружения утечек PII. На вход проверки поступает ответ наблюдаемого приложения; guard LLM оценивает вероятность того, что текст раскрывает персональные данные. Сохраняй числовой результат рядом с другими eval-спанами и связывай его с исходным вызовом модели. Ответы с высоким баллом должны попадать в triage queue, где оператор сможет найти исходную трассу и понять контекст события.

Сформулируй стабильную рубрику judge-проверки: она должна отделять вероятную утечку от безопасного текста и возвращать результат, пригодный для порогового правила. Не отправляй в guard-модель больше содержимого, чем требуется для оценки ответа. Поскольку проект посвящён наблюдаемости, сохрани сведения, необходимые для аудита решения: идентификатор трассы, оценку и связь с проверяемым ответом. Сам текст длинного payload должен следовать принятой схеме хранения, а не дублироваться во всех аналитических колонках.

Проверь judge на наборе безопасных ответов и ответов с поддельными SSN. Высокий результат должен создавать элемент очереди, безопасный — оставаться доступным как оценка без ложного triage-события. Затем проследи элемент очереди обратно до ClickHouse-трассы. Типичные ошибки — ограничиться регулярным выражением вместо требуемого guard LLM, потерять ссылку на родительский спан, считать каждый числовой шаблон PII и не сохранять отрицательные результаты. Функция `eval_pii_leak` из локального эталона проверяет лишь форму числового сигнала и не заменяет настоящий LLM-judge.

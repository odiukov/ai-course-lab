Собери входную точку облачной системы: AWS Lambda принимает webhook от установленного GitHub App для события с меткой issue и для комментария в PR. Из полного payload извлеки данные, необходимые downstream-компонентам: репозиторий, номер и содержание issue или контекст PR-комментария. Обработчик должен различать релевантный запуск и обычную активность GitHub. Для issue пропускай дальше только событие с меткой `@agent fix this`; остальные метки и комментарии не должны создавать дорогой worker.

После фильтрации Lambda не запускает агентский цикл внутри webhook-запроса. Она формирует понятный queue contract и отправляет задачу в SQS, отделяя быстрый приём события от продолжительной работы ECS Fargate. Сохрани исходные идентификаторы GitHub, чтобы dispatcher и worker могли связать запуск с правильным репозиторием и issue, а затем опубликовать результат в том же пользовательском контексте.

Граница этапа заканчивается на подтверждённом сообщении SQS. Здесь не требуется клонировать код, выводить Dockerfile, вызывать модель или открывать PR. Типичная ошибка — считать успешный ответ Lambda доказательством постановки работы в очередь; проверяй фактическое сообщение. Другая ошибка — реагировать на любую метку и тем самым обходить бюджетный вход. Локальная структура `Task` лишь показывает минимальную форму задачи, но настоящая реализация должна пройти через GitHub webhook, развёрнутую Lambda и реальную SQS.

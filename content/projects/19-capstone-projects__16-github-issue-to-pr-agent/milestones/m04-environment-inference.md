Worker начинает с чистой Daytona- или E2B-песочницы и не может рассчитывать на заранее прогретый dev image. После клонирования репозитория и создания отдельного git worktree определи, относится ли проект к Python, Node, Go или Rust, и найди используемый package manager: `uv`, `pnpm`, `go mod` либо `cargo`. Если репозиторий уже предоставляет Dockerfile, используй его как описание окружения. Если его нет, сгенерируй generic Dockerfile под обнаруженные язык, framework, package manager и целевой runtime.

Цель этапа — получить воспроизводимую среду, в которой можно установить зависимости и запустить проектные тесты до вмешательства агента. Эта базовая проверка отделяет проблему окружения от неудачного патча. Зафиксируй сделанный вывод в trace: какие признаки языка и package manager были найдены, существовал ли Dockerfile и был ли он синтезирован. Именно этот след понадобится при разборе отказов benchmark.

Не заменяй облачную песочницу локальным запуском на своей машине: локальные кэши и установленные инструменты скрывают главный риск проекта. Не своди поддержку к одному удобному Python-репозиторию — исходный объём включает четыре семейства языков. Также не позволяй агенту редактировать инфраструктурное описание лишь ради того, чтобы тесты начали проходить: синтез окружения является управляемой стадией worker. Этап заканчивается, когда свежая sandbox способна подготовить выбранный реальный репозиторий и вызвать его исходную тестовую команду.

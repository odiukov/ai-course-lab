На этом этапе ты создаёшь GitHub App — единственную bot identity, от имени которой облачный worker читает issue, получает код, пушит агентскую ветку и открывает PR. Выдай приложению ровно заявленные разрешения: issues read+write, pull requests write, contents read+write и workflows read. Для каждого запуска worker должен получать свежий короткоживущий installation token, ограниченный конкретной установкой и репозиторием, а не постоянный пользовательский credential.

Раздели две поверхности безопасности. Permissions приложения определяют доступ к GitHub API, но не способны запретить запись в конкретный путь или самостоятельно гарантировать отсутствие force-push. Поэтому branch protection должна запрещать прямые изменения `main` и force-push, а GitHub App нельзя включать в bypass list. Отдельно зафиксируй worker-side allow-list: предложенный diff не может содержать записи под `.github/workflows`, хотя приложение имеет `workflows: read`. Проверка должна происходить до push и публикации PR.

Проверь негативные сценарии явно: истёкший token не открывает PR; запрос force-push отклоняется; попытка писать в `main` не проходит; diff с изменением workflow блокируется. Не подменяй эти гарантии договорённостью в prompt агента: они должны исполняться GitHub и worker policy независимо от поведения модели. Локальный Python-эталон показывает форму проверки разрешений, но готовность подтверждается только реальной установкой приложения и защищённым репозиторием.

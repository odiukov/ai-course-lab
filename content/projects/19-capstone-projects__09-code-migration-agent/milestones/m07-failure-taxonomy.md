Для каждого репозитория, который не дошёл до успешного PR, создай структурированную запись отказа. Используй заданные классы: `dep_upgrade_required`, `build_tool_drift`, `custom_annotation`, `test_flake`, `syntax_edge_case` и `budget_exhausted`; регрессию покрытия сохраняй как `coverage_regression`, поскольку её выделяет тестовый шлюз. Запись должна содержать подтверждающий фрагмент журнала, состояние ветки, текущий diff и ссылку на воспроизводимый trace bundle.

Класс выбирай по наблюдаемой первопричине, а не по последнему поверхностному сообщению. Например, ошибка компиляции, вызванная несовместимой транзитивной зависимостью, должна оставаться проблемой обновления зависимости, а не общей синтаксической ошибкой. Для остановок по бюджету сохраняй сведения, позволяющие отдельно исследовать техническую причину, но не скрывай факт достижения лимита.

Построй TypeScript-дашборд, который агрегирует число отказов по каждому классу и показывает показательный diff для категории. Таксономия — самостоятельный результат проекта: она должна объяснять, куда направлять разработку следующих OpenRewrite- или libcst-рецептов. Не допускай свободных вариантов написания меток и бездоказательной категории `unknown`, иначе данные 50 репозиториев нельзя будет сравнить. Типичные ошибки — хранить только счётчики без воспроизведения, выбирать класс вручную без диагностического следа и показывать diff, не связанный с конкретным запуском.

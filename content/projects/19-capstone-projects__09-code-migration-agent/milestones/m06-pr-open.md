Когда сборка и все тесты проходят, а шлюз покрытия не обнаруживает регрессию, отправь миграционную ветку в удалённый репозиторий и открой pull request. До этого момента никаких PR для частично успешных запусков быть не должно. Публикуемая история должна сохранять отдельный recipe-коммит и отличимые агентные коммиты, чтобы ревьюер мог проверить происхождение каждого изменения.

В описании PR укажи, какие детерминированные рецепты применились, сколько преобразований они сделали и какие исправления затем добавил агент. Приложи сводку итогового diff, результат сборки, число прошедших тестов, исходное и конечное покрытие, стоимость, длительность и число агентных ходов. Добавь связь с трассой запуска, чтобы от PR можно было перейти к журналам и решениям цикла.

Открытие PR является побочным эффектом, поэтому выполняй его только один раз после окончательного решения шлюза. Повторный запуск контроллера не должен создавать дубликат для той же успешной ветки. Не сворачивай все изменения в непрозрачный единый коммит и не заявляй, что агент выполнил работу детерминированного слоя. Типичные ошибки — публиковать ветку до измерения покрытия, терять список рецептов, оставлять без объяснения агентные изменения либо открывать PR после бюджетной остановки. Результат этапа должен быть удобен и для ревьюера, и для последующего расчёта вклада двух слоёв.

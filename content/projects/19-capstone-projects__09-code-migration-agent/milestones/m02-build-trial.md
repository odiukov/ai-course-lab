После recipe-коммита создай для ветки отдельный Daytona sandbox с заранее подготовленной целевой средой: Java 17 для Java-репозитория или Python 3.12 для Python-репозитория. Сборка должна использовать реальную систему проекта — Maven, Gradle либо uv, — а не упрощённую локальную проверку. Зафиксируй команду, код завершения, длительность и полный журнал, поскольку именно эта диагностика станет первым наблюдением агентного цикла.

Раздели два исхода. Если сборка проходит, не вызывай агент ради формального участия: сразу передай ветку к тестовому шлюзу. Если сборка падает, сохрани stdout, stderr и контекст sandbox, после чего сформируй задание агенту на основании фактической ошибки. Переход между этапами должен быть машинно проверяемым, чтобы красная сборка не могла случайно попасть к открытию PR, а зелёная — расходовать модельный бюджет без необходимости.

Изоляция на ветку является обязательным свойством архитектуры. Не переиспользуй изменяемое окружение другого репозитория и не подменяй Daytona локальным процессом только потому, что локальная сборка удобнее. Следи, чтобы сборка выполнялась уже после детерминированного прохода и именно на целевой версии runtime. Типичные ошибки — запуск на старой JDK или Python, потеря полного лога и смешивание установки окружения с неучтёнными исправлениями исходников.

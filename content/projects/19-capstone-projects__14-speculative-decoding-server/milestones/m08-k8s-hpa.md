Оформи serving-стек как Kubernetes deployment с GPU-ресурсами через NVIDIA device plugin. Реплика должна соответствовать выбранной схеме: один GPU на сервер либо tensor-parallel shard, если модель требует нескольких GPU. Экспортируй в Prometheus метрику `queue_wait_ms` и настрой HPA так, чтобы решение о масштабировании принималось по времени ожидания запросов, а не по загрузке CPU.

Проведи управляемую демонстрацию. Начни со стабильной нагрузки, зафиксируй исходные число реплик, queue wait, throughput и latency. Затем утрой интенсивность запросов и покажи, что рост очереди приводит к scale-out, новые GPU-реплики становятся готовыми, а сервис продолжает отвечать во время rollout. После масштабирования сопоставь очередь и задержку с состоянием до него.

Инварианты — HPA читает реальную serving-метрику, каждая созданная реплика получает требуемые GPU, а rollout не подменяется ручным изменением replica count. Типичные ошибки: масштабирование по CPU, отсутствие адаптера пользовательских метрик, планирование нескольких моделей на уже занятую GPU, измерение только итогового состояния и потеря запросов во время появления реплик.

Локальный Python scaffold не содержит очереди, Kubernetes scheduler или GPU lifecycle, поэтому здесь у него нет подходящего contract target. Доказательство должно включать временную последовательность нагрузки, `queue_wait_ms`, решения HPA, изменение числа реплик и состояние внешнего endpoint.

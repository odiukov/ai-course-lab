Сначала зафиксируй полный контракт поверхности инструментов: Postgres read-only query, S3 list objects с постраничной выдачей, Jira search/fetch, Linear search/fetch, Datadog metric query, PagerDuty on-call lookup, GitHub read-only, Notion search, Slack search и Salesforce read. Проект не должен заменять эти интеграции фиктивными локальными функциями: адаптеры подключаются к соответствующим внешним или облачным сервисам и возвращают ответы через MCP-контракт.

Для каждого инструмента опиши стабильное имя, назначение, типизированную входную схему, форму результата и отдельный scope. Начни с инвентаризации операций и их минимальных прав, затем определи схемы и только после этого подключай обработчики. Read-only должно быть техническим инвариантом, а не договорённостью: Postgres принимает только чтение, GitHub не изменяет репозитории, остальные адаптеры не вызывают мутирующие API. Ошибки внешних систем переводятся в согласованную ошибку инструмента без раскрытия токенов и секретов.

Проверь отрицательные сценарии: неизвестный инструмент, неполные аргументы, неверный тип, отсутствующий scope, пустая страница и ошибка внешнего провайдера. Типичная ошибка этапа — создать десять названий поверх нескольких заглушек либо использовать один широкий scope для всей поверхности. Ещё одна ошибка — смешать Jira create или Postgres write с безопасными операциями: такие возможности появятся только на отдельном сервере. Локальный `MCPServer.register` задаёт проверяемую форму регистрации, но готовность определяется работой развернутых интеграций.

Создай разреженный индекс Tantivy для тех же chunks и ревизий, которые находятся в плотном индексе. Используй BM25F с весом 4 для имени символа, 1 для тела и 2 для summary. Такое разделение должно поддерживать как точные запросы наподобие поиска функции с заданным именем, так и смысловые вопросы, сформулированные естественным языком. Поля не следует заранее склеивать в один непрозрачный текст: их веса являются частью проверяемой поисковой конфигурации.

Согласуй идентификатор документа и метаданные с векторным хранилищем, чтобы последующий query agent мог дедуплицировать результаты по `(repo, path, symbol)`. Индексирование должно обрабатывать добавление, изменение, переименование и удаление символа без накопления устаревших документов. Убедись, что анализатор разумно работает с идентификаторами из разных языков, путями, `snake_case` и `camelCase`, сохраняя возможность точного совпадения имени.

Python-реализация BM25 из эталона фиксирует ожидаемый смысл field weighting и базовый контракт поиска, но не заменяет Tantivy на корпусе заданного размера. Сравни результаты нескольких точных и описательных запросов, чтобы убедиться, что summary не вытесняет имя символа, а длинное тело не получает преимущество только из-за объёма. Типичные ошибки — одинаковые веса всех полей, документы с нулевыми результатами в top-k, рассинхронизация ревизий с Qdrant и отсутствие удаления старого символа после git push.

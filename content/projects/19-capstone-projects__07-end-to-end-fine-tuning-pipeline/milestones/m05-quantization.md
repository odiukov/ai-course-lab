Возьми хешированный checkpoint после preference tuning и выпусти три независимых формата развёртывания: GPTQ-INT4 с Marlin, AWQ-INT4 и GGUF-Q4_K_M через llama.cpp. Каждый quant должен явно ссылаться на один и тот же исходный checkpoint, чтобы различия в размере и производительности объяснялись форматом, а не разными весами. Сохрани артефакты в долговременном хранилище вместе с командами и конфигурациями конвертации.

Для каждого варианта запиши фактический размер и номинальный throughput. Не переноси примерные числа из исходного брифа в отчёт как измерение: значения должны появиться из настоящего внешнего прогона. Проверь, что артефакты загружаются соответствующим runtime и дают корректный инференс до начала сравнительного сервинга. GPTQ-INT4-Marlin станет основным кандидатом для vLLM, GGUF должен оставаться пригодным для llama.cpp, а AWQ — самостоятельным вариантом deployment flexibility.

Квантизация не завершена, если создан только файл без provenance. Манифест должен связывать формат, размер, источник, инструмент и полученный хеш. Типичные ошибки — перезаписать один quant другим, перепутать единицы размера, сравнить throughput на несопоставимых условиях или обнаружить несовместимость только при Kubernetes-деплое. Не объявляй качество сохранённым без последующего прогона общей eval-матрицы.

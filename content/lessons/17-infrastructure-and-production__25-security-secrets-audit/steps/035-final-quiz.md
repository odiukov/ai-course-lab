check:
  - question: >-
      API-ключ скопирован в сорок конфигов. Какое изменение лучше всего сократит
      последствия утечки и упростит ротацию?
    options:
      - Зашифровать каждый конфиг отдельным паролем и обновлять их вручную
      - >-
        Хранить ключ в едином хранилище, выдавать сервису по роли и
        автоматически ротировать с отзывом предыдущей версии
      - Перенести ключ во внутреннюю документацию с ограниченным доступом
      - Добавить ключ в переменные CI/CD и использовать его без срока действия
    correct: 1
    explanation: >-
      Единое хранилище устраняет множество копий, роль ограничивает доступ, а
      автоматическая ротация сокращает срок полезности украденного ключа. Урок
      рекомендует интервал не более 90 дней.
  - question: >-
      Пользователь отправил промпт с email и попросил модель обратиться к
      неизвестному домену. Как должен поступить защищённый сервис?
    options:
      - 'Передать промпт модели, а подозрительный домен отметить в журнале'
      - 'Удалить весь промпт, потому что частичная очистка всегда небезопасна'
      - >-
        Заменить PII стабильной заглушкой, заблокировать домен по
        egress-политике и записать безопасные метаданные
      - 'Разрешить домен, если пользователь вошёл через MFA'
    correct: 2
    explanation: >-
      Очистка защищает PII, egress-политика независимо ограничивает сетевые
      назначения, а аудит фиксирует событие без сохранения исходного промпта.
  - question: >-
      Сканер нашёл действующий ключ в старом коммите. Какой план действительно
      закрывает утечку?
    options:
      - Удалить ключ из текущего файла и сделать новый коммит
      - Сделать репозиторий приватным и оставить ключ действующим
      - >-
        Отозвать ключ, удалить его из истории git и включить сканирование
        каждого коммита
      - 'Переименовать ключ, чтобы сканер больше не узнавал шаблон'
    correct: 2
    explanation: >-
      Ключ мог быть скопирован, поэтому его необходимо отозвать. Очистка истории
      убирает оставшийся секрет, а проверка каждого коммита предотвращает
      повторение проблемы.
  - question: >-
      Из середины append-only журнала удалили запись. Что даст проверка цепочки
      хешей?
    options:
      - Восстановит удалённую запись вместе с исходным промптом
      - >-
        Обнаружит разрыв при наличии доверенной точки сравнения, но сама не
        докажет сохранность полностью пересчитанной цепочки
      - 'Ничего не заметит, потому что хеши обнаруживают только изменение текста'
      - Автоматически перенесёт журнал в холодное хранилище
    correct: 1
    explanation: >-
      Удаление нарушает связи между записями. Однако злоумышленник может
      пересчитать всю цепочку, поэтому её контрольный хеш нужно периодически
      закреплять во внешнем доверенном хранилище.

Ты запускаешь LLM-сервис в отдельной подсети и видишь странный выбор: разрешить ему весь интернет или заранее назвать несколько допустимых адресов. Первый вариант удобнее — пока вредоносная инструкция не заставит сервис отправить фрагмент запроса на чужой сервер. Guardrails из [шага 18](#step-18) снижают этот риск, но сетевой запрет должен сработать даже при их ошибке.

Белый список egress — это перечень направлений, куда сервису разрешено устанавливать исходящие соединения. В него входят только API используемых LLM-провайдеров, эндпоинты векторной базы и хранилища секретов. Попытка обратиться к любому другому адресу не «проверяется внимательнее», а просто отбрасывается — `drop`. Это и есть инфраструктурное ограничение из [шага 2](#step-2): приложению не предлагают вести себя правильно, ему физически не дают другого маршрута.

Но закрыть только HTTP недостаточно. Сервис сначала спрашивает DNS: «Какой IP соответствует этому имени?» Злоумышленник может закодировать секрет прямо в имени вроде `secret-value.attacker.example`. Тогда сам DNS-запрос станет каналом утечки. Поэтому подсеть использует отдельный резолвер — службу, переводящую разрешённые имена в IP-адреса, — и он отвечает только для белого списка.

В итоге даже скомпрометированный процесс может стучаться куда угодно, но доставить данные ему некуда.

> 🎒 **На пальцах.** Представь архив с единственным окном выдачи. Сотрудник может отправлять папки только четырём заранее зарегистрированным получателям; посылки с другими адресами уничтожаются у окна. Даже записку «уточните адрес» нельзя передать через случайную справочную: архив пользуется своей справочной, знающей лишь этих получателей. Утечку останавливает не внимательность сотрудника, а устройство самого окна.

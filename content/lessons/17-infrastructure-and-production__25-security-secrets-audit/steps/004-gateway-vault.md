Представь: ты заменил `OPENAI_API_KEY` в едином хранилище, но AI-gateway всё ещё работает. Как он узнает новый ключ, если никто не переписал его конфиг и не перезапустил сервис?

При каждом запросе gateway сначала обращается не к модели, а к хранилищу из [шага 3](#step-3). Он представляется своей **IAM-ролью** — цифровым удостоверением, которое инфраструктура выдала именно этому приложению. Это не ещё один постоянный пароль: хранилище проверяет, какой сервис пришёл и разрешено ли ему читать конкретный секрет.

Если проверка пройдена, хранилище возвращает текущее значение `OPENAI_API_KEY` на ограниченный срок жизни токена. Gateway подставляет его в запрос к провайдеру модели. Сам ключ при этом не нужно записывать в репозиторий, переменные сборки или десятки конфигураций.

Главное здесь — порядок действий: gateway сначала подтверждает свою личность, затем получает актуальный секрет и только после этого вызывает модель. Поэтому после замены значения в хранилище следующий запрос берёт уже новое значение. Источник истины один, а gateway не обязан заранее знать сам секрет — ему достаточно иметь право запросить его.

Секрет больше не путешествует по команде: за ним приходит конкретный сервис с проверяемым удостоверением.

> 🎒 **На пальцах.** Представь телестудию, где перед каждым эфиром ведущий получает актуальный текст из редакционной системы. Он входит по своему служебному бейджу: система узнаёт ведущего и показывает только разрешённый сценарий. Если редактор исправил одну реплику, следующий эфир пойдёт уже с исправлением — не нужно разносить новые распечатки по сорока гримёркам. IAM-роль — бейдж, хранилище — редакционная система, секрет — текущий сценарий.

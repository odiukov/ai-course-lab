Из [шага 8](#step-8) ты уже знаешь: решение о вызове принимает модель, а руками работает твой код. Но откуда модель вообще узнаёт, что где-то в твоей программе живёт функция, которая ходит за погодой? Сама она в код заглянуть не может — она видит только тот текст, который ты ей прислал.

Значит, вместе с вопросом пользователя надо прислать и список доступных инструментов. Но не фразой «у меня есть функция погоды»: такое описание модель поймёт, а твой код — нет. Нужна форма, одинаково читаемая обеими сторонами. Ею стала JSON Schema:

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Get current weather for a city. Returns temperature in Celsius and conditions.",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "City name, e.g. 'Tokyo' or 'San Francisco'"
        }
      }
    }
  }
}
```

Посмотри, из чего это собрано. `name` — имя, ровно то, которое вернётся тебе обратно в ответе модели. `description` — что функция делает. `parameters` — какие аргументы она принимает: здесь один, `city`, и рядом сказано `"type": "string"`, то есть строка вроде `"Tokyo"`, а не число и не список.

Модель не пересказывает эту схему словами. Она её заполняет: подставляет в `city` конкретный город и отдаёт готовый набор полей.

Без такой заготовки модели снова нечего было бы предъявить коду, кроме красивой фразы — ровно той ситуации из [шага 3](#step-3), где ответ звучал уверенно и был выдуман.

> 🎒 **На пальцах.** Как бланк для посылки на почте. Ты не пишешь на конверте «отправьте это моей сестре в Питер» — ты вписываешь имя в клетку «получатель», индекс в клетку из шести цифр. Бланк заранее сообщает, какие поля есть и что в них можно класть. Схема инструмента — такой же бланк, только выдаёшь его ты, а заполняет модель.

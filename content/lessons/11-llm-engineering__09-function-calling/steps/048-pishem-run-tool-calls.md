У тебя уже есть две детали: `parse_tool_calls` из [шага 27](#step-27) достаёт из ответа модели список вызовов, а `execute_tool_call` из [шага 42](#step-42) выполняет ровно один. Пришёл ответ с двумя вызовами погоды — Токио и Нью-Йорк. Пишешь цикл `for`, внутри дёргаешь `execute_tool_call`, и получаешь ту самую 600 мс из [шага 47](#step-47) вместо 300.

Так а кто должен запускать их разом?

Не `execute_tool_call` — он про один вызов и пусть таким остаётся. Нужна обёртка над ним: `run_tool_calls` принимает весь список вызовов и возвращает список результатов. Внутри она стартует все вызовы, не дожидаясь предыдущего, и ждёт, пока вернётся последний. Одна функция — один уровень: «много вызовов» отдельно от «один вызов».

Три вещи, за которыми тут стоит следить.

Первое — соответствие. Ответы приезжают в произвольном порядке: Нью-Йорк может ответить раньше Токио. Результат обязан тащить за собой имя функции и `id` того вызова, из которого он вырос, иначе модель получит температуру и не поймёт, чья она.

Второе — один упавший вызов не должен ронять остальные. По правилу из [шага 43](#step-43) ошибка — это тоже результат: четыре вызова прошли, пятый вернул текст ошибки, список всё равно полный.

Третье — потолок из [шага 36](#step-36) проверяется здесь, до запуска, а не после того как двадцать вызовов уже ушли в оплачиваемый API.

Пока каждый результат помнит своё `id`, порядок возврата тебе безразличен.

> 🎒 **На пальцах.** Сдал в аэропорту два чемодана. На каждый — бирка с номером. Едут они по разным лентам, и на выдаче маленький выпадает первым, хотя сдавал ты его вторым. Тебе всё равно: номер на бирке говорит, чей чемодан и с какого рейса. Сними бирки — и два одинаковых чёрных чемодана превратятся в загадку. Ровно за этим результату нужен `id` вызова.

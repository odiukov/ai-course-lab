Ты берёшь `parse_tool_calls` из [шага 27](#step-27), подставляешь ключ Anthropic — и функция возвращает пустой список. Хотя в ответе глазами видно: модель решила звать `get_weather`, и город там указан. Код просто не находит вызов.

Потому что искать нечего: поля `tool_calls` рядом с текстом здесь нет. Ответ Anthropic — это список блоков `content`. Один блок может быть текстом («Сейчас посмотрю»), следующий — вызовом:

```json
{"type": "tool_use", "id": "toolu_01A", "name": "get_weather", "input": {"city": "Токио"}}
```

Пробегаешь список, берёшь блоки с `type` равным `tool_use` — вот твои вызовы. Заодно у ответа есть `stop_reason`: если он равен `"tool_use"`, модель остановилась именно ради инструмента.

Дальше ловушка помельче. Аргументы лежат в `input`, и это уже готовый словарь — не строка. Привычный `json.loads` на нём падает.

Описание инструмента — та же JSON Schema из [шага 10](#step-10), только поле зовётся `input_schema` и лежит прямо в объекте инструмента, без обёртки.

А результат? Он возвращается не отдельной ролью, а обычным сообщением с ролью `user`, внутри которого блок `type: "tool_result"` с полем `tool_use_id`. Туда кладёшь тот самый `toolu_01A`, что пришёл от модели. Идея сцепки та же, что в [шаге 56](#step-56): без совпадения идентификаторов модель не поймёт, к какому из двух городов относится «плюс 18».

Так что пустой список — не сбой модели. Ты искал вызов в поле, которого в этом API нет.

> 🎒 **На пальцах.** Сдаёшь чемодан в аэропорту: одна бирка на ручке, вторая — тебе на посадочный. Номера одинаковые. У ленты никто не спорит, чей чемодан: сверили номер — забрал. `tool_use_id` в `tool_result` — тот же корешок. Пришёл `toolu_01A`, вернуть результат надо с `toolu_01A`, иначе твоя погода уедет на другой круг.

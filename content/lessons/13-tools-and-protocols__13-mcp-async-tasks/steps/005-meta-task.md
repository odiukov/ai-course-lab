Ты уже выбрал номерок вместо ожидания ([шаг 4](#step-4)). Остался неудобный вопрос: а как вообще сказать серверу «не держи меня на линии»? Придумать для каждого долгого инструмента второй, «асинхронный» близнец? Тогда их станет вдвое больше, и каждый придётся описывать заново.

Протокол пошёл другим путём. Инструмент остаётся один и тот же, вызов — тот же самый. Меняется одна пометка в запросе: `params._meta.task.required: true`. `_meta` — это служебное поле рядом с обычными аргументами: там лежат не данные для инструмента, а указания, как обработать сам вызов.

Что приходит в ответ? Не результат — его ещё нет. Приходит вот это, сразу:

```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "_meta": {
      "task": {
        "id": "tsk_9f7b...",
        "state": "working",
        "ttl": 900000
      }
    }
  }
}
```

Посмотри на `state`. Сервер говорит буквально: «принял, работаю». А `id` — это и есть твой номерок, `tsk_9f7b...`; по нему ты потом придёшь за результатом. Про `ttl` — на следующем экране, там своя история.

И есть второй вариант пометки: `optional: true`. Это значит «мне подойдёт и так, и так — решай сам». Быстрый инструмент ответит обычным результатом, долгий вернёт задачу. Одно поле, а не два разных инструмента, — вот почему задачей может стать любой вызов.

> 🎒 **На пальцах.** Ты подходишь к стойке и заказываешь тот же капучино, что и всегда. Добавляешь два слова: «с собой». Напиток не изменился, бариста тот же, меню то же — изменилась только форма выдачи: стакан с крышкой, а не чашка на блюдце. `required: true` — это те самые два слова. А `optional: true` — «как вам удобнее»: решает тот, кто за стойкой.

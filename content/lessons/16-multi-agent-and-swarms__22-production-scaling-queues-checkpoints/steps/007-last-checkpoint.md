В таблице уже лежат чекпоинты двух прогонов: для `thread_id="alpha"` записаны super-step 1, 2 и 3, а для `"beta"` — 1 и 4. Воркер восстанавливает `alpha`. Какую строку должна вернуть `last_checkpoint`? Не строку с самым большим номером во всей таблице — иначе он подхватит состояние чужого прогона.

Сначала функция должна отфильтровать записи по переданному `thread_id`. Затем среди оставшихся строк найти чекпоинт с наибольшим номером super-step — именно этот порядок выбора мы разобрали в [шаге 6](#step-6). В SQL это выражается сортировкой номера шага по убыванию и чтением только первой строки. Подумай, почему одного `LIMIT 1` недостаточно: без явной сортировки SQLite не обещает вернуть последнюю добавленную запись.

После чтения `last_checkpoint` должна превратить сохранённое представление состояния обратно в объект, с которым сможет работать агент, и вернуть вместе с ним номер найденного super-step. Так вызывающий код понимает и **что** восстанавливать, и **после какого шага** продолжать.

Проверь также пустой случай. Для нового `thread_id` строк ещё нет, и это не ошибка базы: функция должна вернуть отсутствие чекпоинта, чтобы прогон начался с первого шага. Посмотри на три сценария: пустой лог, несколько записей одного прогона и перемешанные записи разных прогонов. Если ответы различаются только по нужному `thread_id`, граница восстановления выбрана правильно.

> 🎒 **На пальцах.** Представь шкаф с папками пациентов. На каждой странице стоят номер карты и дата визита. Тебе нужна последняя запись Иры: недостаточно взять самый свежий лист во всём шкафу — он может принадлежать Олегу. Ты сначала находишь только папку Иры, затем открываешь её последнюю датированную страницу. Если папки ещё нет, врач начинает новую, а не объявляет шкаф сломанным.

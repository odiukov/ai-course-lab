check:
  - question: >-
      Какое условие делает разбиение набора данных между рангами корректным,
      даже если локальные части различаются по размеру?
    options:
      - Каждый ранг получает полный набор данных
      - 'Каждый пример попадает ровно на один ранг, без пропусков и повторов'
      - Все локальные части дополняются копиями до одинакового размера
      - Размер process group меняется под число примеров
    correct: 1
    explanation: >-
      Размеры локальных частей могут различаться. Важно, чтобы вместе они
      образовывали исходный набор данных и каждый пример был назначен ровно
      одному рангу.
  - question: >-
      Ручную схему SUM с последующим делением на world_size заменили на
      dist.all_reduce с ReduceOp.AVG. Какое свойство должно сохраниться при
      сравнении времени?
    options:
      - На каждом ранге получается тот же усреднённый градиент
      - Каждый ранг продолжает использовать только локальный градиент
      - Обновление параметров выполняет только нулевой ранг
      - Локальные батчи автоматически становятся одинаковыми
    correct: 0
    explanation: >-
      ReduceOp.AVG объединяет суммирование и усреднение в одной коллективной
      операции. Математический результат должен сохраниться, чтобы замер отражал
      разницу в производительности, а не изменение алгоритма.
  - question: >-
      Один ранг пропустил коллективную операцию, которую остальные вызвали. Что
      вероятнее всего произойдёт?
    options:
      - Остальные ранги автоматически продолжат работу
      - Процессы зависнут или завершатся с ошибкой
      - Операция выполнится только на нулевом ранге
      - Недостающий ранг будет исключён из world size
    correct: 1
    explanation: >-
      Коллективная операция требует участия всех рангов в согласованном порядке.
      Если контракт нарушен, ожидающие друг друга процессы не смогут корректно
      продолжить выполнение.
  - question: >-
      Зачем запускать all-reduce из хука сразу после вычисления градиента
      параметра, не дожидаясь окончания всего backward?
    options:
      - Чтобы заменить обратный проход коллективной операцией
      - Чтобы передавать параметры только нулевому рангу
      - Чтобы совместить обмен готовых градиентов с вычислением оставшихся
      - Чтобы отказаться от синхронизации последних слоёв
    correct: 2
    explanation: >-
      Когда градиент параметра уже готов, его обмен можно начать параллельно с
      вычислением градиентов других параметров. Такое перекрытие не уменьшает
      объём обмена, но может сократить общее настенное время.
---

Дальше тебе пригодится не набор отдельных вызовов, а привычка защищать распределённый контракт: делить данные без потерь, одинаково упорядочивать коллективные операции, усреднять градиенты DDP и вовремя убирать полный параметр FSDP. Чаще всего спотыкаются на том, что корректные локальные числа ещё не гарантируют корректный общий результат. Проверки из [шага 3](#step-3) и круговой рейс из [шага 10](#step-10) помогают поймать это раньше зависания или переполнения памяти.

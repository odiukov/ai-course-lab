Ты сравниваешь два решения задачи на переворот строки. Первое пытается открыть сетевое соединение через `requests`, второе — запустить команду через `subprocess`. Ошибки у них могли бы быть разными, но для метрики разница несущественна: оба кандидата вышли за разрешённую границу и не должны продолжать работу.

После извлечения кода из генерации на [шаге 3](#step-3) раннер проверяет не намерения модели, а реальные действия программы. Перед запуском он подменяет импорты опасных модулей заглушками. Попытка импортировать такой модуль заканчивается `ImportError("denied")`. Отдельная защита подменяет `os.system`, чтобы вызов команды тоже немедленно оборвался.

Список запретов намеренно широкий. Для простой обработки строки не нужны ни сеть, ни управление файлами, ни запуск других процессов. Поэтому безопаснее запретить `socket`, `requests`, `shutil`, `subprocess` и похожие возможности целиком, чем пытаться угадать, какой конкретно вызов окажется вредным.

Но чёрный список — только подстраховка. Python-код может обратиться к модулю обходным способом, поэтому настоящую границу держат снаружи: родительский процесс ограничивает время работы и объём вывода. Сам кандидат не может отменить решение родителя остановить его. В итоге разные опасные попытки сходятся в одном наблюдаемом исходе: допустимый результат не получен.

> 🎒 **На пальцах.** Представь кулинарный конкурс, где нужно только нарезать яблоко. Один участник тянется к газовой горелке, другой — к промышленной пиле. Судье не требуется разбирать, чей инструмент опаснее: оба выключаются из общего щитка. Запрет на инструменты помогает сразу, но решающая защита — питание и таймер находятся у судьи, а не у участников.

title: Как sacrebleu группирует эталоны по потокам
source_anchor: '### Step 2: BLEU and chrF'
---

Ты переводишь два предложения и для каждого получаешь по два допустимых эталона. Возникает естественное желание записать их попарно: сначала два варианта для первого предложения, затем два — для второго. Но `sacrebleu` ожидает другую раскладку.

```python
hypotheses = [
    "Кошки бегут.",
    "Птицы летят.",
]

reference_a = [
    "Кошки бегают.",
    "Птицы летают.",
]

reference_b = [
    "Бегут кошки.",
    "Летят птицы.",
]

score = sacrebleu.corpus_bleu(
    hypotheses,
    [reference_a, reference_b],
)
```

Каждый внутренний список — отдельный **поток эталонов**, словно стопка листов от одного переводчика. На первом листе лежит перевод первого исходного предложения, на втором — второго и так далее. Поэтому `reference_a[1]` сравнивается с `hypotheses[1]`, а не с соседним элементом `reference_b`.

Внешний список собирает такие потоки вместе. Здесь у корпуса два эталонных перевода, значит внутри него находятся две одинаково длинные коллекции. Если эталон только один, дополнительная оболочка всё равно нужна:

```python
sacrebleu.corpus_bleu(hypotheses, [reference_a])
```

Длины потоков должны совпадать с числом гипотез: позиция задаёт, к какому исходному предложению относится текст. Так `sacrebleu` может использовать любой допустимый вариант при подсчёте совпадений, описанных в [шаге 15](#step-15).

> 🎒 **На пальцах.** Представь две проверенные тетради одного класса: синюю заполнила Анна, зелёную — Борис. В каждой первая страница относится к заданию №1, вторая — к заданию №2. Ты передаёшь проверяющему две целые тетради, а не пакет из пар страниц. Цвет разделяет авторов, номер страницы связывает ответы с заданиями.

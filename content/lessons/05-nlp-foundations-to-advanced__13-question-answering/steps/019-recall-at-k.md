У тебя есть результаты поиска для трёх вопросов:

- `["p7", "p2", "p9"]`, правильный пассаж — `"p2"`;
- `["p4", "p8", "p1"]`, правильный — `"p6"`;
- `["p5", "p3", "p7"]`, правильный — `"p5"`.

Функция `recall_at_k` должна проверить идею из [шага 18](#step-18) сразу на наборе вопросов. Для каждого вопроса возьми только первые `k` идентификаторов и выясни, встречается ли среди них правильный. Попадание даёт `1`, промах — `0`; результат функции — среднее этих значений.

При `k = 1` попадание есть только в третьем вопросе, поэтому получится `1 / 3`. При `k = 2` добавится первый вопрос: `"p2"` стоит на второй позиции, и результат станет `2 / 3`. Второй вопрос останется промахом, потому что `"p6"` вообще не найден.

Следи за двумя деталями. Во-первых, `k` означает количество первых результатов, а не индекс: при `k = 2` нужны позиции 0 и 1. Во-вторых, один вопрос учитывается не больше одного раза. Даже если правильный идентификатор случайно повторился в выдаче, это всё ещё одно попадание.

Для пустого набора вопросов верни `0.0`, чтобы не делить на ноль. А если `k` больше длины выдачи, просто проверяй все доступные результаты. Так функция измеряет долю вопросов с успешным поиском, а не число найденных строк.

> 🎒 **На пальцах.** Представь три посылки и отдельную полку находок для каждой. Ты разрешаешь сотруднику осмотреть первые `k` коробок на полке. Если нужная посылка там есть, ставишь одну галочку — неважно, первой она лежит или второй. Затем делишь число галочек на число посылок. `recall_at_k` делает ровно такой журнал проверок.

Ты настраиваешь модель и хочешь проверить три ручки: learning rate от `0.0001` до `0.1`, число деревьев от `50` до `500` и способ расчёта ошибки — `"squared_error"` или `"huber"`. Записать их одним универсальным диапазоном не получится: между `50` и `51` не должно появиться `50.4`, а между двумя названиями вообще нет промежуточного значения.

В Optuna пространство поиска описывается прямо внутри пробной попытки — `trial`:

```python
lr = trial.suggest_float(
    "learning_rate", 1e-4, 1e-1, log=True
)
n_est = trial.suggest_int("n_estimators", 50, 500)
loss = trial.suggest_categorical(
    "loss", ["squared_error", "huber"]
)
```

`suggest_float` разрешает вещественные значения: Optuna может предложить, например, `0.0037`. Здесь `log=True`, потому что learning rate сравнивают по порядкам величины, как в [шаге 11](#step-11), а не по равным числовым промежуткам.

`suggest_int` оставляет только целые числа: `127` допустимо, `127.6` — нет. `suggest_categorical` выбирает один готовый вариант из списка; категории не обязаны быть числами и не имеют естественного порядка.

Строка вроде `"learning_rate"` — имя гиперпараметра. По нему Optuna связывает предложения разных проб и сохраняет результаты. А границы — это не перечень значений для полного перебора: они лишь говорят, откуда можно выбирать. Так идея подходящего типа распределения из [шага 13](#step-13) превращается в точное описание пространства поиска.

> 🎒 **На пальцах.** Представь пульт отопления в теплице. Температуру можно выставить дробно — `21.5 °C`, число включённых ламп бывает только целым, а режим вентиляции выбирается из подписанных кнопок: «тихо», «обычно», «сильно». Optuna нужны такие же разные органы управления: ползунок для `float`, счётчик для `int` и набор кнопок для `categorical`.

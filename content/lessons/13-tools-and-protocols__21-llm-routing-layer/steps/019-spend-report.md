К концу дня у тебя накопился список записей от `charge` из [шага 17](#step-17): по одной строке на каждый успешный ответ — кому приписали трату, какой провайдер ответил, какая модель, сколько входных и выходных токенов, сколько это стоило. За сутки таких строк четыреста. Приходит человек из финансов и спрашивает: сколько за вчера съела команда data-платформы?

Глазами по четырёмстам строкам ты это не сложишь.

Здесь и нужен `spend_report`: он берёт список записей и группирующий ключ — `"user"`, `"team"` или `"project"` из [шага 16](#step-16) — и возвращает по одной сводке на каждое значение этого ключа. Внутри всё просто: идёшь по записям, для каждой достаёшь значение ключа и добавляешь её числа в накопитель этой группы. Первый раз группа встречается — создай пустую запись, дальше только прибавляй.

Складывать надо не одну стоимость. В сводке нужны минимум четыре вещи: сумма цены, число запросов, входные и выходные токены. Иначе на вопрос «почему у них так дорого» ответить нечем — то ли запросов много, то ли каждый жирный.

На что смотреть. Провайдер и модель в записи — те, кто **фактически ответил**, включая замену по fallback ([шаг 18](#step-18)); не подставляй сюда первый элемент цепочки. Округляй только при выводе, а не на каждом шаге сложения — иначе центы разъедутся. И отсортируй результат по убыванию траты: первым должен стоять тот, из-за кого счёт вырос.

Проверка одна: сумма всех групп обязана совпасть с суммой `cost` по всем записям. Не совпала — значит, часть строк потерялась по пути.

> 🎒 **На пальцах.** Представь карман куртки, набитый чеками из магазинов за месяц. Пока они лежат комком, ответа на «сколько ушло на еду» нет — есть только ворох бумажек. Ты раскладываешь их кучками по категориям и складываешь суммы в каждой. `spend_report` делает ровно это, а финальная проверка — пересчитать все кучки вместе и сверить с общей суммой по чекам.

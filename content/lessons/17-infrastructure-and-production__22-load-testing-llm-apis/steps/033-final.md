  - question: >-
      Тест k6 использует фиксированное число виртуальных пользователей. После
      замедления API фактический RPS снизился. Почему такой профиль не
      гарантирует постоянную интенсивность запросов?
    options:
      - >-
        В закрытой модели виртуальный пользователь ждёт завершения итерации,
        поэтому более долгие ответы уменьшают частоту новых запросов
      - k6 всегда случайно меняет целевой RPS после первой ошибки
      - Число виртуальных пользователей определяет только размер ответа
      - RPS снижается исключительно из-за кеширования префиксов
    correct: 0
    explanation: >-
      Фиксированная конкурентность создаёт закрытый контур: скорость подачи
      зависит от длительности итерации. Для заданного RPS применяют arrival-rate
      executor и отдельно контролируют пропущенные итерации.
  - question: >-
      Как реализовать в k6 проверку TTFT для потокового LLM API, если
      стандартная HTTP-метрика фиксирует завершение всего ответа?
    options:
      - >-
        Записать пользовательскую метрику от отправки запроса до получения
        первого токена или первого содержательного события потока
      - Использовать полную длительность HTTP-запроса как TTFT без изменений
      - Измерить только время DNS-запроса
      - Разделить размер ответа на число виртуальных пользователей
    correct: 0
    explanation: >-
      TTFT заканчивается при появлении первого токена, а не при закрытии потока.
      Поэтому клиент должен разобрать поток, поставить временную отметку на
      первом содержательном событии и передать значение в отдельную метрику k6.
  - question: >-
      В soak-тесте RSS растёт. Профиль heap одновременно показывает накопление
      экземпляров одного класса, тогда как использование KV-кеша и число
      открытых соединений стабильны. Какая гипотеза лучше всего подтверждается?
    options:
      - >-
        Приложение удерживает объекты этого класса и не освобождает связанные с
        ними ссылки
      - Рост вызван исключительно переполнением KV-кеша
      - Причина обязательно находится в пуле сетевых соединений
      - Рост RSS доказывает увеличение входного RPS
    correct: 0
    explanation: >-
      Совпадающий рост heap и числа объектов при стабильных GPU- и сетевых
      метриках указывает на удержание объектов приложением. Следующий шаг —
      сравнить снимки heap и найти цепочки ссылок, не позволяющие освободить
      память.
  - question: >-
      В кластере уже установлены Karpenter и vLLM production-stack. Как
      обоснованно задать допустимое время восстановления после spike?
    options:
      - >-
        Измерить критический путь: выделение узла, запуск контейнера, загрузку
        модели, readiness и возврат метрик SLA к норме
      - 'Считать восстановление мгновенным, поскольку автоскейлер уже установлен'
      - Использовать только среднее время ответа до начала всплеска
      - Выбрать произвольный срок и не измерять отдельные стадии масштабирования
    correct: 0
    explanation: >-
      Наличие автоскейлера не задаёт время восстановления само по себе. Бюджет
      получают из измеренных стадий холодного масштабирования и подтверждают
      моментом, когда задержки и ошибки снова устойчиво укладываются в SLA.

Ты запускаешь десять запросов с интервалом 100 мс, но каждый ответ занимает секунду. Если ждать завершения ответа перед следующей отправкой, прогон внезапно растянется на десять секунд. Получился не нагрузочный тест, а спокойная очередь из одиночных запросов.

В `run_load` тебе нужно сохранить моменты прихода, даже когда предыдущие генерации ещё продолжаются. Возьми запросы из `make_workload`, написанной на [шаге 8](#step-8), и сопоставь их с временными отметками из `arrival_schedule` с [шага 15](#step-15). Каждый запрос должен стартовать относительно общего начала прогона, а не относительно завершения соседа. Так одновременно активными окажутся именно те запросы, которые пересекаются во времени.

Для каждой генерации сохрани ключевые события из [шага 20](#step-20): приход запроса, появление первого токена и завершение ответа. Также понадобятся число входных и выходных токенов и признак успешного выполнения. Ошибка одного запроса не должна останавливать весь прогон: запиши её как отдельный результат и дождись остальных задач.

После завершения верни результаты, по которым можно сравнить эффективный TPOT у однообразной и разнообразной нагрузки. Пока не своди измерения к перцентилям — это будет следующим шагом. Здесь важнее проверить сам «хронометраж»: запланированные старты не сдвигаются, параллельные запросы действительно перекрываются, а длительность одного ответа не диктует ритм всей очереди.

> 🎒 **На пальцах.** Представь старт забега с отдельным будильником для каждого участника. Первый бегун ещё на трассе, когда будильник выпускает второго. Если судья станет ждать каждого на финише перед новым стартом, он проверит бегунов по одному. `run_load` должен слушать будильники, а результаты собирать уже после общего забега.

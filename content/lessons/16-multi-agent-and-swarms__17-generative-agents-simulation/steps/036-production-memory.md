Ты перезапускаешь симуляцию после пятидесятого тика — и все агенты внезапно «забывают» прожитый день. Причина проста: список Python жил только внутри запущенной программы. А если агентов станет двадцать пять, перебор каждой записи при каждом поиске начнёт ещё и тормозить.

Значит, пора отделить память агента от самого агента. Неизменяемая запись из [шага 6](#step-6) сохраняется в постоянном хранилище: вместе с текстом туда уходят время, тип, важность и стабильный `id`. Дополнительно можно хранить вектор — числовое представление смысла текста. По нему векторная база быстро находит воспоминания, похожие на текущий запрос, не просматривая весь поток вручную.

Что выбрать? Отдельная векторная БД удобна, когда смысловой поиск — главная и очень частая операция. Postgres подходит, если тебе одновременно нужны привычные таблицы, надёжное сохранение, выборки по агенту и времени, связи рефлексии с исходными воспоминаниями из [шага 34](#step-34). С расширением для векторов он способен выполнять и смысловой поиск, поэтому для первого продакшен-варианта часто достаточно одной системы.

При этом правила выбора памяти не меняются: свежесть, важность и смысловая уместность из [шага 8](#step-8) по-прежнему складываются в итоговое ранжирование. База лишь быстро находит кандидатов и переживает перезапуск. Логика агента остаётся логикой агента, а память наконец перестаёт зависеть от жизни одного процесса.

> 🎒 **На пальцах.** Представь гардероб театра. Список Python — это билеты, разложенные на столе: пока дежурный на месте, всё работает, но после уборки порядок исчезнет. База данных — гардероб с постоянными номерами. Postgres помогает найти вещь по владельцу, времени и номеру, а векторный поиск — подобрать «то длинное тёплое пальто», даже если точная формулировка потерялась.

Ты выполняешь знакомый прямой проход: возводишь значения в квадрат, умножаешь их на 3, складываешь и получаешь одно число. Благодаря eager execution из [шага 5](#step-5) каждый результат появляется сразу. Но затем возникает вопрос: как PyTorch восстановит весь путь к исходным значениям, когда понадобится посчитать градиенты?

Во время прямого прохода PyTorch не только выполняет операции, но и оставляет о них записи на вычислительной ленте. В такой записи хранится, какая операция создала результат, от каких тензоров она зависела и какие промежуточные данные понадобятся для вычисления производной. Новая операция дописывает к ленте ещё один фрагмент, поэтому цепочка строится прямо по ходу обычного Python-кода.

Например:

```python
x = torch.tensor([2.0], requires_grad=True)
y = x ** 2
z = y + 3 * x
```

Сначала лента связывает `y` с возведением `x` в квадрат, затем `z` — со сложением `y` и результата умножения `x` на 3. Тебе не приходится заранее описывать отдельный обратный проход для каждой операции, как в самодельном фреймворке из [шага 2](#step-2).

Когда позже вызывается `z.backward()`, PyTorch читает сохранённую цепочку в обратном порядке и применяет локальное правило производной на каждом участке. Значит, автоматическим здесь становится не прямой расчёт, а восстановление пути назад: PyTorch может пройти его, потому что записал каждый поворот по дороге вперёд.

> 🎒 **На пальцах.** Представь спелеолога, который идёт в пещеру и на каждом повороте оставляет метку: «пришёл из левого тоннеля», «спустился по лестнице», «перешёл мост». У цели ему не нужно угадывать обратный маршрут — он читает метки с последней к первой. Вычислительная лента играет ту же роль: прямой проход оставляет след, а `backward()` идёт по нему назад.

title: state_dict сохраняет переносимые веса отдельно от Python-класса модели

---

Ты обучил `MNISTModel`, закрыл программу, а завтра переименовал файл или перенёс класс в другой модуль. Если сохранить модель целиком, загрузка может сломаться: такой файл помнит не только числа, но и то, где Python должен искать прежний класс. Этот механизм основан на `pickle` и слишком тесно связывает результат обучения со старой организацией кода.

Удобнее сохранить только состояние модели:

```python
torch.save(model.state_dict(), "model.pt")
```

`state_dict()` возвращает словарь: ключи вроде `layers.0.weight` обозначают зарегистрированные параметры, а значения — тензоры с обученными числами. В нём нет описания `forward` и нет самого Python-класса. Архитектуру ты создаёшь кодом отдельно, а затем переносишь в неё веса:

```python
model = MNISTModel()
state = torch.load("model.pt", weights_only=True)
model.load_state_dict(state)
model.eval()
```

Сначала появляется новый экземпляр `MNISTModel` со свежими начальными значениями. Затем `load_state_dict` сопоставляет имена из словаря с параметрами модели и заменяет их сохранёнными тензорами. Поэтому архитектура должна быть совместимой: если ты удалил слой, переименовал его или изменил форму весов, PyTorch сообщит о несовпадении.

`weights_only=True` подчёркивает, что из файла ожидаются веса, а не произвольный сохранённый Python-объект. Наконец, `eval()` включает режим оценки, разобранный в [шаге 48](#step-48); сам по себе он ничего не загружает.

Код модели можно развивать, пока сохранённые имена и формы параметров остаются совместимыми.

> 🎒 **На пальцах.** Представь театральную постановку. Python-класс — сценарий с описанием ролей и сцен, а `state_dict` — чемодан с костюмами, на каждом из которых подписано имя персонажа. Ты не перевозишь весь старый театр: строишь новую сцену по сценарию и раздаёшь костюмы по подписям. Если роль переименована или исчезла, чемодан сразу выдаст несоответствие.

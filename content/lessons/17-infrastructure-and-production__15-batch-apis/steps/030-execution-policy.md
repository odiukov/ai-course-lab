Ты отнёс отчёт к semi-interactive: он обновляется раз в десять минут, а человек получает уведомление. Кажется, решение уже принято. Но инженер спрашивает: «Каким API запускать запросы? Что кэшировать? Что делать при задержке?» Название полосы само на это не отвечает.

Полоса из [шага 25](#step-25) задаёт допустимое ожидание, а из него собирается политика запуска. Для interactive нужен синхронный вызов: пользователь остаётся у экрана. Запасной путь тоже должен быть быстрым — например, повторный вызов или другой синхронный провайдер.

Для semi-interactive запрос можно поставить во внутреннюю очередь и выполнить без открытого экрана. Однако Batch API с окном до 24 часов сюда автоматически не подходит: десятиминутный SLA важнее скидки. При задержке система успевает повторить запрос, а перед дедлайном — переключиться на более дорогой синхронный запуск.

Для batch естественен пакетный endpoint, описанный в [шагах 13](#step-13)–[15](#step-15). Повторяющийся префикс стоит кэшировать, как в [шаге 6](#step-6). Если пакет не готов к сроку, запасным путём может стать синхронная обработка только оставшихся заданий, а не повтор всей ночной партии.

Кэширование при этом не определяется полосой: оно зависит от повторяемости входа. Полоса выбирает время и способ запуска; структура данных — возможность сэкономить; запасной путь — способ всё-таки выдержать обещанный срок.

> 🎒 **На пальцах.** Представь вход на фестиваль. Гость у турникета проходит сразу, обладатель брони может забрать браслет позже, а список большой группы печатают ночью одной пачкой. Одинаковый макет браслета используют повторно — это кэш. Если ночной принтер застрял, сотрудник вручную печатает только недостающие браслеты. Способ работы выбирает срок, а не важность гостей.

Перед тобой доска из четырёх задач: первая уже выполнена, вторая заблокирована, третья ждёт человека, а четвёртая свободна для `builder`. Функция `next_task` должна вернуть именно четвёртую — даже если остальные стоят выше.

Возьми правило выбора из [шага 13](#step-13) и перенеси его в код. Функция получает список задач и роль текущего исполнителя. Она просматривает доску в исходном порядке и возвращает первую задачу, которая одновременно:

- имеет статус `todo`;
- назначена переданной роли.

Если подходящей задачи нет, верни пустой результат, предусмотренный заготовкой, например `null` или `None`. Не выбирай задачу со статусом `blocked`, не передавай агенту работу владельца `human` и не меняй порядок элементов.

Особенно важно не обновлять найденную задачу до `in_progress`. Сейчас `next_task` только отвечает на вопрос «что можно взять следующим?». Согласованное изменение доски и состояния появится позже; если сделать его здесь, функция выбора получит скрытый побочный эффект.

Проверь решение хотя бы на трёх случаях: подходящая задача стоит не первой, подходящих задач несколько, подходящих задач нет. Во втором случае должна победить та, что раньше записана на доске. Так очередь остаётся предсказуемой: одинаковые входные данные всегда дают один и тот же выбор.

> 🎒 **На пальцах.** Представь ленту выдачи заказов в пекарне. Ты ищешь первый пакет с наклейкой «готов» и своим именем. Пакет «печётся» брать рано, а пакет для другого покупателя — нельзя. Найдя свой, ты лишь показываешь на него сотруднику: снимать пакет с ленты и отмечать выдачу будет отдельное действие.

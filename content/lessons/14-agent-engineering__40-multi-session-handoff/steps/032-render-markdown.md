В JSON поле `next_action` уже содержит точное действие, а `open_risks` — готовый список рисков. Но при подготовке Markdown легко незаметно изменить смысл: переименовать действие, переставить риски или вовсе скрыть пустой раздел. Тогда человек и агент получат разные пакеты.

Твоя функция `render_markdown` принимает готовый payload из [шага 29](#step-29) и возвращает строку Markdown. Она ничего не вычисляет заново: не выбирает следующее действие, не выводит риски и не сокращает обратную связь. JSON остаётся источником фактов, а функция только раскладывает эти факты в читаемом виде.

Задай фиксированный порядок разделов, соответствующий обязательным полям из [шага 5](#step-5). Одиночные значения выводи под заголовками как текст, коллекции — списками, сохраняя порядок элементов из payload. Если список пуст, покажи это явно, например нейтральной строкой «Нет», а не удаляй весь раздел: отсутствие раздела можно ошибочно принять за потерянные данные.

Особенно следи за тем, чтобы функция не «улучшала» формулировки. Значение `next_action` должно попасть в Markdown без пересказа, а риск — без смягчения или дополнения догадками. Проверь результат по принципу из [шага 31](#step-31): каждый факт в человеческом представлении можно найти в основном JSON, а сама функция не меняет полученный payload.

Здесь рендерер работает как аккуратный наборщик, а не как второй автор пакета.

> 🎒 **На пальцах.** Судья турнира хранит результаты в электронной таблице, а для зрителей печатает бюллетень. Наборщик может добавить заголовки и списки, но не вправе округлить счёт или поменять участников местами. Если бюллетень вызывает спор, сверяются с таблицей. `render_markdown` готовит такой бюллетень из уже утверждённых данных.

Ты запускаешь сборку на снимке верстака, где тесты прошли, но ревью оставило замечание. Если `build_handoff` просто скопирует несколько полей, замечание потеряется; если начнёт дописывать объяснения от себя, пакет перестанет отражать исходные артефакты.

Дополни заготовку `build_handoff(snapshot)` так, чтобы она только координировала уже написанные функции. Ей нужно:

1. Передать обратную связь в `trim_feedback` из [шага 13](#step-13).
2. Получить открытые риски через `derive_open_risks` из [шага 7](#step-7).
3. Выбрать ровно одно действие с помощью `choose_next_action` из [шага 9](#step-9).
4. Собрать обязательные поля пакета, перечисленные в [шаге 5](#step-5), из данных `snapshot` и полученных результатов.
5. Добавить предусловия продолжения через `resume_blockers` из [шага 21](#step-21).

Следи прежде всего за происхождением каждого значения. Текущая цель, ветка, изменённые файлы и результаты проверок берутся из снимка. Риски, сокращённая обратная связь и следующее действие вычисляются специализированными функциями. `build_handoff` не должна повторять их правила внутри себя: иначе две реализации со временем начнут расходиться.

Проверь результат на снимке с пустыми списками и на снимке с падением проверки. В обоих случаях должны присутствовать все обязательные поля, даже если значение — пустой список. Падение не должно исчезнуть после сокращения обратной связи, а выбранное действие должно соответствовать открытым рискам.

Здесь функция работает как сборщик: она соединяет проверенные детали, но не изобретает недостающие.

> 🎒 **На пальцах.** Представь сотрудника железнодорожного депо, который формирует папку для машиниста. Он берёт маршрут из расписания, неисправности из журнала осмотра и первое действие из распоряжения диспетчера. Если он начнёт сам пересчитывать маршрут или смягчать запись о неисправности, папка станет опасной. Его задача — правильно собрать документы в один комплект.

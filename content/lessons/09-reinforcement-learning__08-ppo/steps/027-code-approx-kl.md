После очередной эпохи ты видишь два набора чисел: сохранённые `old_log_probs` и заново вычисленные `new_log_probs`. По отдельности они почти ничего не говорят. Тебе нужно получить одно число, показывающее, насколько новая политика успела отойти от той, которая собрала ролаут.

Напиши `approx_kl(old_log_probs, new_log_probs)`. Для каждого перехода функция должна вычислить разность «старый логарифм минус новый», как в формуле из [шага 26](#step-26), а затем усреднить разности по всему батчу. Результат — один скаляр, а не массив значений для отдельных переходов.

Здесь легко сделать лишнее. Не применяй `exp`: он превратит разность логарифмов в уже знакомый `ratio`, а функция измеряет не его. Не бери модуль и не возводи разность в квадрат — знак является частью выбранного приближения. И не суммируй значения без усреднения: тогда результат начнёт зависеть от размера минибатча, и сравнивать обновления станет неудобно.

Проверь себя на простых случаях. Если оба набора совпадают, функция должна вернуть ноль. Если для каждого выбранного действия `new_log_probs` меньше `old_log_probs` на `0.01`, результат должен быть близок к `0.01`. Убедись также, что сохранённые старые значения остаются неподвижной точкой сравнения, как обсуждалось в [шаге 20](#step-20).

Так весь батч превращается в один понятный датчик сдвига политики.

> 🎒 **На пальцах.** Представь стопку квитанций с прежними и нынешними показаниями счётчика воды. Для каждой квартиры ты вычитаешь новое показание нужного столбца из старого, а затем находишь среднее по дому. Тебе нужен именно средний сдвиг: сумма зависела бы от числа квартир, модуль спрятал бы направление, а отдельные строки не дали бы одного показания для панели.

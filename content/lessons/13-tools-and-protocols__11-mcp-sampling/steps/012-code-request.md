У тебя уже есть `model_preferences` из [шага 9](#step-9) — словарь с тремя весами и `hints`. Отдай его клиенту как есть — и ничего не произойдёт. Клиент такой посылки не понимает: он ждёт JSON-RPC-конверт, тот самый, с которым ты познакомился в [шаге 7](#step-7), только теперь адресованный в обратную сторону.

Значит, нужна функция, которая складывает конверт целиком. Пусть она принимает то, что сервер знает сам: список сообщений, системную инструкцию, лимит токенов, готовые предпочтения по модели — и возвращает один словарь, который остаётся только отправить.

Внутри четыре поля верхнего уровня: `jsonrpc` со значением `"2.0"`, `method` — ровно `"sampling/createMessage"`, `id` и `params`. Всё содержательное — `messages`, `systemPrompt`, `modelPreferences`, `maxTokens` — живёт **внутри** `params`, а не рядом с `method`. Это первое место, где легко промахнуться: поля расползаются на верхний уровень, и запрос формально валиден, но клиент не находит ни сообщений, ни лимита.

Второе — `id`. Его выдаёт сервер, из своего счётчика. Не подхватывай `id` того клиентского вызова, который тебя разбудил: у клиента своя нумерация, у тебя своя, и по своему номеру ты потом узнаешь ответ.

Третье — форма сообщения. `content` это объект `{"type": "text", "text": "..."}`, а не строка. Одна из самых частых ошибок: положить текст прямо в `content`.

Поле `includeContext` пока просто прими параметром и положи в `params` как дали — чем его заполняют, разберём на следующем экране.

Собрал конверт — и запрос сервера стало не отличить от клиентского: та же структура, только номер твой.

> 🎒 **На пальцах.** Как платёжное поручение в банке. Сумма и назначение платежа не пишутся поверх бланка размашисто — у каждого своя графа, иначе операционист вернёт бумагу. Номер поручения ставишь ты сам, из своей нумерации, и потом по нему ищешь ответ банка. Банк своими номерами нумерует свои документы — и путать их нельзя, даже если оба числа выглядят одинаково скромно.

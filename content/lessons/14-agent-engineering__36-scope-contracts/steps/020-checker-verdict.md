В diff четыре файла. Два лежат под разрешённым `src/auth/**`, один — `docs/login.md`, которого в контракте нет, а ещё один совпал с запрещённым `config/secrets.*`. Если проверщик вернёт только «проверка не пройдена», тебе придётся заново изучать контракт и угадывать причину отказа.

Поэтому он делает два связанных действия. Сначала раскладывает каждый изменённый путь: разрешённые попадают в `in_scope`, остальные — в `off_scope`. Здесь применяются правила из [шага 10](#step-10): запрет сильнее разрешения, а путь без подходящего разрешающего глоба не становится допустимым сам по себе.

Затем для каждого проблемного пути появляется отдельная помеченная находка — `violation`. Она не просто повторяет имя файла, а сохраняет объяснение: какой путь проверялся, какое правило сработало и почему результат считается нарушением. Для `config/secrets.dev` причиной будет совпадение с конкретным запрещающим глобом. Для `docs/login.md` — отсутствие совпадения среди `allowed_files`. Эти причины различаются: первый файл явно запрещён, второй, возможно, требует согласованного расширения контракта.

Список фактически запущенных проверок берётся из `RunSummary`, описанного в [шаге 18](#step-18). Поэтому вердикт можно связать не с намерениями агента, а с наблюдаемыми фактами: вот изменённые пути, вот правила, вот выполненные команды. Проверяющий человек сразу видит не только отказ, но и следующий разумный шаг.

> 🎒 **На пальцах.** Представь контролёра на закрытой репетиции: у него есть список приглашённых и отдельный список тех, кого нельзя пропускать. Он не пишет просто «двое не вошли». В отчёте указано: Анны нет в списке приглашённых, а Борис находится в списке запрета. Итог одинаковый — оба снаружи, но исправлять эти ситуации нужно по-разному.

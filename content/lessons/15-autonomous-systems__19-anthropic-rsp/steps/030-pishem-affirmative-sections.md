Ты вызываешь `affirmative_case_sections` дважды: сначала с оценкой eval-context gaming `0.2`, затем с `0.21`. Значения почти одинаковы, но результаты должны различаться. В первом случае функция возвращает только шесть базовых разделов из [шага 29](#step-29), во втором — добавляет седьмой раздел, посвящённый eval-context gaming.

Здесь легко ошибиться в одном символе: условие говорит «выше `0.2`», а не «не ниже `0.2`». Поэтому ровно `0.2` ещё не пересекает границу. Это полезный крайний случай для самопроверки.

Функция должна принять числовую оценку, собрать базовые названия разделов в заданном порядке и вернуть их списком. Если оценка превышает порог, в конец списка добавляется специальный раздел. Не заменяй им один из базовых: affirmative case расширяется с шести пунктов до семи.

Проследи и за повторными вызовами. Если ты изменяешь один общий список, седьмой раздел может случайно остаться там навсегда: после вызова с `0.21` следующий вызов с `0.1` тоже вернёт семь пунктов. Каждый запуск должен формировать независимый результат.

Проверь три значения: `0.19`, `0.2` и `0.21`. Ожидаемые длины списков — `6`, `6` и `7`. Так граница превращается из формулировки политики в однозначное поведение программы.

> 🎒 **На пальцах.** Представь анкету перед арендой дорогого оборудования. Обычно в ней шесть страниц. Если показатель риска строго выше `0.2`, сотрудник прикладывает ещё одну страницу проверки. При значении ровно `0.2` её не добавляют. И для каждого клиента печатают новый комплект: лишний лист из предыдущей анкеты не должен перекочевать в следующую.

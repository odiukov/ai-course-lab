Представь: ты открыл сессию, поздоровался через `initialize` из [шага 19](#step-19), и теперь хочешь узнать список инструментов и тут же вызвать два из них. Три сообщения — три отдельных похода туда и обратно. Если сервер живёт за медленным каналом, ты трижды платишь за дорогу.

А обязательно ли ходить по одному?

JSON-RPC разрешает положить в отправку не один конверт, а массив: `[{...id:1}, {...id:2}, {...id:3}]`. Сервер разбирает его поэлементно, обрабатывает каждый запрос и возвращает массив ответов. Порядок внутри ответного массива не гарантирован — второй может приехать первым. Именно поэтому у каждого запроса есть `id`, тот самый номерок из [шага 11](#step-11): ты сопоставляешь ответ с запросом по номеру, а не по позиции.

И тут вылезает вторая вещь. Есть сообщения, на которые отвечать не надо вообще. Сразу после рукопожатия клиент шлёт `notifications/initialized` — «принял, начинаем». Ответ на это бессмысленный. Такое сообщение отличается ровно одним признаком: в нём **нет поля `id`**. Нет `id` — это уведомление, и сервер обязан промолчать.

Отсюда неприятный, но логичный случай: если в массиве были только уведомления, отвечать нечем — сервер не возвращает пустой массив, он не возвращает ничего.

Значит, разбирая пачку, ты решаешь по каждому элементу отдельно: есть `id` — готовь ответ, нет `id` — выполни и молчи.

> 🎒 **На пальцах.** Как заказ в кафе. Ты не подзываешь официанта трижды — перечисляешь три блюда за один подход. Приносят вразнобой: сначала суп, потом салат, и ты узнаёшь своё по тому, что заказывал, а не по очерёдности. А фраза «уберите, пожалуйста, лишний стул» — не заказ: официант выполняет и ничего не приносит. Если весь твой «заказ» состоял из таких просьб, поднос к столу не поедет.

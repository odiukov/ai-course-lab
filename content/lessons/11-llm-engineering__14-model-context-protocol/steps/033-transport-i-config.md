Твой сервер работает: в [шаге 32](#step-32) ты подключился к нему через `stdio_client`, и `list_tools()` вернул список инструментов. Но stdio — это труба между двумя процессами на одной машине: хост сам запустил сервер подпроцессом и пишет ему в стандартный ввод. А теперь коллега просит тот же сервер со своего ноутбука.

Переписывать сервер?

Нет. Транспорт — это только способ доставки байтов. Конверт JSON-RPC из [шага 9](#step-9) и шесть методов из [шага 15](#step-15) не меняются ни на символ. Поэтому на сервере правится ровно одна строка запуска:

```python
mcp.run(transport="streamable-http")
```

Сервер поднимает HTTP-адрес. Каждый запрос — один POST. Если инструмент работает долго, ответ может приходить потоком Server-Sent Events — сервер отдаёт прогресс по частям, а не молчит минуту. Это и есть streamable HTTP, он в спецификации с ревизии 2025-06-18.

На стороне хоста меняется блок конфига. Вместо `command` и `args`, которыми хост запускал процесс, — адрес:

```json
{
  "mcpServers": {
    "notes": { "url": "https://tools.example.com/mcp" }
  }
}
```

Никакого подпроцесса: хост просто стучится по URL. Тот же `list_tools()`, тот же ответ.

stdio оставляй для локальной разработки — запустил, отладил, поправил. Как только сервер должен жить не на той машине, где хост, ты меняешь строку запуска и `url` в конфиге. Всё остальное — код инструментов, схемы, обработка ошибок — не узнаёт, что что-то произошло.

> 🎒 **На пальцах.** Ты объясняешь коллеге, где лежит папка. Он за соседним столом — просто говоришь вслух. Уехал в другой город — звонишь. Слова те же, порядок тот же, вопросы те же; сменился только канал. Никто не переучивается говорить из-за телефона. stdio и streamable HTTP — два канала для одного разговора: строка запуска другая, реплики прежние.

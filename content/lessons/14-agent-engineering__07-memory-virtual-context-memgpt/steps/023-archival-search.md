Архив из [шага 21](#step-21) растёт молча. Двадцать, сорок, двести записей — и вот модель спрашивает: «какой у клиента дедлайн?» Вклеить в промпт весь архив нельзя, ради этого его и заводили. Значит, нужна функция, которая из двухсот записей вернёт три.

Считать совпадения ты уже умеешь — оценка из [шага 22](#step-22) даёт по числу на каждую запись. Но что делать с двумястами чисел?

Отсортировать по убыванию и отрезать верхушку. Твоя `archival_search(query, top_k=3)` проходит архив, ставит каждой записи оценку, выстраивает их от большей к меньшей и отдаёт первые `top_k`. Возвращать надо не голый текст, а запись целиком — с `id`, `tags`, `session` и `turn` из [шага 20](#step-20): агенту потом пригодится сослаться, откуда факт.

Три места, где легко споткнуться. Первое: записи с нулевой оценкой в ответ попадать не должны — ни одного общего слова с запросом, а место в промпте занимают, и ты своими руками возвращаешь размывание из [шага 3](#step-3). Второе: при равных оценках порядок должен быть предсказуемым — добавь вторым ключом `id` или `turn`, иначе один и тот же запрос будет отдавать разное. Третье: пустой архив и пустой запрос — это пустой список, а не падение.

Прогони один запрос с `top_k=3`, потом с `top_k=20`. Второй ответ и есть та самая свалка, от которой ты убегал.

> 🎒 **На пальцах.** Как проверка лотерейных билетов после тиража. Ты не читаешь билеты целиком — берёшь каждый и считаешь, сколько чисел совпало с выпавшими. Билеты с нулём совпадений сразу в урну. Остальные раскладываешь по убыванию и оставляешь три верхних. Если два билета набрали по четыре числа, порядок между ними ты задаёшь сам — по номеру, чтобы дважды разложить одинаково.

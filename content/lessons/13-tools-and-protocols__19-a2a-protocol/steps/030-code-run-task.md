Семь функций лежат готовые: `build_agent_card`, `select_skill`, `canonical_json`, `sign_agent_card`, `verify_agent_card`, `next_task_state`, `make_artifact`. Каждая по отдельности работает. И ни одна из них не делает делегирование.

Потому что делегирование — это порядок. `run_task` — та самая функция, которая складывает порядок.

Что она принимает: карточку чужого агента (вместе с подписью), описание того, что тебе нужно, и входные части — текст, файл, данные. Что возвращает: финальное состояние, артефакт и историю переходов.

Внутри — цепочка, в которой каждое звено может её оборвать. Сначала проверка подписи функцией из [шага 17](#step-17): не сошлась — задача заканчивается в `rejected`, и ни одного запроса на чужой эндпоинт ты не отправил. Потом подбор скилла из [шага 9](#step-9) по нужным `inputModes` и `outputModes`: подходящего нет — снова `rejected`. Только после этого задача рождается в `submitted`.

И вот главное место, где обычно спотыкаются: не присваивай состояние напрямую. Каждый переход гони через `next_task_state` из [шага 22](#step-22) — включая `submitted → working`. Тогда запрещённый прыжок вроде `submitted → completed` упадёт сам, а не доедет до продакшена.

Не хватило данных — `input_required`, ждёшь ответное сообщение, возвращаешься в `working`: другого пути назад нет. Упало внутри — `failed`. Отменили снаружи — `canceled`. Готово — результат заворачивается в артефакт функцией из [шага 27](#step-27), и только тогда `completed`.

Проверяй себя по возвращённой истории переходов. Если она читается как разрешённый маршрут — `run_task` собран правильно.

> 🎒 **На пальцах.** Перед готовкой повар раскладывает всё по мискам: лук нарезан, соус разведён, мясо обсушено. Семь мисок — семь твоих функций. Но ужина ещё нет: миски не знают, что после чего. Рецепт и есть `run_task` — он не режет заново, он говорит «сначала это, потом то, а если рыба несвежая — стоп, не начинаем». Порядок и есть блюдо.

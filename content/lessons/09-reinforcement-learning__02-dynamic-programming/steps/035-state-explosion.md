title: Определяем границу применимости табличного DP

Возьми GridWorld из [шага 12](#step-12) и добавь подробности: 200 позиций, 50 уровней заряда, 20 вариантов груза и 10 значений времени. Вместо двухсот состояний получится уже два миллиона сочетаний. Добавь пять режимов погоды — и таблица вырастет до десяти миллионов строк.

Почему это проблема, если сходимость Беллмана гарантирована? Гарантия из [шага 9](#step-9) говорит, что последовательные обновления придут к нужной точке, но не обещает, что один проход будет дешёвым. Табличный DP хранит отдельное значение для каждого состояния, а при проходе из [шага 21](#step-21) перебирает в каждом из них все действия. Поэтому удвоение числа состояний примерно удваивает и память, и работу каждого прохода.

Ориентир в \(10^7\) состояний — не магическая граница. Реальный предел зависит от числа действий, количества возможных исходов, требуемых проходов и доступного компьютера. Но он помогает вовремя заметить главную ловушку: число состояний растёт не сложением признаков, а перемножением их возможных значений. Если один признак непрерывен, например точная температура, перечислить все состояния вообще нельзя; разбиение на интервалы лишь временно уменьшает проблему.

Значит, табличный DP подходит, пока полную модель и отдельную ячейку для каждого состояния действительно можно перебрать. После этого рубежа нужна аппроксимация функций: она хранит закономерность между состояниями, а не гигантский перечень.

> 🎒 **На пальцах.** Представь библиотеку, где для каждой возможной комбинации «жанр, автор, год, язык, состояние книги» заводят отдельную карточку. Пока карточек тысяча, каталог удобен. Когда их десять миллионов, даже простая переоценка каждого варианта превращается в долгий обход шкафов. Тогда нужен не ещё один шкаф, а правило, позволяющее судить о похожих книгах вместе.

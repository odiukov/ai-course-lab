Ты исправляешь в `agent-rules.md` срок действия правила и замечаешь рядом `agent-rules.lock.json` с теми же данными. Где править — в обоих файлах? Если изменить только JSON, проверяльщик увидит новую дату, а человек на ревью — старую. Если изменить только Markdown, кеш временно отстанет.

Выход — заранее назначить одному файлу главную роль. `agent-rules.md` становится источником истины: именно его редактируют люди и именно его дифф обсуждают на ревью. Знакомая по [шагу 8](#step-8) структура правил остаётся читаемой, а парсер из [шага 9](#step-9) может проверить её перед преобразованием.

`agent-rules.lock.json` получает другую роль: это машинный кеш, то есть автоматически полученная копия в форме, удобной проверяльщику. На горячем пути — при каждом запуске проверки — не нужно заново разбирать Markdown. Машина читает готовый JSON быстрее и одинаково в любом окружении.

Но два файла легко рассинхронизировать. Поэтому перед коммитом хук пересобирает lock-файл из Markdown. Изменился текст правила — меняется и JSON. Повреждена запись — сборка останавливается, а старый кеш не маскирует ошибку. Если файлы противоречат друг другу, спор не решают ручным редактированием JSON: его удаляют или заменяют результатом новой сборки из Markdown.

У этой пары нет двух равноправных версий контракта: есть рукопись и её машинный отпечаток.

> 🎒 **На пальцах.** Представь типографию. Редактор исправляет рукопись, а печатный станок работает с готовой формой. Никто не царапает буквы прямо на форме: после правки рукописи её изготавливают заново. Markdown — рукопись, которую удобно читать и обсуждать; JSON — печатная форма, с которой машина быстро делает тираж. Если они расходятся, верят рукописи и пересобирают форму.

Ты просишь агента открыть `config.json`, но вместо файла он пытается прочитать целую папку. В обычном диалоге такая ошибка обнаружилась бы только после выполнения. Здесь между решением модели и реальным действием стоит проверка.

Агент формирует не свободную команду, а структурированную заявку:

```json
{
  "tool": "read_file",
  "path": "config.json"
}
```

Хост — программа, управляющая агентом, — знает правила инструмента `read_file`: поле `path` обязательно и должно указывать на допустимый файл. Сначала хост проверяет заявку по этим правилам и только потом запускает инструмент. Неизвестное поле, неверный тип значения или запрещённый путь можно отклонить ещё до выполнения.

За один такой ход агент совершает одно явно названное действие: читает файл, ищет текст или запускает тест. Если затем нужно изменить файл, потребуется новая заявка и новый ход. Это добавляет переходы между моделью и хостом, зато каждый переход легко рассмотреть отдельно: что запросили, прошло ли это проверку и какой результат вернулся.

Такая проверяемость дополняет защиту траектории из [шага 21](#step-21): ошибка не получает сразу несколько возможностей распространиться. Валидатор ограничивает отдельное действие, а следующий ход начинается уже с его наблюдаемого результата. Получается короткая цепочка контролируемых решений, где у каждого звена есть точное имя и границы.

> 🎒 **На пальцах.** Представь окно выдачи ключей в гостинице. Ты подаёшь карточку: «открыть номер 214». Сотрудник проверяет номер, твои права и выдаёт один ключ. Карточка «открыть все номера и заодно отключить сигнализацию» не пройдёт проверку. Один запрос обслуживается медленнее, чем свободный доступ к связке ключей, зато его последствия заранее ограничены.

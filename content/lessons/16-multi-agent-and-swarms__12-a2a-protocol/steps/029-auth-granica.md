title: Читаем способ авторизации из Agent Card

Ты нашёл агента с нужным skill и уже готов отправить задачу. Но первый запрос возвращается без результата: сервер не понял, кто к нему обращается. Можно вручную спросить другую команду, какой токен или сертификат нужен, однако тогда проверяемый контракт из [шага 6](#step-6) снова превращается в переписку между людьми.

Нужная подсказка находится в самой Agent Card. До сборки запроса клиент читает поле авторизации, например:

```json
{
  "auth": {
    "type": "bearer"
  }
}
```

Значение `type` здесь не является секретом и не даёт доступ само по себе. Оно сообщает клиенту, **каким способом** нужно подтвердить свою личность. Секретный токен, ключ или сертификат хранятся отдельно и в карточку не помещаются.

Порядок поэтому важен: сначала клиент получает и проверяет карточку, как в [шагах 10](#step-10)–[11](#step-11), затем читает `auth.type` и только после этого подготавливает запрос подходящим способом. В карточке могут быть объявлены `bearer`, `mTLS` или подписанные запросы. Сейчас достаточно заметить не различия между ними, а общий принцип выбора.

Если поле отсутствует или указанный тип клиенту незнаком, безопаснее не отправлять задачу наугад. Карточка заранее показывает, сможет ли клиент вообще начать защищённый разговор с агентом.

> 🎒 **На пальцах.** Представь дверь в коворкинг с табличкой «вход по мобильному пропуску». Табличка не открывает дверь и не содержит твой пропуск — она лишь говорит, что приготовить до подхода к турникету. Agent Card играет роль такой таблички: клиент читает требуемый способ, достаёт подходящее удостоверение из безопасного места и только затем делает запрос.

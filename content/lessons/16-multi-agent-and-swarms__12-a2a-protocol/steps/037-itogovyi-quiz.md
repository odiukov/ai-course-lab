check:
  - question: >-
      Сервер уже умеет выполнять навык summarize, но его забыли добавить в Agent
      Card. Что произойдёт с корректно реализованным клиентом, который выбирает
      навык по карточке?
    options:
      - >-
        Клиент автоматически обнаружит обработчик по его имени в исходном коде
        сервера
      - >-
        Клиент не станет выбирать summarize, потому что опубликованный контракт
        не объявляет такой возможности
      - Клиент обязан перебрать все возможные имена навыков запросами
      - Agent Card обновится автоматически после первого вызова обработчика
    correct: 1
    explanation: >-
      Реализация навыка и его описание в Agent Card должны изменяться
      согласованно. Клиент, полагающийся на discovery, не должен угадывать
      необъявленные возможности сервера.
  - question: >-
      Клиент перешёл с периодического запроса состояния задачи на SSE-эндпоинт
      событий. Что ему теперь необходимо делать?
    options:
      - >-
        Открыть поток событий, обрабатывать приходящие обновления и завершить
        или восстановить соединение при нужном условии
      - 'Продолжать опрашивать задачу с прежней частотой, игнорируя поток'
      - Создавать новую задачу после каждого события
      - 'Ожидать, что SSE сразу вернёт единственный итоговый JSON и закроется'
    correct: 0
    explanation: >-
      При SSE клиент поддерживает потоковое соединение и реагирует на события
      сервера. Ему также нужна логика завершения и восстановления потока при
      разрыве.
  - question: >-
      Демонстрационный A2A-сервер успешно проходит основной сценарий. Как
      корректно выяснить, соответствует ли он спецификации?
    options:
      - Считать успешный сценарий достаточным доказательством соответствия
      - Проверить только совпадение названий HTTP-эндпоинтов
      - >-
        Сопоставить нормативные требования актуальной спецификации с
        реализацией, включая ошибки и необязательные для демо сценарии
      - Сравнить объём исходного кода демо с объёмом текста спецификации
    correct: 2
    explanation: >-
      Работающий happy path не доказывает соответствие протоколу. Нужна
      трассировка нормативных требований к конкретным элементам реализации и
      фиксация отсутствующих механизмов.
  - question: >-
      Почему клиенту с несколькими доступными навыками не следует жёстко
      прописывать имя нужного навыка в коде?
    options:
      - >-
        Жёстко заданное имя мешает использовать объявленные сервером возможности
        и делает изменение набора навыков ручной интеграционной правкой
      - A2A запрещает передавать имена навыков в запросах
      - Имя навыка всегда генерируется заново для каждой задачи
      - Agent Card доступна только после завершения задачи
    correct: 0
    explanation: >-
      Клиент должен выбирать подходящий навык из Agent Card по типу задачи.
      Иначе добавление или переименование навыка потребует менять клиент
      вручную, а механизм обнаружения потеряет смысл.

Дальше тебе понадобится не запоминание отдельных полей, а умение собрать из них надёжную границу между агентами. Перед отправкой задачи сверяй возможность по Agent Card из [шага 6](#step-6), затем проходи клиентский цикл из [шага 26](#step-26). Не смешивай сообщение, состояние и артефакт; учитывай допустимые переходы из [шага 21](#step-21). Чаще всего интеграция ломается не на успешном ответе, а на повторе запроса, несовместимой версии или правдоподобном результате неверной формы — именно эти случаи разобраны в [шагах 29](#step-29)–[33](#step-33).

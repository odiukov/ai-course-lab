В редакторе тебе нужно заменить слепое чередование реплик осмысленным выбором. Допустим, нужный префикс есть у `replica-b`, но очередь там чуть длиннее, чем у `replica-a`. Если сначала сравнить нагрузку, запрос уйдёт не туда и потеряет преимущество готового KV-кэша. Значит, порядок проверок здесь важнее самих условий.

Сначала получи стабильный ключ с помощью `prefix_key` из [шага 4](#step-4). Затем найди реплики, чей индекс содержит этот ключ. Дальше возможны два случая:

1. Совпадения есть — выбирай только среди найденных реплик.
2. Совпадений нет — рассматривай все реплики.

Внутри выбранной группы верни реплику с наименьшей нагрузкой, как разобрано в [шаге 9](#step-9). Обрати внимание: нагрузка разрешает ничью между подходящими кандидатами, но не отменяет попадание в кэш. Реплика без нужного префикса не должна победить только из-за более короткой очереди.

Не изменяй индекс кэша внутри функции: маршрутизатор здесь лишь читает уже опубликованное состояние. Также не пересчитывай ключ отдельно для каждой реплики — у одного запроса он один. Если несколько кандидатов имеют одинаковую минимальную нагрузку, сохрани предсказуемое поведение, опираясь на их исходный порядок.

Ключевая проверка для твоей реализации проста: сначала сузь круг по локальности кэша, а уже потом сравнивай нагрузку.

> 🎒 **На пальцах.** Представь пункт проката, где велосипеды заранее настроены под конкретных клиентов. Ты сначала ищешь велосипеды с биркой своего заказа, а затем берёшь наименее занятого сотрудника среди тех, кто их выдаёт. Если твоей бирки нигде нет, выбираешь самого свободного сотрудника вообще. Свободная касса ускоряет обслуживание, но не заменяет уже подготовленный велосипед.

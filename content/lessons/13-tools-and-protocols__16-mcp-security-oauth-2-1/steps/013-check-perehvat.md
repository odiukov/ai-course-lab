check:
  - question: >-
      Злоумышленник перехватил authorization code из редиректа и отправил
      собственный запрос на token endpoint. Что произойдёт?
    options:
      - >-
        Authorization server выдаст токен, поскольку одного кода достаточно для
        обмена
      - >-
        Запрос отклонят, поскольку без правильного code_verifier не получится
        подтвердить сохранённый code_challenge
      - >-
        Authorization server автоматически выдаст токен только с минимальным
        scope
      - Resource server попросит пользователя повторно подтвердить согласие
    correct: 1
    explanation: >-
      При обмене кода authorization server вычисляет challenge из присланного
      code_verifier и сравнивает результат с сохранённым значением. У
      перехватчика кода нет исходного verifier, поэтому проверка не пройдёт.
  - question: >-
      Злоумышленник видел code_challenge в запросе авторизации. Может ли он
      отправить это значение как code_verifier и обменять перехваченный code на
      токен?
    options:
      - 'Да, поскольку code_challenge и code_verifier взаимозаменяемы'
      - 'Да, если одновременно указать тот же redirect_uri'
      - >-
        Нет, поскольку сервер хеширует присланный verifier, а хеш самого
        challenge не совпадёт с сохранённым challenge
      - 'Нет, поскольку code_challenge удаляется сразу после редиректа'
    correct: 2
    explanation: >-
      Code challenge — односторонний отпечаток verifier. Сервер применит
      преобразование ещё раз к присланному значению, поэтому подстановка самого
      challenge вместо исходного verifier не даст совпадения.
---

Здесь проверяется одна связка: ты должен уметь пройти по [шести шагам потока](#step-8) и показать пальцем, где именно вор ломается. Не «PKCE защищает», а: код перехвачен на шаге 3, обмен происходит на шаге 4, и на шаге 4 требуется вещь, которая по сети вообще не летела.

Спотыкаются обычно на двух местах. Первое — думают, что PKCE прячет сам `code`. Не прячет: код по-прежнему уходит в редиректе, и перехватить его можно. Второе — путают направление проверки: verifier хешируют и сравнивают с challenge, а не наоборот, поэтому знание challenge вору ничего не даёт.

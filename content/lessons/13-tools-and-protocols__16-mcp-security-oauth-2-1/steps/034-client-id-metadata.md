title: Клиент публикует свои метаданные — ручной регистрации нет

Представь: ты подключаешь одного и того же MCP-клиента к семи серверам разных команд. У каждого свой authorization server. И каждый из них, прежде чем отправить пользователя на форму согласия, хочет знать про твоего клиента ровно две вещи: куда возвращать `code` (тот самый redirect URI из [шага 8](#step-8)) и с кем связываться, если что-то пойдёт не так.

Старый порядок: заходишь в панель, заполняешь форму, получаешь `client_id`, вставляешь его в конфиг. Семь серверов — семь форм и семь разных `client_id` в настройках. Появился восьмой сервер — снова руками.

А если перевернуть: пусть не сервер хранит анкету клиента, а клиент сам её выложит?

Именно так и сделано. Клиент публикует документ со своими метаданными по фиксированному URL — и этот URL становится его идентификатором. Authorization server видит незнакомый `client_id`, скачивает по нему документ, читает оттуда список redirect URI и контакты — и всё, регистрация состоялась, без единой формы. Механика та же, что у `.well-known` из [шага 14](#step-14): вместо переписки — документ, лежащий по адресу, который знают обе стороны.

Заодно отпадает вопрос, откуда сервер возьмёт `client_id` для проверок вроде той, что в [шаге 33](#step-33): он и есть адрес документа, один и тот же для всех серверов сразу.

Восьмой сервер теперь подключается без твоего участия — он просто сходит по ссылке.

> 🎒 **На пальцах.** Ты выставляешь счёт новому контрагенту. Раньше: письмо в бухгалтерию, анкета, ждёшь, пока заведут в базу — и так с каждым покупателем. Теперь реквизиты лежат у тебя на сайте по адресу, который ты всем и называешь вместо номера счёта. Бухгалтер открывает страницу, забирает данные, платит. Сменил банк — правишь одну страницу, а не двадцать анкет в чужих базах.

  - question: >-
      Вор перехватил code авторизации по пути к клиенту и первым отправил его на
      authorization server. Что произойдёт?
    options:
      - 'Обмен пройдёт: code настоящий, сервер выдаст токен вору'
      - >-
        Обмен сорвётся: у вора нет verifier, а его отпечаток сервер сохранил
        заранее
      - 'Обмен сорвётся: сервер увидит чужой IP и заблокирует запрос'
      - 'Обмен пройдёт, но токен придёт с пустым списком scopes'
    correct: 1
    explanation: >-
      Сервер сравнивает хеш присланного verifier с challenge, сохранённым при
      запросе авторизации. Перехваченного code без verifier недостаточно для
      получения токена.
  - question: >-
      Resource server получил токен с нужным scope, но поле aud указывает на
      другой сервер. Как следует обработать запрос?
    options:
      - 'Разрешить запрос, поскольку нужный scope присутствует'
      - 'Ответить insufficient_scope, чтобы клиент запросил дополнительные права'
      - Отклонить токен как выпущенный для другой аудитории
      - 'Переслать токен серверу, указанному в aud'
    correct: 2
    explanation: >-
      Scope описывает разрешённые действия, а aud — получателя токена. Наличие
      нужного scope не делает токен пригодным для другого resource server.
  - question: >-
      Клиент со scope repo:read получил 403 с error="insufficient_scope",
      требуемым scope repo:write и адресом того же ресурса. Что делать дальше?
    options:
      - Повторить прежний запрос с тем же токеном
      - >-
        Запустить авторизацию для расширенного набора scopes и получить новый
        токен
      - 'Самостоятельно дописать repo:write в существующий токен'
      - Отправить запрос на любой другой authorization server
    correct: 1
    explanation: >-
      Step-up требует нового согласования полномочий. Клиент запрашивает
      расширенный набор scopes и получает новый токен; изменить уже выпущенный
      токен он не может.
  - question: >-
      MCP-сервер получил пользовательский токен и хочет обратиться к внешнему
      API от имени пользователя. Как поступить безопасно?
    options:
      - Передать полученный токен внешнему API без изменений
      - >-
        Получить для внешнего API отдельные полномочия и не передавать ему
        исходный токен
      - Удалить из исходного токена лишние scopes и переслать его
      - 'Передать токен, если оба сервиса доверяют одному authorization server'
    correct: 1
    explanation: >-
      Исходный токен предназначен для конкретной аудитории. Внешнему API нужны
      отдельно полученные полномочия; общий authorization server не делает

Из этого урока дальше в курсе живут четыре вещи. Первая: разделение «кто ты» и «что тебе можно» — оно объяснено в [шаге 2](#step-2) и будет всплывать каждый раз, когда токен вроде бы валидный, а действие всё равно отклоняют. Вторая: aud и scope — две независимые проверки, и путать их ответы нельзя. Третья: 403 с WWW-Authenticate — это не тупик, а адрес и список того, чего не хватает.

Чаще всего спотыкаются на двух местах. На PKCE: кажется, что верификация происходит в момент выдачи code, а сверка идёт позже, при обмене. И на step-up: пытаются «дописать» scope в существующий токен вместо того, чтобы получить новый.

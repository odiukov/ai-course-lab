  - question: >-
      Вор перехватил code авторизации по пути к клиенту и первым отправил его на
      authorization server. Что произойдёт?
    options:
      - 'Обмен пройдёт: code настоящий, сервер выдаст токен вору'
      - >-
        Обмен сорвётся: у вора нет verifier, а его отпечаток сервер сохранил
        заранее
      - 'Обмен сорвётся: сервер увидит чужой IP и заблокирует запрос'
      - 'Обмен пройдёт, но токен придёт с пустым списком scopes'
    correct: 1
    explanation: >-
      Сервер сравнивает хеш присланного verifier с challenge, сохранённым на
      шаге запроса. Code без verifier — половина пары, и обмен не состоится.
  - question: >-
      Resource server получил токен, внутри которого есть нужный scope, но в
      поле aud указан адрес другого сервера. Что он ответит?
    options:
      - 'Пропустит запрос: главное, что scope на месте'
      - 'Отклонит с 403 и insufficient_scope, чтобы клиент дозапросил права'
      - >-
        Отклонит как чужой токен — проверка aud идёт раньше и до scopes дело не
        доходит
      - 'Перешлёт токен тому серверу, чей адрес стоит в aud'
    correct: 2
    explanation: >-
      aud отвечает на вопрос «этот токен вообще мне?». Если адрес чужой, токен
      не свой, и разбирать его права бессмысленно — это ровно тот случай,
      который отделяют от нехватки scope.
  - question: >-
      Клиент работал со scope repo:read и получил 403 с заголовком, где error
      равен insufficient_scope, scope равен repo:write, resource — адрес того же
      сервера. Что делает клиент дальше?
    options:
      - 'Повторяет тот же запрос ещё раз: возможно, сервер ответил случайно'
      - >-
        Запускает поток заново с шага авторизации, попросив repo:read и
        repo:write, и получает новый токен
      - 'Дописывает repo:write в уже имеющийся токен и отправляет его снова'
      - 'Идёт на другой authorization server, где прав побольше'
    correct: 1
    explanation: >-
      Заголовок — это инструкция: сервер сам назвал недостающий scope и свой
      адрес. Клиент проходит шаги авторизации и обмена повторно и получает
      второй токен, уже с расширенным набором прав.
  - question: >-
      MCP-сервер получил твой токен и хочет обратиться к внешнему API от твоего
      имени. Как правильно?
    options:
      - 'Передать твой токен дальше — он уже проверен, значит подходит'
      - >-
        Не передавать: у токена свой aud, для внешнего API нужны отдельные
        права, полученные отдельно
      - 'Передать, но урезать список scopes перед отправкой'
      - Передать только если внешний API использует тот же authorization server
    correct: 1
    explanation: >-
      Проброс доверенного токена не туда — это confused deputy. Токен привязан к
      одной аудитории и дальше границы не идёт; для внешнего вызова нужны
      собственные права.

Из этого урока дальше в курсе живут четыре вещи. Первая: разделение «кто ты» и «что тебе можно» — оно объяснено в [шаге 2](#step-2) и будет всплывать каждый раз, когда токен вроде бы валидный, а действие всё равно отклоняют. Вторая: aud и scope — две независимые проверки, и путать их ответы нельзя. Третья: 403 с WWW-Authenticate — это не тупик, а адрес и список того, чего не хватает.

Чаще всего спотыкаются на двух местах. На PKCE: кажется, что верификация происходит в момент выдачи code, а сверка идёт позже, при обмене. И на step-up: пытаются «дописать» scope в существующий токен вместо того, чтобы получить новый.

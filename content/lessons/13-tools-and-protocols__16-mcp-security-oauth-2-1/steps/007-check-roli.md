check:
  - question: >-
      Ты поднял MCP-сервер с заметками, и токены он выдаёт сам — тот же процесс,
      тот же хост. Что из этого верно?
    options:
      - 'Раз хост один, роль тоже одна: authorization server здесь не нужен'
      - >-
        Ролей всё равно две: одна выдаёт токены, другая проверяет их;
        соответствующие URL следует различать
      - 'Так делать нельзя: профиль MCP требует отдельный IdP'
      - 'Роли две, но для них обязательно использовать один URL'
    correct: 1
    explanation: >-
      Один процесс может одновременно выполнять обе роли. При этом выдача
      токенов и защита ресурса остаются разными функциями, для которых следует
      использовать различимые URL.
  - question: >-
      Claude Desktop подключается к MCP-серверу GitHub, а токены выдаёт
      отдельный IdP. Кто здесь resource server?
    options:
      - 'Claude Desktop, потому что он хранит и предъявляет токен'
      - 'IdP, потому что он решает, выдавать ли токен'
      - 'MCP-сервер GitHub, потому что он предоставляет данные и проверяет токен'
      - 'IdP и MCP-сервер одновременно, потому что оба работают с токеном'
    correct: 2
    explanation: >-
      Resource server предоставляет защищённые данные или операции и проверяет
      предъявленный токен. Claude Desktop выступает клиентом, а IdP —
      authorization server.

После [шага 6](#step-6) ты должен уметь разложить любую реальную связку на три роли и не сбиться, когда две из них живут в одном процессе. Проверь себя на паре вопросов ниже.

Спотыкаются обычно на двух местах. Первое: если authorization server и resource server — один и тот же хост, кажется, что роль тоже одна, и разделение — формальность. Оно не формальность: выдача права и проверка права — разные действия, и разные URL нужны, чтобы токен был привязан к конкретному ресурсу.

Второе: клиента путают с authorization server, потому что токен физически лежит у клиента. Но хранить — не значит выдавать.

Ты нашёл три туториала «OAuth для удалённого MCP-сервера». В первом токен приезжает прямо в адресной строке браузера — это implicit flow. Во втором сервер получает токен сам, по своему секрету, без участия человека — client credentials. В третьем — authorization code плюс PKCE. Все три честно ссылаются на OAuth и все три технически ему соответствуют.

И какой из них правильный для MCP?

Вот в чём затруднение: OAuth сам по себе — это не один способ, а набор разрешённых способов. Спецификация-конструктор. Два сервера, оба «по OAuth», могут оказаться несовместимы: клиент придёт с одним ожиданием, сервер ждёт другого. А каждый лишний разрешённый вариант — ещё одно место, где легко ошибиться и утечь токеном.

Поэтому MCP не изобретает новую авторизацию, а пишет к OAuth 2.1 строгий регламент. Из потоков остаётся один — authorization code с PKCE. Implicit вычеркнут. Client credentials по умолчанию вычеркнут. Сверху добавлены обязательства: resource indicators в каждом запросе токена (та самая привязка к аудитории, из-за которой сервер A не сможет предъявить твой токен серверу B — [шаг 3](#step-3)) и опубликованные метаданные защищённого ресурса, чтобы клиент не угадывал, куда идти за токеном.

Выигрыш простой: тебе не нужно реализовать пять потоков и в каждом не ошибиться. Нужен один — и он же единственный, которого от тебя ждут.

Так что из трёх туториалов два для MCP просто запрещены. Выбор, который тебя мучил, регламент сделал за тебя.

> 🎒 **На пальцах.** Соединить два провода можно скруткой, пайкой, клеммой, гильзой — правила устройства электроустановок допускают всё это. А регламент твоего дома оставляет одну клемму и вычёркивает остальное. Не потому, что скрутка вне закона, а потому что электрику-проверяющему тогда есть что проверять: одно соединение, один способ, один список ошибок. Профиль MCP — такой же вычеркнутый список.

  - question: >-
      Модель за один ход выдала два вызова get_weather: один для Токио, другой
      для Лондона. Хост запустил их параллельно, и результаты вернулись в
      обратном порядке. Что позволяет однозначно сопоставить каждый результат с
      исходным вызовом?
    options:
      - 'Поле name, потому что оно различает все вызовы'
      - 'Поле id, которое сохраняется при возврате результата'
      - Позиция результата в порядке завершения
      - Наличие объекта arguments в описании инструмента

    explanation: >-
      Оба вызова имеют одинаковое имя, а порядок завершения при параллельном

  - question: >-
      Зачем включать id в формат вызова, если конкретный хост сейчас исполняет
      инструменты только последовательно?
    options:
      - Чтобы модель могла восстановить забытое сообщение пользователя
      - >-
        Чтобы использовать единый контракт и при последовательном, и при
        параллельном исполнении
      - Чтобы по id выбирать функцию-исполнитель вместо поля name
      - Чтобы id можно было передать исполнителю как обязательный аргумент

    explanation: >-
      Стабильный формат не должен меняться вместе с режимом исполнения. При
      переходе к параллельным вызовам уже имеющийся id позволит сопоставлять

Ты уже видел из [шага 18](#step-18), что в вызове три поля, и что `id` — метка конкретного обращения, а не инструмента. Теперь проверим, что это не просто запомнилось, а работает: сумеешь ли ты сказать, что именно сломается без `id`, когда вызовов за ход больше одного ([шаг 17](#step-17)).

Обычно спотыкаются на двух местах. Первое: путают `id` с `name` — кажется, что имя инструмента уже достаточно различает вызовы, пока не окажется, что оба вызова называются одинаково. Второе: молча опираются на порядок ответов. При параллельном исполнении он не гарантирован — и именно там, где порядок подводит, `id` остаётся единственной зацепкой.

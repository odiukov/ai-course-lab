Вызов пришёл: `{"name": "get_weather", "arguments": {"city": 42, "units": "kelvin"}}`. Схема из [шага 9](#step-9) говорит: `city` — строка, `units` — одно из `["c", "f"]`. Оба аргумента мимо. Что должна вернуть твоя проверка?

Соблазн — вернуть `False`. Но вспомни первую стратегию из [шага 22](#step-22): ошибку отдают обратно модели, чтобы она исправилась сама. От слова «нет» модель не поймёт, что чинить. Поэтому `validate_arguments(schema, arguments)` возвращает **список сообщений об ошибках**: пустой список — всё чисто, непустой — вот конкретно что не так. Проверка на валидность превращается в `if not errors`.

Внутри — четыре сверки из [шага 23](#step-23), и порядок между ними неслучаен. Сначала пройдись по `required`: каждое обязательное имя должно быть в `arguments`. Потом по тем полям, которые реально пришли, — тип, затем `enum`, затем `minimum`/`maximum`. Если поля нет, а ты полез проверять его тип, получишь падение на `None` вместо аккуратного сообщения.

И главное: не выходи из функции на первой же ошибке. Собери все и верни разом — модель починит два поля за один ход, а не за два.

На что посмотреть, когда будешь писать. Типы в схеме — строки JSON Schema, а в Python объекты: `"string"` это `str`, `"integer"` — `int`, `"number"` — `int` или `float`, `"boolean"` — `bool`. Ловушка: в Python `isinstance(True, int)` даёт `True`, так что `True` проскочит в поле-`integer`, если не отсечь `bool` отдельно. Про поля, которых в схеме вообще нет, пока не думай — это отдельный разговор.

Сообщение пиши так, чтобы его можно было отдать модели дословно: не «invalid», а `city: expected string, got integer`.

> 🎒 **На пальцах.** Приёмка на складе. Кладовщик не разворачивается после первой кривой коробки — он проходит всю накладную и пишет акт: «позиция 3 — не тот размер, позиция 7 — недостача». Один акт, один рейс обратно поставщику. Если бы он звонил после каждой строки, машина ездила бы четыре раза. Твой список ошибок — этот акт.

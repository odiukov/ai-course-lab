Вернись к фальшивому решателю из [шага 16](#step-16) и попроси у него погоду сразу в двух городах. Он выдаёт два объекта вызова — как мы видели в [шаге 17](#step-17), за один ход это нормально. Что внутри каждого?

Минимум два поля. `name` — тот самый машинночитаемый идентификатор из [шага 7](#step-7): `get_weather`, ровно как в объявлении. И `arguments` — объект JSON, заполненный по input schema из [шага 9](#step-9): `{"city": "Tokyo"}` в первом, `{"city": "London"}` во втором.

Хост берёт оба и уходит их выполнять. Токийский сервис отвечает за 80 мс, лондонский подвисает на две секунды. Результаты возвращаются в обратном порядке: сначала `11`, потом `18`.

И тут неприятность. Оба результата пришли от `get_weather`. В самих числах города не написано. Как хост поймёт, какое из них приклеить к какому вызову?

По порядку — нельзя, порядок уже перепутан. По `name` — нельзя, он у обоих одинаковый. По `arguments` — тоже нет: результат не несёт с собой аргументы, он несёт только `11`.

Поэтому в полезной нагрузке есть третье поле — `id`. Уникальная метка конкретного вызова: `call_a1`, `call_a2`. Хост запоминает её на шаге decide, а когда возвращает результат, кладёт тот же `id` рядом с числом. Совпадение метки — единственная связь между «что спросили» и «что ответили».

Один вызов ещё можно опознать на глаз. Два вызова одного инструмента без `id` — это две цифры без адресатов.

> 🎒 **На пальцах.** Багажная лента. Ты сдал две одинаковые чёрные сумки: снаружи не отличить, вес почти совпадает. Порядок выдачи не твой — как загрузили, так и выехало. Спасает только бирка с кодом, наклеенная при сдаче и продублированная на твоём талоне. `id` — эта бирка. Не описывает содержимое, не влияет на перевозку, просто гарантирует, что тебе вернут именно твою сумку.

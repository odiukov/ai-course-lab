Ты вводишь фразу «Я люблю чай», а перевод появляется не одновременно с чтением исходных слов. Сначала проследи по схеме только левую часть: encoder принимает «Я», затем «люблю», затем «чай». После каждого слова его hidden state обновляется — в нём остаётся новая версия смысла уже прочитанного фрагмента.

Когда вход закончился, последний hidden state становится знакомым по [шагу 2](#step-2) context vector. Именно в этот момент заканчивается работа encoder и начинается работа decoder. Между словом «чай» и первым словом перевода нет прямой стрелки: decoder получает не отдельное исходное слово, а context vector целиком.

Теперь двигайся по правой части схемы шаг за шагом. Decoder, инициализированный context vector, выбирает первое целевое слово — например, `I`. На следующем шаге это `I` возвращается ему на вход, и вместе с обновлённым hidden state помогает выбрать `like`. Затем `like` участвует в выборе `tea`.

Но как decoder понимает, что предложение готово? После `tea` он должен выбрать специальный токен `<EOS>` — знак конца последовательности. Если этого не происходит, генерацию всё равно останавливают на заранее установленной максимальной длине.

Здесь нет заранее подготовленных трёх ячеек для трёх слов: decoder сам решает, сколько шагов сделать. Поэтому длина перевода не обязана совпадать с длиной исходной фразы, как ты видел в [шаге 1](#step-1).

> 🎒 **На пальцах.** Представь эстафету. Первый бегун собирает по маршруту три отметки и передаёт напарнику одну эстафетную палочку с записанным результатом. Второй бегун уже не возвращается к отдельным отметкам: он смотрит на палочку, делает первый шаг, затем использует результат этого шага для следующего. Финиш для него — токен `<EOS>`.

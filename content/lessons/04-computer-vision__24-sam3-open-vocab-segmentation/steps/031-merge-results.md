Ты запускаешь поиск для двух концептов. Проход по `"cup"` возвращает экземпляры с ID `0` и `1`, а проход по `"plate"` — ещё один объект с ID `0`. Простое сложение списков создаст путаницу: теперь ID `0` обозначает сразу два разных объекта.

В `merge_concept_results` тебе нужно собрать результаты всех проходов в один плоский список и заново выдать каждому объекту уникальный `instance_id`. Нумерация должна идти подряд: `0`, `1`, `2` — в том порядке, в котором функция обходит концепты и их детекции.

Для каждой детекции создай итоговую запись `ConceptDetection`:

- `concept` возьми из текущей группы результатов;
- `instance_id` замени новым общим номером;
- `box`, `score` и `mask_rle` перенеси без изменений.

Не изменяй исходные объекты на месте: безопаснее собрать новые записи. Тогда локальные результаты отдельных проходов останутся пригодны для проверки и повторного использования.

Обрати внимание и на пустые группы. Если для `"bicycle"` модель ничего не нашла, функция не должна добавлять фиктивный объект или прерывать объединение. Она просто продолжает со следующим концептом. Если пусты все группы, результатом будет пустой список.

Связь `concept → детекции` при этом нельзя потерять: именно она объясняет, какой текстовый запрос породил каждую маску. Получается один список без дублирующихся ID, но с сохранённым происхождением каждого объекта.

> 🎒 **На пальцах.** Представь фестиваль с несколькими входами. На каждом входе счётчик начинается с нуля, поэтому посетители из разных очередей получают одинаковые номера. На центральной стойке ты переписываешь их в общий журнал и выдаёшь сквозные номера, сохраняя название входа. Пустая очередь просто не добавляет строк в журнал.

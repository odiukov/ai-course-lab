Ты запускаешь поиск по изображению с запросом `red car` и получаешь две детекции с ID 0 и 1. Затем добавляешь `bicycle` — и бэкенд снова возвращает ID 0 и 1. Если просто сложить ответы, в общем списке окажутся два разных объекта с одинаковым ID. Как тогда понять, к чему относится, например, маска объекта 0?

Причина в интерфейсе: метод `detect` принимает один концепт. Строку с несколькими понятиями ты уже разделил на короткие именные группы в [шаге 7](#step-7), а теперь для каждой группы нужен отдельный проход. Сначала модель ищет все `red car`, затем все `bicycle`. Склеивать их обратно в один промпт нельзя: `red car, bicycle` станет новым составным запросом, а не гарантированно двумя независимыми задачами.

Ответы отдельных проходов собираются в единый список детекций из [шага 17](#step-17). При сборке важно сохранить поле `concept` и выдать объектам уникальные ID уже в масштабе всего списка: автомобили могут получить 0 и 1, велосипеды — 2 и 3. Если для какого-то концепта ничего не найдено, его проход просто не добавит элементов; результаты остальных концептов останутся на месте.

Получается простой контракт: один концепт — один проход, несколько проходов — один плоский и однозначный список.

> 🎒 **На пальцах.** Представь библиотекаря с несколькими записками: «атласы» и «словари». Он не воспринимает их как название одной странной книги, а выполняет два поиска по каталогу. На каждой найденной книге есть локальный номер полки, но перед выдачей библиотекарь кладёт все книги на одну тележку и присваивает им общие номера — теперь любая книга находится однозначно.

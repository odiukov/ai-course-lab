В начале трейса записано: заказ нужно отправить со склада `north`. Через шесть действий агент вызывает доставку со значением `warehouse="south"`. Сам вызов корректен, инструмент существует, повторов нет — детекторы из [шага 15](#step-15) и [шага 17](#step-17) ничего подозрительного не найдут. Ошибка видна только при сравнении действия с ранним контекстом.

Твоя функция `context_violations` должна находить именно такие противоречия. Для каждого трейса сначала выдели заданные в контексте ограничения и факты, а затем просмотри последующие действия. Если действие использует несовместимое значение или прямо нарушает ограничение, добавь его в результат.

Смотри на три условия:

- ограничение появилось раньше проверяемого действия;
- действие ему противоречит, а не просто не упоминает его;
- в результате можно понять, какое действие нарушило какое ограничение.

Например, отсутствие поля `warehouse` ещё не доказывает нарушение: инструмент мог подставить склад автоматически. А явное `warehouse="south"` при требовании `north` — уже нарушение. По той же причине не помечай действие только за необычность: функция проверяет согласованность с контекстом, а не качество решения вообще.

Используй сигнатуры, предусмотренные синтетическими трейсами: сопоставляй конкретные поля и значения, не пытайся строить универсальное понимание естественного языка. Здесь важно воспроизвести механизм дешёвого детектора из исходного примера. Раннее правило становится проверяемым только тогда, когда позднее действие можно явно поставить рядом с ним.

> 🎒 **На пальцах.** В гардеробе тебе выдали жетон №317. Через час сотрудник приносит пальто по жетону №371. Пальто существует, сотрудник не повторял действие и не выдумал новую услугу — он просто переставил цифры из раннего контекста. `context_violations` сверяет жетон с последующим действием и фиксирует именно это расхождение.

  - question: >-
      Ты добавил в код сервера строку print("дошли до dispatch") для отладки, и
      хост перестал видеть сервер. Что произошло?
    options:
      - >-
        Отладочная строка попала в stdout и встала между JSON-объектами — клиент
        не смог разобрать её как сообщение
      - 'Сервер стал работать медленнее, и клиент отвалился по таймауту'
      - 'Строка съела память, отведённую под ответ'
      - 'Ничего страшного, клиент просто пропустит лишнюю строку и продолжит'
    correct: 0
    explanation: >-
      stdout — это канал протокола, а не место для сообщений человеку. Любая
      посторонняя строка ломает разбор; отладку пиши в stderr или в файл.
  - question: >-
      Модель вызвала инструмент read_note с id заметки, которой нет. Как
      правильно ответить?
    options:
      - Вернуть ошибку JSON-RPC с кодом — вызов не удался
      - >-
        Вернуть обычный результат с content и isError: true, чтобы модель
        прочитала текст и попробовала иначе
      - 'Не отвечать вообще: раз заметки нет, отвечать нечего'
      - Вернуть пустой content без всяких флагов
    correct: 1
    explanation: >-
      Ошибка JSON-RPC — про сломанный вызов: нет такого метода, битые параметры.
      Тут вызов корректный, а не сложилось внутри инструмента, и модель должна
      увидеть текст ошибки.
  - question: >-
      Ты объявил в capabilities для ресурсов subscribe: true, но кода подписки
      не написал. Чем это плохо?
    options:
      - 'Ничем: клиент всё равно проверит наличие обработчика'
      - 'Сервер не запустится, пока обработчик не появится'
      - >-
        Клиент поверит объявлению и пришлёт resources/subscribe — а ответить
        будет нечем
      - Это замедлит initialize
    correct: 2
    explanation: >-
      capabilities — обещание, по которому клиент строит своё поведение. Объявил
      только то, что реально умеешь, иначе получишь запрос, на который нечего
      ответить.
  - question: >-
      У тебя 200 заметок, и модель обычно ищет среди них по слову. Как это лучше
      отдать?
    options:
      - >-
        Инструментом поиска: модель зовёт его с запросом и получает только
        подходящие заметки
      - 'Двумя сотнями ресурсов в resources/list, чтобы хост показал их все сразу'
      - 'Одним промптом, в который вклеен текст всех заметок'
      - 'Ресурсом с одним URI, отдающим все 200 заметок целиком'
    correct: 0
    explanation: >-
      Ресурсы хороши, когда данных немного и их выбирает человек. При
      двухсотенном списке и поиске по содержимому работу делает инструмент с
      параметром запроса.

Ты прошёл путь от пустого файла до сервера, который здоровается через `initialize`, отдаёт список инструментов, читает ресурсы по своей схеме URI и честно помечает опасные операции аннотациями.

Дальше в курсе всё это станет фоном: когда мы возьмём SDK из [шага 31](#step-31), декораторы будут делать ровно то, что ты уже собрал руками, — и ты будешь понимать, что именно они прячут.

Спотыкаются обычно на трёх местах: отладочный `print` в stdout, ответ на уведомление без `id` и попытка вернуть ошибку JSON-RPC там, где нужен `isError: true`. Проверь на этих вопросах, что каждое из трёх для тебя уже не загадка.

  - question: >-
      Ты добавил в код сервера строку print("дошли до dispatch") для отладки, и
      хост перестал видеть сервер. Что произошло?
    options:
      - >-
        Отладочная строка попала в stdout между JSON-RPC-сообщениями, и клиент
        не смог разобрать её как сообщение протокола
      - >-
        Сервер стал работать медленнее, и клиент обязательно отключился по
        тайм-ауту
      - 'Строка заняла память, предназначенную для ответа'
      - 'Ничего критичного: клиент обязан пропускать любые посторонние строки'
    correct: 0
    explanation: >-
      stdout — канал протокола, а не место для диагностических сообщений. Любая
      посторонняя строка может нарушить разбор; отладочные сообщения следует
      направлять в stderr или файл.
  - question: >-
      Модель корректно вызвала инструмент read_note с идентификатором
      несуществующей заметки. Как серверу сообщить о неудаче?
    options:
      - >-
        Вернуть ошибку JSON-RPC, потому что любой неуспешный результат является
        ошибкой протокола
      - >-
        Вернуть результат инструмента с content и isError: true, чтобы модель
        получила описание проблемы
      - 'Не отправлять ответ, поскольку заметка отсутствует'
      - Вернуть пустой content без признака ошибки
    correct: 1
    explanation: >-
      Запрос корректен, а сбой произошёл при выполнении инструмента. Поэтому это
      результат инструмента с isError: true, а не ошибка уровня JSON-RPC.
  - question: >-
      Сервер объявил в capabilities для ресурсов subscribe: true, но обработку
      подписок не реализовал. К чему это приведёт?
    options:
      - 'Ни к чему: клиент обязан сам проверить исходный код обработчика'
      - Сервер не сможет завершить запуск
      - >-
        Клиент может положиться на объявление и отправить resources/subscribe,
        который сервер не умеет обслуживать
      - Изменится только скорость обработки initialize
    correct: 2
    explanation: >-
      Capabilities служат обещанием клиенту. Объявлять следует только
      реализованные возможности, иначе клиент начнёт использовать функцию,
      которую сервер фактически не поддерживает.
  - question: >-
      В хранилище находится 200 заметок, а модель обычно ищет среди них по
      ключевому слову. Как лучше предоставить такой доступ?
    options:
      - >-
        Дать инструмент поиска с параметром запроса, возвращающий только
        подходящие заметки
      - Всегда показывать все заметки отдельными элементами resources/list
      - Встроить полный текст всех заметок в один промпт
      - 'Создать один ресурс, который при каждом чтении возвращает всё хранилище'
    correct: 0
    explanation: >-
      Когда требуется параметризованный поиск по большому набору данных, эту
      работу лучше оформить как инструмент. Ресурсы удобнее для адресуемых
      данных, которые клиент или пользователь выбирает для чтения.

Ты прошёл путь от пустого файла до сервера, который здоровается через `initialize`, отдаёт список инструментов, читает ресурсы по своей схеме URI и честно помечает опасные операции аннотациями.

Дальше в курсе всё это станет фоном: когда мы возьмём SDK из [шага 31](#step-31), декораторы будут делать ровно то, что ты уже собрал руками, — и ты будешь понимать, что именно они прячут.

Спотыкаются обычно на трёх местах: отладочный `print` в stdout, ответ на уведомление без `id` и попытка вернуть ошибку JSON-RPC там, где нужен `isError: true`. Проверь на этих вопросах, что каждое из трёх для тебя уже не загадка.

У тебя уже лежат готовые куски: `initialize_result` из [шага 11](#step-11), `call_tool` из [шага 17](#step-17), таблица «имя метода → функция» из [шага 19](#step-19). А цикл чтения из [шага 6](#step-6) умеет достать из строки словарь. Между ними зияет дырка: кто-то должен взять этот словарь и решить, какую из функций дёрнуть и что вернуть наружу.

Это и есть `dispatch`. Одна функция, один аргумент — разобранное сообщение, — и ровно два вида возврата: либо словарь, который цикл напечатает одной строкой, либо `None`, который означает «печатать нечего».

Развилок внутри три, и порядок их важен.

Сначала достань `method` и `id`. Потом посмотри в таблицу: если имя там есть — вызови обработчик, а результат заверни в конверт с `"jsonrpc": "2.0"` и тем же `id`, что пришёл. Если имени в таблице нет — это не сбой инструмента, а неизвестный метод протокола, то есть та самая ошибка JSON-RPC из [шага 16](#step-16): код `-32601`, «method not found», и снова с тем же `id`.

А теперь тонкое место. Если `id` в сообщении не было, это уведомление — и правило «молчание на уведомления» из [шага 7](#step-7) сильнее всего остального. Даже когда метод неизвестен. Даже когда очень хочется пожаловаться.

Ошибка на уведомление — это ответ без адресата: его никто не ждёт и никто не прочитает.

Проверь себя строчкой из `Use It`: пропусти через пайп `initialize`, потом `tools/list`. В первом случае на выходе один JSON, во втором — три инструмента. Отправь `notifications/initialized` — и стандартный вывод должен остаться пустым. Если оттуда что-то прилетело, `dispatch` вернул словарь там, где обязан был вернуть `None`.

> 🎒 **На пальцах.** Окошко МФЦ. На стекле список услуг, у тебя талон: услуга и номер очереди. Услуга есть — получаешь бумагу со своим номером. Услуги нет — получаешь отказной бланк, всё равно со своим номером: молча тебя не отпустят. А если ты просто бросил заявление в ящик у входа, без номера очереди, — тебя не позовут ни при каком исходе. Звать некого.

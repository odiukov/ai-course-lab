Три функции готовы, и если ты вызовешь их подряд на одном запросе «какой у пользователя номер телефона», получишь три списка разной формы: от `vector_search` — пары (запись, косинус 0.31), от `kv_lookup` — одну запись без всякого числа, от `graph_neighbors` — рёбра, у которых числа нет вовсе. Сложить их в один ответ напрямую нельзя: сравнивать 0.31 с «просто нашлось» бессмысленно.

Значит, перед сплавом каждому результату надо приписать релевантность в одной шкале. Для вектора она уже есть — косинус из [шага 12](#step-12). Для точного попадания по ключу это 1.0: ключ либо совпал, либо нет. Для ребра графа — вес пути: сосед на расстоянии одного шага получает, скажем, 0.8, через два шага — 0.6.

Дальше `hybrid_search(query, user_id, k)` делает четыре вещи. Собирает результаты трёх хранилищ. Каждому считает `fuse_score` из [шага 25](#step-25), подставляя релевантность своего источника, а важность и свежесть беря из самой записи. Склеивает списки по правилу из [шага 27](#step-27): один факт мог прийти дважды, и остаётся ветка с большим score — телефон, найденный и вектором на 0.31, и KV на 1.0, живёт как KV-попадание. Сортирует по убыванию и отдаёт top-k.

Два места, где спотыкаются. KV и граф часто возвращают пусто — это норма, а не ошибка, функция должна спокойно отдать результат по одному вектору. И дедупликация идёт по идентификатору факта, а не по тексту.

> 🎒 **На пальцах.** Как приёмка на складе. Подъехали три машины: одна с паллетами, одна с коробками, одна с мешками. Пока всё не пересчитано в одних единицах — килограммах — сводную накладную не составить. Приёмщик взвешивает каждую партию, замечает, что одна коробка уже есть в паллете, и вписывает её один раз. Только после этого получается один список, отсортированный сверху вниз.

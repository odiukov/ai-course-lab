Одной команде одновременно подходят три правила: для любого инструмента, для всех вызовов `Bash` и только для `Bash(npm test)`. Все три совпали по логике из [шага 13](#step-13), но описывают действие с разной точностью. Теперь тебе нужно превратить эту точность в сравнимое число.

Напиши `rule_specificity`. Функция получает уже разобранное правило — используй результат `parse_rule` из [шага 11](#step-11), а не разбирай исходную строку повторно. Верни числовую оценку конкретности по порядку из [шага 14](#step-14): правило без уточнений получает меньшую оценку, правило с указанным инструментом — большую, а ограничение на конкретные аргументы добавляет ещё конкретности. Чем больше буквальных частей и чем меньше свободы оставляют шаблоны, тем выше результат.

Не учитывай решение правила — `allow`, `ask` или `deny`. Оно отвечает на другой вопрос: что делать после совпадения. Здесь измеряется только то, насколько узко правило описывает действие. По этой же причине не выбирай победителя внутри `rule_specificity`: функция должна лишь вернуть оценку, пригодную для последующего сравнения.

Проверь граничные случаи: пустое ограничение, общий шаблон `*`, точная команда и шаблон с одной буквальной частью. Важен не произвольный размер числа, а устойчивый порядок оценок.

> 🎒 **На пальцах.** Представь билеты на музыкальный фестиваль. Надпись «вся территория» почти ничего не уточняет, «сцена B» сужает область, а «сцена B, сектор 3, место 14» указывает её точно. `rule_specificity` переводит такую детализацию в число, но не решает, пустят ли владельца билета: она лишь показывает, какой билет описывает место конкретнее.

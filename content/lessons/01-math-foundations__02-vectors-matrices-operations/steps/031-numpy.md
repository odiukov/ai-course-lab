title: 'То же самое в NumPy, только в сто раз быстрее'

Когда ты писал умножение матриц руками, каждый элемент считался в трёх вложенных циклах. Для матрицы 2×2 это незаметно. Для слоя настоящей нейросети, где размеры бывают 4096×4096, Python будет думать минутами — и так на каждом шаге обучения. Отсюда и нужна библиотека NumPy: она берёт ровно ту же математику и выполняет её за доли секунды.

Фокус в том, что NumPy не считает на Python. Когда ты пишешь `A @ B`, Python передаёт работу в BLAS — набор процедур на C и Fortran, вылизанных за десятилетия под конкретные процессоры. Представь, что вместо того чтобы диктовать курьеру каждый поворот, ты отдаёшь ему адрес, а дальше он едет сам по маршруту, который знает наизусть. Та же дорога, только без твоих комментариев на каждом перекрёстке.

Из этого вырастает главная ловушка. В NumPy есть два похожих оператора:

- `A * B` — поэлементное умножение: первый элемент на первый, второй на второй.
- `A @ B` — матричное умножение: строка на столбец, с суммированием.

Для `A = [[1, 2], [3, 4]]` и `B = [[5, 6], [7, 8]]` первое даст `[[5, 12], [21, 32]]`, второе — `[[19, 22], [43, 50]]`. Оба запустятся без ошибки. Код работает, модель не учится, а виноват один символ.

Ты запускаешь смешанную пачку запросов и ожидаешь, что похожие формулировки сразу начнут экономить деньги. Но если просто вызвать `semantic_lookup` для каждого текста, симуляция останется незавершённой: кто вызовет модель при промахе, когда новая запись появится в кэше и как параллельность повлияет на повторные запросы?

В `run_semantic_cache` собери полный цикл из [шага 17](#step-17), но уже для всей нагрузки. Для каждого запроса сначала выполняй семантический поиск. При попадании возвращай сохранённый ответ: вызова LLM здесь быть не должно. При промахе вызывай модель, сохраняй полученные ответ и эмбеддинг, а затем учитывай этот запрос как обработанный без L1.

Особенно внимательно реализуй переключатель параллельности. В последовательном режиме следующий запрос видит запись, созданную предыдущим. В параллельном режиме несколько похожих запросов могут проверить кэш до появления первой записи — и каждый уйдёт к модели. Именно поэтому одинаковая нагрузка способна дать разный счёт без изменения промптов.

Ориентируйся на сигнатуру и структуры данных в заготовке: функция должна вернуть сведения, которые `main.py` сможет вывести, но не должна сама решать, хороший ли получился результат. Пока проверь только причинную цепочку: L1-hit останавливает путь, L1-miss продолжает его через LLM и пополняет кэш. Если при попадании модель всё-таки вызывается, симулятор показывает уже другой протокол.

> 🎒 **На пальцах.** Представь общий чат службы поддержки. Один оператор не находит готового ответа и пишет эксперту. Если остальные ждут, ответ появится в базе и следующий оператор его переиспользует. Если пять операторов проверяют базу одновременно, все пятеро увидят пустоту и напишут эксперту. Вопросы те же, но порядок проверки и сохранения меняет итоговую стоимость.

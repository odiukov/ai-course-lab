Ты запускаешь десять одинаковых запросов почти одновременно и считаешь стоимость волны. Здесь легко незаметно удешевить расчёт: записать префикс только для первого запроса, а остальные девять посчитать как чтения. Но это уже последовательный сценарий. В параллельной волне из [шага 32](#step-32) все запросы успевают увидеть промах, поэтому каждый оплачивает собственную запись.

В `parallel_wave_cost` посмотри на три части каждого запроса:

- динамические токены оплачиваются по обычной цене;
- токены общего префикса оплачиваются с множителем записи;
- прочитанных из кэша токенов нет.

Стоимость одного такого запроса уже умеет считать `l2_request_cost` из [шага 29](#step-29). Твоя функция должна передать ей правильное разбиение токенов, а затем получить стоимость всей волны с учётом количества параллельных запросов. Не меняй состояние кэша внутри цикла: второй запрос не должен внезапно стать `hit` только потому, что первый уже был посчитан в Python.

Проверь себя на крайних случаях. При одном запросе результат совпадает со стоимостью одной записи. При увеличении количества запросов вдвое общая стоимость тоже удваивается. А при нулевом размере префикса надбавка за запись исчезает — остаются только свежие токены.

> 🎒 **На пальцах.** Представь мастерскую, куда одновременно принесли десять одинаковых чертежей и попросили срочно изготовить десять форм. Мастера начинают работу в разных комнатах и не знают, что сосед уже делает такую же форму. Поэтому оплачиваются десять изготовлений. В твоём расчёте нельзя задним числом передать готовую форму девяти мастерам: к моменту старта её ещё не существовало.

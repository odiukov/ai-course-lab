Ты открываешь JSON-отчёт после запуска гейта: там точные поля, идентификаторы и пути, но быстро понять результат трудно. Хочется вынести наверх крупное «проверка пройдена», ниже поставить таблицу находок и отправить её в описание задачи.

В этот момент легко получить два разных отчёта. Например, в JSON появилась новая блокирующая находка, а Markdown остался старым и по-прежнему показывает зелёный статус. Какому верить?

Источником истины остаётся JSON по единому пути из [шага 20](#step-20). Markdown — только представление: его каждый раз заново строят из готового `verification_report`, созданного в [шаге 19](#step-19). Гейт не читает Markdown обратно, а человек не исправляет в нём вердикт вручную. Если нужно изменить результат, меняются исходные артефакты или применяется идентифицируемая отмена из [шага 32](#step-32), после чего сводка генерируется снова.

В ней полезны только данные, помогающие быстро принять решение: итоговый вердикт, проверяемый коммит или задача, список выполненных проверок, блокирующие находки и предупреждения. Для каждой находки достаточно её кода, серьёзности, короткого сообщения и ссылки на свидетельство — тех частей записи, которые были введены в [шаге 5](#step-5). Действующие отмены тоже стоит показать вместе с автором и причиной, но не вычислять заново.

Так Markdown становится удобным окном в отчёт, а не параллельной версией событий.

> 🎒 **На пальцах.** Представь электронное табло на складе: оно крупно показывает остатки, взятые из учётной системы. Кладовщик может удобно прочитать «12 коробок», но не должен исправлять число маркером прямо на табло. Сначала меняется учётная запись, затем табло обновляется. JSON здесь — учётная система, Markdown — табло.

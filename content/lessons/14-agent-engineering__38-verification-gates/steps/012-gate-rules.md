Ты открываешь `rule_report.json`: десять правил прошли, одно провалилось. Можно ли вернуть пустой список находок только потому, что большинство проверок зелёные? Нет — важен не счёт, а строгость именно проваленного правила.

Напиши `gate_rules`, которая читает уже готовый отчёт правил и превращает его провалы в записи `Finding` из [шага 6](#step-6). Сама функция ничего не запускает и не проверяет повторно: разделение труда из [шага 2](#step-2) остаётся прежним. Её задача — аккуратно перенести результат из одного формата в другой.

Пройди по всем записям отчёта. Успешные правила пропускай: для них находка не нужна. Для каждого неуспешного правила создай `Finding`, сохранив его идентификатор или понятное название, объяснение провала и исходную серьёзность. Не определяй серьёзность по тексту вроде «критическая ошибка» — используй структурированное поле отчёта. Иначе простая смена формулировки внезапно изменит вердикт.

Особенно проверь случай с несколькими провалами: функция должна вернуть их все, а не остановиться на первом. Один блокирующий результат уже не позволит гейту выставить `passed: true`, но остальные находки всё равно нужны для полного исправления. Почему провал правила с уровнем `block` обязан остановить задачу, разобрано в [шаге 11](#step-11).

Пустой список здесь означает ровно одно: отчёт не содержит проваленных правил.

> 🎒 **На пальцах.** Представь судью на соревновании роботов. Перед ним карточки от нескольких инспекторов: «прочность — пройдена», «безопасность — провалена», «внешний вид — замечание». Судья не испытывает робота заново и не прекращает читать после карточки о безопасности. Он переносит все непройденные пункты в итоговый протокол, сохраняя отметку каждого инспектора.

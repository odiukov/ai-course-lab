У тебя уже есть три отдельных счёта: одиночная картинка в [шаге 13](#step-13), набор в [шаге 15](#step-15), видео в [шаге 16](#step-16). Пока ты хочешь узнать одно число, всё нормально. А теперь попробуй ответить на вопрос из [шага 5](#step-5) — что тяжелее — и тебе придётся руками позвать три разных куска кода, каждый со своими аргументами, и не перепутать, где 2, а где 3.

Отсюда и следующая функция: `scenario_tokens`. Одна точка входа, которая принимает название сценария и его параметры, а возвращает одно целое число — сколько визуальных tokens уйдёт в LLM.

Внутри — три ветки. Для одиночной картинки: число тайлов плюс миниатюра, каждый через `pooled_tokens` из [шага 11](#step-11) с фактором 2. Для набора: количество картинок, каждая по 729 без нарезки и без пулинга. Для видео: количество кадров, каждый через `pooled_tokens` с фактором 3.

На что смотреть, пока пишешь.

Не вписывай 182 и 81 числами. Они должны приехать из `pooled_tokens` — иначе, поменяв фактор, ты получишь старое число и не поймёшь почему.

Миниатюра — отдельное слагаемое. AnyRes-9 из [шага 12](#step-12) — это десять кусков, не девять. Забудешь — получишь 1638 вместо 1820, и ошибка выглядит правдоподобно.

Неизвестное название сценария не должно тихо возвращать ноль. Ноль в бюджете читается как «всё влезло» — самый неприятный вид молчащей ошибки.

И проверь три числа сразу: 1820, 4374, 2592. Если какое-то выпало из полосы 2000–4400 из [шага 7](#step-7) далеко — сломана конкретная ветка, а не арифметика.

> 🎒 **На пальцах.** Одно окно в приёмной. За стеклом три разных формы: заявление, комплект справок, видеозапись. Посетитель не выбирает, какую папку достанет сотрудник, — он говорит, с чем пришёл, и получает одну квитанцию с итоговой суммой. Твоя `scenario_tokens` — это то самое окно: снаружи один вопрос и один ответ, а три разные папки живут внутри и наружу не торчат.

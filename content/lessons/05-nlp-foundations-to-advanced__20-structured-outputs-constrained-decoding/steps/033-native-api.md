title: Родной structured output API применяет ограничения на стороне вендора

Ты отправляешь модели отзыв «Еда была холодной» и хочешь получить одно из трёх значений: `positive`, `negative` или `neutral`. Можно поднять локальную модель и самостоятельно встроить цикл из [шага 18](#step-18). Но если модель уже работает на сервере провайдера, управлять её логитами со своей машины ты не можешь.

Родной structured output API решает это на стороне сервера. Вместе с текстом ты передаёшь JSON Schema: результат должен быть объектом, поле `sentiment` обязательно, а его значение выбирается из заданного `enum`. Провайдер компилирует поддерживаемую схему во внутренние ограничения и применяет их непосредственно во время генерации. Тебе возвращается уже разобранный результат, например через `response.output_parsed`, а не строка, которую ещё нужно уговаривать быть JSON.

Это именно техническое ограничение из [шага 4](#step-4), а не более настойчивая формулировка промпта. Модель не может выдать четвёртую метку вроде `mixed`, если такая строка запрещена схемой. При этом тебе не нужны локальная модель, собственный сервер инференса и отдельная библиотека constrained decoding.

Цена удобства — привязка к возможностям провайдера: набор поддерживаемых конструкций схемы, формат запроса и поведение API определяет он. Перенос к другому сервису может потребовать переделки интеграции. Ты отдаёшь провайдеру не только вопрос, но и форму допустимого ответа — а он обеспечивает её внутри генерации.

> 🎒 **На пальцах.** Представь банковский терминал, где ты выбираешь назначение платежа. Ты не печатаешь ответ вручную: экран предлагает только три кнопки — «товары», «услуги» и «перевод». Ограничение встроено самим банком, поэтому четвёртый вариант ввести нельзя. Пользоваться удобно, но набор кнопок и правила терминала контролирует банк, а не ты.

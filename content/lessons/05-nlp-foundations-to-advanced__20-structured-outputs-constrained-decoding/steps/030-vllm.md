Ты запускаешь локальную модель для десятка приложений. Одному нужен JSON с карточкой товара, второму — строка по регулярному выражению, третьему — один вариант из `approve`, `reject` и `review`. Писать для каждого приложения собственный цикл генерации из [шага 18](#step-18) неудобно: придётся отдельно управлять моделью, маской, состоянием грамматики и завершением.

vLLM переносит эту работу внутрь сервера инференса — программы, которая принимает запросы к модели и организует их выполнение на GPU. Вместе с промптом клиент передаёт ограничение: `guided_json`, `guided_regex`, `guided_choice` или `guided_grammar`. Например, `guided_json` содержит JSON Schema, которой должен соответствовать ответ.

Сервер выбирает настроенный движок — Outlines, XGrammar или lm-format-enforcer — и превращает ограничение в правила допустимого продолжения. Дальше при каждом токене внутри обычной генерации срабатывает знакомая по [шагу 5](#step-5) обработка логитов: движок учитывает текущее состояние конкретного запроса, а сэмплер получает только разрешённые варианты.

Для приложения это важная граница ответственности. Оно описывает требуемую форму, но не реализует автомат и не вмешивается в выбор каждого токена. При этом vLLM продолжает заниматься своей серверной работой: принимает параллельные запросы, объединяет вычисления и загружает GPU. Guided decoding становится параметром запроса, а не отдельным самодельным генератором.

> 🎒 **На пальцах.** Представь большую типографию. Один заказ просит визитку строго по шаблону, другой — наклейку с номером определённого вида. Клиент приносит макет и правила, но не стоит у печатного станка, проверяя каждую букву. Типография сама подключает нужный трафарет к конкретному заказу, не останавливая остальные. vLLM так же совмещает общую очередь генерации с индивидуальными ограничениями каждого запроса.

title: Валидный JSON ещё не означает соответствие схеме задачи

Ты подключаешь отчёт о расходах и просишь модель вернуть сумму покупки. В ответ приходит:

```json
{"sum": "1250 рублей"}
```

Парсер принимает строку без жалоб: кавычки закрыты, скобки на месте, JSON валиден. Но следующий сервис ждёт поле `amount` с числом и поле `currency` со значением из списка `RUB`, `EUR`, `USD`. Для него ответ бесполезен — хотя синтаксически в нём нет ни одной ошибки.

Здесь сталкиваются два разных правила. JSON-режим проверяет только форму самого JSON: можно ли его разобрать как объект, массив, строки и числа. Он не знает, какие поля нужны твоему приложению, какие из них обязательны и допустима ли строка там, где ожидается число. Поэтому валидными окажутся и `{"message":"привет"}`, и `{}`, и объект с неожиданными названиями полей.

Контракт задачи появляется лишь тогда, когда ты передаёшь полную схему: обязательные поля, их типы, допустимые значения и ограничения. Как отмечено в [шаге 33](#step-33), родной structured output API может технически удерживать вывод в этих границах — но только если получил сами границы. Режим «верни какой-нибудь JSON» их не угадает.

При этом соответствие схеме ещё не доказывает, что значение правдиво: эту границу мы разобрали в [шаге 26](#step-26). Схема отвечает не за истину, а за совместимость ответа с твоим конвейером.

> 🎒 **На пальцах.** Представь камеру хранения с ячейками «номер», «размер» и «срок». Аккуратно подписанная коробка — это валидный JSON. Но если на ней написано только «вещи Пети», автомат не поймёт, куда её поставить. Схема — это бланк с нужными ячейками: подпись должна быть не просто аккуратной, а пригодной для конкретной системы.

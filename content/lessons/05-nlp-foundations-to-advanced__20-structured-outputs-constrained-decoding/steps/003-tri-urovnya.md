Представь, что ты собираешь один классификатор для трёх разных сред: быстрый прототип, облачный сервис и локальный сервер. Во всех случаях нужен один и тот же формат, но управлять моделью ты будешь на разных уровнях.

В прототипе ты пишешь в промпте: «Верни только JSON». Это самый простой путь, но инструкция действует как просьба. Модель может нарушить её — именно эту проблему ты видел в [шаге 1](#step-1).

В облачном сервисе можно передать схему через родной API провайдера: например, `response_format`, tool use или JSON-режим. Здесь формат контролирует уже не только текст промпта — сам сервис берёт на себя соблюдение поддерживаемой схемы. Это заметно надёжнее, но решение привязано к возможностям и интерфейсу конкретного вендора.

На локальном сервере доступен третий уровень — constrained decoding, то есть генерация с техническими ограничениями. На каждом шаге модель предлагает возможные продолжения, а система запрещает выбирать токены, которые сделают результат невалидным. Модель может «хотеть» добавить пояснение, но выбрать его не сможет.

Важно: гарантируется форма, а не смысл. Валидный ответ всё ещё может содержать неверную метку. Зато ошибка из [шага 2](#step-2), когда правильный смысл теряется из-за лишнего текста, устраняется по построению.

> 🎒 **На пальцах.** Ты заказываешь печенье в форме звезды. В промпте ты просто просишь пекаря не ошибиться. Родной API — фабрика выдаёт тебе свою фирменную форму, но пользоваться ею можно только на этой фабрике. Constrained decoding — твоя металлическая вырубка: тесто физически не выйдет за контур. Вкус она не гарантирует, зато форма каждой заготовки будет правильной.

У тебя уже есть агент как запись из [шага 9](#step-9) и список видимых инструментов из [шага 11](#step-11). Guardrails пока лежат в этой записи мёртвым грузом: список есть, а вызвать его некому. Пиши `run_guardrails`.

Пусть на вход приходят три вещи: список guardrails, стадия (`"input"`, `"output"` или `"tool"`) и полезная нагрузка — текст запроса пользователя, текст ответа или словарь аргументов инструмента. Каждый guardrail — тоже запись: имя, стадия, к которой он приписан, и функция проверки, которая возвращает «сработало» или «чисто».

Первая ловушка — стадия. В списке лежат все проверки агента вперемешку, и на входе нельзя запускать ту, что помечена `"output"`: она ждёт готового ответа, а его ещё нет. Значит, сначала фильтруй по стадии, потом запускай.

Вторая ловушка тоньше. Тянет пройти все проверки, собрать список результатов и уже потом решить, что делать. Но tripwire из [шага 15](#step-15) — это исключение, а не запись в отчёте. Первая сработавшая проверка обрывает всё: остальные не запускаются, потому что дальше идти всё равно некуда. Тип исключения бери по стадии — `InputGuardrailTripwireTriggered` для входа, `OutputGuardrailTripwireTriggered` для выхода.

И проверь два скучных случая. Guardrails нет вообще — функция тихо пропускает дальше, а не падает. Проверки есть, но ни одна не сработала — верни их результаты, они пригодятся для спанов трассировки.

Порядок в списке — твоя ответственность: дешёвую проверку по ключевым словам ставь раньше той, что дёргает модель.

> 🎒 **На пальцах.** Медсестра перед прививкой читает вопросы по списку: температура, аллергия, лекарства. Ты отвечаешь «да» на аллергию — она закрывает список и отправляет тебя к врачу. Про лекарства уже не спросит: смысла нет, укола сегодня не будет. И вопросы для выписки — из другого списка, их она на входе не задаёт.

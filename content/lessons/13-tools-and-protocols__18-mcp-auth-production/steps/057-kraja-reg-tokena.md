Токен из [шага 24](#step-24) выглядит скучной технической деталью: сервер выдал `client_id`, а рядом `registration_access_token` — чтобы клиент потом мог поправить свою запись. Ну поправить и поправить. Что там править-то?

Правится, например, `redirect_uris`. То есть адрес, куда сервер авторизации отправит код после согласия пользователя. Представь: токен утёк — попал в лог, в скриншот, в публичный репозиторий вместе с конфигом. Злоумышленник делает один запрос на изменение записи и дописывает в список свой адрес. Больше он не делает ничего.

Теперь он запускает собственный поток авторизации: `client_id` — публичное значение, секрета у клиента нет ([шаг 25](#step-25)), `code_challenge` он считает сам. Пользователь видит экран согласия — и на нём знакомое имя доверенного клиента, без единого предупреждения. Код прилетает на дописанный адрес, обменивается на токен.

Теперь посмотри на свой валидатор из [шага 51](#step-51). Подпись верна. `iss` в списке разрешённых. `aud` — твой канонический URI. `exp` не истёк. Скоуп на месте. Все четыре проверки проходят, потому что токен настоящий: его выдал честный сервер честному клиенту.

Поэтому такой токен — не «ещё один пароль», а право переписывать конфигурацию доверия. Отсюда три правила из [шага 28](#step-28): хранить хешем, требовать открытое значение на каждое изменение, менять при малейшем подозрении. И заметь контраст с CIMD ([шаг 17](#step-17)): там менять-то нечего — кто владеет доменом, тот и владеет `client.json`.

Строкой сравнения это не закрыть: `redirect_uri` совпадает с зарегистрированным — его и зарегистрировал злоумышленник.

> 🎒 **На пальцах.** В школе есть список тех, кому можно забрать ребёнка. Поменять список можно по кодовому слову — оно у родителей. Кодовое слово подслушали, в список вписали чужого. Охранник на выходе всё делает правильно: сверяет фамилию со списком, фамилия там есть, ребёнка отдаёт. Ошибки на выходе нет вообще. Ошибка была в тот момент, когда кодовое слово перестало быть тайной.

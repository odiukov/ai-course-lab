id: 029-check-registraciya
type: check
title: 'Проверка: CIMD, DCR или предварительная регистрация'
source_anchor: >-
  ### RFC 7591 — Dynamic Client Registration (fallback / backwards
  compatibility)
check:
  - question: >-
      IdP поддерживает только динамическую регистрацию через POST /register, а
      CIMD недоступен. Клиент работает на ноутбуке пользователя. Какие параметры
      регистрации корректны?
    options:
      - >-
        token_endpoint_auth_method: none, response_types: ["code"] и loopback
        redirect URI; обмен кода защищает PKCE
      - >-
        token_endpoint_auth_method: client_secret_post; выданный сервером секрет
        клиент хранит внутри приложения
      - >-
        token_endpoint_auth_method: none и response_types: ["token"]; публичному
        клиенту следует получать токен напрямую
    correct: 0
    explanation: >-
      Приложение на пользовательском устройстве не может надёжно хранить
      client_secret, поэтому регистрируется как публичный клиент. Оно использует
      authorization code и PKCE, а не устаревшую прямую выдачу токена.
  - question: >-
      Чем опасен открытый эндпоинт /register без ограничения частоты запросов по
      исходному IP?
    options:
      - >-
        Только временным увеличением сетевого трафика: регистрация не изменяет
        состояние сервера
      - >-
        Злоумышленник сможет массово создавать клиентские записи и расходовать
        хранилище и идентификаторы
      - >-
        Любой зарегистрированный клиент автоматически получит право менять
        redirect URI остальных клиентов
    correct: 1
    explanation: >-
      Каждая успешная регистрация создаёт запись и выделяет client_id. Поэтому
      лимит нужно проверять до запуска регистратора: отказ после записи уже не
      предотвращает исчерпание ресурсов.
---

Тут проверяем, умеешь ли ты выбрать путь регистрации под конкретный IdP и не испортить его деталями. После [шагов 17](#step-17)–[19](#step-19) и [23](#step-23)–[28](#step-28) у тебя три варианта: CIMD (сервер сам забирает client.json по URL), DCR через POST /register (теперь MAY, живёт ради обратной совместимости) и предварительная регистрация руками — та самая переписка с администратором из [шага 2](#step-2).

Спотыкаются обычно на двух местах. Первое: тянутся к client_secret, потому что «клиент же должен себя доказать» — а клиент стоит на ноутбуке пользователя, и секрет оттуда достанут. Второе: ставят рейт-лимит после регистратора, где он уже ничего не спасает.

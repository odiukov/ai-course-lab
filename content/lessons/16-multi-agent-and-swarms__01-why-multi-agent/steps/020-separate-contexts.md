В журнале сообщений лежат три записи: исследователь отправил кодеру выжимку документации, кодер передал ревьюеру решение, а ревьюер написал оркестратору замечания. Если просто склеить все записи, каждый агент снова увидит общую переписку — и разделение ролей потеряет смысл.

Поэтому `multi_agent_contexts` собирает не один текст, а отдельный контекст для каждого агента. Для кодера функция берёт его `inbox` из [шага 18](#step-18), для ревьюера — его, для оркестратора — свой. Получается набор независимых текстов, связанных с именами получателей: у каждого агента есть собственная «папка» с нужными сообщениями.

Важно различать общий журнал и контекст агента. Журнал хранит все сообщения и нужен системе для координации. Контекст — это только та часть журнала, которую конкретный агент получит на вход. Одно и то же сообщение остаётся в общем списке, но попадёт лишь в контекст указанного получателя. Если исследователь прочитал 50 тысяч токенов документации, а кодеру отправил краткую выжимку, ревьюер позже увидит результат кодера, но не исходную документацию.

Именно адрес сообщения определяет, какое окно оно займёт. Общая история может расти, а рабочие столы агентов остаются раздельными.

> 🎒 **На пальцах.** Представь гостиницу с тремя гостями и стойкой администратора. На стойке лежат все конверты, но сотрудник раскладывает их по номерам на имени получателя. Письмо для комнаты 204 не копируют в комнаты 301 и 407. `multi_agent_contexts` делает такую раскладку целиком: берёт общую стопку и готовит отдельную стопку для каждого агента.

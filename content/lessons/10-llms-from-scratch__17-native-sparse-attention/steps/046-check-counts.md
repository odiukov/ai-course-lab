  - question: >-
      Почему вклад выбранной ветки в число просмотренных ключей равен k·l, а не
      k?
    options:
      - Каждый из k выбранных блоков раскрывается в l несжатых токенов
      - Каждый выбранный блок сравнивается с каждым из l запросов
      - Параметр k автоматически умножается на размер локального окна
      - Сжатая ветка повторяет каждый выбранный ключ l раз
    correct: 0
    explanation: >-
      Top-k выбирает блоки, а attention выбранной ветки работает с исходными
      токенами внутри них. Поэтому 4 блока по 32 токена дают 4·32 = 128 ключей.
  - question: Как определяется вклад сжатой ветки в число ключей на один запрос?
    options:
      - По одному ключу на каждый исходный токен
      - По одному ключу-представителю на каждый блок последовательности
      - По одному ключу на каждый выбранный top-k блок
      - По числу токенов в локальном окне
    correct: 1
    explanation: >-
      Сжатая ветка заменяет каждый блок одним представителем. Поэтому при 1024
      токенах и блоках по 32 токена она просматривает 1024/32 = 32 ключа; это
      число блоков, а не размер одного блока.

После счёта из [шага 43](#step-43) и функции из [шага 44](#step-44) ты должен уметь сам собрать итог из трёх слагаемых для любых `l`, `k`, `w` — и понимать, какое число откуда пришло.

Спотыкаются обычно на двух местах. Первое: число 32 в раскладке `32 + 128 + 128` встречается дважды в разных ролях — как размер блока и как количество блоков, — и это совпадение конкретных цифр, а не правило. Второе: выбранная ветка отдаёт `k·l` **токенов**, а не `k` ключей; отсюда и разбор по слагаемым из [шага 21](#step-21).

И держи в голове, что 3.5× — это про игрушку на 1024 токена, а не про метод: почему на 64k та же арифметика даёт 25×, разобрано в [шаге 45](#step-45).

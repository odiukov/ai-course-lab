Ты написал уже целую полку функций: `make_block`, `block_append`, `block_replace`, `summarize_block`, `sleep_time_pass`. Работает на локальных словарях. И тут вопрос, который решает, будет ли это жить дальше: где всё это хранится по-настоящему?

Три честных варианта.

Первый — **Letta** (letta.com). Эталонная реализация того, что мы разбирали: три уровня из [шага 6](#step-6), блоки с пятью полями из [шага 10](#step-10), sleep-time агент из [шага 23](#step-23) — всё уже внутри. Можно поднять у себя, можно взять их облако.

Второй — **skills в Claude Agent SDK**. Присмотрись: skill — это именованный кусок инструкций, у него есть версия, и агент подтягивает его сам, когда он нужен. Это ровно блок из [шага 9](#step-9), только с знаниями вместо фактов о пользователе. Отдельного механизма учить не надо, ты его уже понял.

Третий — своё хранилище. Нужен контроль над бэкендом, у вас Postgres, security не пустит чужой сервис к данным. Нормальная причина.

И вот здесь самый практичный совет урока. Если пишешь своё — назови методы как в Letta: `block_append`, `block_replace`, `block_read`. Не «updateMemorySection», не «patchContext». Тогда переезд на Letta через год — это правка одного адаптера на пятьдесят строк. А со своими именами придётся переписывать агента: имена инструментов торчат в промпте, модель обучена звать их именно так.

Контракт API дешевле выбрать один раз, чем переименовать потом.

> 🎒 **На пальцах.** Как резьба на водопроводных трубах. Полдюйма — стандарт, и смеситель из любого магазина встаёт на место за десять минут. А если сантехник когда-то нарезал свою, нестандартную — новый смеситель ты не купишь: сначала переделка стены. Своё хранилище — это твой смеситель, и он может быть любым. Резьбу оставь стандартную.

Ты запускаешь трёх агентов: один собирает требования, второй ищет ограничения, третий предлагает план. Первый кладёт на доску JSON с целью, второй дописывает найденный запрет, а третий замечает новую запись и меняет решение. Кажется, будто такая архитектура появилась специально для LLM.

Теперь замени слово «агент» на **Knowledge Source** — «источник знаний». В модели Hayes-Roth 1985 года это был не склад данных, а специализированный исполнитель: например, один умел распознавать проблему, другой — предлагать следующий шаг, третий — проверять частичное решение. Каждый наблюдал общую доску и вступал в работу, когда её состояние подходило под его компетенцию.

Здесь важен порядок управления. Исполнителей не обязательно запускать по заранее жёсткой цепочке. Новая запись создаёт возможность для следующего вклада: один источник добавил ограничение — активировался другой; тот уточнил решение — появился повод для третьего. Такое управление называют **оппортунистическим**: система выбирает полезное действие по текущей ситуации на доске.

В современных системах формальные Knowledge Sources стали LLM-агентами, а частичные решения — структурированными объектами. Маршрутизация по темам из [шага 6](#step-6) и схемы конкуренции из [шагов 32](#step-32)–[36](#step-36) меняют реализацию, но не сам каркас. Новы модели и интерфейсы; цикл «увидел состояние — внёс вклад — открыл возможность другому» остался прежним.

> 🎒 **На пальцах.** Представь мастерскую, где чинят старый велосипед. Механик снимает колесо и пишет на общей карточке: «обод цел, спицы ослаблены». Эту запись замечает специалист по колёсам, натягивает спицы и отмечает, что теперь можно проверять тормоз. Мастера не идут по фиксированной очереди: каждый подключается, когда на карточке появляется работа именно для него. Карточка управляет эстафетой лучше, чем заранее составленный список.

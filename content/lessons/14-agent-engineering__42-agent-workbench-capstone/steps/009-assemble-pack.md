Ты запускаешь `python3 code/main.py`, а затем повторяешь команду из другой рабочей папки. Если сборщик ищет файлы относительно места запуска, во втором случае он либо ничего не найдёт, либо создаст `outputs` не там. Поэтому `assemble_pack` должна ориентироваться на расположение самого урока, а не на текущую папку терминала.

Открой заготовку функции и сохрани её сигнатуру. Внутри собери один предсказуемый маршрут:

1. Определи исходные файлы и каталог `outputs/agent-workbench-pack/`.
2. Создай канонические каталоги из [шага 6](#step-6).
3. Размести в них ровно 14 рабочих файлов и отдельный `VERSION`, перечисленные в [шаге 7](#step-7).
4. Для каждого файла используй решение `classify_pack_candidates` из [шага 4](#step-4): внутрь попадают переносимые контракты, а проектные данные остаются снаружи.
5. Запиши стабильный `README`: без текущего времени, случайных идентификаторов и абсолютных путей твоего компьютера.
6. Напечатай итоговое дерево, предварительно отсортировав относительные пути.

Смотри на сборку как на синхронизацию состояния, а не на накопление действий. Повторная запись файла по тому же адресу допустима; дописывание в конец README или создание нового каталога с датой — нет. Если обязательного исходника нет, функция должна завершиться понятной ошибкой, а не выпускать неполный пак. При успешной сборке `main.py` заканчивает работу с нулевым кодом.

Иными словами, `assemble_pack` получает известный набор деталей и каждый раз приводит каталог назначения к одной канонической форме из [шага 8](#step-8).

> 🎒 **На пальцах.** Представь автомат для фасовки набора карандашей: в коробке всегда должны лежать 14 карандашей в подписанных гнёздах и одна карточка `VERSION`. Автомат не подбрасывает новый карандаш при каждом нажатии — он заново проверяет каждое гнездо и кладёт нужный предмет на его место. Поэтому вчерашний запуск не меняет результат сегодняшнего.

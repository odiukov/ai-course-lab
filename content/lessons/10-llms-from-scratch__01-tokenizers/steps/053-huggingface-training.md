На игрушечном списке из десяти слов ты можешь сам пересчитать пары. Но что делать, если корпус занимает несколько гигабайт и разбит на десятки файлов? Передавать весь текст одной строкой в Python неудобно: понадобится лишняя память, а подсчёты будут медленными.

В `tokenizers` ты описываешь не отдельные склеивания, а весь конвейер:

```python
from tokenizers import Tokenizer
from tokenizers.models import BPE
from tokenizers.trainers import BpeTrainer
from tokenizers.pre_tokenizers import ByteLevel

tokenizer = Tokenizer(BPE())
tokenizer.pre_tokenizer = ByteLevel()

trainer = BpeTrainer(
    vocab_size=1000,
    special_tokens=["<pad>", "<eos>", "<unk>"],
)

tokenizer.train(["corpus.txt"], trainer)
```

`Tokenizer(BPE())` выбирает модель токенизации. `ByteLevel()` подготавливает текст на уровне байтов — это тот подход, который ты видел в [шагах 22](#step-22)–[24](#step-24). `BpeTrainer` задаёт цель обучения: здесь итоговый vocabulary должен содержать до 1000 токенов. Наконец, `train` получает пути к файлам корпуса, читает их и выполняет знакомую по [шагу 14](#step-14) последовательность подсчётов и склеиваний.

Тяжёлая работа выполняется реализацией на Rust, поэтому Python здесь остаётся пультом управления. После обучения один объект уже хранит vocabulary и порядок merges: вызов `encode` возвращает и текстовые куски, и их ID. Ты задаёшь файлы и параметры — библиотека превращает статистику всего корпуса в готовый токенизатор.

> 🎒 **На пальцах.** Представь типографию с пачками рукописей. Ты не складываешь все страницы на домашний стол и не отмечаешь повторения карандашом. Ты передаёшь типографии список коробок, выбираешь размер набора литер и правила обработки. Машины просматривают страницы, находят частые сочетания и изготавливают набор. После этого тот же цех может сразу набрать новую фразу готовыми литерами.

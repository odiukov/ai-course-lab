Пул потоков из [шага 11](#step-11) вернул тебе три результата, и лежат они в порядке завершения — Цюрих первым, Бангалор последним ([шаг 32](#step-32)). А модель ждёт три сообщения-ответа, каждое со своим id. Как их склеить?

Соблазн — идти по индексам: первый результат к первому вызову, второй ко второму. Работает ровно до первого запуска, где кто-то отработал быстрее. Дальше погода Цюриха уезжает в ячейку Токио.

Значит, `correlate_results` должна брать список вызовов и список результатов и сшивать их **по id**, а не по позиции. Внутри — словарь: id вызова как ключ, чтобы поиск нужного вызова не зависел от порядка. Ни номер в списке, ни имя инструмента ключом быть не могут: два `get_weather` в одном веере неотличимы по имени ([шаг 4](#step-4)).

На что смотреть, когда пишешь:

- каждый результат несёт id того вызова, из которого он родился, — тащи его с собой от старта потока до готового сообщения, а не восстанавливай потом;
- на выходе — ровно столько сообщений, сколько было вызовов: ни одного пропущенного, ни одного лишнего. Ошибка исполнителя — тоже результат, у неё тот же id;
- если пришёл id, которого нет среди вызовов, или один и тот же id пришёл дважды — это не мелочь, которую можно тихо проглотить. Пусть функция об этом кричит;
- порядок сообщений на выходе — порядок завершения, и это нормально ([шаг 33](#step-33)).

Поле с id у трёх провайдеров называется по-разному, но склейка внутри твоей функции одна.

Индекс — случайность конкретного запуска. Id — единственное, что связывает результат с вызовом.

> 🎒 **На пальцах.** Класс сдал контрольные, ты проверил их и раздаёшь обратно. Стопка перемешалась: проверенные лежали по мере проверки, а не по мере сдачи. Ты раздаёшь по фамилии на обложке — не по порядку в стопке. Тетрадь без фамилии не суёшь наугад первому попавшемуся: откладываешь и разбираешься. Фамилия — это id; порядок в стопке не значит ничего.

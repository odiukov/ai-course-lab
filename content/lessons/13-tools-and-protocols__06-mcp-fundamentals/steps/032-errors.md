Ты просишь у сервера `resources/read` с URI `file:///reports/q3.pdf`. Ответ приходит вовремя, но в конверте из [шага 4](#step-4) на месте `result` лежит `error`:

```json
{ "code": -32002, "message": "Resource not found", "data": { "uri": "file:///reports/q3.pdf" } }
```

Три поля вместо одной строки. Зачем такая роскошь?

Представь, что сервер вернул бы просто текст «не удалось прочитать». Клиенту с этим нечего делать: повторить запрос через секунду или сдаться навсегда? Сообщить модели, что файла нет, или что сервер прилёг? Строку для этого пришлось бы разбирать по словам — а формулировку автор сервера завтра поменяет.

Поэтому решение принимается по числу. Диапазон кодов пришёл из JSON-RPC: `-32601` — метод не найден, `-32602` — параметры не той формы, `-32603` — внутренняя ошибка сервера. MCP добавил в этот же список свой: `-32002` — ресурс не найден. Клиент смотрит на число и ветвится, не читая ни слова.

`message` — короткая подпись для лога, человеку на глаз. А подробности живут в `data`: какой именно URI не нашёлся, какой параметр не подошёл, что вместо него было доступно. Это поле свободной формы, и именно туда MCP складывает то, что помогает починить вызов.

Отдельно приглядись к `-32601`. Чаще всего он означает не поломку, а то самое нарушение контракта из [шага 27](#step-27): клиент попросил метод, которого сервер в `capabilities` не объявлял.

Код решает, что делать дальше. `data` объясняет, что чинить.

> 🎒 **На пальцах.** Письмо вернулось. На конверте — штамп из короткого казённого списка: «адресат выбыл», «отказ от получения». По штампу сортировочный автомат сам решает маршрут, не вчитываясь. А рядом приклеена бумажка от почтальона: «дом 14 снесён, жильцы на Садовой». Штамп — для машины, бумажка — для тебя. Убери бумажку — письмо всё равно доедет обратно, но ты не поймёшь, куда его переслать.

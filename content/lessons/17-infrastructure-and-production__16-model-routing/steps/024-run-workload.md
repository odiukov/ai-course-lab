Перед тобой пачка разных запросов: короткий чат, математическая задача, знакомый вопрос и сложный случай. Если запустить только один из них, роутер из [шага 21](#step-21) уже вернёт понятный результат. Но один удачный ответ ничего не говорит о поведении всей нагрузки.

В `run_workload` тебе нужно последовательно передать каждый запрос в `route_request` и собрать результаты в общую статистику. Для каждого ответа сохрани три величины: стоимость, потерю качества относительно дорогой модели и факт эскалации. Стоимость бери из результата маршрутизации — не повторяй внутри этой функции расчёты из `call_cost`, написанной на [шаге 7](#step-7).

Затем преврати накопленные суммы в средние показатели. Здесь легко ошибиться со знаменателем: средние стоимость и потеря качества относятся ко всем запросам, а доля эскалаций — только к запросам, прошедшим через cascade. Pre-route и ensemble не могли эскалировать, поэтому добавлять их в этот знаменатель нельзя. Если каскад ни разу не использовался, верни для его доли ноль, а не дели на ноль.

Проследи также, чтобы один запрос учитывался ровно один раз, даже если cascade или ensemble вызвал две модели. Внутренние вызовы уже отражены в стоимости результата. `run_workload` считает запросы, а не заново разбирает работу маршрутов.

> 🎒 **На пальцах.** Представь диспетчера службы доставки с журналом за день. Для каждой посылки он записывает итоговую цену, опоздание и необходимость подключить срочного курьера. В конце средняя цена считается по всем посылкам, но доля срочных подключений — только среди доставок, где такой курьер вообще мог понадобиться. Иначе разные строки журнала незаметно смешаются в одну неверную статистику.

Три вызова ушли одновременно: `search`, `get_weather`, `fetch_page`. Поиск вернулся через 40 мс, погода через 120, страница через 900. В твоём списке результатов они лежат в порядке прибытия — 1, 2, 3 по времени, но не по тому порядку, в котором модель их запросила.

Если сшить два списка по позициям — первый с первым, второй со вторым, — модель получит содержимое страницы под видом результата поиска. И самое неприятное: ничего не упадёт. Строки на месте, формат правильный, следующий `Thought` строится на подменённых данных.

Отсюда и задача: `correlate_results` берёт список вызовов (у каждого свой `tool_use_id` из [шага 33](#step-33)) и список пришедших результатов, а возвращает наблюдения, пришитые к своим вызовам по идентификатору, а не по месту в списке.

Ключевой разворот — идти циклом по вызовам, а не по результатам. Тогда каждый вызов гарантированно получит ровно один ответ.

Что проверить на входе, пока пишешь:

- результат с `tool_use_id`, которого нет среди вызовов, — лишний, его некуда пришить;
- два результата с одним `id` — надо решить, берёшь первый или это ошибка;
- вызов, для которого результата не пришло вовсе (таймаут), — не пропускай молча, подставь наблюдение об ошибке, как в [шаге 15](#step-15);
- сам `id` пустой или отсутствует — тоже строка-ошибка, а не исключение ([шаг 14](#step-14)).

Проверяй результатом не «функция вернула три штуки», а перемешанным входом: подай результаты в обратном порядке и убедись, что каждый лёг к своему вызову.

> 🎒 **На пальцах.** Кофейня в час пик. Ты заказал латте, бариста пишет на стакане твоё имя. Рядом ещё двое. Готово будет не по очереди: чей-то эспрессо выскочит первым. Именно поэтому имя пишут на стакане, а не раздают по порядку прихода. Убери надпись — и раздача по очереди начнёт работать ровно до первого напитка, который варится дольше.

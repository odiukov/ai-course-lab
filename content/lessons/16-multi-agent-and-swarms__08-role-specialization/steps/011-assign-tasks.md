Перед тобой три задачи: составить план, реализовать функцию и проверить результат. После [шага 9](#step-9) ты уже умеешь выбирать лучшую роль для одной задачи. Но теперь задач несколько — и легко незаметно вернуться к раздаче по очереди: первую планировщику, вторую исполнителю, третью критику.

Попробуй мысленно добавить четвёртую задачу — ещё одну проверку. По очереди она достанется верификатору только случайно. Значит, `assign_tasks` должна рассматривать каждую задачу независимо, как обсуждалось в [шаге 10](#step-10).

Функция получает коллекцию задач и доступные роли. Для каждой задачи она вызывает уже написанную `best_role`, а затем сохраняет пару «задача — выбранная роль» в результирующей структуре, которую требует заготовка. Саму формулу компетентности здесь повторять не нужно: она уже спрятана внутри функций из [шага 7](#step-7) и [шага 9](#step-9).

Обрати внимание на три детали. Не назначай роли по индексу задачи. Не удаляй выбранную роль из списка: одна сильная роль может подходить нескольким задачам. И не придумывай новое правило ничьей — `best_role` уже разрешает её единообразно.

Проверь себя на маленьком примере: если две задачи лучше всего выполняет verifier, обе должны получить verifier. Пустой список задач должен дать пустой набор назначений. Здесь функция не изобретает решения — она многократно применяет один надёжный выбор.

> 🎒 **На пальцах.** На сортировочной станции лежат посылки: хрупкая ваза, замороженные продукты и обычные книги. Диспетчер не раздаёт их грузовикам по кругу. Для каждой посылки он отдельно выбирает подходящую машину. Если двум партиям нужен рефрижератор, обе назначаются ему: правильное соответствие важнее красивой очереди.

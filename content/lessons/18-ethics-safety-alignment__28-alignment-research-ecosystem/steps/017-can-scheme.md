В тесте функции три входа включены: рассогласование целей, целенаправленность и ситуационная осведомлённость. Здесь ответ должен быть `true`. Затем ты выключаешь только последний вход — и ответ уже `false`, хотя два признака сохранились.

Напиши `can_scheme`, которая принимает три логических значения:

- `misaligned` — цели модели расходятся с ожидаемыми;
- `goal_directed` — модель действует ради результата;
- `situationally_aware` — модель понимает ситуацию, включая факт проверки.

Функция должна вернуть одно логическое значение: может ли сочетание признаков соответствовать схемящему поведению. Используй диагностическое правило из [шага 16](#step-16): необходимы все три опоры одновременно.

Особенно следи за двумя соблазнительными ошибками. Нельзя возвращать `true`, когда сработал хотя бы один признак или любые два из трёх. И не нужно заново выяснять намерения модели: функция получает уже готовые ответы по каждой опоре и только соединяет их по правильному правилу.

Перед запуском проверь крайние случаи мысленно. Три значения `true` должны дать `true`. Если хотя бы одно значение стало `false`, результат должен стать `false`. Готовый код здесь не копируй — подбери логическую операцию, которая требует одновременного выполнения всех условий.

> 🎒 **На пальцах.** Представь стартовую площадку с тремя обязательными ключами: один у инженера, второй у диспетчера, третий у руководителя запуска. Два повёрнутых ключа не означают «почти старт» — сигнал остаётся заблокированным. `can_scheme` работает так же: разрешающий результат появляется только при одновременном наличии всех трёх признаков.

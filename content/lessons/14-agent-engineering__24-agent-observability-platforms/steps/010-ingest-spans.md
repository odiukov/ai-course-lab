Ты отправляешь сборщику три спана: два относятся к сессии `session-42`, а у третьего нет идентификатора сессии. Если функция просто сложит всё в один список, отдельные события сохранятся, но восстановить пользовательский прогон уже не получится. Если же она создаст группу и для третьего спана, в данных появится выдуманная «безымянная сессия».

Твоя задача — дописать `ingest_spans`. Для каждого входного спана функция должна применить минимальный контракт из [шага 9](#step-9). Валидный спан нужно сохранить в группе с его `session_id`; невалидный — не допускать в хранилище. Когда идентификатор встречается впервые, создаётся новая группа, при следующих встречах спаны добавляются в уже существующую.

Проверь функцию на маленьком наборе вручную: две записи с одним `session_id`, одна — с другим и одна некорректная. После приёма должны остаться две сессии, причём первая содержит ровно два спана. Смотри не только на количество: поля принятого спана должны сохраниться целиком. Позже они понадобятся для поиска ошибок, guardrails и оценок судьи.

Пока не вычисляй длительность и не решай, успешна ли сессия. Здесь граница ответственности уже: принять корректные события и связать их с нужным пользовательским прогоном. Если эта связь потеряна при входе, последующие метрики её не восстановят.

> 🎒 **На пальцах.** Представь лабораторию, куда поступают пробирки с номером исследования. Лаборант кладёт пробирки с одинаковым номером в один лоток, а пробирку без номера не пристраивает «куда-нибудь»: иначе её результат припишут чужому пациенту. `ingest_spans` работает так же — проверяет маркировку и только после этого выбирает правильную сессию.

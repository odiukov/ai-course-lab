Ты запускаешь проверку три раза: первые две попытки падают, третья проходит. В JSONL появляются три корректные записи, но без связи они выглядят как три независимых запуска. Задача `retry_chain` — выполнить повторы так, чтобы из записей можно было восстановить именно эту последовательность.

Собери функцию вокруг одного правила: каждая новая попытка ссылается на непосредственно предыдущую. У первой записи `parent_command_id` должен явно означать отсутствие родителя, у второй — содержать `command_id` первой, у третьей — `command_id` второй. Не привязывай все повторы к первой команде: тогда потеряется порядок внутри цепочки, о котором шла речь в [шаге 21](#step-21).

На каждой итерации функция должна:

1. Выполнить тот же точный `argv`.
2. Создать для попытки новый уникальный `command_id`.
3. Собрать и сохранить feedback record через уже написанную `make_record` из [шага 16](#step-16).
4. Только после записи решить, нужен ли следующий повтор.
5. Перед следующей итерацией запомнить текущий `command_id` как родительский.

Проверь две границы: успешный `exit_code` останавливает цепочку, а лимит попыток считается вместе с первым запуском. Значение `exit_code: null` нельзя случайно принять за успех — это отсутствие проверяемого результата, как разобрано в [шаге 19](#step-19). Также убедись, что функция возвращает записи в порядке выполнения: ревьюеру важен путь от первого падения до финального исхода, а не только последняя зелёная строка.

> 🎒 **На пальцах.** Представь обращения в ремонтную мастерскую. На новой квитанции мастер пишет номер предыдущей: «повтор после заявки 41», затем «повтор после заявки 42». Последняя квитанция может сообщать «исправлено», но номера сохраняют весь путь ремонта. Если оставить только финальную бумагу, две неудачные попытки словно никогда не происходили.

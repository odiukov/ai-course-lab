Ты вводишь запрос «как отменить списание по подписке XQ-17» и получаешь странный результат: система находит общие статьи о возвратах, но пропускает инструкцию с точным кодом XQ-17. Если заставить дорогую модель внимательно сравнить запрос с каждым из миллиона фрагментов, ответ станет точнее — и неприемлемо медленным.

Поэтому широкий поиск из [шага 35](#step-35) превращают в воронку. Сначала dense bi-encoder быстро просматривает весь индекс и оставляет, например, тысячу смысловых кандидатов. Затем sparse-поиск добавляет документы с важными буквальными совпадениями вроде XQ-17. Его список объединяют с dense-списком через знакомый RRF из [шага 20](#step-20): позиции можно свести вместе, не притворяясь, что сырые оценки двух режимов означают одно и то же.

После этого до дорогой проверки доходят лишь лучшие 50 кандидатов. Multi-vector или cross-encoder рассматривает их внимательнее и переставляет так, чтобы наверху оказались действительно подходящие фрагменты. Здесь задача уже не найти пропущенное во всём корпусе, а точно различить несколько похожих результатов.

Каждый уровень сокращает объём работы для следующего: сначала скорость, затем полнота, в конце точность. Именно поэтому самый внимательный судья не начинает с миллиона вариантов.

> 🎒 **На пальцах.** Представь редакцию, куда пришёл миллион заметок. Первый секретарь быстро раскладывает их по темам. Корректор возвращает в стопку материалы с точным названием события, которые могли потеряться при грубой сортировке. Главный редактор внимательно читает только 50 финалистов и решает порядок публикации. Если поручить ему читать всё с первой строки, выпуск опоздает.

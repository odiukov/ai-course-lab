title: Переносим знакомый Recall@5 на сравнение вариантов chunking

Ты запускаешь fixed chunking и получаешь Recall@5 = 0,76. Затем режешь те же документы семантически — выходит 0,84. Кажется, победитель найден: во втором случае правильный фрагмент попал в пятёрку чаще.

Но есть ловушка. После нового chunking меняются сами чанки и их номера. Индекс `17` в fixed-разбиении может содержать нужный факт, а индекс `17` в semantic-разбиении — совсем другой текст. Поэтому нельзя механически передать обеим стратегиям один список `gold_idxs`. Для каждого варианта нужно заново связать запрос с его **релевантными чанками** — теми, где действительно есть свидетельство для ответа.

Дальше ты переносишь знакомый Recall@5 почти без изменений: кодируешь чанки выбранной стратегии, для каждого запроса берёшь пять ближайших и отмечаешь попадание, если среди них есть хотя бы один релевантный. Затем делишь число запросов с попаданием на общее число запросов.

Сравнение будет честным, только если неизменны документы, запросы, encoder, способ вычисления близости и `k=5`. Меняется одна причина — chunking. На 50 запросах рост с 0,76 до 0,84 означает не абстрактные «восемь процентов качества», а четыре дополнительных запроса, для которых нужный фрагмент оказался в топ-5.

Метрика не выбирает стратегию по названию. Она считает, сколько раз её границы помогли поиску донести свидетельство до ответа.

> 🎒 **На пальцах.** Представь музей с двумя каталогами: один делит экспозицию по залам, другой — по темам. Ты просишь принести пять карточек о конкретном экспонате. Сравнивать номера карточек бессмысленно: после перекаталогизации номер тот же, а содержимое другое. Сначала отметь правильные карточки в каждом каталоге, а затем посчитай, как часто хотя бы одна из них попадает в принесённую пятёрку.

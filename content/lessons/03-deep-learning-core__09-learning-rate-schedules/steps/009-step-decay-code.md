Ты проверяешь функцию на эпохах 29 и 30. Если обе дают `0.1`, граница потерялась; если на 29 уже получилось `0.01`, снижение сработало слишком рано. Именно на таких соседних значениях чаще всего обнаруживается ошибка.

Напиши `step_decay_schedule`, которая принимает начальный learning rate, коэффициент `gamma` и длину ступеньки `step_size`, а возвращает функцию расписания. Эту внутреннюю функцию вызывают с номером эпохи, и она выдаёт текущий learning rate.

Правило снижения уже разобрано в [шаге 8](#step-8). Здесь важно правильно превратить его в последовательность действий:

- определить, сколько полных отрезков длиной `step_size` уже прошло;
- столько раз применить `gamma` к начальному learning rate;
- вернуть получившееся число.

Смотри именно на **полные** отрезки. При `initial_lr = 0.1`, `gamma = 0.1` и `step_size = 30` ожидаются такие результаты:

```text
epoch 0  → 0.1
epoch 29 → 0.1
epoch 30 → 0.01
epoch 59 → 0.01
epoch 60 → 0.001
```

Для подсчёта полных отрезков пригодится целочисленное деление: остаток от неполной ступеньки не должен влиять на результат. Не записывай отдельные условия для эпох 30, 60 и 90 — функция должна работать с любым `step_size` и продолжать расписание дальше автоматически.

> 🎒 **На пальцах.** Представь шкафчик с лотками по 30 писем. Пока текущий лоток не заполнен, печать на письмах остаётся прежней. Тридцатое письмо закрывает первый лоток — и для следующей группы ты берёшь печать меньшего размера. Тебе не нужен список всех будущих переключений: достаточно посчитать, сколько полных лотков уже закрыто.

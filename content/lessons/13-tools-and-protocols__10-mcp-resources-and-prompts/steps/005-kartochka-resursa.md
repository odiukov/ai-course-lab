Ты открываешь список заметок и видишь двадцать результатов. Если сервер сразу вложит в ответ полный текст каждой заметки — по десять страниц в некоторых, — тебе придётся загрузить сотни страниц, хотя выбрать нужно одну. А если вернуть только загадочные адреса, выбрать будет невозможно.

`resources/list` решает именно эту задачу: выдаёт не содержимое ресурсов, а их карточки. Ответ выглядит так:

```json
{
  "resources": [
    {
      "uri": "notes://note-14",
      "name": "План поездки",
      "mimeType": "text/markdown",
      "description": "Маршрут и список вещей"
    }
  ]
}
```

Здесь `uri` позволяет однозначно указать ресурс, `name` даёт человеку понятное название, а `mimeType` сообщает формат данных — например, Markdown-текст или изображение PNG. Поле `description` необязательно: сервер добавляет его, если короткое пояснение помогает сделать выбор.

Обрати внимание, чего в карточке нет: самого маршрута, списка вещей и других данных заметки. Клиент сначала получает лёгкий каталог, показывает его тебе или модели, а уже после выбора отдельно запрашивает содержимое нужного ресурса. Это похоже на разделение «посмотреть варианты» и «открыть выбранное».

Значит, успешный `resources/list` не обязан отвечать на вопрос «что написано в заметке?». Его работа скромнее и важнее: дать достаточно признаков, чтобы ты понял, какую заметку стоит открыть.

> 🎒 **На пальцах.** Представь афишу кинофестиваля. В ней есть название фильма, номер показа, жанр и короткое описание, но нет самого двухчасового фильма. По афише ты быстро выбираешь сеанс, не просматривая все картины подряд. Карточка из `resources/list` работает так же: помогает найти нужный ресурс, оставляя его содержимое до отдельного запроса.

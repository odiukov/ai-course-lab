Ты вызываешь `summarize_pr`, а сервер отвечает: «Какой pull request и для кого резюме?» Формально сценарий существует, но пользоваться им нельзя без ручной переписки. Значит, аргументы должны заранее закрывать развилки, без которых результат неоднозначен.

Для `summarize_pr` задай обязательные `owner`, `repo`, `pr_number` и необязательный `audience` со значением по умолчанию вроде `team`. Номер указывает объект, а аудитория меняет глубину объяснения. Передавать весь текст PR аргументом не стоит: его можно получить через GitHub, а огромная строка только дублирует данные.

Для `triage_issue` понадобятся `owner`, `repo`, `issue_number`. Добавь необязательный `triage_policy`: например, имя набора правил проекта. Тело промпта должно потребовать проверить воспроизводимость, ожидаемое поведение, серьёзность и предложить метки — но не назначать их самостоятельно. Как обсуждалось в [шаге 2](#step-2), промпт описывает повторяемый сценарий, а не выполняет изменение.

У `release_notes` другой диапазон: обязательные `owner`, `repo`, `from_ref`, `to_ref` и необязательный `audience`. Здесь двух ссылок достаточно, чтобы однозначно определить изменения.

В схеме каждому аргументу дай понятное описание и явно отметь обязательность. А в теле, которое создаётся через `prompts/get` из [шага 24](#step-24), уже должны быть цель, нужные источники, формат ответа и правило на случай нехватки данных. Тогда после подстановки значений пользователь получает готовое задание, а не полуфабрикат.

> 🎒 **На пальцах.** Представь редактора, который раздаёт журналистам брифы. «Напиши материал о событии» — бесполезный бриф. Нужны событие, период и читатель; стиль можно оставить стандартным. Но складывать в бриф все стенограммы тоже не надо: журналист возьмёт их из архива. Хорошие аргументы называют работу однозначно, а сам промпт объясняет, как её выполнить.

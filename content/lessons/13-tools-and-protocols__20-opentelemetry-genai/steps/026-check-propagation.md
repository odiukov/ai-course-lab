check:
  - question: >-
      MCP-клиент вызывает сервер по stdio и не передаёт traceparent. Что
      появится в бэкенде трассировки?
    options:
      - 'Один трейс, в котором серверные спаны появятся с задержкой'
      - Два независимых трейса с разными trace id — клиентский и серверный
      - 'Один трейс, потому что бэкенд восстановит связь по имени сервера'
      - >-
        Только клиентский трейс: серверные спаны без traceparent не
        экспортируются
    correct: 1
    explanation: >-
      Без переданного контекста сервер создаёт новый trace id. Экспорт в один
      бэкенд не склеивает такие трейсы автоматически: сопоставлять их приходится
      по внешним признакам, например по времени.
  - question: >-
      Транспорт MCP — stdio. Куда помещать traceparent, пока штатное поле
      спецификации ещё не принято?
    options:
      - В HTTP-заголовок запроса
      - В имя метода JSON-RPC
      - В поле _meta каждого JSON-RPC-запроса
      - В стандартный поток ошибок серверного процесса
    correct: 2
    explanation: >-
      Stdio не передаёт HTTP-заголовки, поэтому traceparent приходится вручную
      включать в _meta каждого запроса. Поле _meta.traceparent пока лишь
      обсуждается в роадмапе спецификации на 2026 год.

После этого куска ты должен уметь глядя на пару «клиент — MCP-сервер» сказать, где именно потеряется trace id и куда его положить на этом транспорте: заголовок при streamable HTTP, `_meta` руками при stdio.

Спотыкаются обычно на двух вещах. Первая — кажется, что если оба сервиса шлют спаны в один бэкенд, они сами склеятся в один трейс. Не склеятся: без переданного контекста сервер заводит новый trace id, и у тебя два дерева вместо одного. Вторая — `_meta.traceparent` воспринимают как готовый стандарт. Пока это обсуждение в роадмапе, а класть поле нужно самому, в каждый запрос.

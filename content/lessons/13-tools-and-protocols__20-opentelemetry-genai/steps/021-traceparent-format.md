title: 'Заголовок traceparent: четыре поля через дефис'

У тебя в клиенте есть CLIENT-спан на вызов MCP-сервера ([шаг 10](#step-10)). На другой стороне провода сервер начинает свой спан — и генерирует ему новый trace id, потому что ничего не знает о твоём. Два трейса вместо одного, связывать их приходится по времени, на глазок.

Значит, серверу надо передать два числа: trace id всего трейса и span id того спана, который станет родителем ([шаг 7](#step-7)). Два отдельных заголовка? Тогда каждая библиотека назовёт их по-своему, и стыковка развалится. Поэтому в стандарте W3C всё уложено в один заголовок с фиксированным именем — `traceparent`, а внутри четыре поля через дефис:

`00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`

Первое поле — версия формата, сейчас `00`. Второе — trace id, ровно 32 шестнадцатеричных символа. Третье — span id родителя, ровно 16. Четвёртое — флаги: `01` значит «этот трейс пишется, записывай и ты», `00` — «не пишется». Всего 55 символов, длины жёсткие: ведущие нули не выкидывают, иначе поле перестанет читаться по позиции.

Дальше сервер берёт trace id из второго поля себе, а третье поле кладёт в parentSpanId своего корневого спана — и его дерево прирастает к твоему.

По Streamable HTTP это обычный заголовок. По stdio заголовков нет вовсе, поэтому ту же строку кладут руками в поле `_meta` каждого JSON-RPC-запроса. Формат один и тот же — меняется только конверт.

> 🎒 **На пальцах.** Бирка на одежде: `AW24-1147-BLK-42`. Не четыре ярлыка, а один код, где каждая позиция значит своё — сезон, модель, цвет, размер. Кассир не гадает, что где: длины фиксированы, и «BLK» нельзя сократить до «BK». Так же и traceparent: одна строка, четыре поля, длины жёсткие — и любая библиотека на том конце разбирает её одинаково.

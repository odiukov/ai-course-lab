check:
  - question: >-
      У всех запросов одинаковые system, tools и context, но timestamp и user ID
      меняются. Какой порядок лучше сохранит общий префикс?
    options:
      - 'timestamp, user ID, system, tools, context, question'
      - 'system, tools, context, timestamp, user ID, question'
      - 'system с timestamp внутри, tools, context, user ID, question'
    correct: 1
    explanation: >-
      Стабильные части идут первыми и остаются общим префиксом. Динамические
      поля появляются лишь после них, поэтому расхождение начинается позднее.
  - question: >-
      Что произойдёт, если добавить уникальный user ID в самое начало системного
      промпта?
    options:
      - 'Дерево сможет переиспользовать весь system, кроме самого ID'
      - >-
        Совпадение оборвётся в начале, и почти весь следующий текст придётся
        вычислять заново
      - 'Положение ID не повлияет на кэш, если tools и context одинаковы'
    correct: 1
    explanation: >-
      RadixAttention сравнивает токены строго слева направо. Раннее различие не

Здесь важно не просто вспомнить порядок из [шага 10](#step-10), а применить его к полям, которые меняются в каждом запросе. Timestamp или user ID в начале заставят дерево разойтись почти сразу: одинаковые `system`, `tools` и `context`, стоящие дальше, уже не спасут переиспользование.

Собери промпт так, чтобы сначала шли стабильные части, затем динамические данные, а вопрос пользователя — в конце. Частая ловушка: считать timestamp «служебной мелочью». Для дерева это полноценные токены, и даже одна ранняя перемена обрывает совпадение.

> 🎒 **На пальцах.** Ты раскладываешь стопку анкет и хочешь одним движением проверить одинаковые страницы. Если на обложке каждой анкеты напечатан уникальный номер и время, стопка различается с первого листа. Перенеси эти данные ближе к концу — и все одинаковые страницы в начале можно обработать вместе.

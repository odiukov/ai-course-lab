После канонизации у тебя есть три факта: `("Tim Cook", "P108", "Apple")`, `("Tim Cook", "P19", "Mobile")` и `("Steve Jobs", "P108", "Apple")`. Если оставить их одним списком, для каждого обращения к Tim Cook придётся просматривать список целиком. На трёх элементах это незаметно, но на тысячах — уже лишняя работа.

Напиши функцию `build_graph(triples)`, которая соберёт список смежности из [шага 23](#step-23). Она должна вернуть словарь, где ключ — субъект, а значение — список пар `(relation, object)`. Для примера выше у ключа `"Tim Cook"` окажутся две пары, а у `"Steve Jobs"` — одна.

Пройди по входным triple по очереди. Для каждого возьми `subject`, `relation` и `object`, найди список субъекта в словаре и добавь туда новое ребро. Если субъект встретился впервые, сначала создай для него пустой список. В конце верни собранный словарь.

Обрати внимание на две детали:

- один субъект может иметь несколько рёбер — прежнее значение нельзя перезаписывать;
- объект не становится ключом автоматически: функция хранит только исходящие рёбра.

На вход здесь должны попадать уже канонизированные triple из [шага 21](#step-21), иначе одинаковые по смыслу отношения разойдутся по разным обозначениям. Проверь функцию на пустом списке, одном triple и двух triple с общим субъектом. Главный сигнал ошибки прост: если у Tim Cook осталось только последнее ребро, список был заменён вместо пополнения.

> 🎒 **На пальцах.** Представь секретаря, раскладывающего поручения по именным папкам. Первое поручение для Tim Cook создаёт папку, второе ложится туда же, а поручение для Steve Jobs открывает другую. Секретарь не заводит папку Apple только потому, что это название встретилось внутри поручения: папки создаются по отправителям, то есть по субъектам.

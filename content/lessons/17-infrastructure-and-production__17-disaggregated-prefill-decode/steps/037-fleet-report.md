Ты подставляешь профиль нагрузки, сеть, число GPU и цену — и вместо решения получаешь россыпь времён, байтов и расходов. По отдельности числа верны, но ответить «стоит ли разделять парк?» всё ещё трудно. Эту россыпь и должен собрать `fleet_report`.

Сделай функцию координатором уже написанных расчётов. Она не должна заново считать задержки вручную. Получи длительность фаз через `phase_ms` из [шага 6](#step-6), совмещённую задержку через `colocated_ms` из [шага 8](#step-8), размер KV-кэша и налог сети — функциями из [шагов 13](#step-13) и [15](#step-15). Затем используй `disaggregated_ms` из [шага 18](#step-18) и `disagg_gain_ms` из [шага 20](#step-20).

После расчётов собери единый результат в формате, заданном на [шаге 36](#step-36): параметры нагрузки, сетевой налог, задержки обеих архитектур, выигрыш, конфигурацию парка и стоимость. Сохраняй исходные миллисекунды и байты без преждевременного округления — иначе небольшая погрешность несколько раз попадёт в последующие вычисления. Округлять стоит только значения, предназначенные для вывода.

Особенно внимательно проверь знак выигрыша: положительное значение означает преимущество дезагрегации, отрицательное — её проигрыш, как разобрано на [шаге 21](#step-21). Итоговый отчёт должен позволять принять решение по одной структуре данных, а не по догадке из нескольких несвязанных чисел.

> 🎒 **На пальцах.** Представь табло управляющего сетью кинотеатров. Кассы отдельно сообщают число зрителей, залы — занятость, бухгалтерия — расходы. Пока данные лежат в трёх ведомостях, решение о новом расписании принять трудно. `fleet_report` работает как единое табло: ничего не измеряет повторно, а правильно собирает готовые показатели и показывает, какой вариант парка действительно лучше.

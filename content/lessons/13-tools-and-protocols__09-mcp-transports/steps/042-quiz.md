  - question: >-
      Ты подключаешь сервер, который клиент сам запускает как дочерний процесс
      на той же машине. Что произойдёт, если вместо stdio взять Streamable HTTP?
    options:
      - >-
        Ничего не изменится: транспорты взаимозаменяемы, разница только в
        скорости
      - >-
        Придётся поднимать порт, проверять Origin и управлять идентификаторами
        сессий без необходимости для локального дочернего процесса
      - >-
        Сервер не сможет отправлять клиенту события, потому что HTTP работает
        только в одну сторону
    correct: 1
    explanation: >-
      Для stdio жизненный цикл дочернего процесса уже задаёт границы сессии.
      Streamable HTTP добавляет сетевой порт, проверку Origin и управление
      session id — механизмы, необходимые при сетевом взаимодействии.
  - question: >-
      Клиент отправляет POST с заголовком Mcp-Session-Id и получает 404. Что
      правильно сделать?
    options:
      - Повторить тот же запрос с прежним session id после паузы
      - Заново пройти рукопожатие и получить новый session id
      - Переоткрыть GET-канал и продолжить с last-event-id
    correct: 1
    explanation: >-
      Ответ 404 означает, что сервер больше не знает указанную сессию: она
      истекла или была отозвана. Повтор с прежним идентификатором не поможет,
      поэтому требуется новая инициализация.
  - question: >-
      В allowlist находится https://app.example.com. Какой Origin должен пройти
      проверку?
    options:
      - 'https://app.example.com.attacker.net'
      - 'https://evil.com/?ref=https://app.example.com'
      - 'https://app.example.com'
    correct: 2
    explanation: >-
      Origin проверяется на точное совпадение с разрешённым значением. Остальные
      варианты лишь содержат разрешённую строку, но относятся к другим
      источникам.
  - question: >-
      SSE-поток оборвался во время долгой операции. Чем правильная реакция
      отличается от переинициализации сессии?
    options:
      - >-
        Клиент переоткрывает GET с прежним session id и last-event-id, поскольку
        потерян только канал
      - >-
        Клиент начинает сессию заново, поскольку обрыв потока аннулирует session
        id
      - 'Клиент повторяет исходный POST, чтобы сервер снова запустил операцию'
    correct: 0
    explanation: >-
      Обрыв SSE-соединения сам по себе не уничтожает сессию. Прежний session id
      сохраняется, а last-event-id позволяет продолжить поток с нужного события
      без повторного запуска операции.

Дальше в курсе ты будешь подключать реальные серверы — и почти каждая проблема там сводится к одному из четырёх вопросов этого урока: какой транспорт вообще уместен, живёт ли ещё сессия, кто стучится на твой порт и с какого места продолжать после обрыва.

Спотыкаются обычно на двух вещах. Первая — путают «повторить» и «начать заново»: 502, 504 и обрыв SSE лечатся повтором, а 404 на session id — только новым рукопожатием. Вторая — проверка `Origin` «по вхождению» вместо точного совпадения, из-за которой allowlist перестаёт что-либо защищать.

Проверь себя на четырёх вопросах — и можно идти к настоящим подключениям.

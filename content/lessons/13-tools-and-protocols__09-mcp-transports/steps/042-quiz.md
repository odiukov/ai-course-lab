  - question: >-
      Ты подключаешь сервер, который клиент сам запускает как дочерний процесс
      на той же машине. Что произойдёт, если вместо stdio взять Streamable HTTP?
    options:
      - >-
        Ничего не изменится: транспорты взаимозаменяемы, разница только в
        скорости
      - >-
        Придётся поднимать порт, следить за Origin и выдавать session id —
        работа, которая на одной машине не даёт ничего
      - >-
        Сервер не сможет отправлять клиенту события, потому что HTTP работает
        только в одну сторону
    correct: 1
    explanation: >-
      Процесс уже сам себе сессия и сам себе граница доверия: пока клиент жив,
      жив и канал. Сетевой транспорт добавляет порт, allowlist и session id —
      всё это нужно только когда между сторонами есть сеть.
  - question: >-
      Клиент шлёт POST с заголовком Mcp-Session-Id и получает 404. Что правильно
      сделать?
    options:
      - Повторить тот же запрос с тем же session id через паузу
      - Пройти рукопожатие заново и получить новый session id
      - Переоткрыть GET-канал и продолжить с last-event-id
    correct: 1
    explanation: >-
      404 означает, что сервер такой сессии больше не знает: она истекла или её
      отозвали. Повторы с мёртвым id будут возвращать тот же 404, помогает
      только новая инициализация.
  - question: >-
      В allowlist лежит https://app.example.com. Какой Origin должен пройти
      проверку?
    options:
      - 'https://app.example.com.attacker.net'
      - 'https://evil.com/?ref=https://app.example.com'
      - 'https://app.example.com'
    correct: 2
    explanation: >-
      Сравнивать надо на точное совпадение целой строки. И первый, и второй
      вариант содержат разрешённое значение как подстроку, но принадлежат чужим
      доменам.
  - question: >-
      SSE-поток оборвался на середине длинной операции. Чем отличается
      правильная реакция от переинициализации сессии?
    options:
      - 'Переоткрыть GET с last-event-id — сессия жива, потерян только канал'
      - >-
        Начать сессию заново: после обрыва потока старый session id
        недействителен
      - 'Повторить исходный POST, чтобы сервер выполнил операцию с начала'
    correct: 0
    explanation: >-
      Обрыв долгого соединения — норма, а не отказ сессии. Session id остаётся
      валидным, и last-event-id говорит серверу, с какого события продолжить,
      чтобы ничего не потерялось и не пришло дважды.

Дальше в курсе ты будешь подключать реальные серверы — и почти каждая проблема там сводится к одному из четырёх вопросов этого урока: какой транспорт вообще уместен, живёт ли ещё сессия, кто стучится на твой порт и с какого места продолжать после обрыва.

Спотыкаются обычно на двух вещах. Первая — путают «повторить» и «начать заново»: 502, 504 и обрыв SSE лечатся повтором, а 404 на session id — только новым рукопожатием. Вторая — проверка `Origin` «по вхождению» вместо точного совпадения, из-за которой allowlist перестаёт что-либо защищать.

Проверь себя на четырёх вопросах — и можно идти к настоящим подключениям.

Ты уже умеешь резать поток на строки — `split_stdio` из [шага 8](#step-8) делал ровно это. Попробуй теперь натравить его на то, что прилетает по GET `/mcp`, и посмотри, что получится:

```
event: message
data: {"jsonrpc":"2.0","id":1,"result":{}}

: keepalive

id: 42
data: {"jsonrpc":"2.0",
data: "method":"ping"}
```

Строк восемь, а событий тут два. Одно сообщение развалилось на три строки, между блоками болтается пустая строка, а `: keepalive` вообще не про данные. Построчный разбор здесь врёт.

Значит, резать надо на двух уровнях. Сначала текст делится на блоки по пустой строке — это и есть граница события, ровно та, про которую было в [шаге 22](#step-22). Потом каждый блок разбирается по строкам вида `поле: значение`.

Что должна уметь твоя `parse_sse`: принять кусок текста, вернуть список событий, у каждого — тип, данные и, если был, `id`. На что смотреть отдельно:

- строки, начинающиеся с двоеточия, — комментарий сервера, чтобы соединение не заснуло; их выбрасываешь;
- несколько `data:` в одном блоке склеиваются через перевод строки, а не теряются;
- один пробел после двоеточия — часть формата, его срезают, остальные пробелы оставляют;
- нет поля `event` — тип по умолчанию `message`;
- последний блок без завершающей пустой строки ещё не дописан. Как и в `split_stdio`, его нельзя отдавать наружу — он остаётся в буфере ждать следующего куска.

Проверь себя на примере выше: два события, второе с `id` и склеенным JSON.

> 🎒 **На пальцах.** Как файл субтитров к фильму. Внутри одного блока реплика может занимать две строки — «Я вернусь» и «завтра утром», — но зритель читает их как одну фразу. Границу между репликами задаёт не перевод строки, а пустая строка между блоками. Разложишь такой файл построчно — получишь обрывки без смысла; разложишь по блокам — получишь реплики.

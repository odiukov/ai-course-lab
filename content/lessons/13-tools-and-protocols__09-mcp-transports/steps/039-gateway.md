У тебя три сервера: Filesystem, GitHub и Postgres. Клиент подключается ко всем трём — значит три URL в конфиге, три отдельных `Mcp-Session-Id`, три allowlist для `Origin`, три места, где может прийти 404 из [шага 15](#step-15). Добавили четвёртый сервер — правь конфиг у каждого клиента заново.

А если поставить между ними посредника?

Шлюз снаружи выглядит ровно как обычный сервер Streamable HTTP из [шага 9](#step-9): одна точка `/mcp`, те же три метода, свой `Mcp-Session-Id` на 128 случайных бит по правилу из [шага 12](#step-12). Клиент не отличает его от одиночного сервера — и не должен.

Внутри шлюз держит таблицу: «сессия клиента `a3f...` = сессия 1 у Filesystem + сессия 2 у GitHub + сессия 3 у Postgres». Приходит запрос — шлюз подменяет свой session id на нужный вышестоящий и отправляет дальше. Это и называется переписыванием session id и мультиплексированием: один входящий поток расходится по трём исходящим. Если сессия у GitHub умерла, шлюз переинициализирует её сам — клиент ничего не заметил.

Список инструментов шлюз тоже собирает сам: берёт по инструментам у каждого сервера и отдаёт клиенту одним списком. Клиент видит один логический сервер.

И вот тут главная работа. У Filesystem есть `search`, у Postgres тоже `search`. Два разных инструмента с одним именем в одном списке — клиент не поймёт, к кому обращаться, поэтому шлюз обязан их развести: например, в `fs.search` и `pg.search`.

Одна точка входа для клиента куплена ценой того, что кто-то внутри разруливает одинаковые имена.

> 🎒 **На пальцах.** Заказываешь ужин из трёх кухонь через одну доставку. У тебя один номер заказа; внутри служба держит три своих номера — по одному на кухню. Ты про них не знаешь. Но если и суши-кухня, и пиццерия предлагают «салат цезарь», в общем меню окажутся две одинаковые строки — и служба обязана подписать: «цезарь (суши)», «цезарь (пиццерия)». Иначе ты нажмёшь, а придёт не то.

Ты запускаешь сервис на FastAPI, отправляешь по одной картинке — ответы приходят быстро. Затем одновременно заходят 40 пользователей: запросы выстраиваются в очередь, p95 растёт, а GPU используется неровно. Переписывать всё или оставить как есть?

FastAPI хорошо подходит, пока нагрузка небольшая и предсказуемая, моделей мало, а тебе важнее простота. Он принимает HTTP-запрос, проверяет изображение и оркестрирует маршрут из [шага 25](#step-25). Для прототипа или небольшого продукта этого часто достаточно.

Inference server — специализированный сервис, который управляет именно запусками моделей. Triton Inference Server, TorchServe и BentoML умеют собирать запросы в батчи, распределять вычисления, обслуживать несколько версий модели, публиковать метрики и сообщать, готовы ли модели принимать трафик. Это становится полезно, когда запросов много, GPU дорогой, моделей несколько или обновлять их нужно независимо от API.

Граница проходит не по правилу «продакшн означает Triton», а по измерениям. Если benchmark из [шага 35](#step-35) показывает приемлемые p50, p95 и пропускную способность — дополнительный слой лишь усложнит систему. Если узким местом из [шага 36](#step-36) стал запуск моделей и помогает микробатчинг из [шага 39](#step-39), inference server уже решает конкретную проблему.

При этом FastAPI не обязательно исчезает: он может остаться входной дверью с валидацией, trace ID и fallback из [шага 40](#step-40), а модели будут работать за ней в inference server.

> 🎒 **На пальцах.** Представь клинику. Пока пациентов пять в день, администратор сам записывает их и ведёт к нужному кабинету. При сотне пациентов нужен диспетчер, который группирует обследования, следит за аппаратами и переключает кабинеты без остановки приёма. Администратор остаётся у входа — просто больше не управляет каждым аппаратом лично.

title: Жизненный цикл Run допускает ожидание ввода и отдельную отмену
source_anchor: '#### Run Lifecycle'
---

Ты отправляешь агенту договор и просишь проверить даты. Он доходит до размытой строки: там написано «12 мая» или «17 мая»? Если агент угадает, результат окажется ненадёжным. Если сразу поставит `failed`, будет выглядеть так, будто произошла ошибка. Но ошибки нет — не хватает твоего ответа.

Поэтому Run может перейти из `in_progress` в `awaiting`. Это пауза, а не финал: агент сообщает, какой ввод ему нужен, и сохраняет тот же Run. Когда ты уточняешь дату, клиент возобновляет его, и статус возвращается в `in_progress`. Новый Run создавать не требуется.

Теперь другая ситуация: проверка ещё идёт, но документ оказался не тем. Ты отправляешь запрос на отмену. Run сначала переходит в `cancelling`: просьба принята, однако агент ещё останавливает работу. Только статус `cancelled` означает, что остановка завершена. Как `completed` и `failed`, он уже терминальный — продолжить такой Run нельзя.

Важно не смешивать эти ветки. `awaiting` говорит: «мне нужен ввод, чтобы продолжить». `cancelling` говорит: «продолжать больше не нужно, я завершаю работу». Выбранный в [шаге 31](#step-31) способ ожидания — `sync`, `async` или `stream` — меняет получение обновлений, но не смысл этих состояний.

Пауза сохраняет работу; отмена закрывает её.

> 🎒 **На пальцах.** Ты готовишь блюдо вместе с поваром. Если он спрашивает, добавлять ли орехи, кухня не сломалась: готовка поставлена на паузу до твоего ответа. Если же ты отменяешь заказ, повар сначала убирает сковороду с огня — это `cancelling`. Когда рабочее место освобождено, заказ становится `cancelled`: возвращаться к его приготовлению уже нельзя.

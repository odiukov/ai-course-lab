Ты отправляешь агенту просьбу проверить договор, а через минуту — уточнение по тому же договору. Если обе записи назвать просто «договор», обновление статуса легко попадёт не туда: первая проверка уже идёт, а вторая только принята.

Поэтому при создании каждая задача получает свежий `id`. Это адрес именно одной работы: по нему менеджер хранит задачу, подписчики получают её события, а клиент позднее запрашивает состояние. Даже две одинаковые просьбы должны иметь разные `id` — иначе их история и результаты смешаются.

Но разным задачам иногда нужно помнить, что они относятся к одному разговору. Для этого служит `contextId`, знакомый тебе по [шагу 17](#step-17). При продолжении разговора вызывающая сторона передаёт прежний `contextId`; новая задача сохраняет его. Если контекста ещё нет, менеджер создаёт новый. Получается важное различие: `id` меняется для каждой задачи, а `contextId` может объединять несколько задач.

Наконец, задача появляется не «без состояния», а сразу со статусом `submitted` и временем создания. Среди состояний из [шага 18](#step-18) это точка входа: запрос уже зарегистрирован, но обработка ещё не началась. Артефактов и истории на этом коротком этапе может не быть — контейнер только подготовлен и сохранён.

Теперь у любой новой работы есть отдельный адрес, принадлежность к разговору и однозначная стартовая точка.

> 🎒 **На пальцах.** В лаборатории каждый анализ получает собственный штрихкод: две пробирки одного человека нельзя спутать. Номер медицинского дела связывает эти анализы между собой, а отметка «принято» говорит, что пробирка зарегистрирована, но исследование ещё не началось. Штрихкод — это `id`, номер дела — `contextId`, отметка — начальный `submitted`.

Ты вызываешь `new_task` дважды с одним `contextId`. Если функция вернёт одинаковые `id`, менеджер примет две разные работы за одну и начнёт перезаписывать данные. Если же она создаст новый `contextId` при каждом вызове, задачи потеряют общую беседу. Поэтому эти идентификаторы нельзя генерировать по одному правилу.

Собери функцию, которая принимает необязательный `contextId` и возвращает новую задачу. Для `id` каждый раз создавай новый UUID. Переданный `contextId` сохраняй без изменений, а при его отсутствии генерируй отдельный UUID. Так продолжение разговора сможет разделять контекст с предыдущими задачами, не разделяя их идентичность.

Начальный статус должен быть `submitted` со временем создания. Поставь актуальную временную метку именно при вызове функции, а не один раз при загрузке программы. `artifacts` и `history` начинаются пустыми: сообщение добавит вызывающий код, когда действительно отправит задачу обработчику. Это сохраняет границу ответственности — `new_task` только создаёт корректную заготовку.

Проверь три случая: два вызова без аргумента дают разные пары идентификаторов; два вызова с одним контекстом дают разные `id`, но одинаковый `contextId`; коллекции одной задачи не меняются при изменении другой. Последняя проверка ловит неприятную ошибку с общими массивами.

Ориентир из [шага 20](#step-20) здесь становится контрактом функции: новая работа уникальна, а разговор может продолжаться.

> 🎒 **На пальцах.** Представь турнир: у каждой партии свой номер протокола, но несколько партий могут относиться к одному туру. `id` различает отдельные партии, `contextId` собирает их под вывеской общего тура. Если тур не указан, секретарь заводит новый. Чистые листы ходов и результатов выдаются каждой партии отдельно — делить один лист между столами нельзя.

title: Проверка разрешает DID и перебирает только ключи authentication
source_anchor: '#### How Trust Works in ANP'

Ты получаешь запрос от агента вместе с DID и подписью. В его DID-документе находятся три открытых ключа: один для входа, второй для подписи утверждений, третий для согласования шифрования. Допустим, подпись математически совпала со вторым ключом. Можно принимать запрос?

Нет. Совпадение доказывает лишь владение закрытым ключом, но не право использовать его для входа.

Сначала проверяющая сторона разрешает DID: по правилу из [шага 42](#step-42) получает актуальный DID-документ с домена владельца. Открытый ключ из самого запроса доверенным источником не считается — иначе отправитель мог бы подложить собственную пару ключей и успешно проверить самого себя.

Затем из документа берутся только методы, перечисленные в `authentication`. Там могут находиться встроенные описания ключей или ссылки на записи из `verificationMethod`; ссылки нужно разрешить внутри полученного документа. Проверка перебирает эти ключи и принимает подпись, если хотя бы один из них подтверждает точные байты сообщения — связь подписи с байтами ты видел в [шаге 44](#step-44).

Ключи из `keyAgreement` и других секций в этот перебор не попадают. Как показал [шаг 43](#step-43), назначение ключа — часть политики безопасности, а не подсказка для удобства. Поэтому ответ на исходный вопрос: даже математически верная подпись неподходящим ключом не подтверждает аутентификацию.

> 🎒 **На пальцах.** Представь проходную киностудии. В базе у сотрудника есть пропуск в здание, ключ от монтажной и печать для утверждения сценариев. Все три предмета настоящие, но охранник проверяет только пропуск. Печать может быть безупречной, а ключ действительно открывать дверь монтажной — права войти через проходную они всё равно не дают.

В журнале маршрута появляются четыре записи подряд: `researcher`, `writer`, `researcher`, `writer`. Счётчик из [шага 10](#step-10) всё равно остановит процесс на пределе, но теперь ты хочешь заметить именно болтанку — раньше, чем будут потрачены все разрешённые передачи.

Функция `detect_bouncing` получает историю агентов, через которых прошла задача, и отвечает: образуют ли последние четыре записи чередование `A → B → A → B`. Смотри на три условия:

- в истории есть хотя бы четыре записи;
- первая из последних четырёх совпадает с третьей, а вторая — с четвёртой;
- `A` и `B` — разные агенты.

Последнее условие важно. История `writer → writer → writer → writer` тоже совпала бы по позициям, но это не bouncing: задача никуда не передавалась.

Проверь мысленно несколько случаев. `researcher → writer → researcher → writer` должно дать положительный результат. `researcher → writer → critic → writer` — отрицательный: здесь три участника, а не возврат между двумя. Короткая история тоже даёт отрицательный результат — данных ещё недостаточно.

Проверяй именно конец истории: функция вызывается после очередной передачи и отвечает на вопрос «болтается ли задача сейчас?». Она только распознаёт ситуацию; решение остановить маршрут остаётся за оркестратором.

> 🎒 **На пальцах.** Представь лифт, который записывает последние этажи: `3, 7, 3, 7`. По такой последовательности ты замечаешь, что он застрял между двумя вызовами. Запись `3, 3, 3, 3` не считается: лифт вообще не ездил. А `3, 7, 5, 7` показывает обычный маршрут, а не повторяющуюся петлю.

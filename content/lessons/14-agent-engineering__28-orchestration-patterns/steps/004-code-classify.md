Ты запускаешь сравнение из [шага 3](#step-3), но запросы приходят обычными фразами: «Верните оплату», «После обновления всё зависает», «Есть тариф для команды?». Остальной программе нужны не эти предложения, а одна из трёх точных меток: `refund`, `bug` или `sales`.

Заполни функцию `classify`. Она должна передать текст запроса скриптованной LLM и вернуть полученный интент. На этом её работа заканчивается: не составляй ответ пользователю, не выбирай агента и не добавляй логику конкретной топологии. Иначе четыре паттерна будут сравниваться уже на разных условиях.

Обрати внимание на контракт функции: снаружи приходит строка с сообщением, наружу выходит ровно одна строковая метка. Регистр и написание важны — `Refund` и `refund` для программы могут оказаться разными значениями. Не возвращай пояснение вроде «пользователь просит возврат»: следующий участок кода ожидает именно короткий идентификатор.

Проверь себя на трёх сообщениях с разными формулировками. Вопрос про возврат должен дать `refund`, описание поломки — `bug`, интерес к покупке — `sales`. При этом не пытайся вручную перечислить все возможные слова: классификацию выполняет модель, а твоя функция аккуратно связывает её с остальной программой.

Когда эта граница соблюдена, любые топологии получают одинаковый смысловой ярлык — значит, сравнение остаётся честным.

> 🎒 **На пальцах.** Представь багажную бирку в аэропорту. Чемоданы выглядят по-разному: один красный, другой в плёнке, третий с наклейками. Сотрудник читает маршрут и прикрепляет короткий код назначения. `classify` делает то же самое с фразой: превращает её в точную метку. Она не решает, по какой ленте поедет чемодан, — только подписывает его без двусмысленности.

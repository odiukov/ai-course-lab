Схема-режим из [шага 9](#step-9) и маскировка токенов из [шага 10](#step-10) упираются в один и тот же вопрос: а на каком языке ты вообще объяснишь системе, какой формы ждёшь ответ?

Написать «поле product — строка, price — неотрицательное число»? Ты это прочтёшь, а валидатор и декодер — нет. Им нужно описание, которое разбирается механически, без чтения между строк.

Такое описание называется JSON Schema:

```json
{
  "type": "object",
  "properties": {
    "product": { "type": "string" },
    "price": { "type": "number", "minimum": 0 },
    "in_stock": { "type": "boolean" },
    "categories": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["product", "price", "in_stock"]
}
```

Посмотри внимательно: сама схема — это тоже JSON. Документ на JSON, который описывает, каким должен быть другой JSON. `"type": "object"` фиксирует, что на верхнем уровне объект, а не строка и не массив. `properties` перечисляет ключи и тип каждого. Строчку `"required"` и `"minimum": 0` разберём на следующем экране — там прячется вся разница между «поле есть» и «поле осмысленно».

Ценность в том, что этот файл читают оба потребителя сразу. Валидатор сверяет с ним готовый ответ. Декодер выводит из него, какие токены разрешить на текущем шаге. Одно описание — два разных механизма, и ни один из них не додумывает за тебя.

Пока формы контракта нет на бумаге, спорить о гарантиях не о чем: гарантировать нечего.

> 🎒 **На пальцах.** Композитор не объясняет словами, как звучит вещь. Он пишет партитуру. По ней играет живой оркестр — и по ней же нарезается валик механического пианино, которое ничего не «понимает», а просто не может нажать клавишу, которой в нотах нет. Один и тот же лист, два способа исполнения. JSON Schema — такая партитура: её читает и проверяющий, и тот, кто физически не даёт сыграть лишнюю ноту.

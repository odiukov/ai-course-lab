Вернись к схеме из [шага 12](#step-12): четыре поля товара — и полтора десятка строк фигурных скобок, где `"type"` повторяется в каждом ключе, а список `required` живёт отдельно от самих полей. Добавил поле — правь в двух местах. Забыл дописать имя в `required` — схема молча пропустит объект без него, и валидатор из [шага 23](#step-23) не скажет ни слова: с точки зрения контракта всё честно.

Неужели это придётся печатать руками каждый раз?

В Python — нет. Ты объявляешь обычный класс, а схему собирает за тебя библиотека Pydantic:

```python
from pydantic import BaseModel

class Product(BaseModel):
    product: str
    price: float
    in_stock: bool
    categories: list[str] = []
```

Посмотри, что здесь откуда берётся. Аннотация после двоеточия — `str`, `float`, `bool` — становится типом поля в схеме. `list[str]` разворачивается в массив строк. А `= []`, значение по умолчанию, — единственное, что отличает необязательное поле от обязательного: три поля без умолчания попадут в `required`, `categories` — нет. Тот самый список из [шага 13](#step-13), только теперь ты не ведёшь его вручную, он вычисляется из объявления.

Дальше класс работает как готовый контракт: Instructor и SDK от OpenAI принимают модель Pydantic напрямую — передаёшь класс, получаешь провалидированный экземпляр `Product`. Если ответ модели не подошёл, Instructor повторит запрос сам.

Контракт остался тем же, изменилась только запись — и рассинхрону между полями и `required` теперь просто негде завестись.

> 🎒 **На пальцах.** Портному не диктуют выкройку в миллиметрах. Говоришь: «рубашка, длинный рукав, воротник-стойка» — лекала он вычертит сам. Объявление класса — такая же короткая фраза: ты называешь поля и типы, остальное Pydantic разворачивает. А передумал насчёт рукава — меняешь одно слово, а не перечерчиваешь весь комплект лекал заново.

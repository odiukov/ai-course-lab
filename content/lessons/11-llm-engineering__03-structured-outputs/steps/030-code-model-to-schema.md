У тебя уже есть две детали: [`python_type_to_schema`](#step-28) переводит один питоновский тип в кусок схемы, а из [шага 29](#step-29) ясно, как из набора полей собираются `properties` и `required`. Но пока это россыпь. Приложению нужен один вызов: даёшь класс модели — получаешь готовый словарь схемы, который можно отправить в API или скормить [`validate`](#step-23).

Этим и займётся `model_to_schema`. На вход — класс модели, на выходе — словарь вида «тип object, вот его properties, вот required».

Внутри порядок такой. Пройди по полям класса в том порядке, в каком они объявлены. Для каждого поля возьми его тип и получи базовый кусок схемы. Потом навесь на этот кусок ограничения, которые лежат в самом объекте поля из [шага 27](#step-27): `minimum`, `enum`, описание. Имя поля становится ключом в `properties`. И параллельно решай: попадает ли имя в `required`.

Вот здесь и прячется главная ловушка. Обязательность определяется не типом поля, а тем, есть ли у него значение по умолчанию. Поле `price: float` без умолчания — обязательное. Поле `discount: float = 0.0` — нет, даже если тип тот же самый. И отдельно посмотри на `= None`: умолчание есть, значит поле необязательное, хотя интуиция подсказывает обратное.

Последний штрих — конверт. Словарь `properties` сам по себе не схема: пока сверху не написано `"type": "object"`, ни валидатор, ни API не поймут, что им прислали.

Проверить просто: собери схему для модели товара и прогони через неё словарь `{"product": "Sony WH-1000XM5", "price": 348.0, "in_stock": true}`. Жалоб быть не должно.

> 🎒 **На пальцах.** Ты переписываешь рецепт в список покупок. Рецепт говорит «мука 300 г, яйца 2 шт, ваниль — по желанию». В списке ты ничего не выдумываешь: строка на каждый ингредиент, галочка напротив обязательных, «ваниль» — без галочки. А сверху обязательно надпись «Продукты». Без неё кассир видит просто бумажку со словами и не понимает, что с ней делать.

title: 'Enum confusion: «available» вместо «in_stock»'

У тебя в схеме поле `status` с перечислением из трёх значений: `in_stock`, `out_of_stock`, `preorder` — тот самый enum из [шага 14](#step-14). Приходит описание товара: «Есть на складе, отгружаем сегодня». Модель возвращает `{"status": "available"}`.

Придраться будто бы не к чему: JSON целый, ключ на месте, значение — строка. Смысл угадан идеально. А приложение всё равно ломается, потому что в коде написано `if status == "in_stock"`, и товар молча уезжает в «нет в наличии».

Почему модель промахнулась, если поняла всё правильно?

Потому что она выбирает не смысл, а токены. «Available» — самое естественное английское слово для этой мысли, и по вероятности оно тяжелее, чем твой внутренний код `in_stock`, который живёт только в твоей базе. Ни просьба в промпте, ни JSON mode из [шага 8](#step-8) тут не помогают: они следят за скобками и кавычками, а не за тем, какие именно слова разрешены внутри строки.

Разница появляется на уровне декодирования ([шаг 10](#step-10)). После открывающей кавычки маска оставляет только те токены, которые продолжают одну из трёх строк списка. Модель начала с `in` — дальше она заперта в `in_stock`. Токен `av` не отброшен постфактум, у него просто нет шанса: такого варианта нет в наборе.

Без этого остаётся ловить чужое значение валидатором ([шаг 23](#step-23)) и уходить на повтор ([шаг 39](#step-39)) — то есть платить лишний запрос за слово, которое можно было не дать сказать.

> 🎒 **На пальцах.** Врач пишет от руки: «жаропонижающее». По смыслу верно, а провизор не выдаст — аптека принимает только коды из справочника. Теперь тот же врач заполняет рецепт в программе, где поле — не строка ввода, а список из справочника. Написать своё слово физически негде: курсор в это поле не встаёт. Ошибка исчезла не потому, что врач стал грамотнее, а потому что вариант «своими словами» убрали из интерфейса.

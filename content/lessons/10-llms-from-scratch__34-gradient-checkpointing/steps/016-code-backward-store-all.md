Список из [шага 14](#step-14) лежит перед тобой целиком: тридцать две активации, все живые, все занимают память. Теперь напиши функцию, которая его тратит:

```python
def backward_store_all(grad_output, activations, params):
    ...
```

Дальше — по плану из [шага 15](#step-15). Заводишь `g = grad_output` — это градиент, пришедший с конца сети. Заводишь `grads` — список той же длины, что `params`, пока забитый `None`. И идёшь по слоям от последнего к нулевому.

На каждой итерации берёшь `x_in = activations[i]` и `params[i]`, отдаёшь их вместе с текущим `g` в `layer_backward` из [шага 12](#step-12). Оттуда возвращаются градиенты по четырём параметрам и градиент по входу. Четыре кладёшь в `grads[i]`, пятый становится новым `g` — он же градиент выхода предыдущего слоя. В конце возвращаешь `g` (это градиент по входу всей сети) и `grads`.

Три места, где легко промахнуться.

Первое: `activations[i]` — это **вход** слоя `i`, а не его выход; так их укладывал forward. Второе: результат клади именно в `grads[i]`, а не через `append` — идёшь-то ты задом наперёд, и `append` выдаст список, перевёрнутый относительно `params`. Оптимизатор потом молча применит градиенты первого слоя к последнему. Третье: `g` обязан обновляться на каждой итерации, иначе все слои получат один и тот же градиент с конца.

И задержись на строке `x_in = activations[i]`. Вот она, вся цена наивного подхода: на момент вызова функции в памяти должны лежать входы всех слоёв сразу.

> 🎒 **На пальцах.** Обходишь дом с крыши вниз, лифтом: девятый этаж, восьмой, седьмой. В акте пишешь не «первая проверка, вторая проверка», а строго по номеру этажа — иначе сантехник поедет чинить трубу на девятый вместо первого. Порядок обхода и порядок записи — разные вещи. Ровно поэтому `grads[i]`, а не `append`.

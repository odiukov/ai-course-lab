Ты отправляешь один вопрос, но внутри он может превратиться в гипотетический ответ, несколько переформулировок или набор подзадач. Главная ловушка — провести через поиск сразу все варианты. В `query` должна сработать ровно одна ветка, выбранная `pick_strategy`, как описано в [шаге 7](#step-7).

Сначала измерь время переписывания. Для HyDE сохрани гипотетический текст; для multi-query или декомпозиции — список подзапросов. Затем выбери способ поиска:

- с гипотетическим текстом вызови специальный поиск;
- несколько подзапросов выполни отдельно и объедини их выдачи через RRF из [шага 4](#step-4);
- во всех остальных случаях ищи по исходному вопросу.

Обрати внимание: числовые оценки отдельных поисков при слиянии не сравниваются. Для RRF важны позиции чанков в списках, поэтому каждому найденному чанку можно передать одинаковую условную оценку. После слияния оставь не больше `top_n` кандидатов.

Дальше границы снова становятся строгими. Реранкер получает исходный вопрос, а не его переписанную версию, и сокращает кандидатов до `top_k`. Генератор получает уже этот финальный список и возвращает одновременно ответ и цитаты — либо отказ по правилам [шага 9](#step-9).

Запиши длительность каждой стадии отдельно: `rewrite`, `retrieve`, `rerank`, `generate`. Итоговый `Result` должен сохранить ответ, цитаты, ранжированные чанки, выбранную стратегию и эти четыре измерения. Проверяй не только текст ответа: потерянная стратегия или смешанные интервалы времени тоже нарушают сквозной контракт из [шага 10](#step-10).

> 🎒 **На пальцах.** Представь посылку в сортировочном центре. Оператор сначала уточняет адрес одним выбранным способом, затем ищет подходящие маршруты, контролёр оставляет лучшие, а упаковщик выдаёт посылку вместе с накладными. На каждом столе стоит свой секундомер. Если передать упаковщику черновые маршруты или включить сразу три способа уточнения адреса, посылка формально движется, но процесс уже неверен.

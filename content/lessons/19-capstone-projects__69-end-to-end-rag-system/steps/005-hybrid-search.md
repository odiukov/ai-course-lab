Ты вводишь запрос и получаешь два списка: BM25 ставит выше чанки с подходящими словами, а плотный поиск — с близким смыслом. Если вернуть только один список, поиск перестанет быть гибридным. Если просто склеить оба, первые результаты будут зависеть от порядка склейки, а одинаковые чанки появятся дважды.

В методе `search` замкни этот разрыв. Сначала передай один и тот же `query` обоим поисковикам и запроси у каждого по `k_each` кандидатов. Это ширина отбора: при значении 8 на объединение поступят максимум 16 позиций, хотя часть чанков может повторяться.

Затем передай оба ранжирования в RRF из [шага 4](#step-4). Именно он должен сопоставить позиции, объединить дубликаты и вернуть пары «чанк — итоговая оценка». Не пытайся складывать исходные оценки BM25 и плотного поиска: у них разные шкалы, поэтому такие числа несопоставимы.

После объединения оставь первые `k_out` результатов. Наружу должны выйти только объекты `Chunk`, без оценок RRF: следующий компонент конвейера ожидает адресуемые чанки из [шага 3](#step-3), а не внутренние данные поискового индекса.

Обрати внимание на два разных ограничения: `k_each` определяет, сколько кандидатов каждый поиск предлагает, а `k_out` — сколько победителей получает следующая стадия. Теперь оба способа поиска действительно работают как один вход конвейера.

> 🎒 **На пальцах.** Представь двух разведчиков на ярмарке: один ищет человека по точному описанию одежды, другой — по поведению и маршруту. Каждый приносит свой список кандидатов. Координатор сверяет места в списках, убирает повторения и передаёт охране только несколько лучших имён. Охране не нужны заметки разведчиков — ей нужны сами люди, которых следует проверить.

После первого merge список соседей меняется. Если пересчитать частоты по исходному тексту, ты снова выберешь пару, которой в текущих последовательностях уже нет. Например, после объединения `[97, 97]` два байта превращаются в один новый токен — значит, пары рядом с ним тоже становятся другими.

Заполни тело функции, не меняя её интерфейс:

```python
def train_bpe(text, num_merges):
    # твоя реализация
    ...
```

Собери обучение в том порядке, который спроектирован в [шаге 25](#step-25):

1. Нормализуй весь текст функцией из [шага 8](#step-8).
2. Получи независимые чанки через `pre_tokenize` из [шага 18](#step-18).
3. Преврати каждый чанк в отдельный список байтов UTF-8.
4. Подготовь базовый `vocab`, таблицу `merges` и следующий свободный ID по правилам [шага 24](#step-24).
5. На каждой итерации заново создай `Counter` и посчитай соседние пары внутри каждого списка. Не соединяй конец одного чанка с началом другого.
6. Если пар не осталось, заверши цикл раньше `num_merges`.
7. Выбери самую частую пару, выдай результату новый ID и сохрани соответствие в `merges`.
8. Добавь в `vocab` байты нового токена: это конкатенация байтов двух его частей.
9. Примени выбранный merge ко всем чанкам функцией из [шага 22](#step-22).

Особенно проверь, что следующий раунд работает уже с обновлёнными последовательностями. Иначе функция будет собирать статистику из прошлого состояния и обучение разойдётся с собственной таблицей merges.

> 🎒 **На пальцах.** Представь аукцион наборов деталей. После каждого раунда два предмета скрепляют и кладут обратно уже как один набор. Перед новым раундом ты заново осматриваешь соседние предметы на каждом столе. Старый список соседей больше не годится: скреплённые детали изменили раскладку. А предметы с разных столов соседями вообще не становятся.

type: check
title: >-
  Какая стадия запрещает merge через границу слова, а какая защищает служебный
  маркер?
source_anchor: '### The Full Pipeline'
check:
  - question: >-
      После pre-tokenization слова the и cat лежат в разных кусках. Что
      произойдёт, если среди правил BPE есть merge для соседних символов e и c?
    options:
      - >-
        BPE создаст общий токен ec, потому что правило merge важнее границы
        слова
      - 'Merge не сработает: BPE обрабатывает каждый полученный кусок отдельно'
      - 'Слова сначала снова соединятся, а затем будут разбиты на байты'
    correct: 1
    explanation: >-
      Pre-Tokenize заранее разделяет слова на независимые куски, поэтому BPE не
      получает возможность объединить e из одного слова с c из другого.
  - question: >-
      Почему добавленный маркер [EOS] не может случайно слиться с соседним
      токеном?
    options:
      - Нормализация удаляет квадратные скобки маркера
      - Pre-Tokenize разбивает маркер на отдельные символы
      - >-
        Стадия Special Tokens вставляет его как неделимый токен с фиксированным
        ID уже вне BPE-merges
      - ID Mapping каждый раз назначает маркеру новый ID
    correct: 2
    explanation: >-
      Служебные маркеры добавляются отдельно и никогда не участвуют в
      BPE-merges; их ID заранее зафиксированы.
---

Представь, что после разделения текста BPE знает заманчивое правило merge для последних букв одного слова и первых букв следующего. Применить его нельзя: границу поставила стадия Pre-Tokenize. Это тот самый раздел ответственности из [шага 4](#step-4).

Со служебным маркером защита устроена иначе. Стадия Special Tokens добавляет `[EOS]` как отдельный неделимый элемент с фиксированным ID, не допуская его к BPE-merges. Частая ошибка — приписывать обе защиты одной стадии.

> 🎒 **На пальцах.** На фестивале ограждения не дают людям из соседних очередей смешаться — это Pre-Tokenize. Служебный браслет сотрудника защищён иначе: его выдают отдельно, и он уже имеет особый номер. Это Special Tokens.

Ты вызываешь текстовый метод с файлом и видишь первые байты: `48 69 FF 00`. Первые два означают `Hi`, но `FF` не может стоять здесь в корректном UTF-8. Если сначала превратить файл в строку, декодер либо выдаст ошибку, либо подставит вместо проблемного места символ `�`. В обоих случаях исходная последовательность уже потеряна.

Возникает кажущееся противоречие: базовый словарь из [шага 10](#step-10) содержит все 256 байтов — почему же токенизатор не принимает любой файл? Потому что способность алгоритма обработать байты и контракт конкретного API — разные вещи.

Текстовый метод принимает Unicode-строку. После нормализации из [шага 7](#step-7) она кодируется в UTF-8, поэтому любой допустимый текст — арабский, китайский, эмодзи — превращается в известные базовые токены. Но строка не может без потерь изображать произвольный набор байтов: не каждая последовательность является корректным UTF-8.

Для файлов нужен отдельный метод, принимающий именно `bytes`. Он не пытается угадать кодировку, не применяет NFKC и не выполняет обратное преобразование в текст. Значения `48 69 FF 00` поступают в byte-level BPE напрямую и при декодировании возвращаются теми же байтами.

Так текстовый API обещает корректную работу с любым Unicode-текстом, а бинарный — сохранность любых данных. Смешивать эти обещания в одном входе нельзя: попытка «сделать строку» может уничтожить байты ещё до токенизации.

> 🎒 **На пальцах.** Представь два окна приёма багажа. В одном чемоданы раскрывают, приводят одежду в порядок и снова упаковывают — это обработка текста с нормализацией. В другом запечатанный контейнер принимают по описи, не заглядывая внутрь, — это бинарный API. Контейнер может содержать что угодно, но отправлять его на глажку опасно: содержимое уже не гарантированно останется прежним.

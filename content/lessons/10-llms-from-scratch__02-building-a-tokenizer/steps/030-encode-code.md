После обучения ты передаёшь токенизатору новую строку и ожидаешь знакомые merge-ID. Но если сразу превратить весь текст в байты, получится две ошибки: обученные merges останутся неиспользованными, а соседние слова смогут склеиться через границу чанков.

В `encode(self, text)` собери тот же путь, который был зафиксирован в [шаге 29](#step-29). Сначала вызови написанную в [шаге 8](#step-8) нормализацию, затем передай результат в `pre_tokenize` из [шага 18](#step-18). Дальше обрабатывай каждый чанк отдельно:

1. Закодируй чанк в UTF-8 и преврати полученные байты в список чисел.
2. Передай этот список и `self.merges` в `apply_merges` из [шага 22](#step-22).
3. Добавь получившиеся ID в общий результат, сохраняя порядок чанков.

Отдельный поиск каждого элемента в `vocab` здесь не нужен. До слияний числа от 0 до 255 уже являются ID базовых байтов, а `apply_merges` заменяет пары непосредственно на выданные при обучении merge-ID.

Проследи ещё за двумя деталями: пустая строка должна естественно дать пустой список, а `encode` не должен изменять `merges`, `vocab` или `next_id`. Сейчас функция работает только с обычным текстом — специальные токены появятся на другом этапе.

Главная проверка: все merges применяются внутри чанка, и ни один — между чанками.

> 🎒 **На пальцах.** Представь переплётную мастерскую: текст приходит стопкой отдельных тетрадей. В каждой тетради ты скрепляешь соседние страницы по заранее записанным правилам, а затем складываешь готовые тетради по порядку. Скрепить последнюю страницу одной тетради с первой страницей следующей нельзя. `encode` делает именно это: превращает каждый чанк в ID отдельно и лишь потом соединяет результаты.

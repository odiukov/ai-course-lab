У менеджера есть одна задача и три возможных исполнителя. Если вернуть один конверт с тремя адресатами, дальнейшие ответы будет неудобно сопоставлять с приглашениями. Поэтому `cfp` должна создать список: по отдельному ACL-сообщению для каждого участника.

Используй `make_message`, написанную в [шаге 8](#step-8). Для каждого имени из `participants` создай конверт со следующими значениями:

- перформатив — `cfp`;
- отправитель — `manager`;
- получатель — текущий участник;
- содержимое — переданный `task`;
- идентификатор разговора — `conversation_id`;
- маркер ожидаемого ответа `reply-with` — общий идентификатор этого тендера.

Последний пункт легко упустить. `conversation-id` объединяет весь разговор, но внутри одного разговора теоретически могут проходить разные запросы. Поэтому всем приглашениям одного тендера нужен одинаковый `reply-with`, например значение, однозначно полученное из `conversation_id`. Когда участник ответит через `reply_to` из [шага 12](#step-12), этот маркер окажется в `in-reply-to`.

Не изменяй `task` для разных получателей и не помещай служебные идентификаторы внутрь `content`: содержимое описывает работу, а поля конверта — протокольные связи. Проверь также крайний случай: пустой список участников должен дать пустой список сообщений, а не один конверт без получателя.

Итак, результат `cfp` — не сам тендер целиком, а аккуратно размеченная пачка одинаковых приглашений с разными адресами.

> 🎒 **На пальцах.** Представь организатора ремонта, который кладёт три одинаковых технических задания в три подписанных конверта. На каждом стоит один номер конкурса, а внутри лежит одна и та же смета. Мастера отвечают отдельно, указывая этот номер. Если отправить один безымянный конверт на всех или спрятать номер внутри сметы, потом будет трудно понять, кто и на какой конкурс ответил.

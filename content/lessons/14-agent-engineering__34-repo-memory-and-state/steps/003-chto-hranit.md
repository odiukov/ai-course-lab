Представь: ты открываешь проект через три месяца после паузы. Чат давно закрыт, агент запущен заново, а автоматическая проверка проекта — CI — пытается продолжить работу. В репозитории лежит длинная расшифровка разговора, несколько внутренних трасс рассуждений и идентификатор использованной модели. Данных много, но ответить на простой вопрос «что делать дальше?» они не помогают.

Значит, объём памяти — плохой критерий. Нужна проверка на устойчивость: сможет ли эта запись помочь при повторном запуске через три месяца?

Такой тест проходят id активной задачи, список изменённых файлов, сделанные допущения, открытые блокеры и следующее действие. Их можно сопоставить с кодом, проверить и использовать для продолжения. Именно проверяемость отличает память репозитория из [шага 2](#step-2) от случайного архива заметок.

Сырые транскрипты чата, токеновые трассы рассуждений, сэмплированные варианты ответа и специфичные для поставщика id моделей этот тест обычно не проходят. Они могут пригодиться для диагностики работы системы, поэтому их место — в телеметрии, то есть в технических данных о конкретном запуске, а не рядом с состоянием проекта.

Спроси о каждой записи: «Если сменятся чат, агент и модель, останется ли здесь проверяемая опора для следующего действия?» Если нет, запись описывает прошлый запуск, а не состояние работы.

> 🎒 **На пальцах.** Представь смену в аэропорту. Следующему диспетчеру нужны номер рейса, закрытая полоса, принятое решение и ближайшее действие. Запись всех реплик предыдущей смены и марка её гарнитуры лишь загромоздят стол. В журнал попадает то, по чему можно безопасно продолжить смену; остальное уходит в архив наблюдений.

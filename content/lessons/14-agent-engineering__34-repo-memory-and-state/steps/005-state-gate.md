Ты завершаешь сессию: активная задача — `T-218`, изменены три файла, следующее действие записано. Но в одном поле появилась недопустимая запись. Возникает соблазн сохранить хотя бы «хорошую часть» — ведь почти всё заполнено верно.

Именно здесь «почти» становится опасным. Следующий запуск прочитает файл как источник правды и не узнает, какие данные были проверены, а какие просочились случайно. Состояние вроде бы есть, но доверять ему уже нельзя.

Посмотри на развилку на схеме. Агент передаёт новую версию состояния в `StateManager` — компонент, который отвечает за его сохранение. После проверки возможен ровно один из двух результатов:

- всё допустимо — новая версия попадает в `agent_state.json`;
- найдена ошибка — запись целиком отклоняется, а менеджер сообщает об исключении, то есть явно останавливает неудачную операцию.

Менеджер не исправляет значение по догадке и не записывает остальные поля отдельно. При отказе прежний файл остаётся действующей версией состояния. Да, он может быть не самым свежим, зато он по-прежнему проверенный.

Почему явная ошибка лучше «частичного успеха»? Потому что её ты видишь сразу и можешь исправить. Тихо испорченная память обнаружится позже, когда уже будет трудно понять, в какой сессии возникла проблема. Здесь надёжность появляется не из удачной догадки, а из отсутствия третьего выхода.

> 🎒 **На пальцах.** Представь типографию перед выпуском книги. Контрольный экземпляр либо утверждают и отправляют весь тираж в печать, либо возвращают из-за ошибки. Нельзя напечатать страницы 1–80 из проверенного макета, а страницу 81 взять из бракованного: книга формально выйдет, но доверять экземплярам уже нельзя. Отказ задерживает печать; частичное принятие портит тираж.

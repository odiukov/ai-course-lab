  - question: >-
      Агент завершает сессию. Что лучше сохранить для продолжения работы через
      три месяца?
    options:
      - Полную переписку и настроение пользователя
      - >-
        Активную задачу, принятые решения, актуальные риски и ссылки на крупные

      - Только время завершения сессии
      - Все промежуточные рассуждения агента
    correct: 1
    explanation: >-
      В состояние идёт то, что позволит следующей сессии сделать конкретное
      действие. Крупные артефакты лежат отдельными файлами, а в состоянии
      остаётся путь к ним, чтобы снимок был маленьким и быстрым.
  - question: >-
      Человек изменил состояние две секунды назад, а агент пытается записать
      новый снимок. Как поступить?
    options:
      - Объединить изменения по совпадающим полям
      - 'Записать снимок агента, потому что он новее'
      - Отказать во всей записи и оставить текущий файл без изменений
      - Сохранить оба снимка в одном JSON
    correct: 2
    explanation: >-
      Запись попадает в запретное окно после правки человеком. Исходов у
      проверки два: снимок целиком становится состоянием или не становится вовсе
      — слияние по полям даёт документ, которого не утверждал ни агент, ни
      человек.
  - question: >-
      Процесс упал во время атомарной записи состояния. Что допустимо увидеть
      после перезапуска?
    options:
      - Целиком старый или целиком новый снимок
      - Половину старого и половину нового снимка
      - Обязательно только новый снимок
      - Пустой файл состояния
    correct: 0
    explanation: >-
      Данные пишутся во временный файл и подменяют целевое имя одной операцией
      переименования. Падение до подмены оставляет старый снимок, после — новый;
      промежуточной раскладки по имени состояния не существует. Гарантировать
      именно новый снимок нельзя: падение могло случиться раньше.
  - question: >-
      Загрузчик получил состояние v1 с полем blockers, затем уже мигрированное
      v2, а потом неизвестное v5. Какое поведение надёжно?
    options:
      - 'Каждую версию мигрировать повторно, а v5 считать v2'
      - 'v1 преобразовать в v2, v2 оставить без изменений, v5 отклонить'
      - Принять все версии и проверить только наличие задач
      - Удалить номер версии после первой миграции
    correct: 1
    explanation: >-
      Миграция идемпотентна: повторный прогон над уже преобразованным документом
      ничего не меняет. Версия, для которой пути перехода не реализовано,
      интерпретации не подлежит — её читают по чужому контракту, поэтому
      загрузка отклоняется вслух.

Дальше тебе понадобится собирать надёжное состояние из уже знакомых деталей: контракта из [шага 6](#step-6), атомарной записи из [шага 10](#step-10), миграций из [шага 21](#step-21) и защиты внешних эффектов из [шага 28](#step-28). Главная ловушка — считать успешное сохранение доказательством корректности. Проверяй весь путь: утвердить снимок, записать, заново загрузить и получить то же состояние.

> 🎒 **На пальцах.** Представь нотариуса, который готовит новую страницу реестра. Если клиент только что внёс исправление, нотариус не подмешивает старую копию, а отказывает в замене. Бланк старого образца он переводит по известным правилам, новый оставляет как есть, а незнакомый не угадывает. В реестр попадает одна целая, проверенная страница.

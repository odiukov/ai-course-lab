Перед тобой состояние версии 1: в нём есть `blockers: ["Нет доступа к API"]`. Текущая схема ожидает версию 2 и поле `risks`. Простая замена имени почти сработает — но что произойдёт, если функция получит уже обновлённое состояние или файл из неизвестной будущей версии?

Допиши `migrate_state`, опираясь на правило из [шага 21](#step-21). Функция получает разобранный словарь и должна вернуть состояние текущей версии. Для перехода с v1 на v2 перенеси значение `blockers` в `risks`, удали старое поле и только после успешного преобразования поставь `schema_version: 2`. Содержимое списка при переименовании теряться не должно.

Не изменяй переданный словарь на месте. Сделай копию: иначе вызывающий код может продолжить работать с объектом, который неожиданно поменялся после вызова миграции. Это особенно неприятно при ошибке посередине — снаружи останется наполовину преобразованное состояние.

Отдельно обработай состояние, которое уже имеет текущую версию. Его не требуется мигрировать повторно: верни независимую копию без новых изменений. Для неизвестной версии не пытайся угадать структуру — заверши работу понятной ошибкой. Отсутствующий или неподходящий `schema_version` тоже не должен незаметно считаться v1.

Последний рубеж — `validate` из [шага 7](#step-7). Проверяй именно итоговый объект по схеме v2 и возвращай его только после успешной проверки. Тогда `migrate_state` не просто переписывает ключ: она гарантирует, что на выходе всегда находится полноценное современное состояние.

> 🎒 **На пальцах.** Представь архив анкет: в старом бланке была графа «препятствия», а в новом — «риски». Архивист переносит запись, ставит штамп «форма 2» и проверяет, что все обязательные графы заполнены. Бланк с таким штампом он второй раз не переписывает, а форму с неизвестным номером откладывает: додумывать правила будущего бланка опасно.

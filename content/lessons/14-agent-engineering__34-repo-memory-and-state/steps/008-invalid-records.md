title: 'Почему T-7, null вместо массива и неизвестный status не проходят?'
source_anchor: '### Schema-first state'
check:
  - question: >-
      Схема требует id по шаблону T- и не меньше трёх цифр, tasks — массив,
      status — из набора active или done. Какая запись пройдёт проверку?
    options:
      - 'id T-91, tasks пустой массив, status active'
      - 'id T-1450, tasks null, status done'
      - 'id T-1450, tasks пустой массив, status active'
      - 'id T-1450, tasks пустой массив, status paused'
    correct: 2
    explanation: >-
      T-91 не добирает до трёх цифр, null не является массивом, paused
      отсутствует в наборе. Проходит только запись, где выполнены все три
      независимых правила сразу.
  - question: >-
      Агент хочет записать status paused, которого нет среди разрешённых
      значений схемы. Почему валидатор отклоняет запись, а не расширяет набор на
      лету?
    options:
      - любое новое строковое значение считается ошибкой разбора JSON
      - >-
        набор статусов — часть согласованного контракта, и значение вне него
        потребители состояния не смогут интерпретировать одинаково
      - status допустимо хранить только числом
    correct: 1
    explanation: >-
      Схема ограничивает status общим набором, чтобы все агенты, ревьюеры и
      скрипты CI одинаково понимали состояние. Расширять набор нужно изменением
      схемы, а не записью мимо неё.

Здесь важно отличить «JSON удалось прочитать» от «состояние соответствует контракту». Проверка из [шага 7](#step-7) применяет три независимых правила схемы из [шага 6](#step-6): `T-7` нарушает шаблон идентификатора, `null` не является массивом, а неизвестный `status` не входит в разрешённый список. Частая ошибка — считать эти значения «почти подходящими» и пытаться исправить их молча.

Ты меняешь у активной задачи только `status`, но вместе с новым снимком случайно исчезает обязательное поле `id`. Если сразу отправить такой объект на запись, атомарность сохранит файл без повреждений — только содержимое окажется неверным. Значит, одной безопасной подмены из [шага 11](#step-11) недостаточно.

В `commit_state` соедини две уже написанные операции в строгом порядке:

1. Передай весь новый снимок в `validate` из [шага 7](#step-7). Проверять нужно не отдельное изменённое поле, а итоговый объект целиком: именно он станет состоянием следующей сессии.
2. Только после успешной проверки передай снимок и целевой путь в `atomic_write` из [шага 11](#step-11).

Обрати внимание на отрицательный сценарий. Если `validate` обнаружит отсутствующее поле, неизвестный `status` или неверный тип, `commit_state` должна завершиться с ошибкой до начала записи. Не перехватывай такую ошибку ради сообщения «всё сохранено» и не заменяй плохие значения значениями по умолчанию: это скрыло бы нарушение контракта.

Проверь порядок вызовов мысленно: при ошибочном снимке `atomic_write` вообще не вызывается, а прежний файл остаётся на месте. При корректном снимке функция не записывает JSON самостоятельно — подготовка временного файла, `fsync` и подмена уже принадлежат `atomic_write`.

Так `commit_state` становится единственной точкой утверждения снимка: сначала доказательство допустимости, затем публикация.

> 🎒 **На пальцах.** Представь кассира перед закрытием смены. Он сначала сверяет весь итоговый отчёт: дату, сумму и число операций. Если не сходится хотя бы одна строка, новый отчёт не кладут в сейф поверх старого. Только полностью проверенный лист заменяет предыдущий. `validate` выполняет сверку, а `atomic_write` — безопасную замену в сейфе.

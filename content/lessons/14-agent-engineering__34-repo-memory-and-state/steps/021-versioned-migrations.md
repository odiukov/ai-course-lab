title: Версия схемы требует известной и идемпотентной миграции
source_anchor: '### Migrations'
---

Ты открываешь файл состояния трёхмесячной давности. В нём версия `1`, а поле задачи записано простой строкой: `"Подготовить отчёт"`. Сегодня схема версии `2` ожидает объект с названием и статусом. Можно попытаться «догадаться» о старом формате прямо во время загрузки — но тогда каждая догадка становится скрытым правилом, которое трудно проверить.

Надёжнее иметь известный переход: миграция `v1 → v2` превращает строку в объект по заранее заданному правилу и меняет `schema_version` только на `2`. После этого результат проверяется контрактом новой версии из [шага 6](#step-6). Если для входной версии такого перехода нет, загрузка из [шага 14](#step-14) должна остановиться: неизвестные данные нельзя безопасно истолковать.

Есть ещё одна ловушка. Сбой может произойти уже после преобразования, но до сохранения, а затем операция запустится повторно. Поэтому миграция должна быть **идемпотентной**: первый запуск приводит состояние к нужному виду, а повторный не добавляет ещё одну обёртку, не дублирует поля и не повышает версию снова.

Иными словами, версия выбирает конкретный маршрут преобразования, а идемпотентность делает повтор этого маршрута безопасным. Тогда перезапуск после сбоя не создаёт новый формат поверх уже нового.

> 🎒 **На пальцах.** Представь пункт обмена старых водительских удостоверений. Для образца 2018 года есть точная инструкция: проверить поля, перенести их в бланк 2026 года и поставить новую отметку. Если ты случайно снова подашь уже обновлённое удостоверение, сотрудник вернёт его без изменений. А незнакомый образец он не станет переписывать по догадке.

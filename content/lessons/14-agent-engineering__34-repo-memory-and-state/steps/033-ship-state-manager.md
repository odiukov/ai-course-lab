Ты открываешь `outputs/skill-state-schema.md` и видишь аккуратную схему состояния. Можно ли считать работу законченной? Попробуй применить её: доска задач имеет другую форму, запись файла всё ещё может оборваться, а старые данные после переименования поля перестанут загружаться. Получился полезный фрагмент, но не готовый артефакт.

В комплекте должны быть три согласованные части. Первая — две JSON Schema: одна для состояния агента, другая для доски задач. Разделение здесь принципиально; причины ты разбирал в [шаге 9](#step-9). Обе схемы должны описывать именно твой проект: допустимые статусы, обязательные поля и текущую версию.

Вторая часть — Python-класс `StateManager`, который использует эти контракты при загрузке и сохранении. Он не просто записывает JSON, а подключён к атомарной записи из [шага 10](#step-10): новый снимок либо становится целым текущим состоянием, либо старый файл остаётся нетронутым.

Третья часть — каркас миграции. Даже если сейчас существует только версия 1, должно быть заранее определено место для перехода к версии 2. Иначе первое же переименование `blockers` в `risks` превратит прежние файлы в неожиданную поломку. Требования к известному и идемпотентному переходу уже заданы в [шаге 21](#step-21).

Готовность здесь означает не «файлы существуют», а «они состыкуются»: менеджер проверяет данные по нужной схеме, сохраняет их безопасно и умеет провести старую форму по предусмотренному пути обновления.

> 🎒 **На пальцах.** Представь съёмочную площадку перед новой сменой. Одного сценария мало: нужны отдельные листы для сцен и реквизита, координатор, который выдаёт только утверждённые версии, и таблица замен на случай, если «красный чемодан» завтра станет «синей сумкой». Когда все три части согласованы, следующая смена продолжит съёмку, а не будет угадывать, что имела в виду предыдущая.

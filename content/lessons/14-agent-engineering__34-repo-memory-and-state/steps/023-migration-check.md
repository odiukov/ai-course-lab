  - question: >-
      Менеджер знает путь миграции только с предыдущей версии на текущую. Почему

    options:
      - >-
        Потому что у незнакомой версии может быть другой контракт полей, и

      - >-
        Потому что версия с большим номером всегда содержит меньше полей, чем

      - >-
        Потому что загружать разрешено только файлы, записанные этим же

    explanation: >-
      Больший номер означает «другой контракт», а не «совместимый». Отказ виден

  - question: >-
      Ты повторно запускаешь миграцию для состояния, которое уже находится в
      целевой версии. Какой результат подтверждает идемпотентность?
    options:
      - 'Состояние возвращается без изменений, в той же целевой версии'
      - Версия поднимается ещё на шаг вперёд
      - Поля целевой версии создаются повторно поверх существующих

    correct: 0
    explanation: >-
      Идемпотентность: повторный прогон на уже мигрированном документе даёт тот

Здесь ты проверяешь правило из [шага 21](#step-21) на трёх конкретных входах и поведение функции из [шага 22](#step-22). Частая ошибка — считать любую более высокую версию «более новой и потому подходящей». Но v5 может иметь совсем другой контракт: принимать её как v2 нельзя. Вторая ловушка — повторно преобразовывать уже готовую v2 вместо того, чтобы вернуть её без изменений.

> 🎒 **На пальцах.** Представь мастерскую ключей: заготовку v1 мастер умеет точно довести до стандарта v2, а готовый ключ v2 просто возвращает владельцу. Ключ v5 незнакомой формы он не подпиливает на глаз — иначе тот может застрять в замке. Безопасный результат здесь не догадка, а честный отказ.

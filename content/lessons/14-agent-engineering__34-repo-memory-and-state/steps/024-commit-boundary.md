Ты исправляешь `status`, и новое значение само по себе допустимо. Но рядом в памяти уже лежит ошибка: например, вместо списка задач случайно оказалась строка. Если проверить только изменённое поле, сохранение пройдёт — и репозиторий получит состояние, которое следующая сессия не сможет загрузить.

Поэтому `commit` работает не как команда «запиши мою последнюю правку». Он рассматривает всё текущее состояние как новый снимок-кандидат: целиком передаёт его валидатору из [шага 7](#step-7) и только после успешной проверки разрешает запись. Ошибка в любом месте отменяет операцию, даже если это место ты сейчас не трогал. Старый файл на диске при этом остаётся прежним.

Что происходит после успешной проверки? `commit` не дописывает отдельное поле внутрь существующего JSON. Он сохраняет полный снимок и подменяет им прежний файл атомарным способом из [шага 10](#step-10). Это важно: файл представляет одно согласованное состояние на конкретный момент, а не историю частичных исправлений.

Получается две границы. Валидатор отвечает: «этот снимок можно считать состоянием». Атомарная запись отвечает: «на диске окажется либо старый снимок, либо весь новый». Сначала снимок получает право стать памятью репозитория — и лишь затем занимает место предыдущего.

> 🎒 **На пальцах.** Представь пакет документов на визу. Ты заменил фотографию, но сотрудник проверяет весь пакет: паспорт, анкету, подпись и даты. Если в анкете пропущена страница, новая фотография ничего не спасает — старое досье остаётся в архиве. Только полностью принятый пакет целиком заменяет прежний.

Ты открываешь файл состояния после работы двух агентов. Один записал статус `done`, другой — `finished`. В одном месте список связанных задач пустой: `[]`, в другом вместо него стоит `null`. Человеку общий смысл ещё понятен, а автоматическая проверка уже не знает, одинаковы ли эти записи и что с ними делать.

Договорённости в обычном тексте здесь недостаточно: их можно забыть или истолковать по-разному. JSON Schema превращает договорённость в исполняемый контракт — набор правил, который программа применяет к каждой записи до того, как принять её в репозиторий.

В контракте можно закрепить, какие ключи обязательны, какие значения разрешены для `status` и какого типа должно быть каждое поле. Если ожидается массив, `null` не считается «почти пустым массивом»: это другой тип данных. Для идентификатора можно задать шаблон `T-\d{3,}` — буква `T`, дефис и не менее трёх цифр. Отдельное поле версии сообщает, по каким правилам создана запись, и позволяет позже переводить старые данные в новый формат.

Это продолжает идею проверяемой памяти из [шага 2](#step-2): состояние становится надёжным не потому, что выглядит разумно, а потому, что его форма допускает однозначную машинную проверку. Агент может предложить новое поле или случайное значение, но контракт не позволит незаметно изменить общий язык репозитория.

Плохая запись теперь не превращается в будущую загадку. Она просто не принимается.

> 🎒 **На пальцах.** Представь турникет в метро. Надпись «проход только по действующему билету» — просьба, которую можно проигнорировать. Сам турникет — исполняемое правило: он проверяет конкретные свойства билета и либо открывается, либо нет. JSON Schema действует так же: файл не убеждает проверяющего, что он «примерно правильный», а проходит заранее заданные условия.

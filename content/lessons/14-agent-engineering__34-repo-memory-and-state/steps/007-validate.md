Ты проверяешь доску задач: снаружи это правильный JSON-объект, все обязательные поля на месте. Но внутри массива одна задача записана неверно. Если `validate` остановится на внешнем уровне, ошибка спокойно попадёт в память репозитория.

Поэтому функция должна проверять не только переданное значение, но и всё его содержимое. Передай ей три вещи: значение, соответствующий участок схемы и путь до значения. Путь пригодится для понятной ошибки: сообщение «неверный тип» почти бесполезно, а `task_board.tasks[1].id: ожидалась строка` сразу приводит тебя к проблемному месту.

Контракт схемы уже разобран в [шаге 6](#step-6). Теперь преврати пять поддерживаемых правил в последовательность проверок:

- `type` сверяет фактический тип значения с ожидаемым;
- `required` убеждается, что в объекте присутствуют обязательные ключи;
- `enum` разрешает только значения из заданного списка;
- `pattern` применяет регулярное выражение к строке;
- `items` запускает `validate` заново для каждого элемента массива.

Последний пункт делает проверку рекурсивной: функция вызывает саму себя для вложенных частей данных. При спуске добавляй к пути имя поля или индекс элемента. Если встретилось нарушение, сразу выбрасывай исключение с путём, ожидаемым условием и фактическим значением.

Обрати внимание на порядок: сначала проверь тип, а уже затем выполняй правила, рассчитанные на этот тип. Нельзя искать обязательные ключи в числе или применять строковый шаблон к массиву. Так каждая следующая проверка работает только с подходящими данными.

Готовая функция должна либо молча завершиться, подтверждая весь документ, либо остановиться на первом точном нарушении. Третьего состояния у проверки нет.

> 🎒 **На пальцах.** Представь отдел контроля на фабрике конфет. Недостаточно увидеть, что большая коробка имеет правильную форму. Контролёр открывает её, проверяет каждую пачку, а внутри — каждую конфету. Если одна обёртка не подходит, он записывает точный адрес: «коробка 2, пачка 4, конфета 7». Рекурсивный `validate` делает с JSON то же самое.

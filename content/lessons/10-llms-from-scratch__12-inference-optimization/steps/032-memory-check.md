  - question: >-
      После загрузки весов и учёта накладных расходов для KV-кэша осталось 20
      ГиБ. Один диалог на 4K токенов требует 1,25 ГиБ. Сколько таких диалогов
      поместится одновременно?
    options:
      - '15'
      - '16'
      - '20'
      - '25'
    correct: 1
    explanation: >-
      Доступные 20 ГиБ нужно разделить на 1,25 ГиБ для одного диалога:
      получается 16. Результат округляют вниз, поскольку для каждого принятого
      диалога должен помещаться полный кэш.
  - question: Почему нельзя делить всю память GPU на размер KV-кэша одного диалога?
    options:
      - Часть памяти уже занимают веса модели и накладные расходы
      - KV-кэш существует только во время prefill
      - Каждый диалог обязательно занимает всю память GPU
      - Число KV-голов меняется после каждого токена
    correct: 0
    explanation: >-
      Для KV-кэшей доступен только остаток после размещения весов модели и
      служебных буферов. Расчёт по полной ёмкости GPU завысил бы допустимое
      число диалогов.
  - question: >-
      Какой объём KV-кэша одного диалога следует использовать при оценке
      гарантированного предела одновременных запросов?
    options:
      - 'Объём, необходимый для целевой максимальной длины контекста'
      - 'Объём, занятый только уже поступившими токенами'
      - Средний объём завершённых ранее запросов
      - 'Объём весов модели, делённый на число слоёв'
    correct: 0
    explanation: >-
      Сервер должен предусмотреть рост каждого принятого диалога до целевой
      длины. Если считать только уже записанные токены, дальнейшее расширение
      кэшей может превысить доступную память.

На панели GPU указано 80 ГиБ, и хочется сразу поделить их на размер одного диалога. Но значительная часть уже занята весами модели и служебными данными. Только остаток можно отдать KV-кэшу.

Размер кэша для выбранной длины контекста ты берёшь из расчётов [шага 27](#step-27), а затем делишь доступный остаток на размер одного диалога и оставляешь только целую часть. При этом не смешивай фактически занятые токены с забронированной ёмкостью из [шага 31](#step-31): для оценки предельного числа диалогов важен именно объём, который сервер обязан для них предусмотреть.

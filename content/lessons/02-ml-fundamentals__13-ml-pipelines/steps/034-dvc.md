Ты открываешь старый коммит, запускаешь знакомый пайплайн и ожидаешь прежнюю метрику. Но вместо 0,82 получаешь 0,76. Код тот же — значит, незаметно изменился `training.csv`: добавились строки, исправились значения или поменялась разметка.

Git хорошо хранит историю кода, но многогигабайтные наборы данных быстро раздули бы репозиторий. Поэтому DVC хранит их отдельно: например, в S3, Google Cloud Storage или другом удалённом хранилище. Рядом с кодом в Git попадает лишь маленький файл `training.csv.dvc`. В нём записан хеш — цифровой отпечаток конкретного содержимого данных.

Когда ты выполняешь `dvc add data/training.csv`, DVC фиксирует текущую версию файла и обновляет этот отпечаток. Затем `.dvc`-файл коммитится вместе с кодом. Получается точная пара: этот вариант программы работал именно с этой версией обучающих данных.

Если позже переключиться на старый Git-коммит, в нём окажется старый `.dvc`-файл. Команда `dvc checkout` по сохранённому отпечатку восстановит соответствующий `training.csv`. Теперь расхождение нельзя списать на неясное «наверное, тогда данные были другими»: версия данных указана прямо в истории проекта.

Трекинг из [шага 32](#step-32) связывает результаты отдельного запуска, а DVC отвечает на другой вопрос: какой именно набор данных был доступен этому коду.

> 🎒 **На пальцах.** Представь археологический архив. В полевом журнале лежит не тяжёлый ящик с находками, а его уникальный инвентарный номер. Сам ящик хранится на складе. Открыв запись за прошлый сезон, ты находишь нужный номер и получаешь ровно тот комплект находок, с которым тогда работала экспедиция.

Ты смотришь на результаты прогона: `safety_refusal_rate = 0.04` укладывается в максимум `0.05`, а `mmlu = 64.8` выглядит лучше baseline `64.5`. Но для `mmlu` требовалось улучшение на `0.5`, значит настоящая граница — `65.0`. Эта метрика провалена, хотя поверхностное сравнение с baseline говорит обратное.

Тебе нужно дописать `gate_failures`. На вход функция получает измеренные метрики, baseline и заранее заданные правила гейтов. Для каждого правила она должна применить один из трёх способов проверки из [шага 20](#step-20):

- минимум: фактическое значение не ниже порога;
- максимум: фактическое значение не выше порога;
- улучшение: фактическое значение достигает baseline плюс требуемая прибавка.

Не возвращай ответ сразу после первого нарушения. Собери **все** провалы: иначе после исправления `mmlu` следующий запуск неожиданно обнаружит уже существовавшую проблему с `cost_total_usd`. Для каждого провала сохрани достаточно данных, чтобы человек понял причину: название метрики, полученное значение и требование, которое не выполнено.

Особенно внимательно обработай отсутствующие данные. Если в результатах нет нужной метрики или для относительного гейта не найден baseline, считать проверку успешной нельзя: отсутствие измерения не доказывает прохождение порога.

Проверь функцию на значениях ровно на границе. `0.05` должно проходить условие `<= 0.05`, а `65.0` — условие `>= 64.5 + 0.5`. Здесь равенство входит в допустимый диапазон.

> 🎒 **На пальцах.** Представь контролёра багажа перед рейсом: чемодан одновременно проверяют по весу, размеру и списку запрещённых предметов. Контролёр не прекращает осмотр, обнаружив лишний килограмм, — он записывает каждое нарушение. А если весы не включились, чемодан не считается подходящим: неизвестный результат нельзя подменить успешным.

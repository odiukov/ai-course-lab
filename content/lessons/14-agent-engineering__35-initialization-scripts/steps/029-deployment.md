Ты запускаешь один проект тремя способами. Локальный hook останавливается на сломанной зависимости, GitHub Actions почему-то продолжает работу, а контейнер запускает агента и прячет ошибку среди логов. Хотя проверка везде одна, результат разный: каждая обёртка по-своему истолковала сбой.

Здесь нужен единый контракт запуска. Hook, job `setup-agent` и Docker entrypoint вызывают один и тот же `run_init`, собранный в [шаге 25](#step-25), и смотрят на его код выхода:

- `0` — стенд допущен, можно запускать агента;
- любой ненулевой код — старт запрещён.

Сами обёртки ничего не перепроверяют и не решают, насколько серьёзна найденная проблема. Это уже сделал init. Они лишь передают дальше его вывод и соблюдают вердикт из [шага 26](#step-26).

Различается только действие после успеха. Hook возвращает управление инструменту агента. В GitHub Actions зависимый job получает право стартовать после успешного `setup-agent`. Entry point выполняет `exec` и заменяет себя процессом рантайма агента. При ошибке все трое прекращают цепочку, сохраняя ненулевой код и доступные логи.

Поэтому переносимым становится не hook или YAML-файл, а сам init: окружение меняется, язык общения с ним — нет.

> 🎒 **На пальцах.** Представь электронный замок, установленный у трёх входов: в квартиру, офис и мастерскую. За дверями происходят разные вещи, но замок принимает один сигнал. Зелёный — дверь открывается, красный — остаётся закрытой. Если один вход начнёт считать красный сигнал «почти зелёным», единая система безопасности исчезнет. Код выхода и есть такой общий сигнал.

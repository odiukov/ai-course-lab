  - question: >-
      Одна обязательная проба завершилась ошибкой, а другая дала предупреждение.
      Как должен закончиться init?
    options:
      - Остановиться на первой ошибке и не создавать отчёт
      - >-
        Собрать результаты всех проб, записать отчёт и вернуть ненулевой код
        выхода
      - Записать обе проблемы как предупреждения и разрешить работу
      - 'Повторять проверки, пока обязательная проба не пройдёт'
    correct: 1
    explanation: >-
      Единый отчёт сохраняет все причины, включая предупреждения, но провал
      обязательной пробы блокирует допуск ненулевым кодом выхода. Предупреждения
      видны, вердикт при этом решает блокирующий сбой.
  - question: >-
      Lock создан минуту назад, но файл зависимостей после этого изменился.
      Можно ли использовать кешированный результат?
    options:
      - 'Да, потому что допустимый возраст lock ещё не истёк'
      - 'Да, если предыдущий init завершился успешно'
      - 'Нет, потому что отпечаток зависимостей больше не совпадает'
      - 'Нет, любой lock разрешено использовать только один раз'
    correct: 2
    explanation: >-
      Доверие к локу требует одновременно неистёкшего срока и совпадения
      отпечатка манифестов. Изменение зависимостей делает прежний результат
      неприменимым к новой конфигурации, каким бы свежим ни был lock.
  - question: Какой набор действий подходит для горячего пути init?
    options:
      - >-
        Локально проверить рантайм, зависимости, окружение, состояние и
        доступность команды тестов
      - >-
        Запросить актуальные версии пакетов из сети и попросить LLM оценить
        совместимость
      - Запустить полный отдельный workflow и дождаться ручного подтверждения
      - Пропустить проверки при наличии вчерашнего успешного отчёта
    correct: 0
    explanation: >-
      Горячий путь состоит из локальных детерминированных проб. Сеть и LLM
      вносят недетерминизм и чужие сбои, отдельный workflow с ручным
      подтверждением ломает бюджет времени, а слепое доверие вчерашнему отчёту
      подменяет проверку её следом.
  - question: >-
      При запуске с --fix отсутствует dev-зависимость, а версия runtime
      несовместима. Что допустимо исправить автоматически?
    options:
      - 'Обе проблемы, чтобы init обязательно завершился успешно'
      - 'Только runtime, потому что он блокирует запуск'
      - Только dev-зависимость; изменение runtime требует одобрения
      - 'Ничего: режим --fix может лишь печатать рекомендации'
    correct: 2
    explanation: >-
      Граница автоисправления проходит по тому, меняет ли действие поставляемый
      продукт. Восстановление dev-зависимости — нет; смена рантайма затрагивает
      среду проекта и требует решения человека. При запрете init всё равно
      выдаёт блокирующий статус и предложенную команду, но не выполняет её.

Дальше тебе пригодится не отдельная проба, а привычка проектировать весь допуск как один контракт. Свяжи формат результата из [шага 5](#step-5), оркестрацию из [шага 25](#step-25), отчёт из [шага 26](#step-26) и единый запуск из [шага 29](#step-29). Чаще всего спотыкаются на трёх подменах: считают свежий по времени кеш достоверным, принимают наличие отчёта за успешный вердикт и разрешают `--fix` менять runtime без согласования.

Ты запускаешь пять проб по отдельности: четыре проходят, одна возвращает `fail`. Но готов ли стенд целиком? Пока результаты лежат разрозненно, на этот вопрос некому ответить.

В `run_init` собери функции из [шагов 7](#step-7), [9](#step-9), [12](#step-12) и [14](#step-14), а также пробу команды тестов из [шага 10](#step-10), в один упорядоченный список. Передай каждой только необходимые ей настройки: требуемую версию Python, зависимости, команду тестов, имена переменных окружения и путь к состоянию.

Запусти все пять проб, даже если первая уже обнаружила блокирующий сбой. Это не продолжение работы на неисправном стенде: агент ещё не допущен. Зато человек сразу увидит все причины и не будет перезапускать init после каждого исправления.

Каждый результат уже имеет единый контракт `(name, status, detail)` из [шага 5](#step-5). Задача `run_init` — не разбирать внутренности проб, а добавить к результатам уровень серьёзности по правилам [шага 24](#step-24) и вычислить общий вердикт: запуск запрещён, если хотя бы один результат с уровнем `block` провален. Предупреждение само по себе запрет создавать не должно.

Не переноси в `run_init` сравнение версий, поиск пакетов или расчёт свежести. Иначе оркестратор начнёт дублировать уже проверенную логику. На выходе функции должны остаться данные: полный список результатов и общий вердикт. Их дальнейшее представление — отдельная задача.

> 🎒 **На пальцах.** Перед открытием музея управляющий получает пять отметок: охрана, освещение, климат, кассы и аварийные выходы. Он не чинит лампы и не измеряет влажность сам — это работа специалистов. Он собирает все отметки, учитывает серьёзность каждой и решает, можно ли открыть двери. Одна критическая неисправность перевешивает четыре успешные проверки.

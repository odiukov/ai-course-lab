Ты запускаешь init-скрипт, а одна из библиотек при импорте сразу читает настройки, создаёт файл или пытается подключиться к внешнему сервису. Получается странно: проверка готовности сама меняет стенд — и может упасть не потому, что зависимости нет, а из-за её поведения при запуске.

Нам пока нужен более узкий ответ: **сможет ли Python найти указанную зависимость?** Для этого подходит `importlib.util.find_spec`. Он обращается к механизму поиска Python и просит найти *спецификацию* модуля — служебную карточку с информацией о том, откуда модуль можно загрузить. Если карточка найдена, зависимость доступна; если результат пустой, Python не видит её в текущем окружении.

При этом сам модуль не запускается. Значит, не выполняются команды, записанные на верхнем уровне его файлов: проверка не открывает соединения, не читает секреты и не создаёт неожиданные объекты. Это делает результат повторяемым и безопасным для ранней стадии допуска.

Важно не приписывать такой пробе лишнего. Она подтверждает наличие зависимости, но не доказывает, что библиотека полностью исправна или совместима со всем проектом. Здесь проверяется ровно один факт: путь загрузки существует. Для перечисленных зависимостей этого достаточно, чтобы вернуть знакомые из [шага 5](#step-5) имя, статус и понятное объяснение.

Так init узнаёт, есть ли нужные инструменты, не включая их раньше времени.

> 🎒 **На пальцах.** Представь библиотечный каталог. Тебе нужно проверить, есть ли книга в фонде, но открывать её и выполнять напечатанные внутри инструкции незачем. Ты находишь карточку с шифром полки: карточка есть — книгу можно получить, карточки нет — искать нечего. `find_spec` работает как такой каталог, а импорт был бы уже чтением книги.

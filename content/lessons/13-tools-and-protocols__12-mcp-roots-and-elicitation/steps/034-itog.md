  - question: >-
      Клиент объявил корень file:///home/user/notes. Сервер хочет прочитать
      file:///home/user/notes/../secrets/keys.txt. Что должно произойти?
    options:
      - 'Доступ разрешён: строка начинается с file:///home/user/notes'
      - 'Доступ запрещён: после разворачивания пути ../ выводит за пределы корня'
      - Сервер сам добавляет secrets в свой список корней и читает файл
      - 'Клиент автоматически расширяет корень до file:///home/user'
    correct: 1
    explanation: >-
      Сравнивать надо не строки, а нормализованные URI посегментно. После
      разворачивания ../ путь ведёт в secrets, за границу согласия, и сервер
      обязан отказать.
  - question: >-
      Инструмент запросил elicitation, а пользователь закрыл окно крестиком,
      ничего не выбрав. Что сервер обязан сделать?
    options:
      - Считать это согласием по умолчанию и выполнить действие
      - 'Повторить запрос ещё раз, пока пользователь не ответит'
      - Обработать это как отдельную ветку и завершить вызов без действия
      - >-
        Вернуть пустой объект с полями схемы, заполненными значениями по
        умолчанию
    correct: 2
    explanation: >-
      У ответа три ветки: accept, decline и cancel. Закрытое окно — не согласие
      и не отказ по существу, действие не выполняется, а вызов завершается без
      изменений.
  - question: >-
      Инструмент удаления заметок вызывают массово, по двести штук за прогон, и
      на каждую он показывает окно подтверждения. Что здесь не так?
    options:
      - 'Ничего: подтверждение каждого удаления — самый безопасный вариант'
      - >-
        Двести окон обесценивают подтверждение, человек жмёт «ок» не читая, и
        оно перестаёт быть согласием
      - Elicitation вообще нельзя использовать для удаления
      - Надо просто увеличить таймаут ожидания ответа
    correct: 1
    explanation: >-
      Elicitation стоит дорого — он прерывает цикл. Когда его показывают на
      каждый рутинный шаг, человек перестаёт читать, и окно превращается в
      формальность вместо реального решения.
  - question: >-
      Сервер заметок хочет получить доступ к папке за пределами объявленных
      корней. Как это правильно устроено в MCP?
    options:
      - Сервер вызывает roots/add и дописывает нужный корень себе сам
      - >-
        Сервер не может расширить область: набор корней объявляет клиент, а
        изменение приходит уведомлением о смене списка
      - >-
        Сервер шлёт elicitation, и ответ пользователя автоматически становится
        новым корнем
      - Сервер читает папку и сообщает клиенту постфактум
    correct: 1
    explanation: >-
      Границу задаёт та сторона, которая отвечает за согласие пользователя, —
      клиент. Сервер может лишь запросить текущий список; расширение приходит от
      клиента вместе с уведомлением о том, что список изменился.
---

Урок держался на одном слове, которого в таблице терминов нет прямо: согласие. Корни — согласие, выданное заранее, одним списком URI. Elicitation — согласие, запрошенное на месте, посреди вызова инструмента.

Дальше в курсе это понадобится постоянно: любой сервер, который трогает файлы, чужие API или деньги, стоит на этих двух опорах. Спотыкаются обычно на трёх местах. Первое — сравнение URI строками вместо посегментного сравнения нормализованных путей ([шаг 8](#step-8)). Второе — обработка только ветки accept: decline и cancel молча проваливаются в «ну наверное да» ([шаг 20](#step-20)). Третье — привычка спрашивать на каждый чих, после которой пользователь жмёт «ок» вслепую ([шаг 28](#step-28)).

Проверь себя.

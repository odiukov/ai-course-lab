type: check
title: 'Проверка: из трубы пришло сообщение без id'
source_anchor: '### Notification handling'
check:
  - question: >-
      Ты ждёшь ответ на tools/call с id 7, а из трубы первым выходит сообщение
      без поля id. Что с ним правильно сделать?
    options:
      - 'Выбросить: раз id нет, сопоставить с запросом нельзя'
      - 'Забрать из трубы и положить в очередь, продолжая ждать ответ с id 7'
      - >-
        Отправить серверу подтверждение, что сообщение получено, и снова ждать
        id 7
      - 'Остановить чтение до прихода ответа с id 7, а потом вернуться за ним'
    correct: 1
    explanation: >-
      Отсутствие id — признак уведомления. Читающий поток забирает из трубы всё
      подряд и складывает в очередь, поэтому труба не забивается, а ожидание
      ответа с id 7 продолжается спокойно.
  - question: >-
      Клиент решил на каждое уведомление отвечать серверу «ок, принял». Чем это
      плохо?
    options:
      - 'Ничем, просто лишний трафик по трубе'
      - 'Уведомление придётся подтверждать дважды — и до, и после обработки'
      - >-
        На уведомления отвечать нельзя: у них нет id, и адресовать ответ
        попросту некуда
      - Сервер после подтверждения перестанет присылать list_changed
    correct: 2
    explanation: >-
      Ответ в этом протоколе всегда привязан к id запроса. У уведомления id нет,
      поэтому подтверждать его нечем и не нужно — на него просто реагируют
      действием.
---

После этого куска ты должен уметь по одному признаку — есть поле `id` или нет — сказать, что за сообщение вышло из трубы, и не перепутать «жду ответ» с «читаю всё». Спотыкаются обычно на двух вещах. Первая: соблазн выбросить всё, чего не ждёшь, — и потерять `tools/list_changed` из [шага 21](#step-21). Вторая: попытка вежливо подтвердить уведомление, хотя отвечать некуда. Ловушку «читаю только то, чего жду» разбирали в [шаге 22](#step-22), а `drain` из [шага 23](#step-23) как раз и снимает всё подряд, не разбираясь, кому это адресовано.

  - question: >-
      Два подключённых сервера объявили инструмент с одинаковым именем search, а
      клиент решил взять первый пришедший. Что увидит пользователь?
    options:
      - Модель получит два инструмента search и сама выберет нужный по описанию
      - 'Второй сервер вообще не подключится, пока имя не станет уникальным'
      - >-
        В списке будет один search, и все вызовы уйдут только на тот сервер,
        который успел раньше
    correct: 2
    explanation: >-
      Список инструментов плоский: одно имя — одна запись в таблице
      маршрутизации. Инструмент второго сервера просто становится недоступен, и
      никакой ошибки при этом не видно.
  - question: >-
      Клиент отправил tools/call и читает из трубы только ответ с нужным id. Из
      трубы приходит сообщение без id — notifications/tools/list_changed. Чем
      это плохо?
    options:
      - >-
        Ничем: сообщения без id можно молча выбрасывать, ответ всё равно придёт
        следующим
      - >-
        Клиент упрётся в сообщение, которое не считает своим, и либо потеряет
        уведомление, либо застрянет, не дочитав до ответа
      - 'Сервер повторит уведомление с id, как только клиент ответит на первое'
    correct: 1
    explanation: >-
      Труба одна и общая: пока непрочитанное сообщение лежит в ней, до ответа не
      добраться. Поэтому читать надо всё подряд, а разбирать — по наличию id.
  - question: >-
      Сервер запущен через stdio и его stdout закрылся (EOF). Что это значит для
      клиента?
    options:
      - >-
        Сессия мёртвая: у stdio процесс и есть сессия, надо перезапускать
        процесс
      - Сервер просто молчит; надо послать ping и подождать ответа
      - 'Надо переподключиться к той же сессии по её id, состояние сохранится'
    correct: 0
    explanation: >-
      У stdio нет id сессии, к которой можно вернуться: время жизни дочернего
      процесса и есть сессия. EOF — это не тишина, а конец, и возможности с
      инструментами надо обнаруживать заново.
  - question: >-
      Сервер падает раз за разом. Клиент перезапускает его с задержками 1, 2, 4,
      8, 16, 30, 30 секунд. Зачем потолок 30, а не просто дальше удваивать?
    options:
      - 'Чтобы не превысить лимит попыток: после 30 секунд клиент сдаётся'
      - >-
        Чтобы паузы не выросли до минут и часов — иначе живой сервер после
        починки будет ждать возвращения слишком долго
      - >-
        Потому что дольше 30 секунд дочерний процесс всё равно нельзя держать
        незапущенным
    correct: 1
    explanation: >-
      Удвоение нужно, чтобы не долбить мёртвый сервер, а потолок — чтобы
      починенный сервер поднялся в обозримое время, а не через полчаса.

Урок начинался с неожиданности: сервер оказался простым, а клиент — сложным ([шаг 1](#step-1)). Всё, что ты писал дальше, было расплатой за это: хендшейк ([шаги 5](#step-5)–[6](#step-6)), состояние сессии ([шаг 7](#step-7)), склейка имён и маршрутизация ([шаги 17](#step-17), [19](#step-19)), фоновое чтение трубы ([шаг 23](#step-23)) и политика переподключения ([шаг 30](#step-30)).

Дальше в курсе эти детали уйдут внутрь SDK — но именно они объясняют, почему инструмент «пропал», почему хост «завис» и почему сервер после падения не вернулся. Обычно спотыкаются на трёх вещах: думают, что модель видит три сервера (она видит один список), что уведомление можно проигнорировать (труба одна, его надо вычитать), и что после EOF сессию можно продолжить.

  - question: >-
      Два подключённых сервера объявили инструмент с одинаковым именем search, а
      клиент решил взять первый пришедший. Что увидит пользователь?
    options:
      - Модель получит два инструмента search и сама выберет нужный по описанию
      - 'Второй сервер вообще не подключится, пока имя не станет уникальным'
      - >-
        В списке будет один search, и все вызовы уйдут только на тот сервер,
        который успел раньше
    correct: 2
    explanation: >-
      Список инструментов плоский: одно имя соответствует одной записи в таблице
      маршрутизации. Инструмент второго сервера становится недоступен, хотя
      явной ошибки может не возникнуть.
  - question: >-
      Клиент отправил tools/call и читает из трубы только ответ с нужным id. Из
      трубы приходит сообщение без id — notifications/tools/list_changed. Чем
      это плохо?
    options:
      - >-
        Ничем: сообщения без id можно молча выбрасывать, ответ всё равно придёт
        следующим
      - >-
        Клиент либо потеряет уведомление, либо нарушит чтение общего потока,
        пытаясь дождаться только выбранного ответа
      - 'Сервер повторит уведомление с id, как только клиент ответит на первое'
    correct: 1
    explanation: >-
      Все сообщения приходят по одной трубе, поэтому клиент должен
      последовательно вычитывать их и затем маршрутизировать. Сообщения с id
      сопоставляются с запросами, а уведомления без id передаются своим
      обработчикам.
  - question: >-
      Сервер запущен через stdio, и его stdout закрылся с EOF. Что это значит
      для клиента?
    options:
      - >-
        Сессия завершена: для восстановления нужно запустить новый процесс и
        заново обнаружить его возможности
      - Сервер просто молчит; нужно послать ping и продолжить ждать
      - >-
        Нужно подключиться к прежней сессии по её идентификатору, сохранив всё
        состояние
    correct: 0
    explanation: >-
      У stdio нет отдельного идентификатора, по которому можно вернуться к
      завершившейся сессии. EOF означает закрытие транспорта; после перезапуска
      возникает новая сессия, требующая повторной инициализации.
  - question: >-
      Сервер падает раз за разом. Клиент перезапускает его с задержками 1, 2, 4,
      8, 16, 30, 30 секунд. Зачем ограничивать задержку потолком 30 секунд, а не
      продолжать удвоение?
    options:
      - Чтобы после достижения потолка полностью прекратить попытки
      - >-
        Чтобы паузы не выросли до минут и часов и исправленный сервер вернулся в
        обозримое время
      - >-
        Потому что дочерний процесс технически нельзя оставлять остановленным
        дольше 30 секунд
    correct: 1
    explanation: >-
      Рост задержки снижает частоту запусков неисправного сервера. Потолок в 30
      секунд при этом не даёт интервалам вырасти настолько, что восстановившийся
      сервер будет слишком долго ждать следующей попытки.

Урок начинался с неожиданности: сервер оказался простым, а клиент — сложным ([шаг 1](#step-1)). Всё, что ты писал дальше, было расплатой за это: хендшейк ([шаги 5](#step-5)–[6](#step-6)), состояние сессии ([шаг 7](#step-7)), склейка имён и маршрутизация ([шаги 17](#step-17), [19](#step-19)), фоновое чтение трубы ([шаг 23](#step-23)) и политика переподключения ([шаг 30](#step-30)).

Дальше в курсе эти детали уйдут внутрь SDK — но именно они объясняют, почему инструмент «пропал», почему хост «завис» и почему сервер после падения не вернулся. Обычно спотыкаются на трёх вещах: думают, что модель видит три сервера (она видит один список), что уведомление можно проигнорировать (труба одна, его надо вычитать), и что после EOF сессию можно продолжить.

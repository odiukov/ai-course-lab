Ты извлекаешь заказ, и модель возвращает вполне правильный JSON: статус `"оплачено"`, сумму `-300`, код клиента `"VIP семь"` и ещё поле `"comment": "кажется, важный заказ"`. Типы соблюдены: статус и код — строки, сумма — число. Но приложению от этого не легче: оно ждёт точные значения и не знает, что делать с самодеятельностью модели.

Здесь контракт из [шага 4](#step-4) можно сузить:

```json
{
  "type": "object",
  "properties": {
    "status": { "type": "string", "enum": ["paid", "unpaid", "void"] },
    "amount": { "type": "number", "minimum": 0, "maximum": 1000000 },
    "customer_code": {
      "type": "string",
      "pattern": "^[A-Z]{3}-[0-9]{4}$"
    }
  },
  "additionalProperties": false
}
```

`enum` закрывает выбор: любое значение вне списка запрещено, даже близкое по смыслу. `minimum` и `maximum` задают включённые границы, поэтому здесь допустимы и `0`, и `1000000`. `pattern` проверяет форму строки: три латинские заглавные буквы, дефис и четыре цифры. Знаки `^` и `$` означают, что правилу должна соответствовать вся строка, а не случайный фрагмент внутри неё.

Наконец, `additionalProperties: false` запрещает поля, которых нет в `properties`. Это важно: неизвестное поле не «безобидно игнорируется», а считается нарушением контракта.

Так схема проверяет уже не только упаковку значения, но и границы свободы внутри неё.

> 🎒 **На пальцах.** Представь аккредитацию на кинофестиваль. В анкете можно выбрать только одну из напечатанных ролей, возраст должен попадать в допустимый диапазон, номер бейджа — выглядеть как `ABC-1234`, а дописывать собственную графу нельзя. Анкета может быть аккуратно заполнена буквами и числами, но без этих ограничений она всё равно не годится для пропускной системы.

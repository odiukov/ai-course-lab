Ты проверяешь верхний объект — `required` заполнен, `additionalProperties` равен `false`. Но API всё равно отвечает 400: нарушение спряталось в объекте внутри массива. Значит, проверки только корня недостаточно.

Твоя функция `strict_mode_problems` должна пройти по всей схеме и вернуть список найденных нарушений, не изменяя саму схему. Здесь полезен рекурсивный обход из [шага 6](#step-6), только теперь путь ведёт не к данным модели, а к месту в самой схеме: например, `$.properties.orders.items`.

На каждом узле проверь три требования из [шага 10](#step-10):

- Если это объект, каждое имя из `properties` должно присутствовать в `required`. Сообщай, какие именно поля пропущены.
- У каждого объекта `additionalProperties` должен быть именно `false`. Отсутствующий ключ тоже считается проблемой.
- Оставшийся `$ref` нужно зарегистрировать как нарушение: на этом этапе схема должна быть уже развёрнута и не зависеть от внешней ссылки.

После локальной проверки спускайся в подсхемы из `properties` и в `items` массива. Не останавливайся на первой ошибке: один запуск должен показать весь список мест, которые придётся исправить.

Не перепутай обязательность с допустимостью `null`. Поле с типом `["string", "null"]` всё равно должно находиться в `required`; твоя функция проверяет устройство контракта, а не выбирает значение за модель.

Хороший результат здесь — не просто «схема нестрогая», а несколько точных диагнозов с путями. Тогда ответ 400 перестаёт быть загадкой.

> 🎒 **На пальцах.** Представь склад с коробками внутри коробок. На каждой должен быть полный список содержимого, пломба от незаявленных предметов и никаких записок «остальное на другом складе». Проверить только внешнюю коробку мало: нарушение может лежать в третьей вложенной упаковке. `strict_mode_problems` раскрывает их все и записывает адрес каждой проблемы.

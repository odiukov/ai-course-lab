Ты передаёшь будущему экстрактору три поля: `amount`, `status` и `comment`. Описания выглядят разумно, но API интересует не намерение, а точная структура JSON Schema. Один забытый `required` — и запрос отклонён ещё до ответа модели.

Твоя задача — написать `schema_from_fields`, которая превращает контракт из [шага 4](#step-4) в схему объекта. Функция должна создать `properties`, поместив под имя каждого поля его подсхему: тип, `enum` и ограничения вроде `minimum` или `maxLength`. Не теряй эти ограничения при сборке — именно они превращают общее описание в проверяемый контракт.

Затем собери `required`. В strict mode туда входят **все** имена из `properties`, включая логически необязательные поля. Если `comment` может отсутствовать по смыслу, его всё равно нельзя пропустить в JSON: подсхема должна разрешать `null`, а модель обязана явно вернуть это значение.

Наконец, закрой объект с помощью `additionalProperties: false`. Проверь три вещи: порядок полей не влияет на результат, пустой список даёт корректную схему пустого объекта, а исходные описания после вызова не изменяются. Последнее легко пропустить, если функция дописывает служебные ключи прямо во вложенные словари.

Ориентир простой: результат должен быть готов к отправке провайдеру без ручного добавления `required` или запрета лишних полей.

> 🎒 **На пальцах.** Представь, что ты комплектуешь настольную игру перед отправкой: карточки раскладываешь по подписанным ячейкам, все названия заносишь в перечень комплектации, а свободные отделения пломбируешь. Даже карточка «нет комментария» должна лежать на месте — просто с таким значением. `schema_from_fields` делает ту же упаковочную работу с полями JSON.

Модель вернула счёт: имя клиента, три позиции и сумму. JSON уже разобран, но перед тобой всё ещё словарь: нужно помнить ключ `"total_usd"`, проверять его наличие и следить, чтобы вместо числа не пришло `"неизвестно"`. А вложенные позиции придётся разбирать отдельно.

Pydantic позволяет описать ожидаемый результат обычным Python-классом:

```python
class Invoice(BaseModel):
    customer: str
    line_items: list[LineItem]
    total_usd: Decimal
```

У этого класса две роли. Для отправки запроса метод `model_json_schema()` превращает поля в JSON Schema: `customer` должен быть строкой, `line_items` — списком объектов `LineItem`, а `total_usd` — числовым значением. Дальше адаптер провайдера упаковывает этот контракт в нужную оболочку — такую разницу между API ты видел в [шаге 15](#step-15).

На обратном пути происходит зеркальное преобразование. Полученный JSON проверяется по тем же объявлениям и становится экземпляром `Invoice`. Поэтому ты работаешь с `invoice.total_usd`, а редактор кода понимает его тип и подсказывает доступные операции. Вложенные элементы тоже превращаются в `LineItem`, а не остаются безымянными словарями.

Если значение не подходит, Pydantic поднимает `ValidationError`. Внутри есть путь к проблемному полю — тот же принцип точной навигации по вложенным данным, который разобран в [шаге 6](#step-6). Класс здесь одновременно описывает форму ответа и форму объекта, с которым продолжает работать Python.

> 🎒 **На пальцах.** Представь ателье: лекало показывает цеху, какие детали нужно вырезать, а готовый пиджак проверяют по тому же лекалу. Если рукав короче, мастер укажет именно на рукав. Pydantic-модель играет обе роли: передаёт машине форму заказа, а тебе возвращает уже подогнанный объект, а не пакет разрозненных лоскутов.

Ты описал счёт в TypeScript:

```ts
type Invoice = {
  customer: string;
  total: number;
  currency: "EUR" | "USD";
};
```

Редактор подсвечивает ошибки, пока ты пишешь код. Но ответ модели приходит уже во время работы программы, а тип `Invoice` после компиляции исчезает. Если модель вернёт строку `"много"` вместо числа, один только TypeScript этого не заметит.

Zod оставляет контракт «живым»:

```ts
const Invoice = z.object({
  customer: z.string(),
  total: z.number().nonnegative(),
  currency: z.enum(["EUR", "USD"]),
});
```

Здесь `z.string()`, `z.number()` и `z.enum()` описывают те же ограничения, которые ты задавал в JSON Schema на [шагах 4](#step-4) и [9](#step-9). Но теперь это исполняемый объект: Zod может проверить реальные данные и либо вернуть корректный результат, либо точно указать нарушение.

Из этой же записи TypeScript выводит статический тип:

```ts
type InvoiceData = z.infer<typeof Invoice>;
```

А помощник OpenAI Node SDK `zodResponseFormat` переводит объект Zod в JSON Schema для запроса к модели. Получается два применения одного описания: API ограничивает форму ответа, а программа проверяет полученное значение перед использованием.

По роли это прямой аналог Pydantic из [шага 26](#step-26): меняется синтаксис языка, но граница безопасности остаётся на том же месте — между внешним ответом и твоим кодом.

> 🎒 **На пальцах.** Представь форму для печенья, по которой кондитер и вырезает тесто, и проверяет готовые изделия перед упаковкой. В TypeScript такую форму играет Zod: SDK превращает её в требования для модели, а затем она же прикладывается к результату. Обычный тип TypeScript похож лишь на рисунок формы в инструкции — полезен при подготовке, но готовое печенье им уже не проверишь.

---
id: 008-constraints-check
type: check
title: 'Проверка: какое ограничение отвергнет значение'
source_anchor: '### JSON Schema 2020-12 — the lingua franca'
check:
  - question: >-
      Поле quantity по схеме должно быть integer, но модель вернула строку «3».
      Какое ограничение отвергнет ответ?
    options:
      - required для поля quantity
      - type со значением integer
      - properties объекта
    correct: 1
    explanation: >-
      Поле присутствует, поэтому required выполнен. Ответ отвергнет type: строка
      «3» не становится целым числом только потому, что выглядит как число.
  - question: >-
      Схема требует массив строк, а второй элемент оказался boolean. Где
      валидатор найдёт нарушение?
    options:
      - В описании самого массива
      - В required родительского объекта
      - В подсхеме items для второго элемента
    correct: 2
    explanation: >-
      items проверяет каждый элемент массива по одной подсхеме, поэтому ошибка
      относится именно ко второму элементу и его типу.
---

Здесь важно связать плохое значение с конкретным ограничением из контракта. Частая ловушка — считать, что `required` проверяет правильность значения. Оно отвечает только за присутствие поля; тип содержимого проверяет `type`. В массиве та же проверка применяется к каждому элементу через `items`, а точный путь до нарушителя даёт валидатор из [шага 7](#step-7).

> 🎒 **На пальцах.** Представь кассу самообслуживания: она отдельно замечает, положил ли ты товар на весы, и отдельно сверяет его вес. Наличие товара — это `required`, соответствие ожидаемому виду данных — `type`. Товар может лежать на месте и всё равно не пройти вторую проверку.

      - Удалить required целиком

    explanation: >-
      В strict mode все объявленные поля объекта должны быть обязательными.

  - question: >-
      Модель вернула корректный JSON, но добавила поле debug, запрещённое через
      additionalProperties: false. Как классифицировать результат?
    options:
      - Успешный результат
      - Parse error
      - Schema violation
      - Refusal
    correct: 2
    explanation: >-
      JSON разобрался, поэтому это не parse error. Но данные нарушили контракт

  - question: Провайдер явно сообщил refusal. Что должен сделать конвейер?
    options:
      - Повторять запрос до исчерпания лимита
      - Передать отказ в отдельную ветку и остановить ремонт
      - Подставить пустой объект
      - Попросить модель исправить JSON
    correct: 1
    explanation: >-
      Refusal — самостоятельный типизированный исход, а не повреждённый ответ.

  - question: >-
      Ты запускаешь модель с открытыми весами и хочешь гарантировать форму

    options:
      - Подробный промпт с примером JSON
      - Проверку результата после генерации

    correct: 2
    explanation: >-
      Grammar enforcement реализует constrained decoding для открытых моделей:
      невалидные продолжения исключаются ещё при генерации. Промпт и
      поствалидация такой гарантии не дают.

Дальше тебе пригодится не запоминание названий, а привычка видеть весь контракт: схема ограничивает форму, strict mode усиливает гарантию, парсер различает три исхода, а повтор чинит только исправимые ошибки. Чаще всего спотыкаются, когда принимают корректный JSON за успешный результат или пытаются «отремонтировать» отказ. Вернись к ветвлению из [шага 31](#step-31), если сомневаешься в решении.

> 🎒 **На пальцах.** Представь пункт приёма анализов. Пробирка может быть разбита, иметь чужую этикетку или не появиться из-за отказа пациента. Это три разные ситуации: переупаковать можно не всё. Надёжный процесс сначала распознаёт исход и лишь затем решает — принять, исправить или остановиться.

title: Детекция требует того же секретного разбиения словаря и обычно API вендора
source_anchor: '### Text watermarking (SynthID-text style)'
---

Ты отправляешь один и тот же текст двум детекторам. Первый уверенно находит водяной знак, второй видит обычный текст. Кажется, один из них сломан: ведь слова перед ними совершенно одинаковые.

Но детектор проверяет не видимые слова сами по себе. Для каждой позиции он должен заново получить именно то разбиение словаря, которым пользовалась модель при генерации. Совпасть должны токенизация текста, длина контекста \(K\), способ хеширования и секретный ключ или другая закрытая настройка. Если хотя бы одна деталь отличается, слово, считавшееся при генерации зелёным, проверяющий может назвать красным.

Тогда накопленный сигнал рассыпается. Детектор всё ещё вычислит знакомый по [шагу 6](#step-6) z-score, но будет считать «зелёные» токены по чужой разметке. Результат окажется около случайного уровня даже для действительно помеченного текста.

Поэтому опубликованного описания метода недостаточно для независимой проверки конкретной модели. Открытая реализация позволяет создавать и исследовать водяные знаки, но не обязательно раскрывает секретные параметры, использованные в чужом продакшене. Журналист, преподаватель или площадка обычно отправляют текст в API вендора: у него есть нужная конфигурация, и он возвращает результат детекции.

Иными словами, сигнал встроен в текст, а способность правильно его прочитать остаётся у владельца ключа.

> 🎒 **На пальцах.** Представь радиостанцию, которая каждую секунду переключается на новую частоту по секретному расписанию. Ты записал весь эфир, но обычный приёмник слышит лишь обрывки и шум. Приёмник владельца знает то же расписание и собирает передачу целиком. Водяной знак похож: текст доступен всем, но без правильной последовательности разбиений его сигнал не складывается.

Клиент подключился к двум серверам сразу: `research-mcp` отдаёт `arxiv_search`, `notes_read`, `generate_report`, а сервер команды соседей — `search` и `summarize_paper`. Модель никакой топологии не видит, ей нужен один список имён — тот самый плоский нейминг из [шага 20](#step-20). А ты как раз стоишь перед пустой функцией `merge_tools`, которой этот список надо собрать.

Первый соблазн — сложить оба списка в один массив и отдать. Но тогда после ответа модели «зову `summarize_paper`» ты не знаешь, на какой из двух адресов слать `tools/call`. Значит, склейка списков — не главное. Главное, что `merge_tools` строит **маршрутную таблицу**: имя инструмента → id сервера плюс сам дескриптор. Список для модели — производная от неё.

Дальше — совпадения имён. Если у обоих серверов есть `search`, безмолвно оставить один нельзя: половина инструментов исчезнет, и ты об этом узнаешь только по странному отказу через час. Решение должно быть явным и одинаковым при каждом запуске — либо разрешаем конфликт по фиксированному правилу, либо возвращаем ошибку, но никогда не «как повезёт с порядком».

Отсюда и то, на что смотреть при проверке. Прогони merge дважды, переставив серверы местами: реестр обязан выйти байт в байт тот же. Сложи число инструментов на входе — оно должно сойтись с числом на выходе. И не потеряй хэш описания у каждой записи: без него `verify_pins` из [шага 17](#step-17) сверять будет нечего.

Плоский список — это витрина; за ней должна остаться запись, кто чей.

> 🎒 **На пальцах.** Забег, два клуба, у каждого свой протокол. Судья переписывает всех в один стартовый лист — но рядом с фамилией держит клуб, иначе медаль потом вручать некуда. А если в обоих клубах бежит Иванов, судья не вычёркивает второго молча: он заранее решил, как их различать, и решает так каждый раз одинаково.

Ты запускаешь три ранжирования на одном наборе запросов и получаешь длинные списки документов. Глазами их уже не сравнить: в одном нужный документ стоит первым, в другом — четвёртым, а для части запросов не найден вовсе. Твоя задача — дописать `evaluate_rankings`, чтобы она превратила эти списки в сопоставимые числа.

Функция должна получить выдачи, эталонные оценки релевантности и значение `k`. Для каждого запроса возьми первые `k` результатов и посчитай три метрики, разобранные в [шаге 34](#step-34): Recall@k, MRR и nDCG@k. Затем усредни значения по запросам и верни их под понятными именами, чтобы одной функцией можно было оценивать BM25, dense и hybrid из [шага 37](#step-37).

Следи за тремя местами, где легко ошибиться. Если релевантного документа нет в выдаче, вклад запроса в MRR равен нулю — такой запрос нельзя просто пропустить. Для Recall@k учитывай только запросы, у которых в эталоне действительно есть релевантные документы. А при вычислении nDCG сначала построй идеальный порядок из тех же эталонных оценок: без него полученный DCG не с чем нормализовать. Если идеальный DCG равен нулю, результат для запроса тоже должен быть нулём.

Баллы ранжировщика здесь не определяют релевантность: они лишь задают порядок документов. Истиной остаётся эталон. Именно это делает сравнение трёх методов честным.

> 🎒 **На пальцах.** Представь судью на соревновании кулинаров. Перед ним три очереди блюд, составленные разными помощниками, и отдельный лист с оценками экспертов. Судья смотрит только первые `k` блюд каждой очереди, сверяет их с листом и заполняет одинаковый протокол. Если блюда нет в очереди, оно получает нулевой вклад — исчезновение результата нельзя выдать за отсутствие ошибки.

Возьми три документа длиной 4, 7 и 1 токен. Если при каждом поиске заново разбирать их текст и считать слова, результат будет верным, но работа повторится для каждого запроса. В [шаге 8](#step-8) ты уже видел, какие данные выгодно подготовить заранее. Теперь собери их в `build_bm25_index`.

Функция должна принять корпус документов и один раз пропустить каждый текст через `tokenize` из [шага 7](#step-7). Для каждого документа сохрани две вещи: его длину после токенизации и `Counter` с количеством вхождений каждого термина. Например, если `error` встретился трижды, в счётчике должно остаться `error: 3`, а не просто отметка о наличии слова.

Затем посчитай общие характеристики корпуса: число документов и среднюю длину. Для длин 4, 7 и 1 среднее равно 4. Обрати внимание на пустой корпус: делить сумму длин на ноль нельзя, поэтому функция должна сразу отклонить такой ввод понятной ошибкой.

Последняя часть — частота документа для каждого термина: в скольких документах он присутствует. Здесь легко случайно посчитать вхождения. Если `error` повторяется пять раз в одном документе, он всё равно увеличивает этот счётчик только на единицу. Поэтому при обработке документа тебе нужен набор его уникальных токенов.

Проверь себя на слове с повторами: локальный `Counter` хранит все пять вхождений, а общий счётчик документов — одно. Если эти числа различаются именно так, каркас индекса собран правильно.

> 🎒 **На пальцах.** Представь архив газет. Архивариус заранее записывает толщину каждого выпуска, число повторов каждого слова внутри него и отдельно — в скольких выпусках слово вообще появилось. Пять упоминаний «вулкан» в одной газете дают пять в карточке выпуска, но только одну отметку в каталоге архива. `build_bm25_index` готовит ровно такие карточки, чтобы потом не перелистывать весь архив заново.

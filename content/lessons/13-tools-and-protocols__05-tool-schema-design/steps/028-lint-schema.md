У тебя уже три готовые проверки: [is_snake_case](#step-7), [lint_name](#step-12), [lint_description](#step-18). Возьми реестр из 30 инструментов и прогони их по каждому инструменту отдельно — все чисты. А модель всё равно путает `notes_search` и `contacts_search`.

Почему? Потому что часть проблем не видна изнутри одного инструмента. Два описания вида «Search records by query» безупречны каждое по себе, и только рядом друг с другом становятся бедой. Значит, линтеру нужен вход не «одна схема», а весь список сразу.

`lint_schema(registry)` принимает список схем — у каждой `name`, `description`, `parameters` — и возвращает список находок. Находка — не строка «ошибка», а структура: имя инструмента, поле, уровень (`error`/`warning`), текст. Уровень важен: отсутствие описания у параметра ([шаг 27](#step-27)) блокирует, а короткое описание в 45 символов — только замечание.

Внутри — два прохода. Первый по каждому инструменту: `lint_name`, `lint_description`, затем параметры — закрытый набор без `enum` ([шаг 24](#step-24)), `type: any`, поле без описания, раздутый `required` ([шаг 25](#step-25)), идентификатор без `pattern` ([шаг 26](#step-26)), аргумент `action` больше чем с тремя значениями ([шаг 22](#step-22)). Второй проход — по реестру целиком: совпадающие имена, описания-близнецы, пары без «Do not use for».

Главное, на что смотреть: линтер не останавливается на первой находке. Он собирает все и отдаёт списком — иначе ты чинишь реестр по одной строчке за прогон.

> 🎒 **На пальцах.** Три корректора вычитали по рассказу: запятые на месте, имена героев не путаются, всё чисто. И только редактор, читая сборник подряд, замечает, что два рассказа называются «Возвращение». Ни один корректор этого увидеть не мог — у каждого на столе лежал один текст. `lint_schema` и есть такой редактор: он держит перед глазами весь реестр.

  - question: >-
      Заданию требуется группа GPU, которую нельзя безопасно запускать по
      частям. Как поведёт себя gang scheduling, если ресурсов для всей группы
      пока недостаточно?
    options:
      - 'Запустит доступную часть группы, а остальные поды оставит в Pending'
      - >-
        Оставит всю группу в ожидании до возможности выделить требуемые ресурсы
        одновременно
      - Попросит HPA уменьшить размер группы
      - Перенесёт работающие поды на недозагруженные узлы
    correct: 1
    explanation: >-
      Gang scheduling размещает группу атомарно: пока нельзя удовлетворить
      запрос целиком, её участники не занимают GPU по отдельности. Так KAI
      Scheduler предотвращает ловушку «7 из 8».
  - question: >-
      GPU почти непрерывно выполняет вычисления, однако ожидающих запросов нет.
      Почему GPU utilization не доказывает, что нужны дополнительные реплики?
    options:
      - >-
        Метрика отражает занятость устройства, но не показывает наличие
        необслуженного спроса
      - Метрика измеряет только время загрузки модели с диска
      - 'Высокая загрузка означает, что Karpenter уже создаёт новый узел'
      - GPU utilization применяется только к обычным CPU-подам
    correct: 0
    explanation: >-
      DCGM_FI_DEV_GPU_UTIL показывает duty cycle GPU. Даже высокая занятость не
      сообщает, растёт ли очередь, поэтому для масштабирования полезнее измерять
      очередь или давление KV-кэша.
  - question: >-
      Почему политика консолидации WhenEmpty безопаснее для работающего
      инференса, чем WhenEmptyOrUnderutilized?
    options:
      - Она удаляет узлы только после достижения максимальной загрузки GPU
      - >-
        Она не считает занятый инференс-подом узел кандидатом на удаление лишь
        из-за недозагрузки
      - Она запрещает HPA создавать новые реплики
      - Она автоматически переносит KV-кэш между узлами без прерывания запросов
    correct: 1
    explanation: >-
      WhenEmpty не удаляет узел, пока на нём работает инференс-под. В уроке эта
      политика дополнена consolidateAfter: 1h, чтобы не консолидировать GPU-пул
      слишком поспешно.
  - question: >-
      После появления нового GPU-узла реплика ещё некоторое время не принимает
      запросы. Какое объяснение наиболее вероятно?
    options:
      - HPA обязан дождаться снижения GPU utilization на старых узлах
      - >-
        Узел готов, но модели ещё нужно загрузить веса и инициализировать
        инференс-движок
      - KAI Scheduler намеренно увеличивает очередь перед запуском
      - Karpenter не позволяет запускать поды на новых узлах
    correct: 1
    explanation: >-
      Поднятие узла — лишь часть холодного старта. Даже после подготовки
      инфраструктуры остаются загрузка весов и инициализация движка, поэтому
      ускорение Karpenter само по себе не гарантирует соблюдение SLO.

Дальше тебе понадобится не набор отдельных настроек, а привычка читать весь путь решения из [шага 33](#step-33): сигнал нагрузки, размещение подов и появление узлов. Чаще всего ошибаются именно на границах слоёв — пытаются лечить очередь новым NodePool или холодный старт более быстрым Karpenter. При спорном выборе возвращайся к потерям запросов и стоимости простоя из [шага 37](#step-37).

> 🎒 **На пальцах.** Представь полярную экспедицию: штаб решает, сколько групп отправить, координатор собирает каждую группу целиком, а база выдаёт подходящие сани. Лишние сани не заменят недостающего участника, а собранная команда не уедет без снаряжения. Успех появляется только тогда, когда все три решения согласованы.

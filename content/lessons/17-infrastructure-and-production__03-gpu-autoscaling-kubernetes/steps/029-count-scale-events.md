После прогона симулятора ты видишь историю числа реплик: например, `2, 2, 5, 5, 3`. Потерянных запросов стало меньше, но автоскейлер дважды дёрнул инфраструктуру. Насколько беспокойно он себя ведёт?

Функция `count_scale_events` получает последовательность значений `replicas` и сравнивает каждое значение с предыдущим. Если число изменилось, это одно событие масштабирования. Поэтому переход `2 → 5` считается одним событием, а не тремя: функция измеряет частоту решений, а не количество добавленных или удалённых реплик.

Первое значение — исходное состояние, сравнивать его ещё не с чем. Повторы тоже не увеличивают счётчик. Для примера выше результат равен `2`: сначала `2 → 5`, затем `5 → 3`. Пустая история и история из одного значения дают `0`.

Обрати внимание на границу ответственности: здесь не нужно оценивать потерянные запросы, простой GPU или качество выбранного числа реплик. Эти показатели разделены в [шаге 28](#step-28). Твоя функция отвечает только на один вопрос: сколько раз автоскейлер менял решение о размере сервиса. Благодаря этому две стратегии можно сравнить не только по результату, но и по «дёрганости».

> 🎒 **На пальцах.** Представь прачечную, где администратор записывает число включённых машин каждые пять минут: `2, 2, 5, 5, 3`. Ты ставишь отметку не за каждую добавленную машину, а за сам момент перенастройки зала. Получатся две отметки: включили больше машин, затем часть выключили. Чем больше отметок, тем чаще система меняет режим.

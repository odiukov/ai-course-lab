Перед тобой три GPU-узла: первый пустует 70 минут, второй — 20 минут, а на третьем работает единственная реплика инференса. Если функция отправит на удаление все «малозагруженные» узлы, третий повторит опасный сценарий из [шага 7](#step-7): рабочая модель будет выселена ради экономии.

Напиши `consolidation_plan`, которая только составляет план консолидации, но ничего не удаляет. Для каждого узла функция должна проверить два условия:

- на узле нет работающих подов;
- узел остаётся пустым не меньше 60 минут.

В итоговый список должны попасть только имена узлов, прошедших обе проверки. В примере выше это первый узел. Второму ещё рано, а третий нельзя трогать независимо от того, насколько мала его загрузка.

Посмотри на поля входных данных в заготовке: одно сообщает количество работающих подов, другое — длительность простоя. Не объединяй проверки через «или»: одного подходящего признака недостаточно. Особенно легко ошибиться на границе — ровно 60 минут уже удовлетворяют правилу `consolidateAfter: 1h`.

Сохрани порядок узлов из входного списка. Так результат будет предсказуемым, а оператор сможет сопоставить план с исходными данными. Главная проверка твоей функции проста: ни один узел с работающей задачей не должен оказаться среди кандидатов, даже если он выглядит недогруженным.

> 🎒 **На пальцах.** Представь ночную парковку спецтехники. Эвакуатору дают список машин, которые можно убрать в дальний ангар. Стоящий час пустой погрузчик подходит. Машина, приехавшая двадцать минут назад, пока остаётся. А мобильную электростанцию с подключённым кабелем нельзя увозить вовсе: свободное место рядом не означает, что она не работает.

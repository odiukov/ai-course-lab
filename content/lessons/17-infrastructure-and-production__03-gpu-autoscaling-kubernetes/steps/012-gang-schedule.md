Перед тобой группа из восьми подов: каждый просит по одной GPU, а свободны только семь. Если выдавать ресурсы по очереди, первые семь подов запустятся, а последний останется `Pending`. Получится та самая бесполезная ловушка из [шага 2](#step-2).

Напиши функцию `gang_schedule`, которая принимает:

- список запросов подов на GPU, например `[1, 1, 1, 1, 1, 1, 1, 1]`;
- количество доступных GPU.

Функция должна вернуть `True`, только если ресурсов хватает всей группе, и `False` во всех остальных случаях. Так принцип «всё или ничего» из [шага 11](#step-11) превращается в конкретную проверку.

Главная ловушка — начать распределять GPU прямо во время обхода списка. Тогда функция успеет мысленно «запустить» несколько подов ещё до того, как обнаружит нехватку. Сначала посчитай общий запрос группы, затем сравни его с доступным количеством. Равенство тоже означает успешный запуск: запрос 8 при наличии 8 должен вернуть `True`.

Проверь три случая: ресурсов больше необходимого, ровно столько же и на одну GPU меньше. Учти и поды с разными запросами, например `[2, 2, 4]`: решение всё равно принимается для суммы всей группы, а не для каждого элемента отдельно.

Здесь ты пока не выбираешь узлы и не запускаешь поды. Функция отвечает на один вопрос: можно ли безопасно начать запуск всей группы прямо сейчас?

> 🎒 **На пальцах.** Представь команду из восьми участников VR-квеста и стойку со шлемами. Администратор не включает первые семь шлемов, пока ищет восьмой: оплачиваемое время уже пойдёт, а игра не начнётся. Он сначала пересчитывает весь комплект и лишь затем запускает сеанс — либо для всей команды, либо ни для кого.

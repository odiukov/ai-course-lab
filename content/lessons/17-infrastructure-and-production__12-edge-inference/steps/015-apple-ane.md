Ты переносишь квантованную модель в iPhone и видишь знакомые 3,5 ГБ весов. Кажется, достаточно включить «ускоритель» — и Apple Neural Engine с производительностью до 38 TOPS сразу возьмёт работу на себя. Но запуск через Metal в `llama.cpp` не означает запуск на ANE: этот путь обращается к GPU через Metal/MPS. Напрямую передать ANE произвольные операции нельзя.

Для ANE нужен вход через Core ML. Модель конвертируют в формат Core ML, после чего система компилирует её под доступные вычислительные блоки и решает, какие операции отдать ANE, GPU или CPU. Практичный вариант для iOS — веса INT4 и активации FP16: первые уменьшают объём модели, вторые сохраняют удобный для выполнения формат промежуточных значений.

Зачем тогда важна унифицированная память? CPU, GPU и ANE используют один общий пул памяти. Если CPU уже загрузил веса, приложению не приходится создавать ещё одну полную копию в отдельной памяти ускорителя. Для модели на несколько гигабайт это экономит время и дополнительное место, особенно при холодном запуске.

Но общий пул не делает чтение бесплатным. ANE всё равно должен получать данные из памяти, поэтому потолок decode из [шага 13](#step-13) никуда не исчезает. Унифицированная память убирает лишний перегон перед вычислением; Core ML открывает сам путь к ANE. Это две разные выгоды, и нужны обе.

> 🎒 **На пальцах.** Представь театральную постановку: актёр и осветитель берут реквизит из одной комнаты за сценой. Не нужно сначала переносить все декорации во вторую кладовую — это и есть выгода общей памяти. Но осветитель допускается к пульту только через режиссёра, который распределяет сцены и команды. В этой роли выступает Core ML: общая кладовая сама по себе не выдаёт доступ к пульту ANE.

  - question: >-
      Toolformer сам разметил корпус вызовами инструментов. По какому признаку
      вызов остаётся в обучающих данных?
    options:
      - Результат вызова помог модели точнее угадать следующий токен текста
      - Вызов оказался синтаксически правильным и прошёл проверку схемы
      - 'Человек-разметчик подтвердил, что инструмент тут уместен'
      - 'Инструмент вернул ответ быстрее, чем за отведённый таймаут'
    correct: 0
    explanation: >-
      Отбор идёт по пользе для предсказания: если подставленный результат снизил
      loss на следующем токене, вызов полезен. Синтаксическая корректность и
      скорость сами по себе ничего не говорят о нужности вызова.
  - question: >-
      Модель прислала вызов, где вместо одного из разрешённых значений enum
      стоит выдуманное. Что правильнее сделать?
    options:
      - Выбросить исключение и остановить весь ход агента
      - Подставить самое близкое разрешённое значение и выполнить вызов
      - >-
        Не выполнять инструмент и вернуть модели наблюдение с описанием, что не
        так
      - Выполнить инструмент как есть — он сам разберётся с неверным значением
    correct: 2
    explanation: >-
      Провал валидации — информация для модели, а не авария. Инструмент не
      запускается, текст ошибки приходит наблюдением, и модель исправляет вызов
      на следующем ходу. Подстановка «ближайшего» значения — угадывание: домен
      нарушен, однозначного восстановления нет.
  - question: >-
      Две модели решили одну задачу разными наборами вызовов, но каталог в итоге
      пришёл в одинаковое состояние. Как это оценит проверка по состоянию
      (state-based)?
    options:
      - >-
        Обе решения верны: сверяется конечное состояние системы, а не текст
        вызовов
      - 'Верна только та, чьи вызовы совпали с эталонной строкой'
      - 'Обе неверны, потому что расхождение с эталоном есть у обеих'
      - 'Решение выбирается по числу вызовов: чем меньше, тем правильнее'
    correct: 0
    explanation: >-
      Оценка по состоянию исполняет траекторию и смотрит на API после неё,
      поэтому дословного совпадения с эталонной цепочкой не требует: разные пути
      к тому же состоянию равноправны. Сверка текста вызова — это AST-матчинг,
      он и даёт ложные минусы на эквивалентных решениях.
  - question: >-
      Инструмент несколько раз подряд упал по таймауту, и предохранитель
      отключил его на минуту. Зачем эта пауза?
    options:
      - Чтобы модель успела переписать аргументы вызова
      - Чтобы агент не молотил в упавшую зависимость и не сжигал ходы вслепую
      - 'Чтобы освободить память, занятую песочницей'
      - Чтобы таймаут инструмента автоматически увеличился
    correct: 1
    explanation: >-
      Серия провалов подряд — сигнал, что дело не в аргументах, а в самом
      инструменте или его зависимости. Пауза не даёт агенту зацикливаться на
      заведомо мёртвом вызове; переписывание аргументов тут не поможет, потому
      что отказ не зависит от них.

Дальше в курсе ты будешь собирать агентов, где инструментов не два, а двадцать, и почти всё из этого урока переезжает туда без изменений: контракт из имени, описания и схемы ([шаг 13](#step-13)), реестр как единственная точка входа ([шаг 15](#step-15)), валидация до исполнения и возврат ошибки наблюдением ([шаг 24](#step-24)), предохранитель ([шаг 31](#step-31)).

Спотыкаются обычно на трёх местах. Первое — путают починку с угадыванием: строка «5» превращается в число, «5 apples» отклоняется ([шаг 20](#step-20)). Второе — считают провал валидации аварией и обрывают ход вместо того, чтобы дать модели шанс исправиться. Третье — забывают про `tool_use_id`, и при параллельных вызовах результаты приезжают не к тем вызовам ([шаг 29](#step-29)).

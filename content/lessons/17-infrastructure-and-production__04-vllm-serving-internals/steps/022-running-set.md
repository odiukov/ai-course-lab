Посмотри на первый вертикальный срез визуализации: в `RUNNING` находятся запросы A, B и C. Они стартовали не обязательно одновременно и уже успели сгенерировать разное число токенов. На очередном decode-проходе каждый получает ровно по одному новому токену.

Допустим, для B этот токен оказался EOS — знаком конца ответа. Важно: B участвовал в текущем проходе полностью. Он исчезнет из `RUNNING` только перед следующим проходом, согласно порядку из [шага 21](#step-21).

Теперь переведи взгляд на следующий срез. Там остаются A и C, а освободившееся место занимает ожидающий запрос D. Новый состав — A, C, D — вместе выполняет следующий decode-проход. Для A это может быть уже сотый токен, для C — двадцатый, а D только что прошёл prefill и получает первый токен ответа.

Ещё через итерацию закончится C, вместо него появится E. Поэтому `RUNNING` — не постоянная группа, набранная в начале, а моментальный список тех, кому сервер готов выдать следующий токен прямо сейчас. На визуализации горизонтальная линия показывает жизнь одного запроса, а каждый вертикальный срез — фактический состав очередного батча.

Батч сохраняется как действие, но постоянно меняется как компания участников.

> 🎒 **На пальцах.** Представь карусель, которая ненадолго останавливается после каждого круга. A, B и C едут первый круг вместе. На остановке B выходит, а на его место садится D; остальные не обязаны покидать свои места. Следующий круг уже делают A, C и D. Карусель продолжает вращаться, но состав пассажиров пересобирается на каждой остановке.

Открой заготовку `schedule_static` и найди место, где формируется очередная группа запросов. Допустим, в очереди лежат длины ответов `2, 7, 3, 5`, а размер батча равен трём. Первый запуск должен взять только `2, 7, 3`; запрос с длиной `5` пока остаётся ждать.

Дальше функция должна воспроизвести модель из [шага 3](#step-3): каждый запрос занимает позицию в батче столько шагов, сколько токенов ему нужно, но весь батч заканчивается лишь после самого длинного запроса. Поэтому для первой тройки длительность раунда определяется числом `7`, а не суммой `12` и не средним значением `4`.

Собери функцию по трём правилам:

1. Бери из очереди не больше запросов, чем разрешает размер батча, сохраняя их порядок.
2. Для выбранной группы вычисляй длительность по самому длинному запросу.
3. Только после завершения этого раунда переходи к следующей группе и прибавляй её длительность к общему времени.

Последний батч может оказаться неполным — это нормальный случай, а не ошибка. Отдельно проверь пустой список: функция не должна искать максимум там, где нет ни одного запроса.

После реализации прогони два мысленных теста: запросы одинаковой длины и один длинный среди нескольких коротких. В первом случае почти нет лишних шагов; во втором результат должен показать тот самый общий барьер из [шага 2](#step-2). Если длинный запрос не увеличил время всей группы, статический батч у тебя смоделирован неверно.

> 🎒 **На пальцах.** Представь маршрутный микроавтобус, который берёт троих пассажиров и возвращается на стоянку только после последней остановки. Двое могут выйти почти сразу, но следующая группа не сядет, пока машина не завершит весь маршрут. `schedule_static` делает то же самое: набирает фиксированную группу, ждёт её самый длинный «маршрут» и лишь затем берёт следующую.

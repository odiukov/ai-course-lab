title: Как статический батч превращает разные запросы в один общий барьер
source_anchor: '## The Problem'
---

Ты собрал четыре запроса, нажал «запустить» и видишь странность: один ответ уже закончен, но его место на GPU остаётся занятым. Пятый запрос ждёт снаружи, хотя внутри будто бы освободился слот. Почему его нельзя просто добавить?

Потому что статический батч фиксирует состав группы перед запуском. Запросы превращаются в один набор данных, который модель обрабатывает синхронно: сначала вся группа проходит prefill, затем вместе делает шаги decode. После каждого шага возникает общий барьер — точка, дальше которой никто не движется, пока текущую итерацию не завершили все участники батча. Это похоже на дверь в музее, которую смотритель открывает только после сбора всей экскурсии.

У запросов при этом разный объём работы. Один быстро выдаёт EOS — специальный сигнал «ответ закончен», другой продолжает генерировать. Но завершившийся запрос не может выйти из зафиксированного набора, а новый не может занять его место. GPU продолжает запускать итерации для всего батча, пока не закончит последняя последовательность.

Получается, статический батч устраняет часть простоя из [шага 1](#step-1), объединяя запросы, но связывает их судьбы. Самый долгий запрос задаёт момент освобождения всей группы: быстрый закончил вычисления раньше, но очередь об этом ещё не выигрывает.

> 🎒 **На пальцах.** Ты идёшь по музею с экскурсией из четырёх человек. Один осмотрел зал за минуту, другому нужно десять. У следующей двери быстрый посетитель всё равно ждёт остальных, а новый человек с улицы не может присоединиться посередине маршрута. Пока группа считается неделимой, скорость всей экскурсии определяет самый медленный участник.

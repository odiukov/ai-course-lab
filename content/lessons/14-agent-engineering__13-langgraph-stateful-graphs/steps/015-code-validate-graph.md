Ты дописал в граф узел `escalate` — на случай, когда возврат больше лимита. Функцию написал, в словарь узлов положил, а в `next_node` из [шага 12](#step-12) новую ветку добавить забыл. Питон промолчал: словарь собрался, функция валидная. Ошибка вылезла через двадцать минут прогона и восемь вызовов модели — узел просто никогда не сработал, и заявка ушла в `done` без согласования.

Вот от этого и защищает `validate_graph`. Она ничего не запускает: на вход берёт описание графа — множество имён узлов и, для каждого узла, список имён, куда он может уйти. И возвращает список найденных проблем. Пустой список — граф здоров.

Проверок три, и все они про имена, а не про данные. Первая: у каждого ребра цель либо есть среди узлов, либо это `END` — иначе висячее ребро. Вторая: пройди от `START` по рёбрам и отметь, куда добрался; неотмеченные узлы недостижимы. Третья: у каждого узла, кроме `END`, должен быть хоть один выход, иначе это тупик.

На что смотреть при обходе. В нашем графе из [шага 6](#step-6) есть цикл — `retry` уходит назад. Без множества уже посещённых обход будет ходить по этому кольцу вечно, так что множество обязательно. И не выходи по первой же ошибке: если сломано три вещи, ты хочешь увидеть три строки, а не бегать по кругу «поправил — запустил — ещё одна».

Тридцать строк проверки имён вместо восьми вызовов модели впустую.

> 🎒 **На пальцах.** План этажа с пожарными выходами. Стрелка на плане указывает на дверь, которой в этой стене нет — это висячее ребро. Кладовка, в которую ни одна стрелка не ведёт, — недостижимый узел. Комната, откуда стрелок нет вовсе, — тупик. Всё это видно за минуту с планом в руках. И совсем не видно, если проверять его в дыму.

title: Чекпоинт пишется после каждого перехода

Возьми граф ReAct из [шага 16](#step-16) и прогони живой запрос: agent → tools → agent → tools → agent. Пять переходов. На четвёртом внешний API отвечает таймаутом, процесс падает. Что у тебя осталось на руках?

Если состояние жило только внутри работающей функции — ничего. Разговор, два успешных вызова инструментов, накопленные messages испарились вместе с процессом. Пользователю остаётся начать сначала.

А теперь то же самое с подключённым чекпоинтером — хранилищем, которое ты передаёшь графу в момент компиляции ([шаг 20](#step-20)). Ключевое слово здесь — «после каждого». Не один снимок в конце, не «раз в минуту», а запись на каждом переходе между узлами. Пять переходов — пять сохранённых состояний. Падение на четвёртом означает, что три первых лежат в хранилище целыми, вместе со всем, что редьюсеры уже приклеили к messages ([шаг 11](#step-11)).

Как этим воспользоваться? Никакого особого API восстановления не нужно. Ты вызываешь граф ещё раз с тем же `thread_id` — номерком из [шага 24](#step-24) — и он не начинает с точки входа, а подхватывает с последнего сохранённого состояния.

Где именно лежат эти снимки — твой выбор: в оперативной памяти, когда гоняешь тесты, в Postgres, Redis или SQLite, когда это продакшен и падение процесса не должно стирать чужой разговор.

Поэтому пауза в графе стоит дёшево: остановиться на переходе не страшно, состояние уже записано.

> 🎒 **На пальцах.** Скалолаз забивает крюк на каждом участке подъёма, а не один на середине. Сорвался на четвёртом — висишь на третьем крюке, в метре ниже, и продолжаешь оттуда. Без крюков тот же срыв означает падение к подножию и весь маршрут заново. Стоимость одного крюка — секунды; стоимость его отсутствия — весь пройденный путь.

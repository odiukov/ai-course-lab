Ты пишешь первый узел — тот, что зовёт модель. На вход к нему приходит состояние из [шага 6](#step-6): `messages` с тремя сообщениями, `user_id`, `iteration`. Ты дёргаешь LLM, получаешь ответ ассистента. И тут вопрос: а что вернуть-то?

Рука тянется собрать словарь целиком — скопировать три поля как были, четвёртое поменять. Работает. И ровно здесь начинаются странности.

Узел в LangGraph — обычная функция Python вида `state -> dict`. Она получает состояние целиком, а возвращает не новое состояние, а правку: только те ключи, которые реально изменились.

```python
def call_model(state):
    answer = llm.invoke(state["messages"])
    return {"messages": [answer]}
```

Одна строчка на выходе. Ни `user_id`, ни `iteration` тут нет — узел их не трогал, значит, и упоминать не должен. Дальше LangGraph берёт этот маленький словарь и прикладывает его к состоянию поле за полем, по ключам.

Разница не косметическая. Пока узел возвращает только `{"messages": [...]}`, видно, что он изменил: это и есть та самая дельта, которую граф умеет стримить и сохранять в чекпоинт ([шаг 3](#step-3)). А узел, вернувший все четыре поля, объявляет себя автором всех четырёх — включая те, которые в этот момент мог менять кто-то ещё.

Приятный побочный эффект: такую функцию можно позвать руками в тесте — передать словарь, посмотреть словарь на выходе. Никакого графа, никакого рантайма.

Узел не владеет состоянием. Он вписывает в него свою строчку и уходит.

> 🎒 **На пальцах.** Медкарта. Терапевт не переписывает её от корки до корки — он дописывает одну запись под сегодняшней датой и кладёт карту обратно. Хирург потом добавит свою. Представь врача, который вместо этого заново перепечатал бы всю карту «как было, плюс моё»: чужие записи он воспроизведёт по памяти — и что-нибудь потеряет. Узел ведёт себя как нормальный врач: только своя запись.

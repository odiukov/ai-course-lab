В списке изменённых файлов встречается `sample_app_backup/app.py`. По названию он похож на разрешённый путь, но простая проверка «строка начинается с `sample_app`» пропустит его по ошибке. А если функция остановится на первой такой находке, часть diff вообще останется непроверенной.

Тебе нужно дописать `classify_touched_files`: она получает список затронутых файлов и адаптированный scope-контракт из [шага 7](#step-7), а возвращает две группы — файлы внутри разрешённой области и файлы за её пределами. Как обсуждалось в [шаге 8](#step-8), классифицировать нужно весь diff, поэтому ранний выход здесь не подходит.

При реализации обрати внимание на три вещи:

- Обрабатывай каждый путь ровно один раз и сохраняй порядок входного списка: так результат проще сопоставить с исходным diff.
- Сравнивай границы путей, а не случайное совпадение текста. Разрешённая директория совпадает либо сама с собой, либо с путём внутри неё после `/`.
- Не угадывай назначение файла по расширению или имени. Даже знакомый `.py` не становится разрешённым автоматически: решение принимает только контракт.

Удобно мысленно разделить работу на два действия: сначала для одного пути получить ответ «в области задачи или нет», затем положить путь в соответствующую коллекцию. Функция не исправляет нарушения и не оценивает качество изменений — она лишь выдаёт полную, детерминированную классификацию для следующих проверок.

Если после её работы ни один файл не исчез и каждый оказался ровно в одной группе, граница задачи стала проверяемым фактом.

> 🎒 **На пальцах.** Представь сортировочную ленту на почте с двумя контейнерами: «наш район» и «другой район». Ты читаешь полный адрес каждой посылки, а не ищешь знакомое слово на коробке. Лента не останавливается из-за первой чужой посылки: к концу смены каждая коробка должна лежать ровно в одном контейнере.

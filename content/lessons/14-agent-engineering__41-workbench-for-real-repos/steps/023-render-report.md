Ты запускаешь `code/main.py` дважды и открываешь `before-after-report.md`. Измерения одинаковы, но строки вдруг поменялись местами — и Git показывает изменение там, где нового результата нет. Значит, отчёт должен быть не просто читаемым, а воспроизводимым.

Допиши `render_before_after`. На входе у неё уже есть результаты двух прогонов и их сопоставление из `compare_pipelines`, написанной в [шаге 20](#step-20). Заново вычислять исходы нельзя: эта функция ничего не измеряет и не решает, какой пайплайн лучше. Она только превращает готовые данные в Markdown.

Собери таблицу «до и после» по всем пяти исходам. Для каждой строки покажи название исхода, значение базового пайплайна, значение пайплайна с верстаком и результат сравнения. Сохраняй один фиксированный порядок строк — тот же, в котором исходы определены в записи прогона из [шага 17](#step-17). Не полагайся на случайный порядок обхода данных.

Обрати внимание ещё на две границы. Представление одинаковых значений должно быть одинаковым во всех строках, а в текст не должны попадать время запуска, случайные идентификаторы или путь к текущей папке. При одинаковом входе функция обязана вернуть посимвольно одинаковый Markdown.

Запись в файл оставь вызывающему коду: `render_before_after` возвращает текст отчёта. Так её можно проверить отдельно, не создавая файлов. Если повторный запуск не меняет отчёт, представление действительно следует измерениям, а не обстоятельствам запуска.

> 🎒 **На пальцах.** Представь табло на соревновании по пяти дисциплинам. Судьи уже выставили оценки, а тебе поручили напечатать протокол. Ты не пересматриваешь выступления и не назначаешь победителя заново: переносишь готовые числа в неизменном порядке. Если завтра те же оценки дадут другой протокол, проблема не в спортсменах, а в твоей печати.

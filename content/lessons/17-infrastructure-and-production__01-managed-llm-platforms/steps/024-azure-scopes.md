В конце месяца ты видишь: Azure OpenAI потратил €4 000. Команда поддержки уверяет, что почти не обращалась к модели, а команда поиска как раз выпустила новую функцию. Но в счёте нет ответа, чья функция создала расходы.

Azure раскладывает затраты прежде всего по **scope** — границе учёта вроде подписки или её части, которую ты выбрал для просмотра счёта. Внутри неё ресурсы можно собирать в **группы ресурсов**: например, отдельно для поиска и поддержки. Теги `team`, `product`, `feature` помогают подписать эти группы и связанные с ними затраты. Резервация PTU тоже видна как самостоятельный объект расходов, поэтому её можно отнести к нужному владельцу.

Но запрос к модели не становится отдельным Azure-ресурсом. Если две функции вызывают один deployment из одной группы, инфраструктурные теги не расскажут, какая из них отправила больше токенов. Ты увидишь общий расход deployment, но не виновника скачка. Это граница подхода из [шага 21](#step-21): подписать счёт недостаточно, если нужная детализация возникает только внутри приложения.

Поэтому признаки запроса — команду, продукт, функцию и объём использования — нужно записывать самостоятельно: в Application Insights через кастомные метрики либо на шлюзе, который добавляет идентификаторы в заголовки и журналы. Настроить это важно заранее: прошлые запросы задним числом разметить уже не получится.

> 🎒 **На пальцах.** Представь гардероб с рядами для разных отделов: scope задаёт весь зал, группа ресурсов — конкретный ряд, а тег подписывает его «Поиск». Но если трое сотрудников кладут пальто на один крючок, бирка ряда не покажет, кто занял больше места. Для этого гардеробщик должен сразу выдавать каждому номерок — это и есть твоя телеметрия на уровне запроса.

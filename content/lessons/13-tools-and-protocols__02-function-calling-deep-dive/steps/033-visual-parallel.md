Агент собирает погоду для трёх городов: Лондон, Токио, Осло. Один вызов твоего API занимает 400 мс. Если гонять цикл по очереди — вызов, ответ модели, снова вызов — набегает 1,2 секунды, и модель три раза ждёт, пока ты сходишь за данными. А данные-то независимые: Осло не зависит от Токио.

Так зачем выстраивать их в очередь?

Модель и не заставляет. В одном сообщении ассистента может прийти сразу три вызова — три записи в `tool_calls` у OpenAI, три блока `tool_use` у Anthropic. Ты запускаешь все три параллельно, и общее время равно не сумме, а самому долгому из них: те же 400 мс. Отвечаешь пакетом — по одному результату на каждый вызов, в форме из [шага 30](#step-30).

Включено это по-разному. У OpenAI параметр `parallel_tool_calls: true` стоит по умолчанию. Anthropic исторически звала инструменты по одному, а `disable_parallel_tool_use: false` (по умолчанию с Claude 3.5) разрешает несколько. Gemini 2 параллельные вызовы допускала, но стабильных `id` не давала; Gemini 3 добавила UUID — и это важнее, чем кажется.

Потому что параллельные ответы приходят вразнобой: Осло может ответить первым, Токио последним. Сопоставляешь ты их не по порядку, а по идентификатору из [шага 28](#step-28) — тому самому, который ты кладёшь в результат в [шаге 31](#step-31). Перепутал `tool_call_id` — и модель уверенно расскажет пользователю, что в Токио плюс девять и морось.

> 🎒 **На пальцах.** Вечером ты запускаешь стирку (50 мин), посудомойку (90) и духовку (40). По очереди — три часа. Вместе — полтора: столько идёт самое долгое. Но вынимать надо по метке: бельё из барабана, противень из духовки. Перепутал дверцы — и ужин в стиральной машине. Метка здесь — `tool_call_id`.

Ты проверяешь значение внутри `user.email` и обнаруживаешь там число вместо строки. Саму ошибку заметить легко. Но если вернуть только «ожидалась строка», непонятно, где именно она встретилась: во входных данных могут быть десятки строковых полей.

Поэтому во время рекурсивного прохода из [шага 7](#step-7) валидатор несёт с собой текущий адрес. Это похоже на запись маршрута: войдя в свойство `user`, ты добавляешь сегмент `/user`; затем входишь в `email` и получаешь `/user/email`. Такой адрес называется JSON Pointer — указателем на конкретное место внутри JSON.

Важно собирать путь по мере движения, а не пытаться восстановить его после ошибки. На каждом уровне известен только один следующий шаг: имя свойства, в которое валидатор сейчас спускается. Новый путь получается из уже накопленного пути и нового сегмента. Корневое значение начинает с пустого пути, поэтому первый сегмент сразу выглядит как `/user`, без лишнего слеша перед ним.

Когда проверка типа провалится, у ошибки уже будет точный адрес:

```text
path: /user/email
expected_type: string
```

Тогда получателю не приходится сопоставлять расплывчатое сообщение со всем объектом. Он читает путь слева направо и добирается ровно до неверного значения. Адрес ошибки возникает не в момент падения — он складывается на всём пути к нему.

> 🎒 **На пальцах.** Представь курьера внутри большого гостиничного комплекса. На входе его запись маршрута пуста. Он проходит в корпус `user` — появляется `/user`, затем к двери `email` — получается `/user/email`. Если дверь окажется не той, курьер не объясняет «я где-то на втором этаже»: у него уже записана вся цепочка поворотов, приведшая к месту ошибки.

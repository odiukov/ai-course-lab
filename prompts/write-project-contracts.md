Ты пишешь локальные pytest-контракты для большого capstone-проекта. Они не
заменяют настоящий облачный прогон: проверяют только архитектурные швы из
готового детерминированного Python-эталона.

{{project_json}}
</project>

Эталон:
<code>
{{project_code}}
</code>

Нужно проверить эти цели, сгруппированные по этапам:
{{targets}}

Верни только JSON в блоке ```json:

```json
{
  "tests": "Полный текст test_contract.py как JSON-строка",
  "nodes": {
    "Budget.exceeded": ["test_contract.py::TestBudgetExceeded::test_turn_limit"],
    "run_agent": ["test_contract.py::TestRunAgent::test_session_end_precedes_return"]
  }
}
```

Правила:

1. Используй unittest или обычные pytest-функции, только stdlib. Импортируй
   проверяемый модуль как `import main`; раннер добавит нужный каталог в
   PYTHONPATH.
2. Для каждой переданной цели в `nodes` должен быть свой непустой список
   точных node ID, и других ключей быть не должно.
3. Тесты цели должны становиться красными, если только её тело заменить на
   `raise NotImplementedError`, и оставаться зелёными при полном эталоне.
   Проверяй наблюдаемое поведение, крайние случаи и инварианты, а не исходный
   текст через inspect.
4. Не вызывай сеть, git, облачные сервисы и реальные shell-команды. Используй
   tempfile, unittest.mock и детерминированные входы. Не меняй эталон.
5. Не принимай сам `NotImplementedError` как ожидаемое поведение: заглушка не
   должна проходить тест по совпадению типа исключения.
6. Один тест не назначай двум целям. Интеграционный тест допустим только если
   он краснеет из-за названной цели, а не из-за соседнего шва.
